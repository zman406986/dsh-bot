# 104 — Stale dispatcher mirror after restart: a deactivated session still renders as a killable dispatcher row

**Status:** open
**Labels:** needs-triage
**Related:** 102 (resolved — the same "visible but inert" family, in the summon/kill direction), ADR-0010 (mirror honesty — the presence/mirror posture this finding tests), ADR-0021 (the floating window and the add/delete ruling)

## Problem

Observed live, 2026-09-21, in the overnight ticket-102/103 lane (one lane, one host restart): after a host restart, a session whose dispatcher binding was **no longer live** still rendered in the floating window's roster as a dispatcher row — carrying the unavailable-status rendering (`状态不可用`) — and the host **refused** `/dispatcher-stop` on it with `kind:"error"` and the message "This chat is not an activated dispatcher session — nothing to deactivate. Run /dispatcher-start in a chat first to activate one."

Evidence (in-repo, git-ignored under `.scratch/testing/2026-09-21-live-102-103/live-inject-fix/`):

- `obs-c3-execute-response.json` — the host's refusal: `POST /api/commands/execute` `/dispatcher-stop` returns HTTP 200 whose body carries `kind:"error"` with the message above, while the same measurement records `rowDispatcherAfter: "true"` (the row still renders as a dispatcher).
- `obs-stale-flag-explain.json` — the lane's explanation: `renderedRows` lists the target `session-650bc552…` with `dispatcher: "true"` and text `dsh-bot状态不可用`, alongside ten other rows all `dispatcher: "false"`.
- The lane's README residue entry: `.scratch/testing/2026-09-21-live-102-103/live-inject-fix/README.md` §Residue item 2 (and §Observation C / §Deviations item 2) — "The stale persisted `dispatcher=true` mirror (a deactivated session renders as a dispatcher row after a restart, with `状态不可用`) was observed but is a separate concern from the transport fix; not filed."

**Actual behaviour (observation).** The row's `data-dispatcher` comes from a **mirror of persisted settings** that survives a restart. The mirror is honest about what was last WRITTEN into it, not about what is LIVE now — so after a restart it can present a deactivated session as a dispatcher.

**Expected.** Either the roster should not present a deactivated session as a dispatcher row after a restart, or the affordance should not be offered where the host will refuse the command — at minimum, the stale row should not look killable.

**Why it matters.** This reproduces the class of complaint that produced ticket 102 — a control that is visible but cannot do anything — now in the **kill** direction, on a freshly restarted app. A user who drags the floating window open and clicks delete on such a row gets a two-press confirmation, a wire request, and an error the UI does not surface as a refusal of that control.

**Evidential weakness (stated deliberately).** This was observed **once** (one lane, one host restart, one target session). The mechanism is **attributed, not proven**: the lane's own words are "Guessed, not proven: the exact reason `session-650bc552` kept a stale `dispatcher=true` (attributed to the persisted settings mirror from `shell-mirror-feed.ts`; the host's own 'not an activated dispatcher' error is the direct evidence, the mirror mechanism is the read-code corroboration)." Do not treat the mirror attribution as established — establish it in the diagnose step.

### 2026-09-21 — diagnosis session

**Mechanism, now confirmed.** The filing's attribution held up, and it is now stronger than an attribution: the durable mirror row was found in the host's own settings document, carrying a clock from the previous process. What was tested and verified here (by this session, reading the cited lines and the evidence artefacts — no live run, no code changed):

*Volatile host truth.* The activated-dispatcher set is a plain in-memory `Map` created in `bindDispatcherLifecycle` (`src/adapter/parent-agent.ts:213`), written only by activation (`sessions.set`, `:314`) and removed only by `deactivateSession` (`:228`). Nothing persists it: no storage domain, no markers, no settings write anywhere in that file. `/dispatcher-start` is the only writer (`src/plugin.ts:689` → `activation-command.ts:114`); the plugin boots dormant and captures nothing on load or session-start (`parent-agent.ts:181`, `plugin.ts:454-458`, ADR-0009). **So the post-boot activation set is provably EMPTY.** `/dispatcher-stop` gates on exactly that set — `if (!options.activeSessionIds().includes(sessionId)) return { kind: "error", text: DISPATCHER_STOP_NOT_DISPATCHER }` (`src/adapter/stop-command.ts:104-106`, wired at `src/plugin.ts:754` to `lifecycle.dispatcherSessionIds()` = `[...sessions.keys()]`, `parent-agent.ts:353`), and the constant at `stop-command.ts:59-61` is the refusal text verbatim.

*Durable mirror.* `src/adapter/roster-channel.ts:181-187` writes ONE merged document carrying both mirror families — the legacy `roster` key and `roster.<sessionId>` — and adds the session to an in-process `writtenSessions` `Set` (`:130`). `clearSession` writes `null` under `roster.<sessionId>` (`:201-204`); `clearAllSessions` iterates **`[...writtenSessions]`** (`:205-209`), so in a fresh process it iterates an empty set and writes NOTHING. The only two call sites are `src/plugin.ts:676` (`onDeactivated` — fired by an explicit stop, a disposed agent, or unbind/HMR) and `src/plugin.ts:796` (the unload cleanup). A hard restart fires neither. **The restart deactivates the binding by DISAPPEARANCE — an event that fires no clear.** No other clear exists (`grep` for `clearSession|clearAllSessions` in `src/` returns exactly those two call sites).

*Client reads the mirror as membership.* One accepted settings document feeds three readers (`src/client/index.ts:371,393-398`); the shell feed takes every `roster.`-prefixed key (`src/client/shell-mirror-feed.ts:52-63`, prefix defined `roster-channel.ts:79`, split at `:91-94`) and hands the RAW value to the store. `applySessionMirror` (`src/client/shell-store.ts:592-605`) classifies `null`/`undefined` → `cleared`, an unparsable value → `unavailable`, otherwise → `snapshot`. `mirrorFlag` (`:492-495`) is `mirror.kind !== "cleared"` — **so `snapshot` AND a corrupt `unavailable` value both read as dispatcher-here; only an explicit `null` clears.** That flag seeds the row (`:521-525`) and outranks any feed claim (`:548-549`).

*The chip is a different gate.* `view()` computes staleness from `publishedAtMs` alone (`shell-store.ts:240-249`) and sets `presenceAvailable`; the `状态不可用` chip renders when `!presenceAvailable || presence === null` (`src/client/shell.tsx:326-329`), while the kill affordance is gated purely on `row.dispatcher` (`shell.tsx:373-401`). Window: `ROSTER_STALE_WINDOW_MS = 60_000` (`src/core/roster-snapshot.ts:49`), clock stamped at publish from `Date.now()` (`src/plugin.ts:357`). The two gates never meet: the lane's own `renderedRows` shows the chip on **all eleven** rows, non-dispatcher ones included — it carries no signal that the dispatcher row specifically is stale. This is pinned offline at `test/client-wrapper-shell.test.ts:538` ("The dispatcher flag is NOT freshness-dependent").

**No boot-time reconciliation exists — and the gap is exactly that, nothing subtler.** The host half of this plugin never READS the persisted roster document. `SettingsOwnerScopeLike` does expose `get?`/`watch?` (`src/adapter/settings-section.ts:53-62`), but `roster-channel.ts` calls only `scope.update` (`:148-154`); `attach()` merely stores the scope and catch-up-writes `lastSnapshot` — which is `null` at boot, since nothing has been projected yet (`:190-196`). A grep for any `scope.get`/`read`/reconcile of the roster namespace in `src/adapter/`, `src/plugin.ts`, `src/core/` returns nothing. So the claim is CONFIRMED: there is no boot sweep, and no other mechanism could have cleared the key.

**Decisive direct evidence.** The host settings document (`C:\Users\TZhen\.dsh\settings.yaml`, out of repo, read-only) under the `multitask-dispatcher:` namespace holds, at this writing: `enabled: true`, `onboarding.seen: true`; the legacy `roster` key = a v4 snapshot whose `dispatcherSessionId` is the inject-fix lane's OWN throwaway `session-6289c3b4-…`, `publishedAtMs: 1789947989261`; `roster.session-cf5249cf-…: null`; `roster.session-cd03250b-…: null`; `roster.session-6289c3b4-…: null`; and — the load-bearing row — **`roster.session-650bc552-a817-40f9-ba17-fbac59313b0b` carrying a NON-null v4 snapshot** (`dispatcherSessionId` = itself, `workers: []`, `publishedAtMs: 1789940590173`).

That key names the exact session the lane measured: `obs-c3-execute-response.json` targets `session-650bc552-a817-40f9-ba17-fbac59313b0b`, records `rowDispatcherAfter: "true"`, and carries the refusal verbatim — HTTP 200 whose body is `{"result":{"ok":true,"value":{"commandId":"cmd-71a80eca-2","result":{"kind":"error","text":"This chat is not an activated dispatcher session — nothing to deactivate. Run /dispatcher-start in a chat first to activate one."}}}}`; `obs-stale-flag-explain.json` lists that same id as `{dispatcher: "true", text: "dsh-bot状态不可用"}` among ten other rows all `dispatcher: "false"`. The hard refusal and the rendered killable row are therefore measured on ONE session — and that session's mirror row is exactly the surviving non-null key.

*Timestamp logic — the snapshot predates the observing process, cleanly.* `publishedAtMs: 1789940590173` = 2026-09-21 05:43:10 local (+08:00) = 2026-09-20T21:43:10Z. The inject-fix lane booted at 2026-09-20T23:35:14Z (`live-inject-fix/server.log`, `boot-launch.txt`) and clicked that row at t=1789947810400 (23:43:30Z), with the refusal at 1789947883565 (23:44:43Z) — `obs-c2-delete-wire-FINAL.json`, `obs-c3-execute-response.json`. The snapshot is therefore **7,293 s (~2h01m) old at the refusal and predates the observing boot by ~1h52m**. It cannot have been written by the process that read it. Which process DID write it is also closed: `live-post-fix/README.md` records `session-650bc552…` as the throwaway created in that lane's **boot 3** (boot 21:34:42Z, child exit 21:47:12Z), and 21:43:10Z falls inside boot 3's lifetime; boot 3 was then force-killed, so the plugin's unload clear never ran. The file's own mtime (21 07:47) matches the inject-fix lane's last write (the kill of its own throwaway wrote `roster.session-6289c3b4: null` at ~23:47Z), which independently proves this file is the document that lane wrote through — the surviving key is in the very document the client read. The two `null`s beside it are the control: sessions deactivated inside a live process ARE cleared; the one deactivated by a restart is not. **CONFIRMED — the numbers support this directly and without strain.**

**Honest boundary on n.** The observation is still one lane, one restart, one session: how often a user reaches this state (any dispatcher session left activated when the host stops hard) is not measured. What is no longer an attribution is the mechanism and the artefact — the surviving row, its previous-process clock, the empty post-boot activation set, the process-local clears and the absence of any boot read are all verified here from code and from the document itself. The render path from that row to the drawn affordance is verified by read-code against the lane's `renderedRows`; it was not re-measured in a browser by this session.

**The two candidate fixes are NOT equivalent.**

1. *Host-side boot reconciliation.* At apply, read the persisted document and invalidate every `roster.*` key found in it. Justified by the provably-empty post-boot activation set (ADR-0009 boot-dormant): after a restart no session is an activated dispatcher, so no persisted `roster.<id>` can be true, and invalidating all of them cannot lose truth. `clearAllSessions()` cannot be reused as-is: its `writtenSessions` set is empty in the new process (`roster-channel.ts:130,205-209`), which is precisely why nothing clears today — the sweep must come from the document, not from memory. Cost/character: this asserts a **durability semantics** for the mirror — process-lifetime, invalidated at boot — which contradicts the currently shipped behaviour of writing it through a durable settings document. That is an ADR-0010-adjacent posture change.
2. *Client-side freshness gate.* Require a non-stale mirror for the kill affordance (fold `stale` into the `row.dispatcher` gate). Cost, and it is disqualifying as a default: the channel has **no heartbeat** (ADR-0010 rule 3 — "Staleness is handled read-side (age window → unavailable), since the channel has no heartbeat"; rule 4 — the settings namespace is "a config channel doing telemetry duty"). A LIVE but idle dispatcher — the overwhelmingly common case, since publishes happen only on semantic transitions — older than 60 s would lose its kill affordance while the host would happily accept `/dispatcher-stop`. That is ticket 102's own "visible but inert" complaint inverted: a control that is live and usable, hidden.

**Why this is the human's call.** The host option is not a contained bug fix: it changes what the mirror IS (a durable projection becomes a process-lifetime one), touching the recorded honesty posture of ADR-0010 — a decision this ticket's own Constraints already require be proposed as an ADR first, not implemented. The client option is not a safe default: freshness cannot distinguish a dead binding from a live idle one, so it trades a stale-but-harmless affordance for a missing-but-needed one. There is a recorded authority rule for exactly this situation — an unrecorded decision must not be silently picked, the human is asked instead (`AGENTS.md` authority stack; `docs/agents-rulebook.md`). **The implementing team did NOT implement either candidate**, and did not touch `src/` or `test/` in this session, for that reason.

(ii) Decide the posture — host reconciliation vs. read-side rule — filing an **ADR first** if the decision is posture-level. Note that the framing itself is what needs settling: the host option is arguably a *defect repair* restoring the posture the repo already claims ("the mirror is not durable truth, the live binding is" — `shell-mirror-feed.ts` header, ADR-0010), whereas the client option is a *rule change* to how the flag is derived. Which reading is correct is the decision. (iii) Then pin it offline. The restart-equivalent IS modelable without a live host: build a fresh store plus a fresh mirror feed, then replay the persisted document into it — the attach-later replay idiom already exists in `test/shell-mirror-feed.test.ts` ("replays the last-known mirrors to a store that attaches later", `:84-100`). Note that `test/client-wrapper-shell.test.ts:538` currently AFFIRMS the divergent state as correct ("The dispatcher flag is NOT freshness-dependent") — that pin must be revisited whichever way the decision goes, and the fact that current tests assert the observed behaviour as intended is itself the signal that this is posture-level, not a local bug.

**Adjacent observation for the human (same asymmetry, inside this ticket, not a separate one).** Because the offer gate is the mirror and the refusal gate is the live set, a user can be OFFERED a delete whose refusal the UI does not surface: `sendCommand` classifies the outcome from the promise alone (`src/client/actions.ts:253-257` — `undefined` → `unresolved`, anything else → `executed`), so the host's inner `kind:"error"` refusal body is never inspected, and the seats' only handling of a non-`executed` outcome is a console-only `reportCommandFailure` (`src/client/index.ts:884-905`, comment: "no UI, no copy, no state, no new result kinds"); the row does not flip. Measured: `obs-c2-delete-wire-FINAL.json` recorded 30 poll cycles after the two-press confirm on the stale row with `rosterDispatcher: "true"` / `deletePresent: true` throughout, alongside `commandsExecuteFromClicks: true` — the click reached the host and the UI showed no trace of the refusal. Whatever is decided above, whether a refused command should become visible to the user is a question this finding raises and does not answer.
