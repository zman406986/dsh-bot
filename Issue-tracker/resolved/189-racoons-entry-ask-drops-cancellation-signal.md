# 189 — RACOONS entry asks drop the caller cancellation signal

**Status:** resolved
**Labels:** ready-for-agent
**Priority:** P2
**Severity:** medium
**Ship blocker:** no — RACOONS is optional and off by default; the confirmed defect affects cancellation of its enabled entry-ask path.

## Problem and impact

The normal installed host supplies the running phase's AbortSignal to `agent/pre-step`, but the RACOONS listener does not forward it. Neither `runStep` nor its entry-ask loop accepts the signal, and the call to `askEntry` omits the cancellation option that the helper already supports. The ask therefore uses its own stream deadline without the caller's phase signal.

If cancellation or agent disposal happens while an eligible entry ask is waiting for its stream, the phase signal aborts while the ask can continue. The pre-step hook remains awaited, delaying the host's post-hook abort check and, during disposal, its wait for idle. A valid answer arriving after cancellation but before the ask's own deadline can still append the ask exchange and apply the entry answer: the caller has no cancellation guard before those effects or before the next queued ask.

`cancel()` itself returns immediately. The confirmed issue is delayed completion of the pending hook/idle/disposal and permitted late entry effects, established by source reasoning. It is not evidence of an indefinite hang, data loss, or measured live-provider behavior.

## Reproduction by source reasoning only — not executed

1. Enable RACOONS explicitly. Consider a normal pre-step with an eligible landed tool result, usable ledger/fork and configured LLM route. Let its entry-ask stream remain pending before the independent deadline expires.
2. Cancel that agent, or begin its disposal. The installed host aborts the phase signal; the cancellation method returns immediately. Because the listener did not pass that signal through, the request's independent deadline signal remains live and the waterfall is still awaiting the entry ask. Disposal is waiting for idle.
3. If the stream then produces a valid entry answer before its deadline, the source takes the answered branch, appends the exchange and calls entry apply before returning control to the host's abort check. With more eligible captures, the loop also has no caller-abort check stopping later asks; a retry has its own stream attempt deadline.
4. Expected behavior: caller abort reaches the pending ask, promptly releases the pre-step/idle wait, and prevents late entry effects and additional asks from this cancelled batch. Ordinary entry answers still apply when the caller remains active.

These steps describe the confirmed static control flow, not an observed runtime reproduction. Filing this ticket does not run probes or tests. No probe, live LLM call, test or build was executed; cancellation latency, live-provider resource behavior and data loss were not measured or established.
