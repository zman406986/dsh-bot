# 103 — Floating-window drag flies across the screen (compounding start-relative delta)

**Status:** resolved
**Labels:** ready-for-agent
**Related:** 100 (resolved — the floating window; its unticked LIVE PASS drag item is where this report lands), 73 (cancelled — the drag need it asked for shipped on 100; this is its first live defect), ADR-0021 (decision 2 — the window vehicle)

## Problem

The human reports (2026-09-21, live use, verbatim): *"floating window when dragged around behave weird: house only move a few pixels but window goes flying across, travelling great distances, not expected dragging behavior"* ("house" read as "mouse"). Expected: the window follows the pointer 1:1. Observed: a few pixels of mouse movement send the window flying a great distance, usually until it slams against a viewport edge (the clamp's pin).

Root cause, identified in the scribe pass (verify, then fix): the drag compounds a start-relative delta onto the live position.

- `beginDrag` (`src/client/floating-window.tsx`, lines ~257–275) captures the POINTERDOWN point and, on every window `pointermove`, calls `store.moveBy(move.clientX - startX, move.clientY - startY, …)` — the delta from the START, not from the last event.
- `moveBy` (`src/client/floating-window-store.ts`, lines ~203–214) adds that delta to the LIVE position: `clampWindowPosition(state.x + dx, state.y + dy, …)`.

So every move event re-applies the full distance-from-start on top of the already-moved window. Trace (pointerdown at x=100, window origin 0): mouse creeps 100→105→108→110→112→113→114 while the window runs 0→5→13→23→35→48→62 — the offset compounds super-linearly and the window rockets away though the mouse barely moved. The clamp then pins it at the peek-strip edge, which reads as "flew across the screen".

Why the offline suite missed it: the rendered drag pins in `test/client-floating-window.test.ts` drive pointer events through the real clamp, but a single `pointermove` applies the delta exactly once and looks correct — only a MULTI-event drag exposes the compounding. This report is ticket 100's unticked LIVE PASS item ("drag/close interaction against a real dsh window — pointer capture feel") arriving as a live defect.

## What to do

- [x] Fix the drag: anchor the window's placement at pointerdown and set the position per move event as `origin + (current − start)` (or equivalently feed per-event deltas measured against the LAST move). Never add a start-relative delta to the live position. The clamp contract is unchanged (`clampWindowPosition`: 64 px peek strip, deterministic edge pinning when the viewport collapses, never NaN). — commit `3fc5024`: `beginDrag` seeds `lastX`/`lastY` at pointerdown and each `pointermove` feeds its OWN delta (`move.clientX - lastX`, `move.clientY - lastY`) into `store.moveBy` (`src/client/floating-window.tsx:265`, delta at :272–277); the store was not modified — `moveBy` still takes deltas and clamps (`src/client/floating-window-store.ts:203`) and the drag path is its only production caller.
- [x] Offline test: a MULTI-event rendered drag pin — two or more `pointermove`s with increasing `clientX`/`clientY` must land the window at `origin + (last − start)`, bounded by the clamp, monotonic in the pointer. This pin must FAIL on the current code (name the compounding in the assertion's failure story); the existing single-move and clamp pins stay. — new pin "three monotonic pointermoves advance the window by the SUM of per-event deltas (no start-relative compounding)" (`test/client-floating-window.test.ts:674`): pointerdown at (400,40), moves to (410,50)/(420,60)/(430,70), then the mandatory `pointerup` (it removes the window-level listeners); asserts `after.x === before.x + 30` and `after.y === before.y + 30`, with the compounding named in the assertion message. ### 2026-09-21 — implementation session

**Shipped (fix `3fc5024`, comment cleanup `e570c50`).** The finding is the scribe's, confirmed in code: `beginDrag` passed a delta measured from the drag START (`move.clientX - startX`) into `store.moveBy`, which ADDS its argument to the LIVE position (`src/client/floating-window-store.ts:203`), so every move event re-applied the whole distance-from-start and the window ran super-linearly to the clamp edge. The fix seeds `lastX`/`lastY` at pointerdown and gives each `pointermove` only its OWN delta, applied exactly once (`src/client/floating-window.tsx:265`, delta at :272–277). The store was NOT modified — `moveBy(dx, dy, viewport)` still takes deltas and clamps, and the drag path is its only production caller (grep: `src/client/floating-window.tsx:277`). The clamp contract is unchanged (64 px peek strip, deterministic pinning, never NaN).

**Red → green.** New rendered pin "three monotonic pointermoves advance the window by the SUM of per-event deltas (no start-relative compounding)" (`test/client-floating-window.test.ts:674`): pointerdown at (400,40), moves to (410,50), (420,60), (430,70), then the mandatory `pointerup` (it removes the window-level listeners); asserts the window advanced exactly +30/+30 from its captured pre-drag position, with the compounding named in the assertion message. On the REVERTED code the pin failed `actual: 300, expected: 270` — the start-relative deltas 10+20+30 re-applied add 60 (`.scratch/testing/2026-09-21-live-102-103/offline/103-test-red.txt`). An independent verifier reproduced the red state itself (`.scratch/testing/2026-09-21-live-102-103/verify/103-red-repro.txt`) and confirmed the store was untouched and the arithmetic right. The existing single-move and clamp pins stay.

**Comment-only follow-up `e570c50`.** The doc comment above `beginDrag` overclaimed "the pointer and the window advance 1:1"; `e570c50` corrected it to the honest behavior: between clamp events the window tracks the pointer exactly, and when the clamp absorbs part of a move the window keeps the clamped position and slips out of phase by the absorbed amount — bounded, never compounding (`moveBy` early-returns when the clamped position equals the current one, so the overshoot is dropped rather than re-applied). No behavior change.
