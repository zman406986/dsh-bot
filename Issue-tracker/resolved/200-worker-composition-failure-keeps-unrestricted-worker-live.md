# 200 — Worker composition failure keeps an unrestricted worker live

**Status:** resolved
**Labels:** ready-for-agent
**Severity:** high
**Ship blocker:** yes — when exceptional composition setup fails before the worker restriction completes and the inherited preset contains forbidden tools, the adapter still admits a live worker.

## Problem and impact

Fresh-worker creation and marked-worker reattachment catch `applyWorkerComposition` errors and continue with the inherited tool surface. This defeats the helper's explicit fail-closed contract: a worker can be reported as successfully spawned, or reclaimed and woken, even though its worker tool barrier was never installed. The high-severity blocker is the failure policy at this authorization boundary. An exceptional setup/API/registration failure before `tools.restrict` completes can preserve forbidden capabilities for the worker's task or resumed turn.

The impact depends on the child's actual inherited preset and each tool's execution guards. The barrier normally subtracts user-delivery/question, agent-message, spawn, job, todo and dispatcher verbs. A surviving `present` implementation can append presented-file records for an open-turn caller; native child-to-parent messaging also has an executable path outside `reply_to_dispatcher`. Prompt instructions alone do not enforce the intended restriction. This audit does not establish that a healthy host routinely fails composition, that every denied verb can execute, or that all dispatcher handlers are inherited.

## Confirmed evidence

- **Fresh creation suppresses the error:** [src/adapter/cordis-dsh-host.ts:3210–3233](../../src/adapter/cordis-dsh-host.ts#L3210-L3233) wraps `applyWorkerComposition` in a catch and warns that the child “keeps its inherited surface”. The comment explicitly says “the spawn still succeeds”. [The spawn activation/catch:3729–3742](../../src/adapter/cordis-dsh-host.ts#L3729-L3742) removes the adapter reservations and rethrows only when the awaited `startActivation` rejects; the swallowed composition error never reaches that rejection path.
- **Reattachment also continues:** [src/adapter/cordis-dsh-host.ts:2840–2867](../../src/adapter/cordis-dsh-host.ts#L2840-L2867) acknowledges that “a failed barrier would leave it with tools a worker must not have”, catches the error, then calls `onWorkerReattached`, delivers the parked wake, and returns `true`.
- **The helper intends rejection:** [src/worker/preset.ts:140–151](../../src/worker/preset.ts#L140-L151) says failures throw “so the spawn fails instead of shipping an unrestricted worker”. [Its strict surface read:90–113](../../src/worker/preset.ts#L90-L113) reports missing, throwing or empty schemas; [composition:172–195](../../src/worker/preset.ts#L172-L195) throws for missing tools, unreadable/empty surfaces (with the documented minimal-stub carve-out), an empty deny intersection or missing `restrict`. The resolver and `tools.restrict({ deny })` can themselves throw. [Prompt registration:160–169](../../src/worker/preset.ts#L160-L169) also precedes the restriction. These are exceptional failure routes, not proof that ordinary live-host schema resolution fails.
- **An existing synthetic test pins continuation:** [test/adapter-cordis-dsh-host.test.ts:486–512](../../test/adapter-cordis-dsh-host.test.ts#L486-L512) injects a `resolveToolFilter` that throws “tool barrier exploded”, then expects a string worker id, `host.owns(workerId) === true` with “the child is still live”, a composition warning and one activation call. This test was read only; it was not executed during this audit. The resolver throws before the restriction call.
- **The boundary remains required:** [src/worker/tool-barrier.ts:16–72](../../src/worker/tool-barrier.ts#L16-L72) lists the normal subtraction, including `present`, `ask_user_question`, `send_message`, spawn candidates, job/todo and dispatcher verbs. [PRD S5/S9:71–75](../../PRD-dsh-multitask-dispatcher.md#L71-L75) requires “Workers cannot address the user directly” and limits messaging/await authority; [src/worker/prompt.ts:104–114](../../src/worker/prompt.ts#L104-L114) names the final answer and mid-task reply as the worker's channels back. [Ticket 10:11–14](../resolved/10-worker-agent-type-and-tool-barrier.md#L11-L14) requires forbidden tools to be absent and execution refused. [Ticket 174:56–60](../resolved/174-remove-worker-access-ask-feature.md#L56-L60) explicitly retains both the worker barrier and `reply_to_dispatcher`.

- A composition error **after** [successful restriction and later worker-local tool registration:195–203](../../src/worker/preset.ts#L195-L203) need not remove an already-installed barrier. The demonstrated unrestricted-worker consequence is limited to failures before restriction completes, or a restriction failure that leaves it unapplied.

## Static reproduction

1. Read the existing throwing-resolver test linked above. Its injected definition throws during filter resolution, before `tools.restrict`; its assertions deliberately require successful spawn, a live owned child and a warning. No test run is needed to identify the pinned failure policy.
2. Follow that call into the fresh `agent/created` composition catch. The catch returns normally, so this composition error does not reject `startActivation`; the spawn caller receives success instead of the helper's intended refusal. Conditional on a preset containing a forbidden tool, that tool has not been subtracted by the worker restriction.
3. Follow the same pre-restriction composition failure through marked-worker adoption. The catch is followed by successful reclaim notification, parked-wake delivery and `true`, so the failure does not gate resumed work.
4. Compare these continuations with the helper's fail-closed statement, the still-required worker barrier, the installed host's real execution guards and its creation-failure disposal path. This is a static control-flow reproduction with a synthetic injection already present in the repository; no live tool execution or routine healthy-host failure was reproduced.

## Acceptance criteria

- [ ] A composition error rejects fresh-worker creation and aborts/cancels/disposes any partially created activation before the worker task or any model/tool execution can start. The caller receives an honest spawn failure, never a successful worker id backed by an incompletely composed child.
- [ ] A composition error during marked-worker reattachment aborts/disposes that activation before successful reclaim notification, parked task/wake delivery or resumed model/tool execution. It cannot return successful adoption or fall through to another permissive creation path. Recovery reports failure honestly instead of publishing a usable worker.
- [ ] Both paths clean up partial registrations, activation handles, ownership entries, worker-id/stream reservations and pending-spawn/wake bookkeeping as appropriate, including the core's pre-activation reservation. Durable recovery state must not silently resurrect the rejected activation or lose the failure; cleanup is scoped to the affected worker.
- [ ] Replace the existing warning-and-success throwing-resolver test with rejection/disposal and **no task/model/tool execution** checks. Cover fresh creation and marked-worker reattachment for pre-restriction prompt/API registration errors, schema read failures/empty surfaces, a throwing resolver/empty deny intersection, and a missing/throwing restriction seam. Assert no reclaim/wake after failure and no stale ownership or reservations.
- [ ] Successful composition still retains available work tools and worker-local `reply_to_dispatcher`, while forbidden inherited tools are absent and execution refused. Add checks for that successful path; preserve the supported mid-task reply and final-report routes. A later composition error must not be described as having removed a restriction that was successfully installed.
