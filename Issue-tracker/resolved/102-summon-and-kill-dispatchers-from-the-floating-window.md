**Status:** resolved

## Problem

The human reports (2026-09-21, live use, verbatim): *"still no way to summon new dispatcher/kill old ones in our floating window - may need to research the reference more on how they deal with it."*

Vocabulary: the human's "summon new dispatcher" = add/activate a dispatcher session (ticket 101's add affordance, `/dispatcher-start`); "kill old ones" = delete/deactivate one (`/dispatcher-stop`, binding off, chat untouched).

On paper the affordances should already be in the window — the code says so:

- `mountShellPage` builds the `ShellHosts` with BOTH seats unconditionally (`onAddDispatcherSession` → `/dispatcher-start`, `onDeleteDispatcherSession` → `/dispatcher-stop`, one command transport — `src/client/index.ts`, the hosts block; ticket 101).
- The floating-window launcher inject mounts the shell through that same `mountShellPage` and renders `createDispatcherShell(t, mount.store, mount.hosts)` (`src/client/index.ts`, the `SHELL_OVERLAY_SLOT` inject) — the window hosts the WHOLE shell, seats included (ticket 100, ADR-0021 decision 4).
- `AddDispatcherSection` renders whenever the add seat is defined, and the per-row delete affordance rides every roster row (`src/client/shell.tsx`).

So the live report CONTRADICTS the code reading. That contradiction is this ticket's opening puzzle: something makes the affordances absent, invisible, or dead in the real floating window, and it must be found before anything is rebuilt.

### 2026-09-21 — implementation session

**The contradiction was real, and it had TWO independent causes.**

**Cause 1 — discoverability (ticket candidate (b) confirmed; (d) half-refuted; (c)'s pointer-events arm refuted).** The seats were mounted and rendered, but invisible or unreachable at rest. `src/client/shell.tsx:117-118` had `.__row-actions{display:none}` revealed only by `li:hover`/`:focus-within`, so the per-row **delete** existed but was un-hover-gated into invisibility; `:122` gave the **add** section `margin-top:auto` at the bottom of an `overflow-y:auto` sidebar inside the fixed 760×520 window, so with a long roster it sat below the fold. The pre-fix live lane measured it exactly (`.scratch/testing/2026-09-21-live-102-103/live-pre-fix/dom-rest-final.json`): the add toggle's rect y 538→564 against a window body bottom of 545 (**+19 px below the fold**), `elementFromPoint` at its centre hitting the SIDEBAR rather than the toggle, with 8 roster rows and **zero** dispatcher rows (`deleteEls: 0`) — so no kill affordance could render at all. That is candidate (b) plus (d) *half*-refuted: the add section renders even with an empty roster (the pre-fix `02-window-hover-row.png`/`dom-hover.json` show the hover gate present but unreachable with no dispatcher row). Candidate (c)'s pointer-events arm is refuted outright: `grep -rn pointer-events src/client/` returns zero rules. Candidate (a) was ruled out by the premise check — the served bundle was the committed HEAD `3fc5024`, rebuilt in isolation (`live-pre-fix/build-head/`, md5 `f61bf302…`), so the page genuinely ran the pre-102 CSS.

**Cause 2 — a silent transport defect the ticket did not anticipate (the load-bearing discovery).** Clicking the (now visible) affordances produced **zero wire traffic**. Our browser client read the nested Cordis service face `ctx.remote.commands.execute`, while its module `inject` array (`src/client/index.ts:203-209`, pre-fix) declared only the top-level `"remote"`. dsh's Cordis resolver matches inject entries by **exact string and never dot-splits**, so the nested read THREW (`cannot get property "remote.commands" without inject`), and the seats' `.catch(() => {})` swallowed it — an inert click with no UI signal. Verified two ways: an independent verifier reproduced the throw with the real installed Cordis runtime (`.scratch/.../verify-102b/cordis-probe2-output.txt`: pre-fix `["remote"]` → `nestedThrew: true`; post-fix `["remote","remote.commands"]` → `execResult {"ok":true}`), and the shipped precedent was found on this box — `@deepseek-ai/dsh-client-ui-commands`' client declares `static inject = ["inputTriggers","sessions","remote","remote.commands"]` (`C:/Users/TZhen/.dsh/profiles/node_modules/@deepseek-ai/dsh-client-ui-commands/lib/client.js:495-500`). Every shipped dsh client reading a nested face declares both names. The whole offline suite was structurally blind to it: the fakes handed out plain objects and no test contained the string `"remote.commands"`.
