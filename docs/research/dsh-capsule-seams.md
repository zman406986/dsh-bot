## Seam 1 (host extension point) — `shell.overlay` entry anatomy: VERIFIED

- **Declaration.** `shell.overlay` is a `list` slot, `scope: 'root'`, declared by ui-layout's AppFrame registration: "Frame-wide floating layer, above every column and outside their scroll containers… The layer itself is click-through — entries opt back into pointer events… a fresh `id` is added beside the shipped entries" (ui-layout `lib/types/client/index.d.ts:71-81`; children declared at `lib/client.js:540-546`).
- **Click-through default and opt-in mechanism.** The layer element is `position:absolute; inset:0; z-index:20; pointer-events:none`, and the shipped CSS re-enables pointer events on its direct children: `.overlayLayer{z-index:20;pointer-events:none;position:absolute;inset:0}.overlayLayer>*{pointer-events:auto}` (ui-layout `lib/client.js:71`). The layer is rendered as the frame's last full-size child, `data-shell-overlay` (ui-layout `lib/client.js:300-304`), fed by `renderSlot("shell.overlay", {})` (`lib/client.js:276`).
- **Structural detail that matters for the capsule:** the slot outlet renders a wrapper `div[data-slot="shell.overlay"]` with `style:{display:"contents"}` (ui-renderer `lib/client.js:767-777`, `ANCHOR_STYLE` at 767). That wrapper is the layer's direct child, so the `>*` rule sets `pointer-events:auto` on it, and since `pointer-events` is an inherited property, **every entry subtree receives pointer events automatically**; a `display:contents` anchor generates no box, so layout is unaffected. Consequence: an entry never blocks the app only where it draws nothing; if the expanded panel wants click-through regions (e.g. no dimming backdrop but pass-through outside the card), the entry must set `pointer-events:none` on those regions itself.
- **Sizing/anchoring.** The owner share passed to entries is `{}` (ui-layout `lib/client.js:276`) — there is **no geometry, anchor, or positioning API**. Entries are plain React roots inside a frame-wide absolute layer; the chip and its expanded card position and size themselves with their own DOM (e.g. absolutely-positioned descendants of the layer). List entries render additively, each wrapped only in the per-entry error boundary (no wrapper element of its own beyond the boundary's children), sorted by `order ?? 0` (ui-renderer `lib/client.js:845-869`).
- **Per-entry crash handling.** Every entry renders inside `SlotErrorBoundary`, a React error boundary per entry ("one registrant crashing… must not take down siblings", ui-renderer `lib/client.js:511-532`). A crash reports through `host.reportEntryError(key, entry, error, { abdicate: spec.kind !== "chain" })` (ui-renderer `lib/client.js:789-790`) — for a `list` slot `abdicate` is `true`, so **a crashing capsule entry is removed from the layer** (the cell shows a bare `data-slot-error` marker, `lib/client.js:869`) rather than taking the shell down. The supervision hook `ctx.slots.onEntryError(key, entry, error, {abdicated})` lets a plugin observe every contained crash (ui-renderer `lib/types/client/registry.d.ts:171-184`).
- **Bounds for ticket 38:** collapsed chip + expanded card = one `shell.overlay` list entry (one `id`), self-positioned; expansion is the entry's own component state; a crash silently removes the capsule (consider `onEntryError` to log/flag).

## Seam 2 (host extension point) — client→host activation path: VERIFIED

- **The composer's own command execution is one RPC.** When the user types a slash line and presses Enter, the conversation submit machine adjudicates the line through the input-trigger pipeline; the host-command source's decision table (`matchEnter`, ui-commands `lib/client.js:712-771`) resolves the command from the session's host directory and — for a command with `input` — returns a claim whose `submit` is `this.execute(session, token + args, attachments)` (`leadingClaim`, `lib/client.js:775-781`); a bare host command without input executes detached via the same `execute` (`runDetached`, `lib/client.js:839-846`). `execute` is a single wire call: `await this.ctx.remote.commands.execute(session.sessionId, line, attachments)` — "The command.execute transaction, addressed to the session's agent — pure admission semantics" (`lib/client.js:795-809`). The frozen contract says the same: a decoration's popup "submits a completed line back through command.execute" (ui-commands `lib/types/client/contract.d.ts:68-76`).
- **The host half is the command registry itself.** `CommandRuntime.execute(agent, line, submittedAttachments, signal)` — a typert `@Remote` endpoint (`dsh-commands lib/index.js:205-231`, endpoint at 318) — parses the line, resolves the command, appends `command/run` / `command/done` lifecycle events with `source: { kind: "user" }` (`lib/index.js:325-329`), and invokes the handler. This is exactly the path a typed line takes; there is no separate "UI" executor.
- **`ctx.remote` is a plain client service any plugin can inject.** `ClientRemoteService` is provided as `"remote"` over the connection (dsh-api-gateway `lib/client.js:1408-1421`), and shipped plugins across the board list `"remote"` in their `inject` arrays (e.g. dsh-client-locale `lib/client.js:1359`, ui-commands `lib/client.js:498`).
- **Addressing from a root-scope capsule.** `ctx.sessions` (the session-controller client service) exposes `list: ObservableSnapshot<SessionListState>` with `current: SessionId | undefined` — the currently selected session (`dsh-api-session-controller lib/types/client/contract/sessions.d.ts:19-21`; `SessionListState` at `sessions/service.d.ts:61-66`) — and `scope(id): AgentContext | undefined`, a use-and-discard Agent-scoped context view (`contract/sessions.d.ts:100-104`). So the capsule reads the current session id from `ctx.sessions.list` and calls `ctx.remote.commands.execute(currentSessionId, "/dispatcher-start", [])`.
- **Verdict:** the capsule's start affordance can execute `/dispatcher-start` through the **same wire transaction** as typing it — same endpoint, same host-side parse, same `command/run`/`command/done` logging, admission marked `source: {kind: "user"}`. ADR-0009 is satisfied: no second activation channel is invented; the button *is* the command path. Two honest caveats: (a) typing additionally runs client-side composer claim UI (the token chip in the draft) which a programmatic call skips — host admission is identical; (b) do **not** use `ctx.conversation.send(text)` for this — that is the plain queued-turn prompt sink ("Send a prompt into the caller scope's session", conversation `lib/types/client/service.d.ts:38,96`), a different channel that does not execute commands.

## Seam 3 (host extension point) — steer composer prefill: VERIFIED (prefill) / focus NOT EXPOSED

- **The per-session input facade is plugin-reachable.** `ctx.conversation` is a root-singleton service whose outward face carries "the scope-addressed verbs and the input registry **other plugins may reach** — and exactly what a test fake must supply" (conversation `lib/types/client/service.d.ts:20-27`, provided as `conversation` at 64). Its `input` member is the `SessionInputResolver`: `.for(actx)` resolves one session's `SessionInput` facade (`lib/types/client/contract/input.d.ts:199-203`).
- **Prefill is a documented programmatic verb.** `SessionInput.setDraft(text)`: "Replace the whole draft (persisted-draft seed and **programmatic writes**). Placeholder-sanitized; newlines split paragraphs; **the caret lands at the end**" (`contract/input.d.ts:172-175`; facade implementation `input/facade.d.ts:113-119`). Session-scope slot components additionally get `InputActions` (setDraft/submit) as "the public provide-channel action face" (`contract/input.d.ts:204-221`) — but the capsule is root-scope, so the resolver path via `ctx.sessions.scope(id)` + `ctx.conversation.input.for(actx)` is the one.
- **Focus is not available.** The only focus-capable faces (`ComposerKeyboard.editor` — the shell-owned Lexical editor — plus its submit/arbitrate verbs) are explicitly package-internal: "Handed to the composer-bar entry through its own inject — **package-internal, never across a plugin boundary**" (`contract/input.d.ts:228-236`). Neither `SessionInput` nor `InputActions` carries a focus verb.
- **Verdict:** the per-row steer affordance can **prefill** the host composer with steer text (caret at end), verified; it **cannot force focus** the composer, and must not reach into the editor. Consequence for ticket 40: prefill + a locale hint ("text placed in the composer — review and send") is the honest composition; the copy-into-composer *hint* fallback is only needed in the edge case where `ctx.sessions.scope(id)` returns `undefined` (session neither listed nor already scoped, `contract/sessions.d.ts:100-104`) — then show copy-only. The steer *transport* is unchanged and host-side (`ctx.subagents.sendMessage`, patterns note (c)); the prefill only fills the user's own composer draft.

## Seam 4 (host extension point) — Settings deep-link: DEGRADED

- **How Settings actually opens.** The settings surface is the `sidebar.settings` **single** slot owned by ui-settings-general; `SettingsRoot` holds its open state in component-local React state — `const [open, setOpen] = useState(false)` and an internal `openSection(id)` callback (ui-settings-general `lib/client.js:178-196`, registration at 601-629). There is no exported service, event, or standard prop to open it or to select a section.
- **The one programmatic page-switch API doesn't cover it.** `ctx.layout.selectPanel(panelId)` — "Select a global panel or return to the Conversation", throws `layout.selectPanel: main panel "X" is not registered` for unknown ids (ui-layout `lib/client.js:399-412`) — addresses `main` keyed panels only. Settings is not a `main` panel; the only shipped `main` key is `"conversation"` (ui-conversation `lib/client.js:16825`).
- **A deep-link exists but is not ours to use.** The `settings.onboarding` slot's owner props include `openSection(id)` — "Open the settings panel directly on one registered section" (runner API catalog, dsh-cordis-client-runner `lib/client.js:3771`). That face belongs to the onboarding coordinator and is only handed to onboarding-step registrants; registering a fake onboarding step to obtain it would hijack onboarding semantics (an onboarding step owns modal chrome and completion) — a dishonest channel, refused under the epic's honesty rules.
- **No URL/hash route** into Settings or a section exists (no hash/pushState handling in ui-settings-general, ui-sidebar, or ui-layout).
- **Verdict: degraded.** Consequence: the capsule footer (epic §5, ticket 42) cannot deep-link to Settings → `multitask-dispatcher`. Fallback prescribed by the epic: the footer's Settings affordance degrades to text only — a locale hint naming the path ("Settings → Multitask Dispatcher") — with no programmatic navigation and no invented channel. The gap is recorded here; if dsh later exposes a settings-open service, ticket 42's link can be upgraded.

## Seam 5 (host extension point) — profile identity: DEGRADED (no client-visible source)

- **The only host facts on the wire.** The Remote-event ready frame carries exactly `{ clientId, host: { home } }` — validated with exact key sets client-side (dsh-api-gateway `lib/client.js:701-712`), emitted host-side as `host: { home: host.home }` (`lib/index.js:497`). The client face is `ctx.remote.$host` = `{ home, isLoopback }` (`lib/client.js:1452-1461`).
- **Profiles are not derivable from `home`.** Profiles are directories *under* the harness home: `resolveProfileDir(name, home) = join(home, PROFILES_DIR, name)` (dsh-app-boot `lib/index.js:311-325`); `home` is shared across profiles and never contains the active profile's name. No client package exposes a profile-identity face — a grep over every `lib/client.js` in the bundle finds no profile-name source (the only "profile" hits are unrelated fixtures and provider-card rows).
- **What the footer can honestly render.** Flag state: the watched settings namespace via `ctx.settingsScope` (dsh-client-ui-settings `lib/types/client/index.d.ts:2-3`; `SettingsScopeSnapshot` = `{status: 'loading'|'ready'|'unavailable', value, base, user}`, `settings-contract.d.ts:6-26`) — as the ticket assumed, this source is real. Host/install provenance down to `home` and loopback-ness is available via `ctx.remote.$host` if ever useful.
- **Verdict: degraded — the profile line has no honest client-side source.** Consequence: the footer's "which profile" segment (epic §5, ticket 42) is dropped; the footer renders flag state (and, if wanted, `$host.home` basename is *not* profile identity and must not be relabeled as such — that would be an invented fact). Record as a permanent v1 gap; revisit only if a future dsh build ships the profile name in the ready frame.

## Mount-test pattern from the reference plugins (abstract; clean-room)

Read from a shallow clone of `omdsh-dev/DSH-better-sidebar` (2026-09-18, pattern-level only — no code, identifiers, or assets copied; mixed-license third-party tree). Its real-browser mount test works as an abstract pattern:

1. **Server out of the spec's hands:** a shell script (not the test runner) boots a real dsh web instance with the plugin installed through the official install channel from a packed artifact, and exports the base URL to the browser test run through an environment variable.
2. **The test run is a crash probe:** Playwright drives headless Chromium against that URL, configured serially (one worker, zero retries, no parallelism) because the assertion target is "the plugin mounts and the shell does not crash", which only stays meaningful without retries.
3. **Filename separation:** the browser test specs use a filename pattern the offline unit runner's include never matches, so `unit test` and `mount test` never collect each other.

Mapped to our epic: this is process req 3 / ticket 33's launcher boot (`dsh --profile web --patch`) plus a Playwright mount smoke test, complemented by the served-page bundle-presence check (`dsh-plugin-ui-examples.md` Finding 3 — page-level only, not repo-verified). The other two reference repos were not read this pass; their interaction patterns (visualize's replay-safe tool cards, deep-whale's config-layer toggles) remain page-level summaries in the examples note, and nothing in the five seam verdicts above depends on them.

**Clean-room statement:** no source, prompts, tool strings, identifiers, or protocol artifacts were copied from any reference plugin repo or from the forbidden reference tree (which was not opened). Everything above is either dsh's own shipped MIT code or an abstract behavioral description.
