# The upstream plugin's ordered lock chain: does our core need it?

**Question:** the upstream dsh-grokbot plugin runs every turn through an ordered chain of exclusive locks — a task lock, then a bot lock, then a workspace write queue (`runExclusively`, its `src/exec.mjs`). The plugin's docs call this chain a "ladder". Does that pattern belong in our core?

**Verdict: NOT APPLICABLE as a chain of locks; one narrow guard against concurrent duplicate spawns is warranted (see "The one real window" below).** Every concurrency hazard the chain exists to prevent already has an existing, verified guard in our core, and the hazard the guards do miss is a single check-then-set gap in one function, not a missing lock hierarchy.

**Status:** decision input only — this note does not take a side on the precedence rules in `docs/agents-rulebook.md`, level 8. It is not a ruling and creates no exception-list item.

---

## The upstream pattern, and why matching the reference does not require it

The lock chain is described in the 2026-10-02 upstream comparison, §3 (turn execution) and §10 (differences that matter): `.scratch/testing/2026-10-02-grokbot-upstream-compare/upstream-findings.md` — a git-ignored scratch file, so the facts the rest of this note relies on are restated here: upstream "workers" are **persistent named bot sessions** that stay alive between turns and compete for shared per-project git workspaces (`upstream-findings.md` §4: no spawned worker processes; concurrency limited by `maxConcurrentJobs` and the lock chain). The chain enforces mutual exclusion so that a bot is not mid-turn in two conversations at once, and two bots do not write one workspace at the same time.

That premise has **no equivalent here**. Our workers are spawned per task and are leaves with no shared session and no shared workspace: only the dispatcher spawns and workers are leaves (`docs/adr/0003-dispatcher-only-spawning.md`), each worker is its own host child session (`src/adapter/cordis-dsh-host.ts:674-681`), and no two workers share mutable state by design. Note also that dsh-grokbot is **not** the reference tree — it is an independent reimplementation of a different product's patterns (`upstream-findings.md` §9), so ADR-0018's imitation rule does not reach it. Adopting or rejecting the lock chain is a free design decision, not a requirement to match the reference — which is exactly why it must be decided by hazard analysis, below.

## Hazard by hazard: what the lock chain protects against, and what we already have

**1. Illegal lifecycle transitions (double settle, revival after abort, steering a worker that has finished).** Status changes flow through a pure state machine where terminal states accept nothing and `applyEvent` returns null for any illegal event (`src/core/worker-fsm.ts:30-44`, `src/core/worker-fsm.ts:50-54`); the core applies events only when legal and ignores the rest (`src/core/multitask.ts:406-425`). A second settle for an already-terminal worker is dropped before it can wake anyone (`src/core/multitask.ts:486-491`). No lock is needed: the state machine itself refuses the race.

**2. Spawn/restart race (crash between the start of a spawn and recording it).** The spawn path writes its durable marker **and waits for the write to complete** before the spawn returns (`src/core/multitask.ts:611-616`), so any crash after the caller sees success leaves a marker behind. On restart the rebuild restores terminal rows and converts markers for workers that were live at crash time into unknown-state holds (`src/core/multitask.ts:877-900`); a held stream key refuses re-spawn with a distinct, resolvable reason (`src/core/multitask.ts:568-577`; the refusal's documented intent, `src/core/types.ts:99-110`). Settle records the terminal status, and abort deletes the marker (`src/core/multitask.ts:502-506`, `src/core/multitask.ts:652`) — writing the marker before awaiting the spawn closes the window where a worker exists but no record does.

**3. Steer races (two steers mid-flight, steer vs settle).** Steer delivery is serialized by a single-slot last-wins queue — one held message per worker, and a new steer replaces the undelivered one (`src/core/steer-queue.ts:1-15`, `src/core/steer-queue.ts:21-23`) — plus park-then-interrupt with a check after the interrupt that drops the steer if the worker stopped steering in the meantime (`src/core/multitask.ts:678-689`), and a step-boundary pop that fires only while the state machine says `steering` (`src/core/multitask.ts:521-529`). Upstream solves the same contention with a bot-level mutex; ours is narrower because last-wins makes ordering irrelevant: only the newest steer can ever be delivered.

**4. Stop vs settle race.** The stop path transitions to `aborted` **first** and only then interrupts, so a late host settle lands on a terminal state and cannot revive the worker (`src/core/multitask.ts:636`, then `src/core/multitask.ts:653-655`; the protection comes from the state-machine rule in hazard 1). The reverse refusal also holds: stopping an already-settled worker is refused without interrupting, so a delivered completion is never undone (`src/core/multitask.ts:626-644`).

**5. Settle vs pending access asks.** The settle handler clears the worker's access tickets **before** the state transition, so a settled worker cannot leave a parked ask behind (`src/core/multitask.ts:483-489` — the clear at :485 comes before the transition); the stop path clears the same tickets too (`src/core/multitask.ts:648`).

**6. Writes for an unknown worker (steer/stop of an id from another dispatcher or an id that is gone).** The steer path refuses an unknown id without side effects (`src/core/multitask.ts:660-676`) and only a live mid-work worker accepts a steer at all; the adapter's interrupt authority likewise resolves only through the worker's recorded parent entry, which exists only for workers this process spawned (`src/adapter/cordis-dsh-host.ts:690-702`).

## The one real window: two concurrent spawns for the same stream key

Stream-key uniqueness is checked and then set: `spawnWorker` reads the live map at `src/core/multitask.ts:553`, then **awaits the host spawn** (`src/core/multitask.ts:578`) before registering the worker on the map at `src/core/multitask.ts:600-601`. The await between the check and the set yields the event loop, so two concurrent `spawnWorker` calls with the same `(parentSessionId, streamKey)` can both pass the check and both spawn — the one-worker-per-stream invariant is violated for that pair.

This is the one hazard here that the upstream lock chain would also cover. The fix is small and local — a synchronous reservation of the stream key before the await, released on refusal or when the worker reaches a terminal state — not a chain of locks. A companion ticket for that fix was filed this session; per repo rule it is its own ticket, so this note records the hazard and the shape of the fix only.

## Governance notes

- **Per-stream exclusivity is already a settled ruling.** The one-stream-one-worker rule and its refusal-without-host-call semantics were specified and resolved in `Issue-tracker/resolved/05-worker-registry-and-stream-uniqueness.md`. The uniqueness **domain** is `(parentSessionId, streamKey)` — a key written by the model and scoped to the dispatcher session — recorded in `docs/adr/0019-per-dispatcher-scoped-tools-draft-nonhuman-approved.md:33` (context: `:23`). Any NEW cross-session or process-global lock would change that recorded domain and is therefore an unrecorded decision: it would require its own draft ADR before implementation, not a code-first change.
- **Why the upstream lock chain's purpose does not transfer.** Upstream needs it because its persistent bot sessions are long-lived shared resources that compete across conversations and workspaces (`upstream-findings.md` §3–§4). Our workers have no between-turn life to compete over — a worker is one task, one child session, one settle — and the dispatcher (the only persistent session) is already serialized by the host's turn model plus the wake bus's queue-while-busy behaviour (`src/core/multitask.ts:238-243`).
