# Research: what dsh actually lets a plugin extend (facts for the PRD §15 decisions)

- Question: What can a plugin actually extend in dsh, and what does that provide that the dispatcher's adapter and the PRD §15 decisions (core language; in-process vs sidecar) depend on? Four sub-questions: (1) extension model — in-process plugin API or sidecar-only, and what "Cordis" means here; (2) adapter API surface — spawn / interrupt / jobs / todo / user send, with exact names; (3) facilities — durable key-value store, attachment/artifact handling, timer/scheduling, session/job store; (4) the facts each §15 option rests on (no decision made).

- Method: (a) extracted every dsh claim from `PRD-dsh-multitask-dispatcher.md` (§8, §9, §11) and `docs/research/prd-vs-reference-capability-gaps.md` (Gaps 1, 3, 4 "check whether dsh ships X"); (b) searched the local machine for a dsh install or repo (Desktop, Documents, WorkBuddy, Downloads, npm globals — all negative, ~6 min, forbidden tree pruned); (c) found dsh as a **public product**: npm package `@deepseek-ai/dsh`, GitHub repo `deepseek-ai/deepseek-harness`, and its official docs site — then read the docs site's English reference pages directly (fetched 2026-09-15; page text cached locally under `%TEMP%\dshdocs\`, cited below by URL + page name).

## Verdict

**Update 2026-09-16:** dsh is installed locally after all — this note's Finding 1 "no install" claim was wrong; everything else holds and is now readable in real installed code (`docs/research/dsh-local-install.md`).

dsh is real, public, and exactly the host the PRD hoped for. **DeepSeek Harness (`dsh`) is an MIT-licensed TypeScript agent harness by DeepSeek AI, "Everything is a Plugin", powered by Cordis** — a vendored fork of the Cordis meta-framework (`cordiverse/cordis`), i.e. the same plugin framework family as Koishi's. The extension model is **in-process TypeScript plugins** (`apply(ctx)` modules loaded from Cordis overlay files); there is also a first-party **Python SDK** that embeds or drives a dsh process from Python over a JSON-RPC server, and an HTTP gateway for remote clients. Every dispatcher ability the PRD §11 checklist asks to "confirm" exists as a named service, tool, or event: spawn (`ctx.subagents.start` / `startContinuable`), steer (`sendMessage` / `Agent.steer` — mid-run, context preserved), interrupt (`interrupt_agent` / `ctx.jobs.kill`), jobs (`ctx.jobs` with `onJobDone` completion wakes), todo (`todo_write` with `allowParallelInProgress: true` shipped), and user delivery (dispatcher-turn wakes + `present` tool + `ask_user_question`). Facilities: durable typed key-value storage (`ctx.storage`/`ctx.storageDomain`, json+sqlite backends), spill storage + `present` for artifacts, a session-local durable reminder scheduler (no cron; minimum 5-minute interval; session must be live), and a session store with durable, resumable child sessions. No built-in per-agent memory ships (memory is via third-party MCP servers per the official guide) — the gaps note's "check whether dsh ships a memory facility" resolves to "no; build on `ctx.storage` or MCP". Both §15 decisions now rest on verified facts. The single most important fact is that **an in-process dsh plugin must be a JavaScript/TypeScript module loaded into dsh's Node process**, while the only first-party non-TypeScript route is the Python SDK host, with plugins still being TypeScript bundles.

## Finding 2 — extension model: in-process TypeScript plugins on a vendored Cordis (sub-question 1)

- **Cordis here is a vendored fork of the Cordis meta-framework.** The dsh docs say: "Cordis is the vendored plugin framework underneath DeepSeek Harness" (https://deepseek-harness.github.io/deepseek-harness/en/reference/cordis-primer). The npm package `@deepseek-ai/cordis` 4.0.2 is described as "Meta-Framework for Modern JavaScript Applications", repository `deepseek-ai/deepseek-harness` directory `vendor/cordis`, MIT, DeepSeek maintainers (https://registry.npmjs.org/@deepseek-ai%2fcordis). Upstream `cordis` 4.0.0-rc.10 has the same description ("Meta-Framework for Modern Applications") at `cordiverse/cordis`, MIT, maintainer `shigma` (https://registry.npmjs.org/cordis; https://github.com/cordiverse/cordis — "A Meta-Framework of Spatiotemporal Composability", the same arXiv paper the dsh README links). The Koishi connection: upstream Cordis is maintained by `shigma`, who is also the author and maintainer of `koishi` (https://registry.npmjs.org/koishi, author Shigma); the cordiverse README itself does not mention Koishi, so treat "Cordis is Koishi's extracted plugin framework" as background knowledge consistent with, but not asserted by, these primary sources.
- **A plugin is a TypeScript module with an `apply(ctx)` function, loaded in-process.** "In Harness, a plugin is a TypeScript module that exports an apply function. The framework calls apply when loading the plugin and passes a ctx context object through which the plugin registers capabilities" — https://deepseek-harness.github.io/deepseek-harness/en/develop/basic/ ("Your first plugin"). Loading is via a Cordis overlay file (`cordis.yml`) with `insert` rows pointing at a local `.ts` path, run with `pnpm dsh web --patch ./cordis.yml`; persistent install via `dsh plugin --profile <name> add file:/path/to/bundle` (same page; and https://deepseek-harness.github.io/deepseek-harness/en/guide/python-sdk).
- Cordis model per the primer (same cordis-primer URL): a plugin implements `Service` with optional `inject` (a declarative dependency on other services) and `apply(ctx)`; services claim stable `ctx.<key>` slots (`ctx.tools`, `ctx.llm`, `ctx.sessions`, …); typed events via TypeScript declaration merging, dispatched as `emit`/`waterfall`/`parallel`/`serial`/`bail`; all registrations are reversible effects (`ctx.effect()` / `ctx.on()`). Hot reload is supported (`@deepseek-ai/cordis-plugin-hmr` is a dsh dependency, npm metadata above; the subagent docs call registrations "HMR safe", https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/subagent).
- Tool registration is exactly what PRD §8 guesses: `ctx.tools.register(definition)` returning "the exact disposer that unregisters the tool" (https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/tools, ToolRegistry section). The tool pipeline has policy waterfalls `tools/pre-execute` (allow/deny/ask) → `tools/execute` → `tools/post-execute` → `tools/result` (same page).
- dsh even ships Cordis tools the model can call at runtime (`cordis_define`, `cordis_run`, `cordis_stop`, `cordis_inspect_*` from `@deepseek-ai/dsh-tool-cordis`) so an agent can define and load plugins at runtime (tool catalog: https://deepseek-harness.github.io/deepseek-harness/en/reference/tool-catalog).
- Other host facilities are plugins too (everything-is-a-plugin): the CLI dependency list shows ~70 first-party packages including `@deepseek-ai/cordis-plugin-timer`, `dsh-jobs-local`, `dsh-tool-subagent`, `dsh-tool-todo`, `dsh-schedule`, `dsh-storage-json`, `dsh-storage-sqlite`, `dsh-mcp-client`, `dsh-sdk-app`, `dsh-webhook(-github)`, `dsh-headless` (https://registry.npmjs.org/@deepseek-ai%2fdsh, dependency list).

## Finding 3 — adapter API surface: spawn, interrupt, jobs, todo, user send (sub-question 2)

All names below are from the generated reference docs (each page carries a "Generated from source … gen-cordis-catalog" note, i.e. generated from the shipped TypeScript source).

**Spawn (start a worker)**
- `ctx.subagents` (`SubagentRuntime`, https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/subagent):
  - `start(name, request)` — delegate one task and get a result → `SubagentRun { id, result: Promise<SubagentResult>, dispose() }`; result carries `output`, optional `structured` (json-schema), `stopReason` (`completed | aborted | error | max-tokens | refusal`).
  - `startContinuable(spec)` — a durable child session → `{ childId, messageId }`; the child can be resumed after a process restart ("cold resume"), and starts by activation.
  - `registerProvider(provider)` — the subagent extension point is itself pluggable (providers `spawn`/`fork` in-process, plus `acp`, `codex`, `claude-code`, `dsh-sdk`).
  - The blank-worker requirement matches dsh's meaning: the `subagent` tool's own description says "Give it a complete, standalone prompt: it does not see this conversation" (https://deepseek-harness.github.io/deepseek-harness/en/reference/tool-catalog, `@deepseek-ai/dsh-tool-subagent`).
- Model-facing tools: `subagent` (with `run_in_background: true` → returns a job id, collected via `job_output`, stopped via `job_kill`), `list_subagent_models` (tool catalog, same page). The spawn request supports `toolFilter` (which tools the child may see — implemented as a scoped `tools.restrict()`: named tools "vanish from the child's prompt AND refuse to execute"), `persona`, `maxDepth`, `outputSchema`, `agentOptions` (subagent page).
- Lower-level: `ctx.agents.create()/resume()` → `AgentHandle` (https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/core, `ctx.agents — AgentRegistry`). Experimental: `@deepseek-ai/dsh-experimental-tool-agent-team` adds `spawn_teammate`, a shared team task board (`team_task_create/get/list/update`), and team-scoped `send_message`/`interrupt_agent`/`list_agents` (tool catalog — evidence that dsh already experiments with dispatcher-like agent teams).

**Interrupt (abort a running job mid-run)**
- `ctx.subagents.interrupt(targetSessionId, authority)` — "the one public stop": issues `Agent.cancel(cause, { keepInbox: true })`, returns immediately without waiting; unclaimed inbox work and descendants are preserved (subagent page). Tool: `interrupt_agent` — "Only the current turn stops: messages already queued for the agent stay parked until a later send_message… the agent itself stays available for follow-ups" (tool catalog, `@deepseek-ai/dsh-tool-subagent-control`).
- Jobs: `ctx.jobs.kill(id, caller?, reason?)` → `'requested' | 'already-finished'`; tool `job_kill` (jobs page + tool catalog).

**Steer (send a correction into a run — PRD S3: the worker continues without replaying from zero)**
- `ctx.subagents.sendMessage(sender, targetId, content, options)` — routes by target state: running → "steer the nearest step in the same Activation"; idle → "wake and steer"; absent child → "cold-resume a new Activation, then steer it" (subagent page). No restart; conversation/tool context is the child's own session.
- `Agent.steer(message)` — "An idle driver starts a turn; a running driver consumes it at its next step boundary" (core page, Agent interface). Also `Agent.send(message, target, wakeup)`, `Agent.followup()`, `Agent.inject()` (context queued without waking) — same block. Model-facing tool: `send_message` ("If the target is still working, the message steers its nearest step; if it is idle, the message starts a turn"; tool catalog).

**Jobs**
- `ctx.jobs` (`JobRegistry`, abstract interface; local provider `@deepseek-ai/dsh-jobs-local`): `start(spec)` (kinds `bash`, `subagent`, extensible "by declaration merging" by plugins), `list`, `get`, `read`, `kill`, `wait(id, timeoutMs)`, `onJobDone(listener)`, `onJobsChanged(listener)`, `attachController(name)`; status `running | stopping | completed | killed | failed`; owner-scoped access; `maxConcurrentJobsPerOwner` default 10 (https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/jobs). Tools: `job_list`, `job_output`, `job_kill` (tool catalog).

**Todo**
- `todo_write` (`@deepseek-ai/dsh-tool-todo`): each call replaces the whole list; statuses `pending | in_progress | completed`; config `allowParallelInProgress` is "required with no default… the catalog states its choice: **true**, whose description invites several in_progress items" — i.e. dsh's shipped tool allows multiple `in_progress`, satisfying PRD §11 item 3 as-is. Caveat: no `cancelled` status in dsh todos — the PRD's `cancelled` maps to dropping items from the replaced list (tool catalog, `@deepseek-ai/dsh-tool-todo`). `todo/write` is a durable log-only session event; UIs render it as a checklist (https://deepseek-harness.github.io/deepseek-harness/en/reference/persistence-catalog).

**User send / delivery and wake**
- The dispatcher, being the primary chat agent, delivers in its own turns. Proactive wake exists natively: job completion listeners "may open a model turn synchronously" (jobs page, `reported`/first-wins settlement section); a settling continuable child gets "one notice to the child's durable direct parent… reaches a resident parent through the same waking Agent delivery as an Agent message" (`subagent-settled` source, subagent page); `Agent.followup()`/`send(…, wakeup: true)` open turn boundaries (core page). The `list_agents` doc confirms push-not-poll: "you are told when one finishes" (tool catalog).
- PRD §11's literal name `completionDelivery=wakeup` does **not** appear in the docs — the equivalent mechanisms are the two above (fact-check result: rename needed, capability exists).
- Asking the user: `ctx.userQuestions` interface + `ask_user_question` tool (options, multiSelect, batched questions) — https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/user-questions and tool catalog. File delivery: `present` tool — "Declare existing files accessible through the Session filesystem as final deliverables… you must call present after writing it and before your final response" (tool catalog, `@deepseek-ai/dsh-tool-present`).
- Workers addressing the user: background and continuable children have no user-messaging tool by default; even the optional `send_message` control is limited to adjacent agents (direct parent or direct child only, sender-authorized). S5 ("workers cannot address the user") is enforceable via child `toolFilter`/scoped `tools.restrict()` if a deployment loads such controls into children (subagent page + tool catalog).

## Finding 4 — facilities available to a plugin (sub-question 3)

- **(a) Durable key-value store: YES (`ctx.storage`); per-agent memory facility: NO.** `ctx.storage` is a hub over named backends (`json`, `sqlite`); the shipped part is key-value: `KvFacet.open(descriptor)` → `KvUnit` with `loadAll`, `putRecord`, `deleteRecord`, `setGlobal`; writes are atomic and "durable once resolved" (https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/storage). A typed layer on top (`ctx.storageDomain`) adds zod-schema'd, versioned tables with `single`/`per-record` layouts and a global slot (same page). But no per-agent memory ships: the official guide wires **third-party memory MCP servers** (Memorix, MCP Reference Memory, Engram) through `@deepseek-ai/dsh-mcp-client` and states "No memory server is present in the shipped composition" (https://deepseek-harness.github.io/deepseek-harness/en/guide/mcp-memory). This answers the gaps note's Gap 1 check: memory must be built (a natural starting point is a `ctx.storageDomain` domain) or attached via MCP.
- **(b) Attachment/artifact handling: YES, three mechanisms.** The `present` tool declares files as user-facing deliverables (tool catalog); spill storage persists large content verbatim → an opaque `SpillLocator` with owner/source provenance (`saveText`, https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/spill); and the web/gateway subagent prompt path "admit[s] and persist[s]" image parts "through the attachment store before delivery" (subagent page, `@Remote('prompt')`).
- **(c) Timer/scheduled tasks: YES, two tiers.** Generic timers via the Cordis timer plugin (`@deepseek-ai/cordis-plugin-timer` dependency; plugin tutorial: anything registered through ctx — "event listeners, tools, or timers — is cleaned up when the plugin unloads", https://deepseek-harness.github.io/deepseek-harness/en/develop/basic/). A user-facing Session-local Schedule: durable reminders with `after` (delay), `at` (absolute RFC 3339/local + IANA zone), `every` (fixed-rate, minimum 5 minutes; **no cron/calendar expressions**); records persist as `schedule/change` session events; tools `schedule_create/delete/list`; delivery mode is `'session-local'` — "the original Session must be live: no external notification channel or cold-session scheduler exists" (https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/schedule; tool catalog; persistence catalog). This answers the gaps note's Gap 4 check: timers exist, but timer wakes are session-local and coarse (5 minutes or more for recurring timers); external webhook sources exist as packages (`dsh-webhook`, `dsh-webhook-github`, npm dependency list) — what they offer was not verified here.
- **(d) Session/job store to persist WorkerRecords/SteerTickets: YES (sessions), NO (jobs).** `ctx.sessions` (`SessionStore`) is the in-process live store (`create`/`prepare`/`enter`/`announce`/`get`), with persistence attached by the agent lifecycle as a session-log writer — "a session published outside that lifecycle persists nothing"; sessions carry an immutable `SessionHeader` (absolute cwd, seed/parent lineage, delegation depth) and resume via `ctx.agents.resume()` (https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/session; core page). The durable event catalog (todo/write, schedule/change, subagent/catalog, subagent/descriptor, agent/inbox/spliced, …) is the persistence vocabulary (persistence-catalog page). By contrast `ctx.jobs` is a process-local registry (`dsh-jobs-local`); job records are not presented as durable across restart (jobs page). Practical mapping for the PRD's data model: WorkerRecord-like durable state is best persisted either as continuable child sessions (which dsh itself persists, enumerates via `listChildren`/`listDescendants`, and cold-resumes) or in a `ctx.storageDomain` domain; in-memory core maps survive only with the process (subagent page + storage page).

## Finding 5 — what the PRD §15 decisions 1–2 rest on (sub-question 4; no decision expressed)

**Decision 1 (core language).**
- Fact: an in-process dsh plugin is loaded into the host's Node.js process as a JavaScript/TypeScript module; Cordis is a JavaScript meta-framework ("Meta-Framework for Modern JavaScript Applications"), and the docs define plugins as TypeScript modules (Finding 2 citations). Therefore: in-process core ⇒ TypeScript (or JS).
- Fact: dsh's own dependency list includes `node-addon-require-builtin`, and the Python SDK ships "a matching native runtime wheel" — native components exist in the ecosystem, but the documented plugin surface is TypeScript/JavaScript only (npm metadata; python-sdk guide).
- Fact: a first-party **Python SDK** (`pip install deepseek-harness-sdk`) exists; it "starts the bundled `dsh --profile sdk-minimal` process lazily and reuses it", needs no system Node.js, and a valid profile must include `@deepseek-ai/dsh-sdk-app` "or another JSON-RPC server row" — i.e. the first-party way to integrate a non-TypeScript program is an external process speaking JSON-RPC to dsh, with plugins still installed as TypeScript or bundle layers (`dsh plugin add file:…`) (https://deepseek-harness.github.io/deepseek-harness/en/guide/python-sdk). Therefore: a Go/Rust (or Python) core is only reachable out-of-process today (via the SDK pattern's JSON-RPC server / gateway), not as a documented in-process plugin language.
- Fact: AGENTS.md in this repo mandates a non-TypeScript core (Go/Python/Rust preferred) while PRD §8/§15 resolved TypeScript — the facts above are the input both sides need; this note takes no side.

**Decision 2 (sidecar vs in-process embed).**
- Fact (in-process): a plugin gets typed, in-memory access to all services used by the adapter — `ctx.subagents`, `ctx.jobs`, `ctx.sessions`, `ctx.storage(Domain)`, `ctx.tools`, `ctx.agents`, Cordis events (`subagent/start|end`, `job`-completion listeners, `todo/write`) — plus effect-scoped lifetime, hot reload, and scoped tool registration/restriction (Findings 2–4 citations). The whole adapter surface in Finding 3 is in-process API.
- Fact (sidecar): dsh runs a gateway for remote clients (API Gateway docs page exists, `@Remote`-annotated service exports like `SubagentRuntime.remoteExportList`/`prompt`/`interruptByParent` are served through it — subagent page), and `dsh-sdk-app` provides "a JSON-RPC server" profile row used by the Python SDK host (python-sdk guide). An out-of-process core would therefore sit on the HTTP/JSON-RPC interface; whether that interface is complete for dispatcher needs (e.g. arbitrary service access, events push) was **not** audited page-by-page in this pass and is the main open verification item for a sidecar option.
- Fact (hybrid): nothing prevents a TypeScript in-process adapter plugin (thin, dsh-facing) plus a Go/Python/Rust core process behind it, bridged over the same JSON-RPC/local socket — the Python SDK demonstrates the host-side pattern in the opposite direction (python-sdk guide). Both AGENTS.md's language rule and PRD §15's in-process preference could then apply to different layers; this note records the mechanism, not a recommendation.

## Confidence & unknowns

**Confirmed fact (primary sources, all fetched 2026-09-15):** dsh's identity, license, npm/GitHub presence, the Cordis-vendored in-process TypeScript plugin model, and every API/tool/event name quoted in Findings 2–4 (official docs site pages, each individually cited; npm registry metadata; GitHub repo metadata and README). The docs' service/event sections are explicitly "generated from source" by the project's own catalog scripts, so names reflect shipped code.

**Confirmed absence:** dsh is not installed anywhere on this machine (bounded local search, forbidden tree excluded); no built-in memory facility ships; no `cancelled` todo status; no cron-style scheduling; no `completionDelivery=wakeup` config name.

**Inference / unverified:**
- The Koishi lineage of Cordis (maintainer overlap `shigma` is cited; the cordiverse README itself never mentions Koishi).
- Completeness of the out-of-process surface (API Gateway / JSON-RPC `dsh-sdk-app`) for a sidecar-style core — the gateway page was not read in this pass; anyone pursuing Decision 2's sidecar option should audit `en/reference/api-gateway` next.
- Runtime behavior under real load (e.g. schedule delivery when the dispatcher session is cold, `every`-reminder catch-up, cold-resume latency) — docs describe contracts, not benchmarks.
- dsh is in developer preview with an explicit breaking-change warning; any API name above may shift between releases (README), so pin the dependency and re-verify at integration time.
- Webhook packages (`dsh-webhook`, `dsh-webhook-github`) exist as dependencies; their wake behaviour was not read in this pass.
