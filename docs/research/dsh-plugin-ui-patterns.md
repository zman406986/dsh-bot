- Question: Which UI surfaces can a dsh plugin register into (settings sections, commands, chat rendering, web-UI pages and overlays, routes, delivery and approval surfaces), what is the exact registration API and lifecycle of each, and what happens when two plugins claim the same slot? ## Verdict

dsh has **two kinds of plugin code and one shared set of registration rules**. The *host side* (Node, in-process) exposes capabilities as services: `ctx.settings.installSection(...)` for a settings page, `ctx.commands.register(...)` for slash commands, `ctx.web.registerSearchProvider/registerFetchProvider` for web tooling, `ctx.webServer.register({kind, path, handler})` for HTTP routes, `ctx.approval`/`ctx.userQuestions` for prompts to the human, and the `present` tool plus the deliverables UI for file delivery. The *client side* (browser) is a second Cordis runtime: any package that declares `dsh.client: {platform: "web"}` in its `package.json` gets its browser bundle loaded into the web app, where its `apply(ctx)` registers **React components into named slots** (`ctx.slots.register({name, key/id, order, children}, Component)`) — slots are how a plugin adds pages, side-panel tabs, input-bar controls, overlays, settings entries, and per-tool-call renderings. Every registration on both sides is an effect on the calling plugin's fiber (unloading the plugin reverses it; HMR swaps the fiber), and every surface has an explicit collision rule: settings namespaces, command names, web provider ids, exact routes, and client command contributions **fail loudly on collision**; web-UI *list* slots are additive and sorted by `order`; *keyed* and *single* slots allow only one entry per cell, so a later or higher-priority entry replaces the earlier one, and dsh's own doc comment steers plugins to the additive `shell.overlay` slot for surfaces that float over the whole app. No notifications/toast surface exists in 0.1.5-rc.1.

## Finding 1 — Host side: settings sections (`ctx.settings`)

Owner: `@deepseek-ai/dsh-settings` ("Abstract user-settings seam (ctx.settings)"), with provider implementations in `dsh-settings-file`.

- **Registration.** `installSection(owner, ns, schema, entry, hooks)` (dsh-settings lib/index.js:327) — the convenience path for a section owned by one plugin; it wraps `register(ns, schema, {base: entry, validate?})` (same file, line 281), which returns an owner scope `{ get, watch, update, replace }`. `hooks` = `{ setSource, onChange, validate? }`; `setSource` receives a function that returns the resolved value, `onChange` fires on any commit. The repo already calls exactly this from `src/adapter/settings-section.ts:75` (`installSection(ctx, "multitask-dispatcher", schema, config, {...})`).
- **How a value is resolved** — three layers, in fixed order: schema defaults → the plugin's composition `base` (the `entry` passed in) → the user's stored document section (lib/index.js:509–513, docstring at 75–79). Fields declared `.role("secret")` in the schemastery schema are blanked on wire surfaces (`describe({redactSecrets: true})`, lib/index.js:66–72, 351–381).
- **Lifecycle.** Registration is `this.ctx.effect(...)` on the calling plugin's fiber: "disposing that fiber removes the namespace and its observers" (lib/index.js:271–297). An invalid *stored* section fails the registration itself; an invalid stored section arriving later through `publish` keeps the last good value and logs a warning (lib/index.js:488–500).
- **Coexistence.** Namespaces are globally unique and match `/^[a-z][a-z0-9-]*$/` (lib/index.js:82). A duplicate registration throws loudly: `settings namespace "X" is already registered` (lib/index.js:283) — first claim wins, the second plugin's fiber FAILS. Naming the namespace after the plugin id (e.g. our `multitask-dispatcher`) is therefore the whole convention; there is no ordering or priority — the order of the settings *page* is decided client-side by each section entry's `order` (Finding 5). Events: `settings/updated` (resolved value) and `settings/document-updated` (raw revision) are emitted per namespace (lib/index.js:527, 549).
- **Shipped example.** `dsh-agent-default-model` lib/index.js:44–51 — `ctx.inject(["settings"], (settingsCtx) => settingsCtx.settings.installSection(ctx, NAMESPACE, SCHEMA, entry, { setSource, onChange }))`, mirroring our adapter's shape (the repo comment in `src/adapter/settings-section.ts:10–11` is accurate).

## Finding 2 — Host side: human slash commands (`ctx.commands`)

Owner: `@deepseek-ai/dsh-commands` ("Plugin-owned human command registry for DeepSeek Harness UIs").

- **Registration.** `ctx.commands.register(definition)` with `{ name, description, input?: { hint, attachments? }, recordInput?, handler(invocation) }` (dsh-commands lib/index.js:142–173, 252–260). The name must match `/^[a-z][a-z0-9_-]*$/u` (line 71). The handler runs **instead of** sending the line to the model (`execute` "Parse and execute a known command without sending it to the model", lib/index.js:303–318) and returns `{kind: "success", text?}` or `{kind: "error", text}` (lib/index.js:175–195). The invocation carries `{commandId, agent, rawInput, attachments, signal}`.
- **Lifecycle.** `register` returns "the exact effect disposer that unregisters this definition" through `layers.effect(this.ctx, ...)` (lib/index.js:257–260) — scoped to the plugin's fiber, safe across hot reload. Each execution appends `command/run` / `command/done` log-only session events, so the transcript shows the command ran.
- **Coexistence.** Names are unique per scope; a duplicate throws `command "X" is already registered (for a per-agent variant, mount a command-injected plugin under that agent's agent.ctx)` (lib/index.js:82). There are two scopes: **global** (plain context) and **per-agent** (a command-injected child of an agent context overrides globals for that agent only — the per-agent command takes precedence for that agent; `list()` returns name-sorted descriptors after that precedence is applied, lib/index.js:278–279, 414–416). Registry changes emit `commands/change` (line 419). For the dispatcher this means: a `/dispatcher` command coexists with any other plugin's commands unless names collide, and dispatcher-scoped variants can be mounted under the dispatcher agent only.
- **Shipped example.** `dsh-command-goal` lib/index.js:173–184 — registers `/goal` with description, input hint, `attachments: true`, and a handler returning error/success results.

## Finding 3 — Host side: capability registries (`ctx.web`, `ctx.webServer`), prompts (`ctx.approval`, `ctx.userQuestions`), delivery (`present`)

- **Web providers** — `@deepseek-ai/dsh-web` (`ctx.web`): `registerSearchProvider(provider)` / `registerFetchProvider(provider)` (lib/index.js:67–79). Duplicate id throws `WEB_DUPLICATE_PROVIDER` (line 80–87); the disposer is fiber-scoped. Selection is deliberately **registration-order-independent** and resolved at call time: a configured provider id wins; with no configuration exactly one usable provider is required, otherwise `WEB_PROVIDER_AMBIGUOUS`/`WEB_PROVIDER_UNAVAILABLE` (lib/index.js:30–40). So many plugins can coexist; the *user's* `searchProvider` config (as in the old `cordis.patch.yml` row cited in `dsh-local-install.md` Finding 3) picks the active one. Shipped example: `dsh-web-search-deepseek`; third-party worked example: `dsh-web-search-exa` (`dsh-local-install.md` Finding 4 — package since removed from disk, Finding 0).
- **HTTP routes** — `@deepseek-ai/host-webserver`: `ctx.webServer.register(route)` with `kind: "exact" | "prefix"`, `path`, `handler` (lib/index.js:176–186); duplicate **exact** paths throw, prefix routes coexist and the longest matching prefix wins after an exact-table miss (lines 147–177, 321–324). Separately, the `webserver/index-inject` event lets composed plugins push `<head>` rows (scripts/globals) into the served index page — that is how the client module system injects its startup graph (dsh-client-modules lib/index.js:489–491, 387–432). This is the surface for serving a plugin's own web page or app route.
- **Prompts to the human** — `ctx.approval` (`dsh-user-approval`: "one-shot permission decisions dispatched to composed answerers over the approval/request waterfall, fail-closed by default") and `ctx.userQuestions.ask(request)` (`dsh-user-questions` lib/index.js:52; the model-facing tool is `ask_user_question`). Both are **shared surfaces where one plugin can take over answering**: the web client's answering composer is itself a plugin (`dsh-client-ui-approval`, `dsh-client-ui-user-questions` — "composer takeover over the scoped Remote Event waterfall"). Relevant to ticket 13's relay UX: the host surface exists and is UI-agnostic; a custom prompt UI would be a client plugin registering an answering composer, not a new host pathway.
- **File delivery** — `dsh-tool-present` ("Explicit workspace file delivery declarations") marks files as deliverables; `dsh-client-ui-deliverables` renders them as a "Produced-files turn tail and clickable final-response file references for Web". This is how worker artifacts reach the user visually; no custom renderer is needed to benefit from it.
- **Console output** is not a plugin surface: plugins log through the Cordis `ctx.logger` (used throughout, e.g. dsh-settings lib/index.js:493). There is no plugin-facing "console panel" API in this build.

## Finding 4 — The client side: how a plugin gets browser code into the web UI at all

Owner: `@deepseek-ai/dsh-client-modules` ("Client module system, dual-face").

- **Declaration.** A package adds to its `package.json` a `dsh.client` record `{ platform: "web", inject?: string[], external?: string[], immediately?: boolean }` plus `exports["./client"]` pointing at the built browser bundle (parsed at dsh-client-modules lib/index.js:140–166). The host half scans loaded plugins incrementally (per fiber construction/disposal, lines 66–88), composes the `window.__DSH_BOOT__` module graph in dependency order (`orderByModuleGraph`, lines 349–371; `external` entries name other client packages your bundle requires), serves combined bundles at `/plugins/??…` (route registered onto `webServer` as a prefix, lines 481–487), and injects the startup queue and graph into the page index (lines 387–432, 489–491).
- **How the browser runs it.** The bundle registers a factory: `window.__ModuleLoader__.load({ id, factory })`; module bodies (including CSS) run only on first use, recursively, so load order needs no sequencing (lib/client.js docstring, dsh-client-ui-renderer lib/client.js:1–3 shows the wrapper). The browser half is a real Cordis loader: client plugins export `apply(ctx)` and run with the same service/effect semantics as the host (every `dsh-client-ui-*` `apply` follows this).
- **Lifecycle and hot reload.** Bundle content changes reach the graph only through `ClientModuleRegistry.rebuilt(id)` (re-hash → graph recomposition → notify, lib/index.js:541–562); the dev driver `@deepseek-ai/dsh-client-hmr` ("Dev-only hot-reload driver for script-loaded client entries: SSE rebuilt frames → invalidate/prefetch → fiber swap through the vendored Loader entry") swaps the client fiber; host-side hot reload is `@deepseek-ai/cordis-plugin-hmr`. Composition errors fail loudly: a package resolving from **two active loader sources** throws (`client-modules: package X resolves from multiple active Loader sources … remove one entry`, lib/index.js:816–819), and a missing built bundle fails activation with `pnpm run build` instructions (lines 90–105).
- **Coexistence.** Many client packages compose into one graph — the shipped web UI is itself ~40 `dsh-client-ui-*` packages. Adding one is additive as long as external dependencies form an acyclic graph and no package is double-sourced.

## Finding 5 — Client side: the slot system (`ctx.slots`) — chat rendering, pages, overlays, settings UI, tool views

Owner: `@deepseek-ai/dsh-client-ui-renderer` (`ctx.slots`, a Cordis `Service` over the pure `SlotCore` from `@deepseek-ai/dsh-client-ui-slots`).

- **Registration.** `ctx.slots.register(options, ReactComponent)` — options `{ name: <slot key>, key? | id?, order?, locale?, children?: {<child slot>: {kind, scope}}, store?, inject? }` (dsh-client-ui-renderer lib/client.js:1388–1391). It MUST stay callable per-plugin: the service proxy binds `this.ctx` to the *caller's* context at call time, routing the registration effect into the caller's fiber (lib/types/client/registry.d.ts:77–83). Disposal cascades on fiber unload.
- **Waiting for a slot's owner.** `ctx.slots.inject(slotKey, callback)` installs an effect once the slot's *declaration* exists (declarations come from whoever registers the parent component with its `children` spec); if the declaration disappears, the effect is disposed, and the controller belongs to the caller's fiber (lib/client.js:991–1074). This is the universal pattern: `ctx.slots.inject("settings.section", () => ctx.slots.register({...}, Comp))`.
- **Slot kinds and scopes.** Four kinds — `single` (one entry; a later registration replaces the earlier one), `keyed` (one entry per `key` cell; one registration replaces another in the same cell), `list` (additive; each entry needs an `id`; the UI sorts by `order ?? 0`), `chain` (all entries render in sequence; each entry gets to consume the result in turn). Scopes: `root`, `session`, `session-maybe` (remounts per session; state leakage between sessions is prevented by design, lib/client.js:685–697). The entry that wins a cell is "the first live (non-abdicated) entry of each cell in priority order" (registry.d.ts:156–164); dynamically registered entries get lower priority than the shipped one, so a dynamic entry is the one that takes over a single/keyed cell (registry.d.ts:24–27). Render-time crashes are contained by error boundaries; a crashing entry **gives up its cell** (the cell falls back or frees up) and reports through `ctx.slots.onEntryError` — the documented way for the host to supervise entries (registry.d.ts:172–184; lib/client.js:790).
- **Slots that can be claimed only once.** `install(renderer)`, `installLocale(face)`, `installScope(scope, adapter)` throw on a second install (lib/client.js:1081–1105, 1138–1150); `provideRoot({hooks, props})` contributes globally-unique root hooks (duplicate hook/prop names throw, lib/client.js:1296–1318, 1379–1386). `renderSlot('root')` is the shell's only ctx-level render; it throws if nothing registered into `root` (lib/client.js:1177–1182).
- **The one documented DO-NOT.** The `root` SlotMap entry says: "DO NOT register here … a second entry … shadows [the frame] … For a surface of your own that floats over the whole app, register into `shell.overlay` instead (a list slot: additive, and click-through until your entry opts into pointer events)" (registry.d.ts:16–38). This is dsh's own statement of the convention for plugin coexistence on the visual surface.
  - **2026-09-18, confirmed** (ticket 36, first extension point in `dsh-capsule-seams.md`): mechanism verified — overlay layer CSS is `pointer-events:none` with a `>*{pointer-events:auto}` rule (ui-layout lib/client.js:71), and the outlet's `display:contents` anchor is the direct child, so inherited `auto` restores pointer events to every entry subtree automatically.

## Finding 6 — Client-side extension point: command UI (`ctx.commandUi`) and locale/theme

Owner: `@deepseek-ai/dsh-client-ui-commands` (contract: lib/types/client/contract.d.ts).

- **Two registries.** `ctx.commandUi.register(contribution)` adds a **client-owned** slash-menu entry (`{name, description(), available(session), ui}`) whose behavior never reaches the host catalog; `ctx.commandUi.decorate(decoration)` hangs a bare-invocation popup on an **existing host** command — "Not a second command: the host command keeps its catalog row, its argument claim, and its lifecycle logging; the decoration replaces only the bare menu-pick/enter" (contract.d.ts:50–84). Both return effect disposers; duplicate names throw at registration (contract.d.ts:88–96).
- **UI kinds.** `ui` is either `popupSelect` — `{options(session, signal): Promise<SelectOption[]>, onSelect(option, session)}` with optional per-option confirmation gates (contract.d.ts:16–35) — or `action` — a bare `{run(session)}` client-side callback (contract.d.ts:37–49). The shared popup shell component is owned by ui-commands; business packages never see it.
- **Coexistence with host commands.** Client contributions are merged with the host catalog **by name — "a collision with a host command fails loud at candidate synthesis, never shadows"** (contract.d.ts:52–57). This is the cleanest extension story in the product: a plugin can add a menu command or enrich `/dispatcher`-style host commands without touching host state.
  - **2026-09-18, confirmed** (ticket 36, second extension point in `dsh-capsule-seams.md`): the decoration doc's "submits a completed line back through command.execute" is the literal wire call `ctx.remote.commands.execute(sessionId, line, attachments)` (ui-commands lib/client.js:795–809), served host-side by `CommandRuntime.execute` with `command/run`/`command/done` lifecycle logging, `source: {kind: "user"}` (dsh-commands lib/index.js:318–329).
- **Wiring.** The popupSelect shell self-registers into `conversation.input.overlay` (list slot, entry id `"command-popup"`, order 1) once `slots`/`commandUi`/`sessions` are up (lib/client.js:1102–1127). The '/' and '@' input trigger pipeline lives in `dsh-client-ui-input-trigger` ("'/' and '@' detection, candidate menu, pick routing to registered sources").
- **Locale/theme.** `ctx.locale.register(NS, {zh, en})` for copy dictionaries (lib/client.js:1103–1106); theme is a service + `theme/change` event consumed by the layout (dsh-client-ui-layout lib/client.js:557–567). Slot entries declare a `locale` namespace so the kit's `t` function is bound to it (dsh-client-ui-renderer lib/client.js:602–606).
  - **2026-09-18 — correction/addition (ticket 49): the theme *service* is not how a surface becomes theme-correct — the `--dsw-*` token layer is.** The paragraph above is accurate about `ctx.theme` (`dsh-client-ui-theme/lib/types/client/index.d.ts:109–188`: preference ownership, theme registration, `overrideTokens`, `theme/change`) but its silence about tokens let an implementer conclude "there is no theme contract" and ship a private dark palette. What actually exists: the shipped stylesheets define a large semantic alias layer split by scheme — `body{--dsw-alias-…}` (light) and `body[data-ds-dark-theme]{…}` (dark), over a `:root` static palette — inside `dsh-client-ui-theme/lib/client.js:1052–1060`. Because the definitions sit on `body`, **every descendant inherits them**: a `shell.overlay` entry becomes theme-correct by writing `var(--dsw-alias-…)` and doing nothing else — no service bind, no subscription, no `dsh.client.inject` edge. Scale: **368 distinct `--dsw-*` tokens** referenced across shipped client bundles; **79 `--dsw-alias-*` tokens** defined per scheme. The host's own floating surfaces use `--dsw-specific-menu: var(--dsw-alias-bg-layer-3)` (lib/client.js:1053) — the value to copy for a chip/card surface — and the host's own CSS uses `color-mix(in srgb, var(--dsw-alias-bg-layer-1) 75%, transparent)`, so `color-mix` over a token is a shipped idiom rather than a novel dependency. Two traps recorded with the mapping in ticket 49: `--dsw-alias-brand-primary` is the high-contrast **label** colour (`neutral-bluish-1000` / `neutral-bluish-50`), not an accent — the accent is `--dsw-alias-state-business-primary`; and `--dsw-font-*` is the conversation-content scale, not a control scale. Private palettes are now pinned out of the client surfaces (ticket 49, `test/client-theme-tokens.test.ts`).

## Finding 7 — Shipped-plugin worked examples (the patterns to imitate)

4. **Client command UI** — `dsh-client-ui-commands` lib/client.js:1102–1127: `commandUi` runtime + popup shell into `conversation.input.overlay`.
5. **Client tool views** — `dsh-client-ui-cordis` lib/client.js:1374–1387: `tool.call.toolview` keyed entries `key: "cordis_define"` / `"cordis_run"`, one declaring a nested keyed child `tool.view.cordis`.
6. **Host provider into an existing service** — `dsh-web-search-exa` registered `ctx.web.registerSearchProvider(...)` and its own settings section (`dsh-local-install.md` Finding 4; package no longer on disk, Finding 0).

## Consequences for the dispatcher UI design (ticket 16 Phase 2 input)

- **(a) Activation control** — coexist-safe options: the existing settings section (flag flip) plus a host command (`ctx.commands.register`, Finding 2) and/or a client commandUi contribution/decoration for a menu affordance (Finding 6). Both fail loud only on exact name collision, so pick `dispatcher`-prefixed names.
- **(b) Roster/status visibility** — the dsh-documented answer for a free-floating plugin surface is `shell.overlay` (list slot, additive, click-through until opted in; registry.d.ts:24–31). Alternatives: a `sidebar.right.pane.tab` keyed entry (claim key `dispatcher` — unclaimed keys are ours; claimed ones replace, which we must not do to shipped tabs) or a `sidebar.panellist` list entry. Chat-injected status would fight the node-type key domain (no new node types).
- **(c) Steer input** — a `conversation.input.dock`/`.left`/`.right` list entry or header action can host a control for steering; the actual steer mechanism stays `ctx.subagents.sendMessage` (dsh-extension-surface.md Finding 3). The input overlay slot is shared with the command popup (the `order` field keeps them apart).
- **(d) Access-request prompts (ticket 13 relay)** — do not build a new prompt path: `ctx.approval` / `ctx.userQuestions` are the host surfaces, and the web answering composers are themselves plugins (`dsh-client-ui-approval`, `dsh-client-ui-user-questions`, Finding 3). A relay should answer through the existing approval waterfall or register its own answerer, and if custom UI is needed, `conversation.approval.detail` is a single (one-entry) slot owned by the shipped approval UI.
- **What is NOT possible (do not design against these):** no notifications/toast surface exists in 0.1.5-rc.1 (a search over all `dsh-*` type surfaces found none); no new chat *node types* (the keyed domain is fixed by the shipped set); `root` must not be registered; slots and registries that allow only one claim (renderer/locale/scope installs, exact routes, settings namespaces, command names) throw on a second claim; and there is no plugin-facing console surface beyond `ctx.logger`.

## Recommendations (ticket 16 phase 1, part 4)

Cross-reference of the hijack diagnosis (`.scratch/multitask-dispatcher/research-16-hijack.md`, commit cbb61a9; cited as "diagnosis §n") against Findings 1–7. Two forced constraints bind every choice: **(1) spawn/interrupt authority** — some live Agent must stay bound as the host parent (`cordis-dsh-host.ts:336-339, 381-398`); UI affordances drive that path, they never replace it. **(2) delivery** — `deliverToUser` is unwired (`src/core/tools.ts:67-71`), so the only delivery path today is the dispatcher speaking as a chat agent (`dsh-adapter-api-notes.md:213`); no pure-UI dispatcher (diagnosis (d)) is recommended because it breaks (2).

### (a) Activation control (ending the hijack)

- **Recommended: slash-command opt-in.** `ctx.commands.register({name: "dispatcher-activate", …})` (Finding 2; dsh-commands lib/index.js:142-173). The `agent/session-start` capture (diagnosis §1.1) stays registered but defers bind+policy-inject until the command fires in a session. The handler runs *instead of* sending the line to the model and logs `command/run`/`command/done` (lib/index.js:303-318), so consent is explicit and auditable. Duplicate names throw (lib/index.js:82) — use `dispatcher`-prefixed names.
- **Runner-up: session-scoped flag marker** read at `agent/session-start` (diagnosis (b)), building on the existing settings section (Finding 1). Consistent with ADR-0005's read-once semantics, but the settings surface is scoped to one plugin namespace; a session-scoped config source is unverified.
- **NOT possible / unverified:** a settings flip cannot end a *running* hijack — the flag is read once in `apply` and `onChange` is a deliberate no-op (`plugin.ts:153`, `settings-section.ts:67-84`; ADR-0005), it only shapes the next session. Whether `Agent.inject` mid-session composes identically to session-start injection is unverified (diagnosis (a)). Full per-chat activation (diagnosis (c)) hinges on per-session tool scoping, which is unverified — `ctx.tools.register` is process-global (`dispatcher-tools.ts:120`), so non-activated chats would still see the five tools.
- **ADR forced:** is command activation a forbidden live-toggle under ADR-0005? Recommended answer: no — activation happens once per session and is never flipped off while running (diagnosis §3, row (a)).

### (b) Worker roster/status visibility

- **Recommended: `shell.overlay` list slot** — dsh's own documented additive surface for a plugin panel that floats over the app (registry.d.ts:16-38, Finding 5): additive, `order`-sorted, click-through until opted in; no competition with shipped UI for a single-entry cell.
- **Runner-up: `sidebar.right.pane.tab` + `.tab.title` keyed entries** with an unclaimed key `dispatcher` (Finding 5 catalog) — ours by default, but the slot allows only one entry per cell and the surface is confined to the right panel. Complement, not alternative: per-tool rows for `check_workers`/`spawn_worker` via `tool.call.toolview` keyed by wire tool name (dsh-client-ui-tool contract/slots.d.ts:9-23; worked example dsh-client-ui-cordis lib/client.js:1374-1387).
- **NOT possible / unverified:** a `main` keyed page exists (dsh-client-ui-layout lib/client.js:515-518) but how a third-party key gets *opened* is unverified (Status item 2) — do not design against it. No new chat node types (the key set is fixed, Finding 5). Overlay/tab buttons must route spawn/interrupt through the bound parent agent (constraint 1).

### (c) Steer input

- **Recommended: `conversation.input.dock` (or `.left`/`.right`) list entry** as a steer control (Finding 5 catalog) — additive, and its `order` keeps it from colliding with the shipped command popup (entry id `command-popup`, order 1; lib/client.js:1102-1127). The transport stays `ctx.subagents.sendMessage` (dsh-extension-surface.md Finding 3); the UI is only a control — last-wins queueing and context preservation are core-side (PRD steer rules).
- **Runner-up: `conversation.session.header.actions` list entry** (worked example 3; dsh-client-ui-agent-preset lib/client.js:1474-1526) opening a steer composer.
- **NOT possible / unverified:** steering rendered as a new chat node type; per-chat steer-tool visibility has the same unverified scoping gap as (a).

### (d) Access-request prompts (ticket-13 relay)

- **Recommended: the existing host prompt surfaces.** `ctx.userQuestions.ask` (dsh-user-questions lib/index.js:52) for structured asks and `ctx.approval` for one-shot permission decisions (Finding 3) — the web answering composers are themselves plugins, so the relay answers through the existing approval waterfall instead of inventing a new prompt pathway.
- **Runner-up: conversational relay** — the dispatcher surfaces the request in its own turn (status quo; works only while the dispatcher is an activated chat, constraint 2). Custom detail rendering, if ever needed, is `conversation.approval.detail` (Finding 5 catalog) — a **single-entry slot owned by the shipped approval UI**; registering into it means competing with shipped UI for that cell.
- **NOT possible:** a new host prompt pathway; an unanswered request must fall to ticket 13's deny-by-default timeout (ADR-0008), not hang.

### Hard limits (all four)

- Console output is not a plugin surface — plugins log through `ctx.logger` (dsh-settings lib/index.js:493, Finding 3). No notifications/toast surface exists in 0.1.5-rc.1, so status changes are visible only in surfaces the user opens (overlay/tab/tool rows/chat), never pushed.
- Official docs were not fetched (Status item 3). The two unverified areas Phase 2 must not assume: `main`-page key navigation, and per-session tool scoping.

This resolves Status/handover item 1.
