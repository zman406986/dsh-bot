# DD-138 — Liveness addition vs MCP stall diagnostic (mixed)
- **Area:** agent runner / turn execution (A16)
- **Type:** build-only-addition (recorded) + missing-feature half (unrecorded)
- **Date:** 2026-09-23

## What the reference does
The reference has no worker-health probe — it is a single-agent harness with no dispatcher/worker split to monitor — and the closest thing to a health signal in its runner is a per-tool-call stall diagnostic inside the turn-observation layer. A module-level constant sets the stall window at fifteen minutes; a named expiry policy is created from it when the turn observer is built, and the observer sets that expiry separately for every tool call, keyed by the call's id, firing a diagnostic event whose kind names the call as stalled if the call is still pending when the window lapses. The timer handle is disposed when the call completes, so the timer tracks in-flight tool execution only. It is attribution, not recovery: nothing restarts or cancels the hung call — the diagnostic exists so the operator can see which call got stuck.

## What the current build does
The build answers the same need with a worker-level liveness verdict and no tool-call timer at all. `deriveWorkerLiveness` (`src/core/liveness.ts`) is a pure function over the worker's existing check fields that returns one of three verdicts — active (advancement observed inside the window), quiet (silence inside the window), or stalled (silence beyond the ten-minute worker threshold) — and is deliberately not a watchdog: per its own header and the ADR-0018 register, it only makes a stuck worker visible on the `check_workers` row; nothing recovers it. The blocked and terminal FSM states never read `stalled` (rule R3: terminal and blocked states outrank the silence test), and unknown timestamps read quiet rather than guessing. A project-wide grep over `src/` finds no per-tool-call stall timer anywhere: every "stall" hit is the liveness module or comments referencing its verdict.

## The deviation
Two-directional. The addition half — the build ships a bounded worker-liveness signal the reference entirely lacks — is real but already settled: ADR-0018 exception D22 records it ("the reference matches by absence"), with the register's A-8 row recording the implementation (ticket 61) and the ruling's ground that matching the reference is the wrong target here, because a user may reasonably expect the dispatcher to notice a stuck worker. The missing half is unrecorded: the reference's fifteen-minute per-tool-call stall diagnostic has no build counterpart, and no exception, register row, or ADR line speaks to it specifically — D22 was written for the liveness signal, not for tool-call attribution. Under ADR-0018's master rule an unmatched reference behavior is presumed to be imitated, so this half is formally an open gap even though the detection need behind it is already served (cf. DD-133 for the related first-token stall deadline, a different mechanism serving a similar need).

## Verdict: DO-NOT-INCORPORATE
The liveness addition is approved (D22, originally a human ruling) and already covers the user-visible need the diagnostic serves: a tool call hung long enough to trip the reference's fifteen-minute window implies a live, unblocked worker silent for fifteen minutes, and the build's stalled verdict fires at ten — earlier, on the approved signal. What the diagnostic would add is attribution only (which call got stuck), and a faithful port is doubtful because the expiry wraps tool execution inside a runner the dispatcher does not own — whether dsh host events expose per-tool identity mid-turn is unverified here (DD number pending) — while a new dispatcher-side timer would cut against the visibility-only, no-watchdog rule D22 approved. The residual value (per-tool attribution on the `check_workers` row) is a nicety; if the human wants it, that is a new design request, not a port of this mechanism, and should be raised as such rather than folded into D22.

## Incorporation notes
- **Where it would live:** nowhere, on this verdict — the approved liveness code stays exactly where it is (`src/core/liveness.ts`, surfaced via the `check_workers` row). Only if the human asks for attribution would a study of the host interface come before any code: the host-observation layer (`src/adapter/cordis-dsh-host.ts`) and the roster/check join (`src/core/tools.ts`) are the only candidate homes, and only if host events actually carry per-tool progress mid-turn.
- **Constraints:** any future attribution surface must stay derived, bounded, and visibility-only per D22's rule — no new timers, no polling, no recovery action, and it must respect the R3 rule that blocked and terminal states are never labelled stalled. Nothing here may add a watchdog.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S as ruled (record-only; zero code). An attribution feature, if ever requested, is M plus a host-behavior verification task first — whether the host exposes what it needs is unconfirmed.
- **Key reference anchors:**
  - the reference tree's `source/host/runner/turn-observation.ts` — stall window constant (:14); expiry policy built from it, carrying an MCP-execution-stall diagnostic name (:99-103); per-call timer set up keyed by tool-call id emitting the stalled-kind diagnostic event (:158); handle disposed on completion (:175); the observer's async-task tracking with start timestamps (:16-24) is task visibility, not a health probe.
