# DD-076 — Secret request: value-provision form vs name-only permission ask
- **Area:** message cards (A10) / approval flows (A28)
- **Type:** behavior-delta (deliberate decision to never accept a secret value)
- **Date:** 2026-09-23

## What the reference does
Two halves of one feature:

**Card (A10).** The recovered transcript renders an in-conversation password form for secret requests (the reference's secret-request view): the card shows the requested credential's label and optional description, then a password input that opts out of browser autocomplete (with a paste-style placeholder derived from the label) and a submit button labeled with a save-securely phrase. On submit the typed value is handed to a secret-requests adapter (the reference's secret-request action module, resolved from the card directory's parent) that transmits it; while in flight the card is non-submitting, and once settled it swaps to a compact confirmation card that restates the label with a kept-private line and a check-marked status. A shield-icon line on the form reassures the user the value is never displayed to the agent.

**Flow semantics (A28).** The reference tree's `source/host/runner/tools/sand-secret-request.ts` is a *provision* flow, not a permission flow: the worker requests a secret by clamped label (120 chars) plus description (400 chars); the human supplies the value out-of-band through a secure channel; the value is written directly to its destination (e.g. an env slot) by the host side; the worker never sees the value; and the ack it receives tells it to confirm the secret is in place and continue working.

## What the current build does
A credential is just one access class in the same ask/relay pathway (`src/core/access-types.ts:8-36`). The worker asks permission to *use* a named credential — the request body carries a `credentialName` field documented as name-only — and the user answers with an allow/deny decision. The `AccessDecision` type carries no value field at all; the module doc states the hard rule that no secret values appear on any type in the file, only names (ticket 13). There is no submit-secret input anywhere in `src/client/`: the `secret-ask` card kind (`src/client/approval-cards.ts:54-55,136`, rendered in `approval-pane.tsx`) shows the credential name plus a privacy line and offers only decision buttons. Where an allowed credential ask is surfaced to the user, the adapter shows a reassurance notice that the credential is stored securely and never displayed (`src/adapter/access-prompt.ts:174-179,382-393`). No value-transfer mechanism — no provision event, no secure channel, no host-mediated write-to-destination — exists in the build.

## The deviation
The reference treats a secret ask as a **value-provision** interaction: the transcript card is itself the intake form, the user's typed value flows through an adapter to a destination, and the worker later resumes on ack. The build reduces the same ask to a **name-only permission decision**: the card collects nothing, the decision type deliberately cannot carry a value, and the only user-facing secret handling is the promise that the stored credential is never shown. The build therefore covers the *reassurance* half of the reference UX (privacy line, saved-securely phrasing family) but not the *provision* half — the worker in this build cannot trigger a user-supplied secret delivery at all, it can only be granted or denied use of a credential that already exists.

## Verdict: ASK-HUMAN
The build's name-only rule is a recorded deliberate stance — ticket 13's module doc in `src/core/access-types.ts` hard-codes "no secret values on any type" and the decision type's missing value field is documented as intentional, so the reference's in-transcript intake form is DO-NOT-INCORPORATE in its current shape. Whether the delta is *permanent* is not settled by that rule alone: a host-mediated provision channel (user supplies the value to the host out-of-band, host writes it to the destination, the value never appears in any worker-visible type) would still obey ticket 13's rule while reproducing the reference's flow semantics — the rule bans values on types, not the existence of provisioning. But adding such a channel widens what an access ask can result in, which ADR-0011's consent-cannot-widen rule covers, and it also touches the PRD's scope, so the choice belongs to the human, not to an agent inference from the rulebook.

## Incorporation notes
- **Where it would live:** a provision event type alongside `AccessRequestEvent`/`AccessDecision` in `src/core/access-types.ts` (carrying label/description only, never a value); a value-intake surface in `src/client/` (an extension of the `secret-ask` card in `approval-cards.ts` rendered via `approval-pane.tsx`); host-side destination-write and ack in the core/host layer, mirroring the reference's worker-never-sees-it split.
- **Constraints:** the value must never appear on any type in `src/core/access-types.ts` (ticket 13 hard rule) nor in any worker-visible message; label/description clamps if reproduced should be re-derived independently (120/400 chars are reference constants); ADR-0011 consent-cannot-widen must be ruled on before any ask can resolve to "provisioned" instead of allow/deny; ADR-0018 B9 — independent re-derivation, no verbatim copying.
