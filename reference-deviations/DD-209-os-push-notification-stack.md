# DD-209 — OS-level push notification stack (delivery, click-through, badge, mobile relay)
- **Area:** A27 platform integration
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference is an Electron/React desktop app, and its **main process owns the whole OS delivery path** — four cooperating pieces.

**1. A transition decider (the substantive half).** A pure module holds the judgment about which agent events are worth interrupting a human for. It reduces each agent to a small snapshot (running or not, the awaiting-reason, the per-agent notify preference, a hidden-from-sidebar flag, the last message identity and a preview), diffs the previous snapshot map against the incoming one, and emits only two transition kinds: an agent newly needing input, and an agent that stopped running without waiting on the user (the reference tree's `source/shared/os-notification.ts:2-6`). A single gate function then decides whether each transition is actually delivered, and it requires **all** of: not hidden, per-agent preference on, window not focused, and a per-(agent, transition-kind) throttle window elapsed (the reference tree's `source/shared/os-notification.ts:1,7`). The decider class additionally keeps **message-id accounting** so a finished-agent transition whose message identity is unchanged (or absent) is suppressed as a duplicate, and a discard path drops all per-agent bookkeeping — snapshot, accounted id, and both throttle keys (the reference tree's `source/shared/os-notification.ts:11`). **Baseline seeding** is the burst guard: the decider records the current roster as the prior state without emitting, so launching the app does not fire a notification per pre-existing agent (the reference tree's `source/shared/os-notification.ts:11`).

**2. An OS notification manager.** The manager owns support checking and window resolution: with no window or no platform support it returns early, and in the per-agent-delta path it only records the snapshot so bookkeeping stays current while nothing is shown (the reference tree's `source/electron-main/notifications/os-notification-manager.ts:38-44,66-71`). It builds notification content from the transition — a needs-input title naming the agent plus the reason, or the agent name plus a truncated preview of the last message, with a body length cap and whitespace collapsing (the reference tree's `source/shared/os-notification.ts:1,8-9`). It constructs the OS notification with an explicit silent flag (silent for the finished case) and an urgency level (elevated for the needs-input case), tracks live notifications in a set, drops them on their close event, and on the click event **restores a minimized window, shows it, focuses it, and only then opens the specific agent** (the reference tree's `source/electron-main/notifications/os-notification-manager.ts:81-98`). Deltas arriving before the baseline is seeded are buffered rather than dropped, then flushed once seeding is done (the reference tree's `source/electron-main/notifications/os-notification-manager.ts:27-28,46-54,73-79`), and a reset path closes every live notification and clears all state.

**3. A dock/taskbar badge manager.** A separate manager projects unread totals onto the OS badge count. It reduces roster agents to a badge-relevant shape, computes a single total from the tracked set, and pushes it through an injected badge-count port, guarding the call and remembering the last projected total so a failing or repeated projection does not churn (the reference tree's `source/electron-main/notifications/dock-badge.ts:7`; the reference tree's `source/electron-main/notifications/dock-badge-manager.ts:28,33,37-46,55-77`). It also refuses stale data: roster rows stamped with an older epoch/sequence are rejected so a late-arriving snapshot cannot roll the badge backwards (the reference tree's `source/electron-main/notifications/dock-badge-manager.ts:16,41,65`).

**4. A host-side mobile push relay.** In the host (not the desktop shell), an extension reuses the *same* decider and the *same* gating logic, but replaces the focus signal with a freshness check on the last window-focus timestamp: the desktop counts as focused only if the window was focused recently; otherwise the transition is treated as unfocused and forwarded (the reference tree's `source/host/extensions/notifications/mobile-push-notifier.ts:5`). The extension wires host events to that notifier, obtains an authenticated backend client and a machine identity, and sends the push through a generated backend service call, swallowing send failures (the reference tree's `source/host/extensions/notifications/extension.ts:8`). The desktop side feeds both the OS manager and the badge manager from one control feed that fans agent events and roster seeds to each, the seed path being what primes the no-launch-burst baselines (the reference tree's `source/electron-main/notifications/agents-control-feed.ts:14-39`; wiring in the reference tree's `source/electron-main/main-production-services.ts`).

## What the current build does
Nothing of the delivery path, and it says so on its own surfaces.

- `docs/surfaces.md:20-38` — the "No push notifications" designed-absence record states the installed host runtime has **no notification or toast interface**, that attention therefore routes only through pull surfaces, and that the absence is the host's rather than the plugin's. It enumerates the three pull surfaces (a needs-you roster section, conversational narration, and the activation success copy) and explicitly refuses to simulate push: no notify-me controls, no fake toasts, no bell or badge affordance, and no polling loop pretending to be a subscription (`docs/surfaces.md:22-35`).
- `src/adapter/activation-command.ts:29` — the activation presence-hint doc comment carries the same expectation-setting rule in code: results arrive as ordinary chat turns, never as a notification, because no push interface exists.
- `src/client/shell-feed.ts:110` and `src/core/multitask.ts:947` — the build's only "notification" vocabulary is in-process projection signalling (a feed binding that syncs on store changes; a roster-change fan-out that deliberately does not fire for unknown-state rows). Neither reaches an OS surface, and neither is a subscription.
- In-app notification *hosting* is already filed as DD-004, and the native menu-bar shell as DD-208. Neither covers the OS delivery path.

## The deviation
The build has **no** OS delivery path: no platform support check, no notification construction, no click-through routing, no dock/taskbar badge count, and no mobile push relay. That whole path is doubly unreachable here — the build has no application window to focus or restore, no Notification-capable process to construct a notification in, and no host interface to attach any of it to (`docs/surfaces.md:22`).

The **transition-decider** half is a different matter and should be named separately. "Which events justify interrupting a human, and how do you keep from nagging them?" — needs-input and finished only, deduped by message identity, throttled per agent and kind, suppressed while the window is focused, respecting a per-agent preference and a hidden flag, and seeded from the current roster so a cold start is quiet — is conceptually independent of *how* the interrupt is delivered. It is a product-behavior decision, and it is the substantive part of the reference's stack: the OS notification is only its transport. The build currently answers that behavior question with pull surfaces only, and that answer is a **recorded design stance** (`docs/surfaces.md:8-18,22-35`), not an omission — the surfaces record explicitly says the absence is a decision rather than a gap left open by accident.

## Verdict: DO-NOT-INCORPORATE
ADR-0020 (draft, non-human-approved; `docs/adr/0020-wrapper-shell-vehicle-own-frame-over-shipped-runtime-draft-nonhuman-approved.md`, exclusion table line 28) rules the native/Electron desktop shell out of scope by citing the PRD non-goal against chasing the compared product's binary or UI parity, and excludes it "without further study" — that ruling covers the OS delivery path, which is unreachable without exactly that shell. Its application-shell choice was later replaced by ADR-0021 (and in part by ADR-0022), but the exclusion of the native shell is a PRD non-goal and depends on the PRD, which sits above ADR-0020 in the authority stack, so the exclusion survives that replacement. The **transition-decider half is not covered by any recorded ruling**: no ADR, PRD amendment, or ticket ruling addresses which agent events should interrupt a user, and ADR-0020's shell ruling does not reach it — a host could expose a notification interface someday. Per the authority stack, an uncovered conflict should be raised rather than silently resolved; it is flagged below as a small open point for a human look, and the verdict above is unchanged by it.

## Incorporation notes
- **Where it would live:** The delivery path has no place in this repo: it would need an application frame, a Notification-capable process, and a host interface, none of which exist. If the decider half were ever separated out, the natural place is the core projection layer beside the roster-change fan-out (`src/core/multitask.ts`), emitting transition facts on the existing projection point rather than any OS call.
- **Constraints:** ADR-0018's B9 rule against verbatim copying applies to any re-derivation. The surfaces record's own rule — presence is a projection of existing core state, and anything needing new core state, a new host interface, or a second source of truth is out — would still apply to a decider built on the current host. Any bell, badge, or notify-me affordance would also break the explicit no-simulation stance at `docs/surfaces.md:32-35`, which the project has committed to in writing.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — the delivery path needs a native shell the project does not have and has ruled out; the decider alone would be S/M, but with no delivery target it would be dead logic.
