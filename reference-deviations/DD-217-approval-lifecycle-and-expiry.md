# DD-217 — Approval lifecycle: expiry taxonomy, pending caps, generation checks
- **Area:** A28 approval & policy
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference keeps a live pending-approval record per agent and treats the *lifecycle* of that record as first-class state, not just a promise waiting on an answer.

A pending record carries the target's fingerprint, the asker's reason, a short summary, an optional proposed rule, the user-message epoch in force when it was raised, and the host generation that raised it (the reference tree's `source/host/runner/sand-auto-review.ts:27, 32-33, 46, 122-129`).

Three bounds and policies apply:

- **Per-agent pending cap.** At most four asks may be outstanding for one agent; the fifth is refused immediately with a resolve-the-pending-asks-first reason rather than queued (the reference tree's `source/host/runner/sand-auto-review.ts:4, 118`).
- **Two expiry policies, chosen by source.** The default is a timer (ten minutes) that retires the ask with the time-to-live cause (`:3, 122, 132-136`). Asks that come from a turn or a handoff-resume instead get no timer at all — no expiry clock, so a parked ask survives until something else ends it (`:11, 58`).
- **A named expiry-cause set.** Expiry is typed, not boolean: each ending carries a named cause — the time-to-live timer, an explicit cancellation, a user redirect, a settings change, session end, and a host wind-down (`:10`). Each cause has its own trigger — the timer (`:133`), the request's abort signal (`:139`), a new user message bumping the epoch (`:160`), a surface's settings changing (`:161`), session teardown (the reference tree's `source/host/extensions/auto-review/auto-review-service.ts:42`; the reference tree's `source/host/runner/sand-agent-runner.ts:639, 907`), and a host shutdown for an update (`:163`).

The pause-for-update path is the most important part of the design: a host update that interrupts an ask tells the model explicitly that the user did **not** deny it, and directs it to re-run the action after resume (the reference tree's `source/host/runner/sand-auto-review.ts:76, 116`). Every retirement emits an expiry event carrying the cause alongside the settled record (`:165`).

Resolution is validated, not trusted: a resolution for an id is refused outright unless the record's host generation and user-message epoch still match the live ones and its expiry has not already passed (`:150`). Separately, the reference's local-tool permission controller remembers already-settled request ids (with a bounded memory) so a late answer cannot land on a finished ask (the reference tree's `source/host/extensions/local-tool-permission/local-tool-permission-controller.ts:86`) — that controller is the subject of DD-214/DD-215, not of the auto-review approval path, and this deviation does not restate it.

## What the current build does
The build's code for dispatch approvals has exactly one time limit and one ending word.

`createDispatchApprovalSeam` asks the host answerer and races the ask against a deadline (`src/adapter/dispatch-approval.ts:113-136`). The deadline reuses the relay's ADR-0008 constant (`DEFAULT_ACCESS_TIMEOUT_MS`, 120 s) rather than defining a new policy (`:49, 91-96`, `src/core/access-relay.ts:239`). Every failure mode below the caller — answerer absent, not a function, throwing, silent past the deadline, or returning something outside the outcome vocabulary — collapses to the single outcome `unavailable` (`src/adapter/dispatch-approval.ts:99-104, 144-190`). The gate then turns any non-`allowed-once` outcome into an honest `auto-review-refused` spawn result, and the dispatcher re-plans; the module's own comment records that this spawn result is the durable record and that dispatch approvals get no approval-feed entry at all (`:30-32`).

So on the dispatch side there is no expiry-cause vocabulary, no pending cap, no generation or epoch validation, and no pause-before-update path. The client's access-ask path shares the same deadline, which denies the ask when it expires and surfaces an honest "expired" notice when an answer arrives for a ticket the relay already settled (`src/adapter/access-prompt.ts:519-524, 547-548`); the approval-card feed carries pending-ask truth only, and states plainly that "resolved" honestly means "left the pending list" because no notice feed exists (`src/client/approval-feed.ts:2-23`).

The build's two approval paths are not consistent with each other. The *access* side already keeps a partial cause vocabulary in its deny copy — user-denied, policy-denied, timeout, aborted (`src/core/access-relay.ts:219-226`) — while the *dispatch* side flattens everything into one word.

## The deviation
The reference distinguishes *why* an ask ended and tells the model which ending it got, including the explicit case where the ending was not a denial. The build tells the model one word, `unavailable`, and by construction cannot say whether the wait ran out, the host cancelled, the answerer was never there, or a host update interrupted it.

Two honest readings, and they are not exclusive:

- The build's single outcome is the **conservative and simple** approach: it refuses on every non-allow, claims nothing it cannot prove, and re-plans. Under ADR-0010's rule that the UI only reports what it can read and never guesses, and the "no optimistic flips" phrasing restated at `docs/adr/0022-floating-capsule-revived-by-human-ruling.md:40`, refusing to assert a cause it did not observe is defensible — and the timeout part is positively recorded (ADR-0008's deny-by-default deadline, which denies the ask when it expires, `docs/adr/0008-worker-access-ask-structured-relay.md`).
- The reference's **taxonomy gives the model better information to act on**: being told that the settings changed and it may retry, that a new message superseded it, and above all that an update interrupted the ask without the user denying it are all actionable in ways that a bare `unavailable` is not. A model told only "unavailable" can reasonably read it as a soft refusal and abandon a plan the user never actually rejected.

The information loss is real but narrow, and the build does not *need* the reference's state to recover most of it: the code that handles dispatch approvals already catches the deadline rejection, the host's thrown error, and the absent answerer on distinguishable paths (`src/adapter/dispatch-approval.ts:151-188`), so a small cause vocabulary is reachable without inventing a pending-record store. What the build genuinely cannot report is a user redirect, a settings change, or a host wind-down, because it has no host-wind-down path and no epoch notion — those parts of the reference's taxonomy describe mechanisms the build does not have.

## Verdict: ADAPT
No recorded ruling reaches the expiry taxonomy. ADR-0018 exception **U-D** — "Always allow" rules are session-scoped, not persisted, with no settings-managed rule store and no dedicated local tool-permission controller (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:37`) — settles the *rule-storage* question, and it does **not** reach expiry causes, pending caps, or generation/epoch validation; those are a different question and U-D is silent on them. What *is* recorded is the part that refuses when in doubt: ADR-0008's deny-by-default deadline is the build's stated behavior (`docs/adr/0008-worker-access-ask-structured-relay.md`, cited in `src/adapter/dispatch-approval.ts:27-32, 91-96`), and ADR-0010's rule to report only what it can read and never guess (`docs/adr/0010-dispatcher-presence-is-a-projection-of-core-state-draft-nonhuman-approved.md:16`) is the reason an unknowable cause should never be fabricated. ADAPT is therefore the move that keeps both recorded stances: keep the deadline and the fail-closed refusal exactly as they are, and adopt a small cause vocabulary so the refusal stops discarding what the approval code already observed. The pending cap and the generation/epoch validation are deliberately **not** incorporated by this verdict — the build holds no durable pending approval record for dispatch asks to attach them to, and inventing that state on the strength of this deviation would exceed it.

## Incorporation notes
- **Where it would live:** the outcome vocabulary on the approval module's own type (`src/core/tools.ts`, alongside `DispatchApprovalOutcome`), the places that collapse outcomes to one word in `src/adapter/dispatch-approval.ts` (`:144-190`), and the gate's refusal copy that today renders one `auto-review-refused` result. The access side needs no new vocabulary — it already carries `timeout` / `user-denied` / `policy-denied` / aborted in `src/core/access-relay.ts:219-226` and should simply stay the precedent to copy rather than a second scheme to invent.
- **Constraints:** every non-allow outcome must keep refusing (fail-closed is unchanged; the cause only changes *what is said*, never *whether* the spawn proceeds). The cause must be derived from what the approval code observed on its own error paths — never inferred, never optimistic. Do not add a pending-record store, a timer beyond the existing denying deadline, or an epoch/generation notion to serve this: if a cause cannot be observed from the current approval code, the honest word stays `unavailable`. ADR-0018 B9 governs all of it — no reference identifier, tool-name string, prompt text, or protocol artifact crosses over, and the reference's cause labels are re-derived as our own vocabulary, not transliterated.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — a few distinct catch paths already exist and only need distinct outcomes plus copy; the risk is regression in the gate's refusal contract, so it wants the existing offline tests extended rather than replaced.
- **Key reference anchors:** the reference tree's `source/host/runner/sand-auto-review.ts:3-4` (ten-minute TTL, cap of four per agent), `:10` (cause set), `:11, 58` (park policy for turn and handoff-resume sources), `:76` (explicit not-a-denial copy), `:116-118` (pause-for-update refusal, cap refusal), `:122-136` (record fields, TTL timer), `:150` (resolution refused on generation/epoch/expiry mismatch), `:160-165` (epoch bump, settings change, host pause for update, retire-with-cause), `:170` (fingerprint helper); the reference tree's `source/host/extensions/auto-review/auto-review-service.ts:42` and the reference tree's `source/host/runner/sand-agent-runner.ts:639, 907` (session-end expiry); the reference tree's `source/host/extensions/session/pending-card-sweeps.ts:7-14` (pending cards moved to expired).
