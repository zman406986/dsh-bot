# DD-068 — Card registry/protocol/frame system vs ad-hoc card surfaces
- **Area:** message cards (A10)
- **Type:** missing-feature (architecture layer)
- **Date:** 2026-09-23

## What the reference does
The reference gives transcript cards a dedicated architecture layer rather than scattering them across call sites. `registry.ts` exports a frozen, keyed transcript-card registry mapping a derived protocol key to per-kind metadata: a placeholder height for layout before content arrives, a shared frame descriptor (variant plus a wrapper class, nullable for frame-less kinds), and a source path plus chunk file so each card's real view can be loaded lazily. The frame type enumerates exactly five shared variants (a tab variant, a link variant, a file variant, a widget variant, and a question variant) that carry the common chrome (group-start marker, timestamp) so individual cards do not re-implement it. Companion modules split the concerns: `protocol.ts` defines the key vocabulary and entry types, `resolver.ts` turns a key into the lazy-loaded view, `frame.tsx` renders the shared shell. A dozen send-message card kinds are registered, and the file's `@evidence` block pins per-kind lazy views and chunk files to byte offsets in the shipped renderer bundle.

## What the current build does
The build has no card registry, protocol, resolver, or frame layer at all — no placeholder-height, chunk-file, or frame-variant concept exists anywhere under `src/client/` (a search finds no matches). It has exactly two card surfaces, each ad hoc: (1) the approval-card components in `src/client/approval-cards.ts` with their hosting section in `src/client/approval-pane.tsx`, and (2) read-only per-tool rows in `src/client/toolviews.ts`, which register view models into the stock host slot `tool.call.toolview` and deliberately stay pure data (no React, no lazy loading). There is no shared placeholder/reserve-space behavior, no uniform frame chrome, and no single place that enumerates which card kinds exist.

## The deviation
The reference invests in a registry/protocol/frame layer keyed by card kind; the build composes its (two) card surfaces directly without any such layer. This is an architecture-level gap, not a missing card: the build's two surfaces work, but every additional card kind added ad hoc (as the individual card deviations DD-069..082 propose) would re-implement placeholder sizing, frame chrome, and kind-keyed lookup independently, drifting apart over time. The reference's payoff, however, comes from scale — twelve registered kinds sharing five frames — and the lazy chunk-loader machinery is irrelevant to a plugin that renders inline.

## Verdict: DO-NOT-INCORPORATE
The build should not port the reference's layer wholesale: the lazy chunk-loader and five-variant frame system only pay off with many card kinds, which the build does not have yet, and the resolver machinery would fight the host's existing keyed-slot pattern (which `toolviews.ts` already follows and design-16 §5 — the dispatcher UI design note at `.scratch/multitask-dispatcher/design-16-dispatcher-ui.md` — mandates). What is worth adapting is the pattern — one keyed metadata table that enumerates card kinds with placeholder-height and frame-variant fields — introduced when (and only when) the individual card deviations DD-069..082 land enough kinds (roughly three or more) to make a single enumeration point earn its keep; with only the current two surfaces, DO-NOT-INCORPORATE applies. Per the ruling order defined in `docs/agents-rulebook.md` this stays within PRD scope (client presentation only, no new authority), TypeScript per ADR-0001, and the shipped-slot rule from design-16 §5; if the human prefers strictly ad-hoc cards even at higher kind counts, that is a human ruling that overrides this adaptation.

## Incorporation notes
- **Where it would live:** a `src/client/` sibling to `toolviews.ts` (e.g. `src/client/card-registry.ts` plus a thin frame component), consumed by the existing approval-pane and toolview-panel hosts; no new host slot names — reuse `tool.call.toolview` and the approval-pane section.
- **Constraints:** TypeScript only (ADR-0001); keyed by wire/source kind names that already exist, nothing invented (design-16 §5 slot/key rule); registry stays pure data with offline tests (the PRD's S8 success criterion — core modules unit-tested without network or LLM — as `toolviews.ts` does); placeholder heights are presentation-only with no fetch or authority (design-16 §3.4 read-only rule); do not add lazy chunk loading — views are already in-bundle.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the table and frame component are small, but the real cost is retrofitting DD-069..082's cards onto it and keeping the two existing surfaces coherent; risk is over-building before the kind count justifies it.
- **Key reference anchors:** `the reference tree's frontend/src/recovered/features/conversation/cards/transcript-card/registry.ts` (keyed table, metadata shape, five frame variants, twelve send-message kinds, byte-offset evidence block incl. per-kind lazy views at bundle offset 5108848 and placeholder metadata entries); `protocol.ts` (protocol-key derivation); `resolver.ts` (key → lazy view); `frame.tsx` (shared frame owner, group-start chrome).
