# DD-180 — Client-persisted UI slices vs the build's ephemeral floating-window state
- **Area:** A21 storage
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does

The reference gives its renderer a general client-state persistence port on the desktop bridge: read/write/remove plus prefix-listing and a one-shot migration from legacy per-key web storage (`reference material-NOT LICENSE SAFE DONT COPY-grok bot/frontend/src/recovered/contracts/desktop-bridge.ts:367-373`). Feature code owns named slices of client state, each declaring a descriptor — slice name, schema version, a client-persisted scope, and an account-sensitivity flag — and binds it to that port: composer drafts (`.../frontend/src/recovered/features/conversation/workspace/draft-state.ts:9-14`), sidebar layout carrying width/collapse/info-pane geometry (`.../frontend/src/recovered/features/conversation/workspace/sidebar-layout-state.ts:10-15`), sidebar collapse (`.../sidebar-collapse-state.ts:12`), roster selection (`.../features/roster/selection-state.ts:14`), and one more descriptor in the workspace model (`.../features/conversation/workspace/model.ts:39`).

Composer drafts in detail: the storage key is a fixed prefix plus the percent-encoded account slot plus the slice name, so each signed-in account gets its own record (`draft-state.ts:57-64`); the payload is one envelope per account holding a map keyed by agent, each entry a draft plus a separate recovery draft and a draft id (`draft-state.ts:32-48`). Restore runs on account-slot change: in-memory records are cleared, in-flight writes are awaited, a generation counter rejects a stale async landing, and a schema-version mismatch or corrupt payload clears the stored record rather than throwing (`draft-state.ts:237-262`). Writes are serialized through a promise chain and failures are swallowed (`draft-state.ts:139,162-167`). The host side owns the bytes: a file-per-key blob store with an allowed key prefix, a per-value byte cap, a total byte cap, and a marker file recording the legacy migration (`.../source/shared/client-persistence-store.ts:1-25`; wired host-side at `.../source/electron-main/secrets/secrets-ipc.ts:117`). The layout slice shows the pattern is generic UI state rather than a drafts special case: it persists sidebar width/collapse and info-pane width/open with declared defaults and min/max bounds, and its descriptor marks it NOT account-sensitive while the draft slice is — the per-slice flag decides whether the data is scoped per account, not one global rule (`sidebar-layout-state.ts:10-15` and the defaults/bounds block that follows).

## What the current build does

The build's client source lives under `src/client/` (the top-level `client/` directory holds only the built bundle entry, `client/index.js`). The floating-window store (`src/client/floating-window-store.ts`, ticket 100 under ADR-0021; resize/maximize ticket 105) states its design rule in the module header: in-memory only, no persistence claimed, a reload starts closed at the default placement again, and the store records no storage of any kind (`:1-58`). Published state is `open`/`openEpoch` plus geometry x/y/width/height/maximized (`:60-93`), with the pre-maximize rect held in the closure (`:297-305`); within a session a reopen returns the window to where it was, re-clamped against the live viewport (`:342-372`). The launcher capsule (ticket 107, ADR-0022) carries its own position under the same rule — no persistence, no `window` reads (`:48-57`, `:499-506`, `:582-612`). The window component is `src/client/floating-window.tsx`, reached through the launcher overlay entry in `src/client/overlay.ts` (per ADR-0022's citations of `:52,61`). The tickets record the same rule as an implementation constraint — "in-memory state only — no persistence claimed" and "do not add storage while implementing" (`Issue-tracker/resolved/100-floating-dispatcher-window-and-stock-ui-launcher.md:19,44`; `Issue-tracker/resolved/103-floating-window-drag-flies-across-the-screen.md:29`; `Issue-tracker/resolved/105-floating-window-not-resizable-no-maximize.md:34`). No host-side storage path for client UI state exists today (the same finding is recorded in `reference-deviations/DD-002-window-state-persistence.md`).

## The deviation

Two parts with different standing. Drafts: the reference persists composer drafts per account through its bridge-backed slice store; the build persists nothing, and the build's chat surface is the stock host chat (ADR-0018's vehicle clause as amended — the clause that fixes what the product is delivered as, with stock dsh staying primary, `docs/adr/0018-imitate-reference-in-entirety-exception-list.md:3`). The exclusion is explicit: U-B rules out the rich-chat-ergonomics class including "per-agent drafts" (`docs/adr/0018-...:35`), which is exactly what the reference's draft slice is — a per-agent record keyed by agent (`draft-state.ts:32-48`). Geometry: the build's own floating window and capsule keep placement in memory as a documented engineering choice, and no recorded ruling covers persisting it. ADR-0022 rules the capsule's information model — counts, the overlay entry that launches it, whole-shell window — and says nothing about persistence (`docs/adr/0022-floating-capsule-revived-by-human-ruling.md:17-19,44-46`); ADR-0021's only persistence mention concerns a different matter, a host composer reconcile gap (`docs/adr/0021-addon-coexistence-floating-dispatcher-window.md:41`); the tickets' "do not add storage while implementing" constrains those tickets' scope, it does not rule the feature out. That small geometry question is already filed separately as DD-002 in this folder (verdict ASK-HUMAN) and is not re-litigated here.

## Verdict: ASK-HUMAN

The draft half is settled at the accepted-ADR level: ADR-0018's exception list is exhaustive and is the definition of done for imitation scope (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:21,46`), and U-B names per-agent drafts, so no new ruling is needed to keep the build as it is. The slice mechanism itself should not be imported either: A5 keeps persistence in dsh's session/job store with no second database (`:25`), which constrains any client-state persistence that does survive to reuse existing dsh storage rather than adding a new one. One small question is genuinely uncovered — persisting the geometry of the build's own floating window/capsule, a usability property the build added under ADR-0021/0022 rather than a reference imitation. No recorded ruling addresses it; it is already before the human as DD-002, whose ruling governs that question. The stricter outcome governs the file as a whole: the draft half is refused outright, while the uncovered geometry question is what leaves this verdict at ASK-HUMAN.
