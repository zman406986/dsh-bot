# DD-071 — Interactive question widget card vs access-ask cards only
- **Area:** message cards (A10)
- **Type:** missing-feature (partial analog exists)
- **Date:** 2026-09-23

## What the reference does
The reference has a generic widget card in the chat transcript: any agent turn can attach a question with a prompt, optional help text, and a list of options, each option fronted by an auto-generated keycap letter (A, B, C… by index). When the card is the pane's keyboard target, the view installs a capture-phase document keydown listener that maps a single letter press to that option; the listener stands down while focus is in an editable field or a dialog is open, and each option button advertises its key via an aria shortcut attribute. An optional free-text answer row (gated by an allow-custom flag) gives a textarea that submits on Enter (Shift+Enter excluded), with a submit button appearing only once the text is non-empty. A ghost close control dismisses the question without answering. Two terminal states replace the live form: a resolved card showing only the chosen option with its settled letter and a checkmark, and a dismissed card reduced to the prompt plus a dismissed pill. All answers route through a widget-interactions adapter pulled from providers (snapshot read, respond, dismiss), so the card is fully generic — nothing about it is tied to credentials or access requests. The card registry registers the widget as a lazy view with placeholder metadata, and gives the send-message widget a question frame variant.

## What the current build does
The build has no widget or question card in the message flow at all — a search for "widget" across `src/client` returns nothing. Its only option-button card is the access-ask family (`AccessAskCardKind = "access-ask" | "secret-ask"`): a shape frozen by design with one selectable answer per option, projected from pending tickets and resolved notices in `src/client/approval-cards.ts` and rendered in the Workers panel's "Needs you" section (`src/client/approval-pane.tsx`), which `docs/surfaces.md` names as a surface the user pulls from when they look (the build has no push notifications). The underlying agent-asks-user plumbing does exist — a host service that emits user questions (`userQuestions`) surfaces in `src/plugin.ts`, `src/adapter/access-prompt.ts`, and `src/adapter/cordis-dsh-host.ts` — but it feeds the access/secret-ask flow in the panel, not a generic in-transcript question card.

## The deviation
Five concrete deltas: (1) no generic question card inside the message flow — the build's only ask surface sits in a separate panel section; (2) no letter-key keyboard shortcuts for options; (3) no optional free-text custom answer alongside the fixed options; (4) no resolved/dismissed terminal presentation (chosen-option-plus-checkmark, dismissed pill); (5) no generic (non-access) use — build questions are hard-wired to the access/secret request flow even though the `userQuestions` service itself is generic.

## Verdict: ASK-HUMAN
The build already owns both halves of a question mechanism — the host `userQuestions` service and option-button cards in the "Needs you" section — so this is a presentation and scoping gap, not a missing capability. The reference's interaction quality (letter-key shortcuts scoped to the card, optional custom-answer field, resolved/dismissed terminal states) can be folded onto the existing access-ask cards without new core state, which is the line `docs/surfaces.md` draws for surface work. Promoting a generic widget card into the transcript flow is a different matter: it would add a second question surface and a new transcript message type, which needs a decision about host support, so that part is one for the human. Nothing in `docs/adr/README.md` currently rules on widget/question cards, and ADR-0018's license rules govern any porting.

## Incorporation notes
- **Where it would live:** interaction affordances onto the existing ask cards in `src/client/approval-cards.ts` and `src/client/approval-pane.tsx`; if a generic in-flow card is ever ruled in, it would ride the transcript card system alongside `src/client/conversation.tsx`, fed by the existing `userQuestions` service (`src/adapter/access-prompt.ts`, `src/adapter/cordis-dsh-host.ts`, `src/plugin.ts`).
- **Constraints:** no new core state or second source of truth (`docs/surfaces.md`); letter-key capture must not collide with the build's escape/overlay key contracts (see DD-017; and DD-016 for the no-global-shortcut-registry stance); the access-ask card shape is frozen by design (`approval-cards.ts` design-§3.1 comment), so extending it needs a design note first; any generic in-flow card needs a human ruling (ASK-HUMAN).
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — respond/dismiss plumbing already exists for the access flow; main risks are scope creep toward a second question surface and keyboard-capture regressions against existing key handling.
- **Key reference anchors:** `views/widget.tsx` (keyboard-target keydown effect, allow-custom custom-answer row, resolved card with checkmark, dismissed pill); `widget-interactions.ts` (respond/dismiss/snapshot adapter); `registry.ts` lines 10 and 14 (widget lazy view and placeholder metadata evidence lines), line 71 (the question frame variant).
