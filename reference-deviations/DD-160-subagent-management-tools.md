# DD-160 — Subagent management tools: check / message / stop and their not-running feedback
- **Area:** A19 tool surface
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference ships three communication-style tools for managing a background subagent it has already dispatched — one to inspect a subagent, one to inject a course-correction into it, and one to tear it down — grouped in a single shared management-tools module with a controller interface behind them (`"reference material-NOT LICENSE SAFE DONT COPY-grok bot/source/host/runner/tools/sand-subagent-management-tools.ts":1-24`, `84-143`).

The critical detail is the negative path. All three tools funnel a call naming an id that is not currently live through one shared helper that composes a not-running message (`:74-82`). That message does two things at once: it names the id that was not found, explains the two likely causes (already finished, or a wrong id), and then — the central usability point — lists the ids that *are* currently running, or states plainly that nothing is running. So a caller who names a stale id is told in the same breath what it should have named instead. Its three call sites are the check tool's single-id miss (`:104-107`), the message tool's not-running steer result (`:124-126`), and the stop tool's not-running abort result (`:136-138`); the helper takes the full running list as its second argument at each (`:75-77`).

The check tool also carries its own listing mode: with the id omitted it lists every running subagent, or reports that none are running (`:95-103`). Subagent identity here is an agent-id string returned by the dispatch tool (`:26-45`).
## What the current build does
The build already has the three corresponding verbs as dispatcher tools in `src/core/tools.ts`: `check_workers` (with an optional worker id; omitted lists all, `:413-458`), `steer_worker` (`:462-491`), and `stop_worker` (`:493-546`). Functional parity on the three verbs is not in question.

The deviation is confined to what the negative path tells the caller.

- **Unknown id is terse.** `check_workers` given an id that is absent from the roster returns `{ ok: false, reason: "unknown-worker", detail: "unknown worker: <id>" }` (`src/core/tools.ts:419-423`, and again at `:427-433` when the id is absent from the list). `steer_worker` mirrors that refusal form from the core (`src/core/multitask.ts:661-667`). The build does not list the ids that are live; the caller is told only that the one it named is not there.
- **Already-settled stop carries no hint.** `abortWorker` refuses a worker whose status is terminal with `reason: "already-settled"` and the detail "worker <id> is not running; it may already be done" (`src/core/multitask.ts:626-635`, repeated for the transition race at `:637-644`), and `stop_worker` maps a missing record to the same already-settled form (`src/core/tools.ts:528-534`). "May already be done" is the whole hint — the reference's list of running ids has no counterpart here.
- **Steering is single-slot last-wins.** The build's core documents a single-slot steer queue where a newer message replaces any undelivered one (`src/core/multitask.ts:153-156`, implemented at `:678-679`), and the tool's steer path routes straight through it (`src/core/tools.ts:477-490`). The reference's message tool does not describe a replacement rule in this module (the reference tree's `sand-subagent-management-tools.ts:110-129`).
- **Unknown-state worker releases the hold.** `stop_worker` handles a worker not on the roster by looking for an unknown-state stream hold for the current session and, if found, releasing it and returning a distinct note (`src/core/tools.ts:506-527`). This is a build-specific path with no reference equivalent in this module.

## The deviation
The three verbs match; the *feedback* on a non-live target does not. The reference treats "that subagent is not running" as an occasion to hand the caller the set of live ids — an error the caller can fix itself — and reuses one message for all three verbs. The build's negative paths are terse single-id refusals per tool ("unknown worker: <id>", "not running; it may already be done"), with no list of live ids anywhere. A caller that named a stale or mistyped worker must therefore make a second listing call to recover, where the reference's caller recovers from the refusal itself. The build's already-settled stop is the sharpest case: it says the target may be done but cannot say what else is running, even though the roster is at hand at that point (`src/core/tools.ts:503-505`). Last-wins steering is a separate stance, not part of this usability difference.

## Verdict: ADAPT
No recorded ruling names this. I checked the places where rulings live — the PRD, the ADRs (`docs/adr/README.md`), and `CONTEXT.md` as read for this file — and found nothing that decides how much a not-running refusal tells the caller; the closest recorded material is the surrounding tool-surface behavior, which does not address how refusals read. Absent a ruling, this stays a practice-level adoption rather than a behavior the PRD requires. The verbs already have parity, so nothing about the tool *set* is at stake; the adoptable piece is the practice of listing live ids in the not-running response, which improves recovery at small cost and touches only response text. The build should ADAPT that practice rather than INCORPORATE the reference's module wholesale. The build's last-wins steering should be left as is: it is a deliberate, documented single-slot stance, defensible on its own terms, and I found no contrary evidence in the build that it misleads callers.
