# DD-191 — Memory prompt injection (bounded memory sections in the system prompt)
- **Area:** A23 memory
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference injects durable memory into the agent's prompt as a small set of explicitly budgeted sections, assembled by a dedicated memory module and spliced into the system prompt by the system-prompt assembly stage.

- **Every section carries a stated bound, declared as module-level budget constants.** The profile section is capped at 100 facts; the recency-ordered section is capped twice over — at most 30 items and a 4000-character budget; user-scoped memory has its own pair (50 profile items, 15 recency items); project-scoped memory is capped hardest, at 3 injected items (`the reference tree's source/host/runner/sand-memory.ts:1-3`, `:13-17`). The renderer walks the sections under the character budget, decrementing it line by line as it emits, and substitutes an empty-state placeholder line when both the profile and recency sections are empty (`the reference tree's source/host/runner/sand-memory.ts:78-100`). A separate, much larger listing budget exists for the UI (`:4`), so the prompt budget and the browse budget are deliberately different numbers.
- **The injected snapshot is frozen per compaction epoch.** A snapshot value pairs the rendered text with the compaction epoch it was rendered at, and a resolver returns the frozen render whenever the snapshot's epoch still equals the current epoch — re-rendering and handing back a fresh snapshot to persist only when it does not (`the reference tree's source/host/runner/sand-memory.ts:24`, `:30-37`). The system-prompt assembly calls that resolver with the host's live compaction epoch and reads and writes the snapshot through host deps (`the reference tree's source/host/runner/system-prompt-assembly.ts:50-51`, `:191`). Net effect: the memory text injected into a conversation does not shift turn to turn — it changes only when compaction rolls the epoch, which is the stability property that makes a frozen block safe to cache and safe to reason about.
- **Memory also reaches subagents.** A prior study finding records that the injected memory is not confined to the top-level agent but reaches spawned subagents as well, and associates that with a ticket (ticket number pending — the ticket reference was not verifiable from the material at hand). The agent-facing way to write and forget facts is the state tool's memory kind (`the reference tree's source/host/runner/tools/sand-state-tool.ts`), with the per-turn recall and extraction cadence driven by the turn-memory module (`the reference tree's source/host/runner/turn-memory.ts`).

## What the current build does
**Absent.** The build's worker prompt is a single assembler emitting fixed sections in a fixed order — role, autonomy, limits, the access-ask exception, the todo-ledger section, work style, final-answer shape, safety — with no memory section and no slot where one could be spliced (`src/worker/prompt.ts:46-86`). Nothing worker-facing varies with accumulated knowledge about the user or the project.

The only dynamic prompt text in the build is the ledger reminder, and it is **dispatcher-facing, not worker-facing**: the standing-rules block and the wake-turn instruction tail are injected into the dispatcher's per-turn reminder (`src/core/policy/prompts.ts:110-121`, `:124-131`), assembled alongside the rendered ledger lines by the reminder assembler (`src/core/policy/assembler.ts:60-71`). Workers never see it.

**However — the pattern of capping sections is not absent from the build; it is applied elsewhere.** The report clamps are exactly this pattern in non-memory form: a 4000-character report-body cap, a 1200-character error cap, a 200-character check-activity cap, a 300-character recent-result excerpt cap, and a 20-row tool-result cap (`src/core/report-clamp.ts:17`, `:20`, `:23`, `:32`, `:35`). The build caps prompt-bound content by both count and characters — it just does so for worker reports rather than for remembered facts.

## The deviation
The reference treats the injected memory block as a budgeted, epoch-stable prompt section. The build injects no memory at all. Two separable things are in play, and a reader should keep them apart:

1. **The memory injection itself** — a memory-specific capability: it presupposes a durable fact store, a tier/scope model, and a recall cadence, none of which the build has.
2. **The practice of capping prompt sections** — a general prompt-engineering pattern: cap a section by count *and* by characters, and keep injected text stable within a compaction epoch. The build already applies the capping half of this pattern in its report clamps, and it solves the stability half differently rather than not at all: the worker contract is delivered in a *system position* and recomputed every turn, which is why it survives compaction by construction (`src/worker/prompt.ts:8-11`). The reference's answer to the same problem is to freeze the rendered text per compaction epoch instead of re-rendering it. Both are coherent; they are different trades — recompute-per-turn buys freshness and pays tokens each turn, freeze-per-epoch buys cacheability and stability and pays a possible staleness window.

The frozen-snapshot idea is therefore worth **naming** as a design idea next to the build's own compaction reasoning — the build already reasons explicitly about compaction survival in its worker-contract comments — but naming it is not recommending it: the build's existing mechanism covers the need, and no recorded ruling asks for a change there.

## Verdict: DO-NOT-INCORPORATE
The memory half of this deviation is **ruled, not unruled**: ADR-0018 (accepted, authority-stack position 2, the human-ruled master among the ADRs) names per-agent memory explicitly in exception **C14** — no org chart, no routines/automations subsystem, no per-agent memory, no group rooms (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:29`). Prompt-side injection is an internal part of that same excluded feature and shares its verdict family with the parent finding (DD-188, "Per-agent memory feature absent"); C14 settles it and no PRD amendment is recorded as reinstating memory. The *bounded-section pattern as such* is not the ruled-out thing — it is a general technique, not the capability — but it is also not a gap: the build already practices capping by count and characters in its report clamps, and its recompute-per-turn system position already covers the compaction-stability need that the reference's epoch freeze addresses. With the memory-specific content ruled out and the general pattern already present, no uncovered independent value remains, so the frozen-snapshot idea is recorded here as a named design idea only, with no incorporation recommended and none implied.

## Incorporation notes
- **Where it would live:** Nowhere, under C14 — the injection has no source of facts to inject. If the human ever reverses C14, the prompt-side half would be a new section in the worker-prompt assembler (`src/worker/prompt.ts`) fed by a recall hook in `src/core/`, with the dispatcher's reminder assembler (`src/core/policy/assembler.ts`) as the existing precedent for a dynamic, per-turn-injected section. The bounded-section constants themselves would sit naturally beside the report clamps (`src/core/report-clamp.ts`), which is where the build already keeps prompt-bound size constants.
- **Constraints:** C14 forbids the memory capability outright, so any work here needs a dated human reversal of C14 first, not an agent ruling. The general pattern is unconstrained but unnecessary: adding a second capping mechanism beside the report clamps would duplicate work already done. If it were ever reopened, the capping numbers would be new policy (the reference's 100/30/4000/50/15/3 are its own tuning, not a derived requirement), and the epoch-freeze would have to reconcile with the build's existing recompute-per-turn system position rather than sit beside it unexamined.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S if ever unblocked — the pattern is small and the build has a home for its constants — but the real gate is the C14 reversal, which is an L-sized capability decision (see DD-188), not a prompt-assembly task.
