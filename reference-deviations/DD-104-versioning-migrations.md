# DD-104 — Versioned settings store with migrations vs host-schema document
- **Area:** settings (A12)
- **Type:** architecture-delta (deliberate)
- **Date:** 2026-09-23

## What the reference does
The reference persists its desktop settings through a self-owned JSON file store that versions and migrates itself. The document carries a hard-coded version constant (the settings version constant, `sand-settings-store.ts:15`), and the parser rejects any document whose version does not match — a document from a different version parses to nothing and the store falls back to defaults (`sand-settings-store.ts:45-47,97`). Inside the document lives a list of applied migrations: a list of named migration ids plus an applier that, on load, runs any migration not yet recorded and immediately writes the result back. The one shipped migration rewrites a stored model selection so an older client can survive a feature the format no longer expects (a downgrade-recovery migration id, `sand-settings-store.ts:16-17,43,100-105`). Per-account state is wiped when the account scope changes or clears (`sand-settings-store.ts:134-135`), and every write goes through a temp file in the destination directory followed by an atomic rename (`sand-settings-store.ts:106`). Secondary structures get the same treatment independently: the inference-router usage record carries its own schema-version field (`the reference tree's source/shared/inference-router.ts:13-16`).

## What the current build does
The build owns no settings file and no persistence code. `installMultitaskSettingsSection` waits for the host settings service and claims its namespace through the provider's scope-returning API — `settings.register(ns, schema, { base })` (`src/adapter/settings-section.ts:132-141`) — yielding a settings document composed by the host: a composition base plus user-layer overrides, where a cleared field reverts to base. There is no version field, no migration ids, no custom read/write path; storage, durability, and document lifecycle belong to the host dsh-settings provider. The module header documents why the scope-returning `register` (not `installSection`, which returns void on the live host) is the standard host pattern, citing the live host's own consumer `dsh-agent-presets/lib/index.js:1311-1318` (`src/adapter/settings-section.ts:20-46`, citation at `:33-35`).

## The deviation
Reference: a self-owned, versioned document with a list of migrations stored inside it, rejection of documents from other versions, atomic temp-then-rename writes, per-scope key clearing, and a second, independently versioned usage record. Build: an unversioned slice of a settings document composed by the host — versioning and durability are delegated to the host facility. The delta is deliberate (structural typing only; no parallel persistence machinery), but it leaves the build without an explicit answer for what happens to its namespace's data if its settings shape ever changes incompatibly across host upgrades.

## Verdict: ADAPT
Keep using the host provider: ADR-0018's exception list already delegates persistence to dsh's own stores (A5), and rebuilding a version list inside a document composed by the host would duplicate machinery the host owns and reopen settled architecture (ADR-0001's in-process plugin approach; ticket 93's one-claim-per-namespace rule). Honestly assessed, though, delegation covers storage, not schema evolution — the host will faithfully store whatever the schema hands it, so an incompatible change to the dispatcher's settings shape would land silently on stale documents. The adaptation is therefore (a) to state an evolution policy in the module header — additive schema changes, tolerant composition, no rename-and-drop — and (b) to route any future self-owned, mutable user state into the host's session/job store (A5, with ADR-0006's durability split) before it ever needs migrations. Escalate to ASK-HUMAN only if durable dispatcher state with a legacy on-disk format must live in this namespace.
