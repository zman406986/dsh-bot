# DD-157 — Central tool registry and per-agent tool governance
- **Area:** A19 tool surface
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference keeps a central tool registry: one module (the reference tree's `source/packages/agent/tools/all-tools.ts`) holds a map of about 118 tool entries, each routed to one of six owning teams (an agent-quality team, an async team, a bugbot team, a core team, a data-infra team, and an extensibility team) via a lookup of the tool's canonical identifier, with an explicit fallback for an unrecognized tool. Per-model name resolution lives separately (the reference tree's `source/packages/agent/tools/task-tool-name.ts`): it takes the parent model's info (a prompt-version string plus two Composer flags) and returns the delegate-task tool name that model should see, so different model families get differently-named callable tools for the same capability. A third module (the reference tree's `source/packages/agent/tools/exclude-tools.ts`) subtracts tools from a given agent's surface — it derives a base set of static native tool identifiers, builds a set of agent-protocol tool names by reflecting over the proto `ToolCall` oneof fields, and exposes an offload predicate plus a subagent-exclusion predicate, with a normalized-name map keyed on both proto field names and their uppercased forms.

## What the current build does
Tools are registered ad hoc per agent, not through a registry. The dispatcher's tool surface is a small fixed set — six dispatcher tools (`spawn_worker`, `check_workers`, `steer_worker`, `stop_worker`, `deliver_result`, `send_peer`) defined together in `src/core/tools.ts`, plus the worker-side `request_access` (`src/adapter/worker-access-tool.ts:27`). There is no map of which team owns which tool, no per-model name resolution (no canonical-tool to model-specific-name mapping), and no exclusion/offload module.

The build does take an explicit position on how a tool surface should be narrowed, and it is a deliberate opposing stance rather than an omission. `src/worker/tool-barrier.ts:1-7` states the rule directly: the host's tool-restriction call throws on unknown names, so the build must "never pass a hard-coded full deny list — always intersect the candidates with what is actually registered as a global tool at spawn time." The implementation matches: `WORKER_DENIED_TOOL_CANDIDATES` (`tool-barrier.ts:14`) is a candidate list only, and `buildWorkerToolFilter` (`tool-barrier.ts:52-59`) filters it against a live set of known global tool names, leaving out unknown candidates so the build's layer never throws, and returning an empty deny rather than an invalid one. The blocked-tool list is therefore derived from what is actually registered, not asserted from a static registry.

## The deviation
This is a difference in how the tool surface is governed, not a missing user-visible capability. Nothing the user can do with the reference is unavailable in the build. What differs is how the tool surface is *administered*: the reference centralizes the mapping from tool to owning team, to model-appropriate name, and to per-agent exclusion in three dedicated modules, while the build registers the small surface per agent and derives the one narrowing rule it needs from what is actually registered.

The build's stance is coherent, not an oversight. The reference's ownership map exists because it is an internal platform whose many teams need to route ~118 tools across ~6 owners and audit that routing; a registry with no consumer is pure overhead. The build's tool-barrier comment addresses the same underlying hazard — an agent seeing or being denied a tool that does not exist — and solves it by intersecting with what is actually registered, which is the opposite of trusting a static list. The per-agent exclusion idea is the one piece that still affects which tools an agent sees, but the build already performs the equivalent subtraction in `buildWorkerToolFilter`, at six tools, and it does so with the correctness property (no throw on unknown names) that a static exclusion module would put at risk.

## Verdict: DO-NOT-INCORPORATE
No recorded ruling covers tool-registry governance specifically, so this rests on the authority stack rather than a direct ruling. The PRD §2 non-goals exclude rebuilding dsh's inference/transcript/tool runtime — the reference's registry is exactly such runtime-adjacent platform machinery, and importing it would push a small Cordis plugin into dsh's tool-runtime territory. ADR-0018 governs what may be imitated from the reference, and it does not authorize importing an administrative layer whose only consumer is a much larger platform. The build has also already recorded a deliberate opposing position in `tool-barrier.ts`: no hard-coded full deny list, derive from live registration instead. That recorded design stance argues against mechanically importing the reference's exclusion module, which is built around static identifier sets. A 118-entry ownership map has no consumer at a six-tool surface, so the registry itself is DO-NOT-INCORPORATE; the remaining exclusion question is answered by the build's existing derived filter.

## Incorporation notes
- **Where it would live:** Nowhere as a port. If any remaining idea were ever wanted, it would be a narrowing predicate beside the existing derived filter in `src/worker/tool-barrier.ts`, not a new registry module, and it would read what is actually registered the same way `buildWorkerToolFilter` does.
- **Constraints:** The build's tool surface is fixed and small (six dispatcher tools + `request_access`); any narrowing must stay derived from the live known-global-tool set, preserving the no-throw-on-unknown-names property the host requires. An ownership map with no team process consuming it is dead metadata and must not be added speculatively. Any per-model naming would need a build-side consumer (a real model-family difference the build observes), not a speculative branch.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S if ever revisited — the only plausible variant is a small extension of the existing derived filter predicate; the registry itself is not applicable (no consumer). Risk of any mechanical import is Medium: it would add static-list fragility the build deliberately avoids and pull platform machinery into a plugin.
- **Key reference anchors:**
  - the reference tree's `source/packages/agent/tools/all-tools.ts:1-129` — the ownership map (~118 entries, six owner teams) and its lookup function.
  - the reference tree's `source/packages/agent/tools/task-tool-name.ts:1-14` — per-model task-tool name resolution.
  - the reference tree's `source/packages/agent/tools/exclude-tools.ts:1-59` — per-agent exclusion/offload predicate and static native identifier set.
