# DD-216 — Auto-review enforcement modes and per-surface gating
- **Area:** A28 approval & policy
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

Auto-review has an enforcement *level*, not just a decision. Three levels exist — off, observe-only, and blocking (the reference tree's `source/host/runner/sand-auto-review.ts:7`) — and a resolver turns three inputs into a per-surface level map (`:65-69`): a settings-side enable flag short-circuits everything to off; an optional local override, when present, is applied to every surface; otherwise an experiment feature gate selects blocking versus observe-only. The three frozen presets are the same shape (`:61-63`), and the settings flag and feature gate are supplied by the caller at the reference tree's `source/host/extensions/auto-review/auto-review-service.ts:49`, with the local override parsed and rejected unless it is one of the three known levels at `:6`.

The level is **per surface**, and the surface set is fixed and typed: the host shell, the sandboxed shell, MCP, the computer surface, automation writes, cloud agents, and subagent launches (`sand-auto-review.ts:13-21`). Automation writes are pinned: the mode map's field for them is typed as the single literal off, so no preset and no local override can ever raise them (`:18, 61-63, 67`). The gate keeps its own surface vocabulary and maps mode keys onto surface ids (the reference tree's `source/host/runner/auto-review-gate.ts:31-45`), and — the main consequence — every surface found *not* at the blocking level has its outstanding approvals retired on the spot (`:43`, retiring with the settings-change cause at `sand-auto-review.ts:161`). A surface's approval identity also carries a per-surface side-effect generation counter, bumped when a side effect starts (`auto-review-gate.ts:68-75`).

Separately, a global barrier: the same gate exposes an assertion that reads the controller's whole pending set and refuses — with a dedicated error type — when anything at all is awaiting a decision, on the stated ground that no new side effect may start while another action is undecided (`auto-review-gate.ts:46-53`). It is cross-request by construction (it consults the pending set, not the caller's own request) and it is actually wired: three composition sites hand it through (the reference tree's `source/host/host-runner-composition.ts:1000, 1556, 2504`) and it is consulted at action entry points for the computer surface, remote-box resource access, and turn-agent tool admission (the reference tree's `source/host/runner/host-computer-tool-dependencies.ts:297`; the reference tree's `source/host/runner/remote-box-resources.ts:134`; the reference tree's `source/host/runner/turn-agent-composition.ts:1271, 1317, 1434`). A per-agent cap of four simultaneous pending approvals and a ten-minute TTL sit alongside it (`sand-auto-review.ts:3-4, 118, 133`); the TTL and durable-record side is DD-215's subject, not this file's.

## What the current build does

There is no enforcement level anywhere. `src/core/review-posture.ts` is a decision table, not an enforcement-level resolver: each row pairs an ask kind with allow or deny and a target pattern (`:36-56`), and the table is consulted **only after** the consent table returns "ask" — a consent allow or deny always wins (`:180-186`, wired at `src/core/multitask.ts:355-359`). The ask-kind key is `AccessClass | "worker-dispatch"` (`review-posture.ts:33`), so the build does have a coarse per-surface-ish axis — worker access classes versus worker dispatch — but a single treatment applies to all of them; there is no observe-without-blocking level, and nothing in the module can express one.

The shipped table is deliberately empty (`review-posture.ts:130-149`), which makes un-configured behavior byte-identical to pre-ticket-69 (`:14-15`), and the emptiness is a ruled position: ticket 69 Q1, 2026-09-19, on the ground that a non-empty default or a settings-seeded decision table would auto-answer access prompts without an explicit user act. That ruling names ADR-0018 exception U-D and ADR-0011's rule that consent never silently widens, and it closes the door on both a shipped default and a Config seeder. The module's own header records the broader list of things deliberately not imitated — no classifier layer, no persistence beyond session scope, no settings-managed store, no approve tool (`:1-18`) — and writes are fenced at the sink, with a wildcard-bearing pattern refused rather than remembered (`:195-200`, helper at `:72-75`).

Where the build *does* gate, it gates one request at a time. `lookupDispatch` has exactly one caller, the spawn tool (`src/core/tools.ts:297`), and that call site is the whole gate: a deny row auto-denies, an allow row defers to the host approval path, a gated dispatch with no approval call refuses fail-closed, and an outcome that is not allowed-once refuses the spawn (`:288-327`; the outcome vocabulary at `:112-128`). A miss in the decision table means the spawn proceeds exactly as shipped with no approval call at all (`:288-295`).

The build does track outstanding asks, but only as projection, never as a barrier: the relay holds one outstanding ask per worker (`src/core/access-relay.ts:175`), the wake bus queues pending requests and notices (`src/core/wake-bus.ts:113, 163-165`), and the roster envelope projects the full pending-ask set for display (`src/core/roster-snapshot.ts:158, 187, 256-261`). No code path refuses a new dispatch because some *other* request is undecided. The nearest thing to "a surface leaving enforcement" is session-scope clearance, which drops decision-table *rows* (`review-posture.ts:206-213`, wired at `multitask.ts:1042`) — a decision table's contents, not live approvals — plus the pending-ticket drop when a worker settles or is stopped (`multitask.ts:484, 647`).

## The deviation

The mode machinery — three enforcement levels, resolved from a settings flag, an experiment gate and a local override, held per surface with automation writes immovable — has no build counterpart at all, and the surface set it is defined over (MCP, the computer surface, cloud agents, automation writes, the sandboxed shell) mostly names surfaces the build does not ship. Only two surfaces in that list have build analogues: worker spawns and worker access asks, which the decision table already keys separately.

The interesting part is that two ideas here are separable from the ruled-out classifier apparatus.

**(a) The per-surface gating model.** Different surfaces carrying different enforcement levels is a scope design, not a classifier. The build has the axis but not the dimension: ask kinds are already per-row addressable (`review-posture.ts:33`), so the *gating* half is present, while the *level* half (observe-only versus blocking, and the ability to drop a surface's level at runtime) is entirely absent — and with no level there is nothing for the reference's expire-on-leaving-enforcement consequence to act on. That consequence is genuinely uncovered by any build machinery, but it is a consequence of a mechanism the build is ruled not to have, so it is not an independent gap.

**(b) The pending-approval interlock, compared honestly.** The build's gate looks similar and is not the same thing. What the build provides is the interlock's *local* half: within the one request being gated, no outcome other than an explicit allow-once lets the side effect start (`tools.ts:319`), so there is no window in which a gated dispatch begins before its own decision. What it lacks is the *cross-request* half. The reference's assertion reads the controller's whole pending set and refuses any new side effect while anything is undecided, whichever request it belongs to; the build's gate reads one decision-table row for the title it was called with and knows nothing about outstanding asks. So a dispatcher holding a pending worker access ask can still spawn another worker — the relay's one-ask-per-worker rule (`access-relay.ts:175`) is per worker, and the roster's pending set is a display projection. Two further asymmetries sharpen the comparison: the build's barrier exists *only* on a dispatch gated by the decision table (the shipped empty table means the default path performs no approval call at all), and its protection is per-request rather than per-window. Verdict on the comparison: **the build's single-ask gate is only the one-request case of the reference's interlock, not an implementation of it.**

## Verdict: DO-NOT-INCORPORATE

ADR-0018 exception U-D (line 37) rules out both halves of the mode machinery — "always allow" rules are session-scoped and never persisted, with no settings-managed rule store and no dedicated local tool-permission controller — and a level resolver fed by a settings flag, an experiment gate and a local override is exactly that settings-managed controller, while the observe-only and blocking levels are the classifier layer that the ticket-69 record of imitation limits lists as excluded (`src/core/review-posture.ts:1-18`). The shipped empty decision table is itself a ruled position (ticket 69 Q1, 2026-09-19) that already names U-D, so the build's off behavior is the ruled outcome rather than an unbuilt feature. One gap is genuinely uncovered: no recorded ruling speaks to a cross-request discipline forbidding a new side effect while any approval is pending, and the build's gate supplies only the one-request case of it. Per the authority stack that gap is not authorized by this deviation — if it is ever wanted it needs its own ruling, on the pattern of DD-004's narrow-slice note, and this file should not be read as a gap to be filled.

## Incorporation notes
- **Where it would live:** Nothing for the mode machinery — there is no place in the build for an enforcement level and the empty decision table already reproduces the reference's off behavior byte-identically. If a human ever ruled for the cross-request gap, it would sit where dispatch is admitted, beside the decision-table check in the spawn tool (`src/core/tools.ts:288-327`), reading the relay's live pending state (`src/core/access-relay.ts`), *not* inside the decision table — that module is a decision table and deliberately holds no live request state (`src/core/review-posture.ts:130-149`). A per-surface level dimension, if ever wanted, would extend the decision table row's ask-kind key rather than introduce a level resolver.
- **Constraints:** ADR-0018 U-D (no settings-managed rule store, no dedicated controller) and the ticket-69 Q1 ruling that any non-empty default or Config seeder is a U-D amendment needing a human signature first; ADR-0011 (consent never silently widens — session-scoped, exact target, wildcard-fenced, already enforced at `review-posture.ts:195-200`); ADR-0008 (timeout-deny honesty), so any barrier that parks new work must surface that honestly rather than drop it silently; and the PRD's stay-responsive rationale for delegation, which a global barrier directly tensions with.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S to keep absent — zero work, and the ruled empty decision table is already the reference's off case. Any interlock work would be M and high-consequence: a global barrier serializes the dispatcher against undecided requests, which is the responsiveness property the dispatcher exists to provide, and it would need its own ruling before code.
- **Key reference anchors:** the reference tree's `source/host/runner/sand-auto-review.ts:3-4, 7, 13-21, 61-69, 118, 133, 161`; the reference tree's `source/host/extensions/auto-review/auto-review-service.ts:6, 49`; the reference tree's `source/host/runner/auto-review-gate.ts:31-53, 68-75`; the reference tree's `source/host/host-runner-composition.ts:1000, 1556, 2504`; the reference tree's `source/host/runner/host-computer-tool-dependencies.ts:297`; the reference tree's `source/host/runner/remote-box-resources.ts:134`; the reference tree's `source/host/runner/turn-agent-composition.ts:1271, 1317, 1434`.
