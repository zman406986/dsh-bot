# DD-169 — Awaiting-user-response state and pending-card expiry
- **Area:** A20 session & durability
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference agent database treats "this agent is waiting on its user" as a durable, first-class condition rather than a transient in-memory flag. Each per-agent database stores the awaiting condition as a keyed value alongside its other session state: a record naming the tab that owns the wait, a human-readable reason, and the timestamp the wait began (`agent-db.ts:55`, the KV key mapping at `agent-db.ts:64`). The store exposes a symmetric surface — read the current condition, set or clear it, and a tab-scoped variant that only writes when the existing condition belongs to that same tab and was recorded before a supplied cutoff (`agent-db.ts:213-216`). Because it lives in the database, the condition survives process restarts and is repopulated from disk.

The condition is not decorative: it feeds outward surfaces. Session summaries carry it out to the sidebar and notification tiers (`session-summaries.ts:8`, `:11`, `:16`), the OS-notification layer derives a needs-input transition from it (`os-notification.ts:3`, `:5`; `mobile-push-notifier.ts:3-5`), and the send-acceptance path clears it when the user answers (`send-acceptance.ts:100-101`). Handoff and resume code sets it on the receiving side (`box-handoff-resume.ts:63`, `:78`).

Alongside the durable condition, the reference ships a discrete sweep module for stale pending cards (`pending-card-sweeps.ts`). It scans transcript entries of two pending-approval kinds and settles any that are still pending into an expired terminal status, returning the request identifiers it retired (`pending-card-sweeps.ts:6-9` for the auto-review approval kind, `:11-14` for the local tool-permission ask kind). The second sweep takes an optional cutoff so only entries older than a supplied point are expired (`:11`).

## What the current build does
The build has no persisted awaiting-user condition. Neither `src/core/` nor `src/adapter/` declares a "waiting on the user" status, and the durable-session surface (`src/core/durability.ts`) has no such stored entry.

The only place in the build where something waits for a user decision is the access-prompt / permission path. A transient ticket is created when a worker's ask reaches the host; the core relay starts a one-shot deny-by-default timeout at the moment the ticket enters the waiting state (`src/core/access-relay.ts:324-332`, default bounded by `DEFAULT_ACCESS_TIMEOUT_MS` at `:19`). If no allow or deny answer arrives before the timeout, the timeout handler settles the ticket with a deny decision whose reason is the timeout (`src/core/access-relay.ts:325-330`).

The build does carry accurate wording for the post-expiry case. The adapter defines an approval-expiry constant whose text states that the request already expired and was denied by default (`src/adapter/access-prompt.ts:170-171`). A notice helper emits a deny-by-timeout decision carrying that text as its detail (`src/adapter/access-prompt.ts:364-372`), and the module documents that an answer arriving after the relay already resolved the ticket surfaces the expired text through the wake bus and resolves nothing (`src/adapter/access-prompt.ts:65-67`, `:511-523`). What the build does not have is a stored status recording that a worker is waiting, and no sweep that retires stale pending prompts on a schedule — the timeout is the entire lifetime mechanism.

## The deviation
The reference models "waiting on the user" as durable session state, with its own lifecycle: recorded when the wait begins, carried outward to summaries and notifications, cleared when the user answers, and — on the pending-card side — retired by an explicit sweeper that expires cards left too long. The build models the same moment as a transient ticket with a single bound: it enters the waiting state, the relay starts a deny timer, and an unanswered ticket is denied and the work moves on (`src/core/access-relay.ts:324-332`). There is no persisted state a restart could recover, nothing for a UI or notification surface to read as "this worker needs you", and no periodic sweep — expiry is per-ticket and happens exactly once.

The nuance is that this is not simply a missing mechanism bolted onto an otherwise complete feature. The reference's durable condition is meaningful because the reference has a general agent-to-user question channel (DD-163). In the build the permission flow is the *only* place a user-facing wait arises, and a timeout-deny there is a deliberate completion policy, not a gap: the worker gets a definite answer and re-plans. The durable state and the sweep are natural requirements of a design where an agent may sit on a substantive question indefinitely; they are largely inert in a design whose only wait already has a defensible terminal outcome.

## Verdict: ASK-HUMAN
No recorded ruling names "awaiting user response" as a state, a sweep, or a durable wait condition — this is not covered. ADR-0018 exception A5 rejects the reference's SQLite-backed session model, so the store this state lives in is out of scope as-is; but the *condition* is a lifecycle question, not a storage question, and the build's own durability layer could carry it without mirroring the reference's store. ADR-0008's timeout-deny and ADR-0010's rule that state is reported as it is both favor a definite outcome over an indefinitely pending one, which argues for leaving the build as it is. The deciding question is upstream: whether DD-163 lands a general ask-user channel. If it does not, a durable awaiting state has nothing to describe and this is a do-not-incorporate; if it does, that channel's lifecycle needs exactly this state, and the sweep becomes its garbage collector. That sequencing makes this a human sequencing call — it should be answered after DD-163, and the two should not be decided independently.

## Incorporation notes
- **Where it would live:** The condition, if adopted, belongs in the durability layer alongside the existing persisted markers (`src/core/durability.ts`, and the adapter's durable-marker helper `src/adapter/durable-marker.ts`), with the set/clear call sites at the ask channel's open and answer points. A pending-prompt sweep of build-local scope would sit with the access ticket lifecycle (`src/core/access-relay.ts`) or as a small periodic reconciler beside `src/core/todo-reconciler.ts`. It is only worth building if a genuine waiting channel exists to describe.
- **Constraints:** Do not adopt the reference's storage shape (ADR-0018 A5 rejects its session model); re-derive the state against the build's own persistence. Any sweep must not second-guess ADR-0008's semantics: the core relay owns deny-by-default and the single started timeout, and a sweep that expires tickets out from under a running timer would be a second, competing authority over how long a ticket lives. The existing expired-answer check in `src/adapter/access-prompt.ts:511-523` already assumes the timeout is the only expiry path; adding a sweeper means revisiting that assumption. This deviation cannot be settled before DD-163.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the state itself is small, but its value is entirely contingent on DD-163, so effort spent before that ruling risks building a status with no writer.
- **Key reference anchors:** durable condition record and KV key mapping: `agent-db.ts:55`, `:64`; accessor surface including the tab-scoped conditional write: `agent-db.ts:213-216`; session-store pass-through: `agent-session.ts:204-205`; outward projection: `session-summaries.ts:8`, `:11`, `:16`, `os-notification.ts:3`, `:5`, `mobile-push-notifier.ts:3-5`; clearing on user answer: `send-acceptance.ts:100-101`; handoff/resume writes: `box-handoff-resume.ts:63`, `:78`; pending-card sweeps: `pending-card-sweeps.ts:6-9` (auto-review approval kind) and `:11-14` (local tool-permission kind, with cutoff at `:11`).
