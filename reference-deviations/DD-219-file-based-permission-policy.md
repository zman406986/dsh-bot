# DD-219 — File-based permission policy: user and workspace policy documents
- **Area:** A28 approval & policy
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

Policy can arrive from files that live outside the UI, and there are two layers of them.

**A user-scope document.** A provider reads a permissions file from the product's config directory (the reference tree's `source/packages/cursor-config/permissions-file-provider.ts:40-42`), JSON-with-comments, and pulls four things out of it. Two of them are allowlists — one naming MCP servers, one naming terminal commands — read through a helper that matches field names case-insensitively, so the author's capitalization does not matter (`:56-57, 112-123`). The other two are instruction lists for automatic review: one list of things to allow, one of things to block, reached under a key that accepts either of two spellings (`:58-61`). The two allowlists are then translated by role into allow rules for the shell and MCP surfaces, and the resulting permission set carries an empty deny list (`:74-78`). The effective-permissions record the provider hands back declares an unrestricted approval mode and a fixed marker saying nothing is configured (`:18-21, 84-91`). Two fail-closed properties are worth naming: a missing file, an unparseable file, or a file whose four fields are all empty yields *no provider at all* rather than an empty policy (`:44-48, 66-73, 79-81`), and the write path is a no-op — the app reads this document and never rewrites it (`:100-102`).

**A workspace-scope document.** Each workspace may carry its own permissions file at a fixed project-relative path (the reference tree's `source/packages/agent/smart-mode-project-permissions.ts:10`). Its instruction lists are parsed under the same two spellings, with trailing commas tolerated and any parse error rejecting the whole document (the reference tree's `source/packages/cursor-config/project-permissions-file-provider.ts:32-48`). When several workspaces are open, candidate paths are built per workspace and every existing file is read and folded into one aggregate (`smart-mode-project-permissions.ts:82-114`). The aggregation is capped and the caps are declared as named constants: twenty project instructions per workspace, one thousand characters per instruction, and twenty user instructions (`:7-9`). Deduplication is set-based on both the project side and the user side (`:50-70`).

**The layering, which is the actual mechanism.** Project entries and user entries are combined into one pair of instruction lists, and the order is the precedence: project instructions are emitted first, then user instructions (`:130-131`). A user instruction that already appears in the project aggregate is dropped rather than repeated (`:59-70, 118-119`), so project wins by position plus exclusion. The cap for the project side scales with the number of open workspaces while the user side is a flat twenty (`:122-127`).

**Truncation is flagged, not silent.** The truncation helper returns both the clipped value and a boolean, appending an explicit truncation marker to any instruction that was cut (`:25-34`), and the aggregation reduces the four lists' flags into a single truncation boolean on the context object it returns (`:17-23, 133`). A caller can therefore tell that it is looking at a clipped policy. The cap and the marker are one mechanism: the reference neither drops the overflow silently nor pretends the list was complete.

## What the current build does

There is no permission-file reader, and no layered policy input of any kind.

Settings is a single namespaced scalar schema. The plugin declares one namespace constant (`src/adapter/settings-section.ts:50`) and claims it once at registration, passing the composition's base config through (`:126-142`); the module comment records that a namespace can be claimed only once, because a second claim throws. What that namespace holds is pinned to two fields — a boolean enable flag and a request-timeout number — and the settings card's field list is deliberately exactly those two, asserted offline against the schema so a field added without a control fails the suite rather than rendering a partially editable card (`src/client/settings-card-store.ts:194-212`). There is no list-typed field, no document field, and nothing that reads a file.

Policy rows enter only through in-memory APIs. `src/core/review-posture.ts` builds a table backed by a `Map` (`:150-215`), with rows carrying an ask kind, an allow-or-deny decision, a target pattern, and one of two scopes — session or profile (`:151-215`). Lookup walks session rows first, then profile rows, then falls through to "ask" (`:179-186`); writes refuse a wildcard-bearing pattern rather than remembering it (`:195-200`); session-scope clearance drops rows from the map (`:206-213`). The table's contents are populated by callers, not loaded from anywhere, and the module's own comment forecloses the nearest thing to a file-based input: any non-empty default or config seeder is recorded as a U-D amendment requiring a human signature first (`:145-148`).

So the build has no policy *document* at all — nothing on disk to read, nothing to layer, and no precedence question because there is only one source.

## The deviation

The reference treats policy as a **layering** problem: policy can arrive from a user-level document, from per-workspace documents, and from the UI, with a defined ordering between them and explicit caps on how much of it is honored. The build's policy is in-memory only, single-sourced, and populated by API calls. Two elements of the reference mechanism can be separated from the file-reading code and are worth naming precisely.

**(a) The precedence rule.** Workspace over user, expressed as emission order plus exclusion of already-present entries (`smart-mode-project-permissions.ts:59-70, 118-119, 130-131`). Two honest qualifications. First, this is *positional* precedence rather than a conflict resolver: it orders and dedupes, it does not adjudicate two instructions that contradict each other — the reference has no mechanism for noticing that one layer's instruction contradicts another's. Second, the build has no second policy source for a precedence rule to relate, so the idea is a design property with no consumer here. It is a genuinely clean expression of "more specific scope wins," but importing it would mean importing the layering first.

**(b) Caps with truncation flagged rather than silent.** This is the part worth the most attention, and it is the part most independent of the file-reading code. The reference bounds policy input (twenty per workspace, one thousand characters each) *and* reports that it bounded it, both per instruction and as one boolean on the returned context (`:7-9, 25-34, 133`). A caller cannot mistake a clipped policy for a complete one. The build does have a recorded habit of naming its known gaps rather than hiding them — ADR-0010's fourth rule is titled for reporting only what can be read, and records a config channel doing telemetry duty as "the recorded honest gap" (`docs/adr/0010-dispatcher-presence-is-a-projection-of-core-state-draft-nonhuman-approved.md:16`) — but that rule is about a read path with no push channel, not about bounding input, and ADR-0010 is a draft awaiting human sign-off. The similarity is real, but it is only a similarity: no recorded ruling in the build covers disclosing that policy input was cut short, so this is an observation about a shared instinct, not a citation of authority. Stated at the strength it deserves: flagged truncation is a good property that the build's own habits happen to point toward, not a rule the build is bound by.

**One honest scoping note.** Where policy documents are *read from* is partly a host question in the build's architecture, and this deviation should not be read as a plugin-level gap the plugin is failing to close. The build is a plugin inside dsh, not its own product shell: it does not own the config directory, does not own a workspace concept, and the settings namespace it registers is the host's settings facility (ADR-0018 has the build owning the wrapper UI, but the config directory and workspace enumeration are host surfaces, not wrapper surfaces). A file-based policy input could therefore land in the host, be surfaced to the plugin through the settings facility, or be a wrapper concern — and the build's own settings module already treats the host as the owner of where values live (`src/adapter/settings-section.ts:40-47`). Deciding which layer would own a policy document is upstream of deciding whether to have one.

## Verdict: DO-NOT-INCORPORATE

ADR-0018 exception U-D (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:37`, verified verbatim) rules that always-allow approval rules are session-scoped and never persisted, with **no settings-managed rule store** and no dedicated local tool-permission controller. A file-based policy document that seeds allow rules from disk is the strongest possible form of a settings-managed rule store — it is persistence plus an out-of-band write path — so the mechanism as a whole is squarely ruled out. The build's own module goes further and pre-empts the adjacent case: `src/core/review-posture.ts:145-148` records that any non-empty default *or config seeder* is a U-D amendment requiring a human signature first, which is the closest existing ruling to this deviation and it points the same way. The verdict is not quite complete, because U-D's wording addresses *rules and their persistence* and does not name a read-only policy document that is never written back — so the honest statement is that U-D covers the main points of this deviation through its rule-store clause and its config-seeder clause, not by naming a file input. That leaves one gap: the flagged-truncation honesty property (b) above is an idea about reporting that input was cut short, with no build ruling against it, and the workspace-over-user precedence rule (a) is a design idea no ruling forbids — but neither has a consumer without the layering the build is ruled not to have, so neither is authorized by this file. If either is ever wanted it needs its own ruling; this file is not a gap to be filled.

## Incorporation notes
- **Where it would live:** Nothing for the file reader or the layering — no build connection point exists and U-D forecloses the store. If a human ever ruled for a policy document, the reading would sit in the adapter beside the settings registration (`src/adapter/settings-section.ts:126-142`), not in `src/core/review-posture.ts`, which is deliberately an in-memory decision table with no load path (`:145-148`). The precedence rule would be meaningless before there were two sources. The truncation-disclosure idea, if ever wanted, would apply to whatever list a future surface does bound, and belongs with that surface's return shape rather than here.
- **Constraints:** ADR-0018 U-D (session-scoped rules, never persisted; no settings-managed rule store; no dedicated local tool-permission controller); the U-D amendment warning recorded in `src/core/review-posture.ts:145-148`, which makes any config seeder a human-signature matter; ADR-0011 (consent never silently widens — session-scoped, exact target, patterns with wildcards are refused); ADR-0005 (the enable flag is frozen for the session and never re-read live), which is relevant to any input the host would re-read mid-session; and the host-ownership question named in the deviation — the config directory and workspace enumeration are host surfaces, so this is not a plugin-only decision.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S to keep absent — zero work, and the build's single in-memory source already behaves as the reference's no-document case (`permissions-file-provider.ts:44-48, 66-73`). Any file-based input would be M and would need its own ruling before code: it would reintroduce persisted policy by a side channel, and the host-ownership question would have to be settled first.
- **Key reference anchors:** the reference tree's `source/packages/cursor-config/permissions-file-provider.ts:8-21` (instruction pair, permissions pair, effective-permissions shape), `:40-48` (config-directory path, absent means no provider), `:56-61` (case-insensitive allowlist lookup, dual-spelling instruction key), `:74-78` (allowlists mapped by role to shell and MCP allow rules, empty deny), `:84-91` (unrestricted approval mode and fixed policy marker), `:100-102` (write path is a no-op), `:112-123` (case-insensitive field helper); the reference tree's `source/packages/cursor-config/project-permissions-file-provider.ts:19-30` (instruction parsing), `:32-48` (strict parse with trailing-comma tolerance); the reference tree's `source/packages/agent/smart-mode-project-permissions.ts:7-10` (cap constants and project file path), `:25-48` (truncation with per-instruction flag), `:50-70` (set-based dedup and project-excluding-user), `:82-121` (per-workspace candidate paths and aggregation), `:122-134` (caps applied, project-before-user emission, single reduced truncation flag).
