# DD-143 — Tone & reply-shape prompt sections vs thin style clauses
- **Area:** system prompts / persona (A17)
- **Type:** missing-feature (PRD-required asset partially unimplemented)
- **Date:** 2026-09-23

## What the reference does
The reference system prompt devotes two of its largest sections to how the bot sounds and how replies are physically shaped. The tone section establishes a warm, human peer voice: everyday vocabulary and contractions over formal register, an explicit list of banned help-desk opener patterns, sparse punctuation habits (minimal em-dash use), restrained emoji that only mirrors what the user themselves uses, and care with pronouns so the bot never refers to the user by the wrong gender or talks past them. A separate reply-shape section governs message mechanics: match the user's message length and go shorter for light moments, split thoughts across multiple chat bubbles instead of one wall of text, prefer flowing prose over outlines and bullet lists, open with the result or answer rather than setup, and skip both signpost preambles and filler closings. Beyond those two sections, the prompt also carries etiquette for threaded replies and for the platform's decision-widget prompts, treating channel behavior as part of voice rather than a separate concern.

## What the current build does
The build's dispatcher prompt contains only scattered single clauses touching user-facing style: speak as one busy person; never name the machinery — workers, streams, wakes, dispatch — to the user (stated in the behavior rules, repeated in the "what you never do" list, again in the standing-rules block, and a final reminder in the wake instructions); lead with the concrete thing that finished rather than a bare pronoun or a bare "done"; and never dump a worker transcript or long tool log into the user's chat. That is the entire user-facing style surface. Nothing in any build prompt asset addresses warmth or register, matching the user's message length, bubble splitting, formatting preferences (prose vs. lists), punctuation habits, emoji, pronoun handling, threading etiquette, or any channel-specific reply conventions. The clauses that do exist are all privacy-of-machinery or anti-clutter rules — they govern what the bot must not reveal, not how it should sound.

## The deviation
The reference treats voice as a first-class, extensively specified dimension of the persona; the build treats it as a side effect of a few prohibitions. PRD §10 row 1 explicitly lists "user-facing tone rules" as required content for the dispatcher system section, alongside "privacy of machinery" — and only the privacy half got implemented (ticket 31 / design-17 §4.9 covered narration, i.e. the rules that machinery stays private and that no task board or milestone view is ever mentioned, not tone). The build is therefore running a PRD-named asset at roughly half its specified content: a dispatcher that never leaks machinery names but has no guidance on sounding human, sizing replies to the moment, or respecting channel conventions. This is not a cosmetic gap; it is a required, enumerated deliverable that is missing.

## Verdict: INCORPORATE
The PRD itself demands user-facing tone rules in the dispatcher section, so closing this gap is not optional judgment — it is completing a specified asset, which makes this one of the strongest candidates to incorporate in the enumeration. The incorporation must be fresh writing: the value to bring over is the *coverage* (warmth and register, length-matching, bubble/prose formatting, opener and closing discipline, emoji restraint, pronoun care, channel etiquette), expressed in dsh's own voice and fitted to the dispatcher's situation, never the reference's sentences, examples, or banned-opener wording. Adapt the specifics to what a dispatcher actually does — most turns are delivering worker results, acknowledging steers, or going quiet — rather than transcribing a general chatbot's style guide. Under the authority stack this ranks as PRD compliance (level 3), with the original-authority constraint from ADR-0018 governing how the reference content may be used.

## Incorporation notes
- **Where it would live:** the dispatcher system-prompt builder in `src/core/policy/prompts.ts` — either a compact "How you sound" block in the main prompt plus one standing-rules line, mirroring how the machinery-privacy rule is reinforced across blocks; any channel-level reply mechanics (bubble splitting, threading) belong in the adapter/send path or the send-tool description, not the dispatcher's reasoning prompt.
- **Constraints:** must coexist with the existing machinery-privacy clauses without weakening them; tone rules must not conflict with "silence is a valid outcome" or the lead-with-the-concrete-result rule (length-matching and lead-with-result should work together, not compete); keep the block short — the prompt already carries heavy duty-cycle rules; pronoun care and emoji mirroring depend on the individual user, so phrase them as habits, not hardcoded assumptions.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying of reference prompt text under any circumstances (the tone rules must be written fresh).
- **Effort/risk:** S–M. Small for a tone block in prompts.ts; M if reply-shape mechanics (bubbles, threading) are pushed into the adapter send path, which touches message-splitting behavior and needs offline prompt tests updated.
- **Key reference anchors:**
  - the reference tree's `source/host/runner/system-prompt.ts` — its tone section (line 113) and its reply-length-and-shape section (line 122); threaded-reply and decision-widget etiquette elsewhere in the same prompt.
  - the reference tree's `source/packages/agent/prompts/project-prompt.ts` — a secondary prompt asset with related voice content (not yet read in detail; survey before writing).
