# DD-183 — Routines/automations subsystem absent
- **Area:** A22 automation
- **Type:** deliberate-divergence
- **Date:** 2026-09-23

## What the reference does
The reference ships a full routines/automations subsystem — recurring or event-triggered work that the product stores and fires on its own, independent of any user turn.

Its parts, described by role:

- **An automation domain module** owning the concept of a stored automation: identity, name, an intent statement describing what should happen at each fire, an arming flag, and run bookkeeping (`the reference tree's source/host/automations/automation.ts`, `the reference tree's source/host/automations/automation-id.ts`).
- **A fire-condition model** covering both calendar-style recurrence and event listeners, plus a shared schedule-normalization layer used on both sides of the boundary (`the reference tree's source/host/automations/automation-trigger.ts`, `the reference tree's source/shared/automation-schedule.ts`, `the reference tree's source/shared/automations.ts`).
- **A file-backed automation store** — the durable home. Per-agent directory holding one folder per automation, with list/definitions-only listing, create-or-replace, update, remove, enable/disable, and raised-notice bookkeeping, plus a debounced directory watch so external edits are noticed (`the reference tree's source/host/automations/automation-store.ts:52-72`; directory resolution helpers in the same file).
- **An agent-facing state tool** whose state kinds include a routine kind alongside the workflow kind, i.e. CRUD over stored routines from inside a turn — create, update, list, pause/resume, delete — with the input schema enforcing that a schedule and an event trigger are mutually exclusive (`the reference tree's source/host/runner/tools/sand-state-tool.ts:14`, `:138-143`, `:208`, `:235-236`, `:261-267`).
- **Status reminders and routine notices** injected back into the agent's view, so an armed automation can announce itself and warn about stale or misconfigured state (`the reference tree's source/host/automations/automation-status-reminder.ts:18`, `:31`; `the reference tree's source/host/automations/routine-notices.ts:29-40`).
- **Listener integrations** for third-party event sources, so a routine can be fired by an external service rather than by polling (`the reference tree's source/host/automations/listener-integrations.ts`; `the reference tree's source/host/extensions/automations/extension.ts:7`).
- **Command wiring** — a set of workflow commands carrying the automation/workflow management operations (`the reference tree's source/host/extensions/transcript/workflow-commands.ts`, `the reference tree's source/host/extensions/transcript/transcript-manager.ts:161`, `:590-597`), a per-agent session facade exposing automation list/create/update/remove/enable accessors (`the reference tree's source/host/extensions/session/agent-session.ts:211-216`, `:233`), store factories keyed off the agent database path (`the reference tree's source/host/extensions/session/session-store-factories.ts:10`; `the reference tree's source/host/extensions/session/session-materialization.ts:23`, `:71`), and a runner-composition hook that hands the store to the runtime (`the reference tree's source/host/host-runner-composition.ts:274`, `:1687`, `:1938`, `:2594`; `the reference tree's source/host/extensions/transcript/runner-registry.ts:59`).

A separate workflow-automation store area observed during the study was folded into this filing during the dedup pass, since it is the same capability family (a persisted, self-firing work store) reached through the same store-factory hook (`the reference tree's source/host/extensions/session/session-store-factories.ts`, workflow-store factory).

## What the current build does
**Absent.** The build has no routines, no automations, no recurring or calendar scheduling, no external event listeners, and no workflow store of any kind.

The only scheduling-related code in the tree is a one-shot timer hook: an injectable single-shot scheduler used for the access-request approval timeout, so tests can drive expiry manually rather than waiting on wall-clock time (`src/core/access-relay.ts:145-148`, `:193`, `:241`, `:324`; threaded through `src/core/multitask.ts:79-80`, `:352-353`; named in prose at `src/adapter/dispatch-approval.ts:115`). That is a timeout mechanism inside one request flow, not a scheduling subsystem — nothing in it can express recurrence, a stored trigger, or a self-initiated wake.

The closest structural relative the build does have is the **wake bus** (`src/core/wake-bus.ts`), which is deliberately source-agnostic: its wake-source vocabulary already accepts time-based and external-event origins as reserved members even though only user, worker-settlement, worker-access-request, and peer sources actually enqueue wakes today (`src/core/wake-bus.ts:14-30`). That reservation is exactly the design position that "the wake contract should not need to change when routines arrive"; it carries **no scheduling** — no clock, no recurrence, no persisted trigger, no firing. See DD-174 for the wake-kind taxonomy.

## The deviation
The reference treats self-firing stored work as a first-class product feature with its own domain module, durable per-agent store, agent-facing CRUD, reminder injection, and event-listener integrations. The build ships none of it, and has no reserved extension point for a stored-trigger store — only a wake bus whose source enum leaves room for the wake *kind* should such work ever exist.

This is a **ruled exclusion, not an oversight**. It is an explicit item on the recorded exception list, so the gap is intentional and the divergence is deliberate.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 (accepted, position 2 in the authority stack, and the human-ruled master among the ADRs) names this capability in exception **C14**: no org chart, no routines/automations subsystem, no per-agent memory, no group rooms (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:29`). The ruling is decisive and explicit — it uses the word "routines/automations subsystem" verbatim, so this is squarely inside the exception and requires no new judgment. The capability-gaps research register independently reaches a compatible reading: its Gap 4 is framed as a wake-source gap rather than an automation-store gap, notes the reference's automations subsystem (stored automations with triggers, status reminders, external listener integrations, and routine notices) as the reference-side evidence, and recommends only that the wake contract be made source-agnostic now with routines/automations explicitly left to a later phase (`docs/research/prd-vs-reference-capability-gaps.md:42-48`). Research notes are evidence and never rulings, so C14 is what settles it. Nothing in the build's recorded rulings reverses C14, and no PRD amendment (ticket-64 or later) is recorded as reinstating routines.

## Incorporation notes
- **Where it would live:** Nowhere, under C14. If the human ever reverses C14, the natural shape is a sibling of the existing core modules under `src/core/` (a stored-automation domain plus a file-backed store) with its own adapter layer, and it would arrive through the already-reserved `timer` / `external-event` wake sources in `src/core/wake-bus.ts:14-30` rather than by changing the wake contract.
- **Constraints:** C14 forbids the subsystem outright, so any work here needs a dated human reversal of C14 first, not an agent ruling. Independently, the wake bus is the only reserved extension point and it is deliberately source-agnostic — keep it that way, since that reservation is the recorded design decision and is cheap to preserve. No durable per-agent store exists in the build (see the storage-architecture deviation, DD-177), so a store would have to solve persistence rather than reuse one. Scheduling also implies a clock and a firing loop the build does not have; the one-shot timeout hook in the access relay is not a basis for it.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — the ruling is what blocks this, not the code: a reversal of C14 would reopen a whole capability area (domain model, durable store, clock/firing loop, agent-facing CRUD, reminder injection, external listeners) plus the persistence question the build has not yet answered.
