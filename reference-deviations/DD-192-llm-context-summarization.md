# DD-192 — LLM-driven context summarization (nine-section prompt with fallback)
- **Area:** A24 context management
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference owns conversation compaction end to end. Its agent-summarization package holds a single large handler (about 1300 lines) that rebuilds a conversation's context by asking a model for a structured summary and, when that path cannot complete, falls back to a purely deterministic reduction.

The model path: the handler composes a summary request from the transcript and sends it with a system-role instruction, a fixed marker string prefixed to any prior summary, and a note attached to a preserved recent image. The request body is a worked instruction set — an analysis pass over the conversation, then an explicit list of **nine required sections** covering, in category terms: the user's stated intent; the technical concepts in play; the files and code regions touched; errors and their fixes; problems solved and open; every non-tool user message; pending tasks; the work in progress at the cut point; and an optional next step, with a worked output example following the list. The request is budgeted to roughly 3.2 million characters, with a separate byte ceiling and a floor below which truncation is refused. The call is wrapped in a retry loop of up to 3 attempts, set by a named retry-count constant, each attempt narrowing the prompt budget on failure, and it distinguishes per-attempt counters from per-try success/failure counters in telemetry.

The deterministic path: when the model path fails, a fallback builder takes a fixed ratio of the window — 2% by default — subject to a 50,000-character floor, so the kept tail never collapses to nothing and never exceeds a 3.2-million-character ceiling. Summaries are **marked distinctly** so downstream consumers can tell them apart from ordinary turns: a bracketed prefix on the previous-summary text and a note on the retained image both exist as named constants. Adjacent modules in the same package handle prompt truncation, message preparation, token estimation, error classification, durable blocks, skill persistence, and background summarization; provider-specific compaction handlers also exist for two major vendors.

## What the current build does
**Absent.** The build does not summarize conversation context, and has no prompt for doing so — `src/core/policy/prompts.ts` composes dispatcher policy, standing rules, wake instructions, access policy, and peer-wake instructions only; `src/worker/prompt.ts` composes the worker contract only. Neither contains a summarization request, a retry loop, a token/window budget, or a fallback reducer.

What the build *does* have in the same area:
- **A system-position contract for the worker.** `src/worker/prompt.ts` documents that the worker contract is delivered at a system position — the adapter passes it as the spawn request's persona, which the host renders into a system-prompt section that is recomputed every turn. The file's own header states the consequence: the contract *survives compaction by construction* and is restated after every steer without the build appending anything to steer messages. The register row behind this is **D-1** (`docs/research/dsh-core-loop-deviations.md:30`), which recorded the opposite state — the contract concatenated into the child's first user turn rather than a system position — and is marked removed; D-2 (line 31) dissolves with it. So the build's compaction-survival claim is a *contract-placement* claim, not a compaction mechanism: it governs whether the worker contract outlives compaction, not how the conversation is compacted.
- **Inline clamping of what the build delivers.** `src/core/report-clamp.ts` bounds worker report bodies at 4000 characters, error bodies at 1200, check-row activity lines at 200, and the roster's recent-result excerpt at 300, with a 20-row bound on check-roster rows before head/tail folding (a row count, not a character clamp). It carries deterministic substitution paths — an empty-report placeholder, an aborted-report body, and a truncation marker carrying the shown/total counts and an optional transcript pointer — and `formatWakeReportBody` routes by settle status. The register's A-7 row is carried as ADR-0018's exception 10 (**D21**, `docs/adr/0018-imitate-reference-in-entirety-exception-list.md:32`), and the ADR's Consequences records that mapping (`:47`). The module's own header attributes a re-tune to a report-clamp ticket (ticket number pending).

## The deviation
The reference compacts a conversation with a model, under a structured nine-section request, a large character budget, a bounded retry loop, and a deterministic ratio-plus-floor fallback; and it marks summaries so they cannot be read as ordinary content. The build compacts nothing: it is a plugin inside dsh, the host owns the conversation and its compaction, and the plugin never sees or writes the compaction prompt. The build's substitutes are of a different kind — a contract placed where compaction cannot erase it, and hard clamps on the text the build itself hands back into the dispatcher's context.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 is the master rule — imitate the reference in its entirety except the enumerated exception list — and that list (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:19-42`) is exhaustive and says nothing about conversation summarization or compaction, so no recorded ruling directly covers this mechanism; the nearest recorded ruling is exception 17 (**U-F**, `:39`), which rules that the build's context hygiene is *clamping inline* rather than spilling large outputs to storage with prompt-side references, and exception 10 (**D21**, `:32`), which approves the clamp bounds themselves. The mechanism is therefore not a candidate for incorporation on its own merits: the host owns the conversation and its compaction, and a plugin that reached into the compaction prompt would be doing the host's job — the same shape as the register's `approved-by-necessity` label, where the reference behaviour is unreachable on dsh. The build's own contract for surviving compaction is its substitute and it is already in place: D-1's fix puts the worker contract in a system-prompt section recomputed every turn, so `src/worker/prompt.ts`'s survival-by-construction claim is the honest analogue of "what must persist across a compaction event." Two practices in the reference do have live equivalents the build already carries — a deterministic path when the model cannot be relied on (the clamp module's placeholders and truncation marker, which are pure functions, never model calls) and distinct marking of derived text so it is never mistaken for ordinary content (the truncation marker; the stable section headings in `src/core/policy/prompts.ts`, including the peer-wake headings that exist precisely so a hidden turn is never read as the user's). If the team ever wanted a register item here, it would be a new one requiring a human ruling, since nothing on ADR-0018's list covers it.

## Incorporation notes
- **Where it would live:** Nowhere in this build. If a summary-survival guarantee were ever wanted, the only build-side places to put it are the contract text (`src/worker/prompt.ts`) and the clamp module (`src/core/report-clamp.ts`) — not a new summarization subsystem, which would be a host concern.
- **Constraints:** The build is a plugin inside dsh; the host owns the conversation, its window, and its compaction, so the build has no way to influence compaction except the position and wording of its own injected sections. Any build-side work here would be a claim about survival, not a mechanism — and such a claim would need to be tested against real host compaction behaviour, not asserted.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — no implementation is proposed; the surviving analogues (deterministic clamp substitutions, distinct marking) already exist, so the item closes as a documented absence.
