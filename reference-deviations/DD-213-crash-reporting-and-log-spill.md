# DD-213 — Crash/error reporting, unclean-exit detection, and structured log spill
- **Area:** A27 platform integration
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference owns its application process, so it treats the process itself as an observable subject.

**Crash/error reporting SDK in the main process.** A thin adapter layer (no-op by default, replaced at install) initialises the reporting SDK only when a build-level enable flag is set, with a configured reporting credential plus environment and release tags. On top of the SDK it adds a privacy filter fed by the account's privacy mode, user binding, a conversation tag, an offline transport with spool flush and spool purge, and a bounded ring of recent accepted event ids that the feedback submission cites (validated against an id pattern, capped at five). Identity changes clear the ring and purge the spool. Anchors: the reporting-SDK integration module under the reference tree's `source/electron-main/telemetry/` (vendor-named file, name not reproduced per the copy policy), the reference tree's `source/shared/observability/` privacy-mode/tier module, the reference tree's `source/electron-main/feedback/feedback-report.ts:5-6`. The gate is tiered, not binary: modes that permit training on usage data get full payloads, a no-training mode gets scrubbed payloads, and an unset mode or a no-storage mode falls to the most restrictive tier — the default setting is to disclose the minimum, broadening only when the account allows it. Feedback submission authenticates with the account's access token and refuses when the signed-in identity does not match the submission's account slot.

**Process-level fault observation.** An uncaught-exception / unhandled-rejection reporter with a crash-sequence counter and a 20-event cap (the reference tree's `source/electron-main/telemetry/desktop-process-crash-telemetry.ts:4-28`). A separate subscription to renderer-gone and child-process-gone events, classifying the gone child (window, webview, utility, GPU, zygote, sandbox helper, plugin) and the reason (clean exit, abnormal exit, killed, crashed, OOM, launch failure, integrity failure, unknown), with an exit-code class and an error code only for the abnormal cases (the reference tree's `source/electron-main/telemetry/renderer-lifecycle-telemetry.ts:4-41`). Window unresponsive/responsive events, the recovery carrying the unresponsive duration (`:42-46`).

**Structured log spill to disk.** Records are written to a spill file with three independent caps — 1 MiB of bytes, 18 hours of age, 1000 entries — and five named drop reasons, each carrying observed and acknowledged-through counters; eviction past the entry or byte cap is itself accounted as overflow (the reference tree's `source/electron-main/telemetry/desktop-structured-log-spill.ts:6-10, 30, 48-51`). The spill file name is versioned.

**Unclean-exit detection.** A session-marker file holds version, pid, app version, start and last-alive timestamps, and a crash-seen flag. A 60-second heartbeat rewrites the alive timestamp. On the next launch the prior marker is parsed and validated, and if the recorded pid is not alive a settlement is decided: a marker older than a 30-day orphan bound is reported as orphaned, otherwise as an unclean exit, with the prior uptime bucketed, whether the version matched, whether a crash had been seen, and the prior start time; the unclean case also carries an error code and a warn level. A clean settle on session end stops the heartbeat and removes the marker; malformed markers are removed and reported as an edge failure (the reference tree's `source/electron-main/telemetry/desktop-unclean-exit-telemetry.ts:6-32, 58-81`).

**Taxonomy and lifecycle telemetry.** Eight bounded desktop error codes, each with a retryable flag and a fixed payload field list, with tag values pattern-fenced to a bounded shape (the reference tree's `source/electron-main/telemetry/desktop-error-tags.ts:1-26`). A startup-phase tracker with a 120-second stuck threshold reporting start / stuck / ready / failed per phase (the reference tree's `source/electron-main/telemetry/desktop-startup-telemetry.ts:4, 12-52`). Lifecycle families with a pre-attach buffer of 100 records so early events are not lost before the reporter attaches (the reference tree's `source/electron-main/telemetry/desktop-lifecycle-telemetry.ts:1-11`).

## What the current build does
Absent. No reporting SDK, no crash handler, no structured log sink, no session marker. The only diagnostic output in the entire build is a single console warning in the client bundle (`src/client/index.ts:848`), the command-egress failure notice — deliberately a console line, not a surface. Nothing under `src/` writes a diagnostic record to disk, counts a dropped record, or subscribes to a process-level fault event.

**Not reachable.** The plugin is loaded inside a host process it does not own: without owning a process it cannot observe crashes, unclean exits, or renderer unresponsiveness. And the host interface it consumes (`src/core/dsh-host.ts:9`, the `DshHost` interface) has no logging or telemetry interface — the boundary exposes spawn, interrupt, send, settle/step subscriptions, wake, and access requests, so a plugin-side sink would have nothing host-side to feed it.

The recovery/projection family (session maintenance, DB recovery, summaries, roster projection) is separately filed as DD-176 — cross-referenced here, not duplicated.

## The deviation
The reference area splits into two halves with different reachability.

**The process-observing half requires a process we do not own.** Installing a reporting SDK in the main process, catching uncaught exceptions, subscribing to renderer-gone / child-process-gone / unresponsive, and startup-phase telemetry all presuppose an application shell of our own. ADR-0020 records that shell as a rejected option: "Native/Electron desktop shell — PRD non-goal ...; no evidenced seam; excluded without further study" (`docs/adr/0020-wrapper-shell-vehicle-own-frame-over-shipped-runtime-draft-nonhuman-approved.md:28`; status at line 3: draft (non-human-approved), shell choice superseded 2026-09-20 by ADR-0021). The PRD non-goal it cites is the binary/UI-parity line at `PRD-dsh-multitask-dispatcher.md:38`. ADR-0021 (accepted, human-ruled 2026-09-20) keeps stock dsh as the primary UI with the dispatcher in a separate floating window, so no shell arrives by that route either. Two further recorded lines bear on the reporting half specifically: outbound diagnostics conflict with the PRD's local-first line (`PRD-dsh-multitask-dispatcher.md:31`), and the privacy filter that would govern them sits on ADR-0018's exception list — U-A excludes "privacy/account gates" (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:34`).

**Two leftover pieces do not require a shell.**

(a) *A bounded structured diagnostic sink with caps and drop counters.* A plugin can write records into its own storage domain, so the mechanism is available; what is missing is a source. The host boundary exposes no log or telemetry interface (`src/core/dsh-host.ts:9`), so such a sink could only record the plugin's own events, never the host's. Note that ADR-0018's U-F exception does not cover this: U-F is about clamping large tool outputs inline rather than spilling them to storage with prompt-side references (a different subsystem in the reference, the reference tree's `source/host/runner/large-output-spill.ts`), not about a diagnostic record file.

(b) *An unclean-exit marker.* Compare honestly against the build's durability layer, because the two are structurally adjacent and the difference is the whole point. `src/core/durability.ts` writes a per-worker marker (ADR-0006) at spawn — status snapshot, transcript pointer, todo id, redrive attempts, start and update timestamps — and deletes it once the obligation closes; the adapter backs it with a host storage domain keyed by worker id (`src/adapter/durable-marker.ts:27-28, 98-147`). On rebuild, markers still in a live status become unknown-state, and the restart notice tells the dispatcher what was in flight before the restart (`src/adapter/restart-notice.ts:1-23`).

So what does the durability layer actually answer? It answers *per-worker fate*: which workers were running and whose outcome we must state as unknown. It does **not** answer *whether the previous run ended cleanly*. There is no process-level marker, no recorded pid, no heartbeat, no clean-stop settlement, and no way to distinguish "the process died" from "the process is still running and the marker is merely stale". A marker left in a live status means "fate unknown" — it is not evidence that the previous run crashed, and a marker whose obligation closed cleanly is indistinguishable from one abandoned by a crash if the write itself never landed. A grep of `src/` for heartbeat / clean-exit / unclean-exit / session-marker returns only comments about the presence mirror channel lacking a heartbeat — a config-channel staleness concern, not process liveness. The build's nearest neighbours are worker-level, not process-level: D22's bounded worker-liveness signal (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:33`) notices a stuck *worker*, and DD-173's restart-replay rules govern what a restart does with records, not whether the restart was a crash. The gap is therefore real, and it is small: the durability layer supplies the *consequence* (unknown-state workers, honestly reported) without the *cause* (an unclean previous run, distinguishable from a clean stop).

## Verdict: DO-NOT-INCORPORATE
The process-observing half is excluded by recorded ruling: ADR-0020 rejects the native/Electron shell as a PRD non-goal (`docs/adr/0020-wrapper-shell-vehicle-own-frame-over-shipped-runtime-draft-nonhuman-approved.md:28`, citing `PRD-dsh-multitask-dispatcher.md:38`), and ADR-0021 (accepted, human-ruled) keeps stock dsh primary with the dispatcher in a floating window, so no shell arrives that way either. ADR-0018's exception list does not name crash reporting or telemetry, but it does exclude the privacy/account gates that would govern outbound reporting (U-A, line 34), and the PRD's local-first line (`:31`) cuts against shipping diagnostics off the machine — so the reporting half is excluded on two separate grounds without our own process to observe. On the two leftover pieces, no recorded ruling covers them: there is no ADR or PRD line that rules on a bounded diagnostic sink or a process-liveness marker (the PRD's only telemetry item is an optional product-metric one — dispatch/steer counts, time-to-first-reply — carrying a no-prompt-text constraint, `PRD-dsh-multitask-dispatcher.md:358` — and the register's delivery-path telemetry row was removed 2026-09-18, `docs/research/dsh-core-loop-deviations.md:35`). The unclean-exit gap is a genuine uncovered gap, but it is small, the durability layer already answers the question that matters in daily operation, and that does not change the verdict.

## Incorporation notes
- **Where it would live:** The leftover pieces only — a process-level marker as a second table in the existing marker domain (`src/adapter/durable-marker.ts`, `MARKER_DOMAIN_NAME`), with its parse/decide/settle logic alongside `src/core/durability.ts`; any bounded diagnostic sink over the same domain. The reporting-SDK half has no place to live: it would need a process the plugin does not own, plus a log/telemetry interface on `src/core/dsh-host.ts:9` that does not exist.
- **Constraints:** ADR-0006 marker discipline (minimum-to-reconstruct; no second database — A5) applies to any new marker, and a process marker must survive the host's own storage lifecycle to be worth writing. A clean-stop settle needs a hook the host boundary does not currently expose. ADR-0018 U-A means no account-privacy gate exists to govern a reporting feature, and the PRD's local-first line bounds where anything may be sent. Copy policy B9 applies to every string.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — both leftover pieces are small and reuse the existing marker store; the shell-dependent half is excluded and not costed.
- **Key reference anchors:** the reference tree's `source/electron-main/telemetry/desktop-structured-log-spill.ts:6-10, 30, 48-51` (caps + drop counters); the reference tree's `source/electron-main/telemetry/desktop-unclean-exit-telemetry.ts:6-32, 58-81` (marker, heartbeat, settlement); the reference tree's `source/electron-main/telemetry/renderer-lifecycle-telemetry.ts:4-46` (gone/unresponsive); the reference tree's `source/electron-main/telemetry/desktop-process-crash-telemetry.ts:4-28`; the reference tree's `source/electron-main/telemetry/desktop-error-tags.ts:1-26`; the reference tree's `source/electron-main/telemetry/desktop-startup-telemetry.ts:4, 12-52`; the reference tree's `source/electron-main/telemetry/desktop-lifecycle-telemetry.ts:1-11`; the reference tree's `source/electron-main/feedback/feedback-report.ts:5-6`; the reporting-SDK integration module and the shared privacy-mode/tier module (vendor-named paths under the reference tree's `source/electron-main/telemetry/` and the reference tree's `source/shared/observability/`, not reproduced).
