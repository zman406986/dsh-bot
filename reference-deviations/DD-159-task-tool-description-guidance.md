# DD-159 — Task tool description: guidance depth and when-not-to-use
- **Area:** A19 tool surface
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference assembles the task tool's model-facing description from a dedicated builder function (roughly lines 195-236 of its schema module) rather than from a literal. The builder takes an options bag and emits conditional content, so what the model reads depends on which flags are on. The description's content categories are:

- A lead paragraph saying the tool launches a specialized autonomous subprocess for complex multi-step work, and that a type parameter must be supplied.
- A return-message contract line: the agent finishes with a single message back, so the caller should specify exactly what to return.
- A concurrency line: launch multiple agents at once when work is parallelizable, using one message carrying several tool uses.
- A result-visibility statement whose wording is chosen by notification flags. In the base case it tells the caller the agent's returned result is NOT visible to the user, and that the caller must send its own concise text summary to show the user anything. With background-notification hooks on, it instead says completion messages already carry a user-visible summary portion and the caller should not restate a lone background agent's result, reserving a response for when the user asks, when several results need synthesis, or when a blocker needs parent action.
- A when-not-to-use-this-tool section: simple single- or few-step work that one agent can do with parallel or sequential tools should be done directly; plus a per-tool example list steering specific read/search lookups to the dedicated read and glob tools instead of this one, each example naming the alternative tool.
- A proactive/explore recommendation (only when the explore subagent and its flag are present): when broadly gathering context for a large task, prefer this tool with the explore type; for a narrow specific question, do not; followed by three worked user-request/assistant-action examples contrasting a needle query, an MCP call, and a broad structure question, then a parallel-exploration line.
- A resume paragraph whose wording varies by client-side/async mode and interrupt flag.
- General usage bullets: always include a short 3-5 word description; on non-resume invocation each call starts fresh, so give a detailed self-contained task description; the subagent cannot see the user's message or prior assistant steps; the subagent's outputs should generally be trusted; and act on any proactive-use note in a subagent's own description.

All of this is guidance for the model attached to a tool definition, generated by a builder with conditional branches and per-subagent-type interpolation.

## What the current build does
The build's spawn tool carries a static description string, not a builder. `TOOL_DESCRIPTIONS[SPAWN_WORKER_TOOL]` in `src/core/policy/prompts.ts:29` is a single three-sentence literal: start a background worker for one stream; give a complete standalone prompt because the worker cannot see the conversation; the call returns immediately and the worker's final response arrives later, so do not wait or poll; one live worker per stream key; write a todo entry first when the work is user-visible. `src/core/tools.ts` (spawn definition near line 263) binds that constant directly as the tool's `description` and attaches the parameter schema; the per-parameter descriptions live at `src/core/tools.ts:205-229` and, like the tool description, are static literals with no conditional branches.

The build does carry delegation guidance elsewhere: the dispatcher policy section (`buildDispatcherPolicySection`) supplies a when-to-work-yourself-vs-hand-off rule, a parallel-streams rule, a return-message contract for workers, a "do not poll in a loop" rule, and a "workers cannot talk to the user; only you deliver" line; `buildStandingRulesBlock` carries the short recurring version. That is the slot DD-153 examined. It is a separate place from the tool definition itself.

Result visibility on the build side is stated where it belongs for this architecture. The worker contract at `src/worker/prompt.ts:77` (the "Final answer" section) tells the worker its final answer is the stream's report and is delivered to the parent — and often the user — essentially verbatim, so lead with the outcome. `src/worker/prompt.ts:92` tells the worker it cannot message the user and that only the dispatcher delivers. The tool description itself does not restate a visibility rule; it only says the worker cannot see the conversation.

This is the opposite of the reference's default framing, and not an inversion of the build's own text: the reference's default description tells the calling agent the subagent result is invisible to the user and that the caller must summarize it. The build's architecture has the worker produce the text that reaches the user verbatim, with the dispatcher's `deliver_result` tool as the delivery path and the dispatcher policy forbidding the machinery from being named. The two statements are about different hops (reference: subagent result → parent → user; build: worker final answer → parent stream → user). The brief's suggestion that `prompt.ts:77` is "inverted" relative to the reference does not hold: line 77 is a worker-facing instruction, not a caller-facing tool description, and it is consistent with the build's own delivery model.
## The deviation
Both sides answer the same question — how much instructive guidance to hang on the delegation tool's own definition — with different structural choices and different content coverage.

Structural: the reference's description is built by a function with flags and interpolated tool names and subagent types, so the text varies by deployment. The build's is a fixed string. That is a build-side simplification, not a gap: the build has no cloud/self-hosted/machine placement options, no per-type subagent catalog, and no notification-hint flag to branch on, so a builder would have nothing to vary over. The deviation is therefore not "builder vs literal" but "which content categories are present."
Coverage: the reference includes a dedicated negative section (when NOT to use the tool, with named-alternative examples) and a proactive-recommendation-with-examples block; the build includes neither on the tool definition. The build does include an equivalent negative rule, but only in the policy section and standing rules ("Do the conversational and one-step parts yourself. Hand non-trivial multi-step work to a worker"; "Non-trivial multi-step work → spawn"), not attached to the tool and not as worked examples. The build's tool description does cover the return-later / do-not-poll instruction, the self-contained-prompt requirement, the one-live-worker-per-key rule, and the todo-before-spawn preference — that is real overlap with the reference's usage-notes content.

Result visibility: both sides state it, but at different hops and from different speakers, as described above. This is a genuine behavioral delta only in the sense that the reference's default tells the caller the result is hidden and must be summarized while the build tells the worker its text reaches the user verbatim. That difference follows from a delivery-model choice, not from a missing sentence.

## Verdict: ADAPT
No recorded ruling covers this particular deviation; I checked the ADR index and ticket record for a decision on tool-description content and found none, so the analysis below is my reading, not a ruled outcome. The positive teaching (parallel launch, self-contained prompts, return-later) is already present in the build, and the delegation-discipline core it belongs to is PRD-required and already expressed in the policy section and standing rules (DD-153's verdict relied on that), so importing the full reference description would duplicate guidance the build already carries in a better-placed spot. What is genuinely thin on the build side is the negative guidance — an explicit "do not delegate this shape" statement with concrete alternative-tool examples — attached to the tool itself, and the build's positive statement of result visibility at the caller hop is absent from the tool description even though the architecture makes it a real obligation (the dispatcher must deliver; the worker's text is the report). ADAPT: fold a short negative-guidance clause into the existing static spawn description, and decide separately whether the caller-facing result-visibility obligation belongs on the tool or stays in the policy section. Do not move the worker-facing line at `src/worker/prompt.ts:77`; it is correct for its hop and rewording it would break the build's delivery model.
