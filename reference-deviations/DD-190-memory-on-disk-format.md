# DD-190 — Memory on-disk format (profile, monthly log, ids, tombstones, shards)
- **Area:** A23 memory
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference stores an agent's durable memory as plain markdown files in a memory folder, with no database behind them. DD-188 covers the memory feature itself; this filing covers only the format those files take on disk, described by role.

Its parts, described by role:

- **A profile document with a human-readable section title.** The profile is a single markdown file whose first content is a top-level section heading written for the user to read, followed by an explanatory legend held in an HTML comment that states the line shape the entries follow (`the reference tree's source/host/extensions/memory/memory-service.ts:16`). The header is what a fresh store is seeded with, and what the store is reset back to when memories are cleared (`:94`, `:129`).
- **A monthly log directory of dated entries.** The memory folder holds a log subdirectory, and the store keeps one markdown file per calendar month, selected by the year-month prefix of the entry's timestamp (`the reference tree's memory-service.ts:13`, `:70`). Both the profile and the logs share a single entry convention: each entry is one bullet line that begins with a parenthesized ISO date and then the fact text, matched by a strict line pattern on read and produced by a single serializer on write (`:18`, `:33`). A malformed or non-matching line is simply skipped, not an error (`:36-40`).
- **A per-entry length cap of 500 characters.** The cap is recorded in the synthesis service — stated in its instructions to the model and enforced as a validation bound on every proposed change's content (`the reference tree's source/host/extensions/memory/memory-synthesis-service.ts:85`, `:114`).
- **Short stable ids derived from content.** Each fact's id is a hash of its normalized content, truncated to 16 hex characters, so the same fact always yields the same id and two agents recording the same text agree on it without coordination (`the reference tree's memory-service.ts:32`; the normalization and dedupe key it hashes live in `the reference tree's source/host/runner/sand-memory.ts:59`). The id is what the origin and tombstone marker filenames are built from (`the reference tree's memory-service.ts:71-72`).
- **Tombstones instead of destructive deletes.** Deleting a fact removes its line from the file it lives in and writes a zero-byte marker named by the content-derived id into a tombstones subdirectory of a hidden metadata directory beside the logs (`the reference tree's memory-service.ts:63`, `:72`, `:78-79`, `:124`). The marker is the record that a human removed this fact, so synthesis will not re-add it; re-adding the same content explicitly clears the tombstone rather than duplicating the entry (`:94-97`). The same metadata directory also holds per-fact origin markers distinguishing explicitly written facts from synthesized ones (`:71`, `:78`).
- **User-memory shards annotated with their contributing assistant.** User-scope memory is sharded one folder per assistant under a user-level memory area, and recall walks the shard folders and stamps each returned record with the contributing assistant's id and resolved name (`the reference tree's memory-service.ts:134-135`, `:146`). The line format has a provenance variant for this: the same dated bullet with a bracketed attribution clause inserted before the fact text (`the reference tree's sand-memory.ts:254`).
- **Project shards.** Project-scope memory is sharded the same way under each project's own memory area, one folder per assistant, and recall sweeps the projects the agent is a member of and tags each record with its project and contributing assistant (`the reference tree's memory-service.ts:138-139`, `:151`).

## What the current build does
**Absent.** The build writes no memory files and has no memory folder, no entry line format, no content-derived ids, and no tombstones, because it has no memory feature at all (DD-188).

The only on-disk artifacts the build owns are host-managed durability markers — worker records holding just enough to rebuild state, which ADR-0006 declares durable, written through the host's storage domain rather than as files the build formats itself (`src/core/durability.ts:9`, `:36`, `:80`, `:100`; the domain and table naming and the storage-domain adapter live in `src/adapter/durable-marker.ts:27-28`, `:88`, `:98`). Those markers are dispatcher bookkeeping keyed by worker id, not user-facing prose, and the build does not define a readable file layout of its own. The wider persistence picture is the storage family: DD-177 (storage architecture) and DD-182 (JSON config stores).

## The deviation
The reference treats memory as a durable, human-readable, plain-text artifact and makes a set of format-level decisions about it: a profile document with a user-facing heading, append-only monthly log files, one dated bullet per fact, a 500-character per-entry cap, 16-hex-character content-derived ids, deletion by tombstone rather than erasure, and per-assistant sharding at both user and project scope. The build ships no such format and no memory files to put in it, so the whole feature is absent rather than merely built differently.

The nuance worth stating plainly: this format is the storage half of the per-agent memory feature that C14 rules out (DD-188). Its ideas are general patterns — append-only monthly logs, short stable content-addressed ids, tombstones in place of destructive deletes — and each could serve a system other than memory. But in the reference they exist in service of a ruled-out feature, and the build has no store for them to describe, so there is nothing here they would format.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 (accepted, position 2 in the authority stack, and the human-ruled master among the ADRs) names per-agent memory explicitly in exception C14 — no org chart, no routines/automations subsystem, no per-agent memory, no group rooms (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:29`) — and this filing is the on-disk format of that ruled-out feature, not a separable utility: the files exist to hold the facts the ruled-out feature would maintain. C14 covers it, so the format falls with the feature and the ruling is decisive rather than an open judgment. The sibling feature filing reaches the same verdict (DD-188), and no recorded ruling reverses C14 or reinstates memory. The format's individual patterns, abstracted away from memory, are not addressed by any recorded ruling and are left for the human to decide rather than folded into this verdict.

## Incorporation notes
- **Where it would live:** Nowhere, under C14. If the human ever reverses C14, the format would need a home on the build's persistence side — most naturally a core-side module under `src/core/` defining the layout and the entry codec, with the actual storage question deferred to the storage-architecture deviation, DD-177, since the build's only durable storage today is the host-managed marker domain (ADR-0006) and not a file tree the build owns.
- **Constraints:** C14 forbids the feature outright, so any work here needs a dated human reversal of C14 first, not an agent ruling. If it were ever reopened: the build owns no user-facing on-disk file format, no directory the build creates and formats itself, and no reader for such files — a format module would be durable storage nothing reads, and it would inherit every constraint recorded against the memory feature in DD-188. Content-derived ids also assume a content-normalization rule and a dedupe key, which the build has no equivalent of.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the format itself is small and mechanical, but the risk is inverted: adopting it without the feature creates a durable file tree nothing consumes, and the real cost is the ruled-out feature it serves, so the ruling is what blocks this rather than the code.
