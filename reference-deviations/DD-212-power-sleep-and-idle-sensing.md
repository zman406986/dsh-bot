# DD-212 — Power, sleep/wake, and idle sensing as platform inputs
- **Area:** A27 platform integration
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference injects two main-process platform APIs — the OS power monitor and the network-status API — into a desktop-connectivity module that answers exactly two questions: whether the machine is online, and whether it woke from sleep recently. The module is tiny and pure: a factory takes an online predicate, a subscription for a wake-from-sleep event, and a monotonic clock; the wake event stamps a timestamp; the "recently woke" answer is that stamp falling inside a fixed one-minute window (the reference tree's `source/electron-main/coordinator/desktop-connectivity.ts`, lines 1–7). A second factory binds the real Electron ports — the network-status API for online, the power monitor's wake event for the subscription — and defaults the clock to the performance clock (same file, lines 8–10). A third function reduces the whole module to two string-valued stamps, one per question, for attaching to outbound telemetry (same file, line 11). It is constructed once in the production coordinator wiring (the reference tree's `source/electron-main/coordinator/production-provider.ts`, lines 45 and 382).

Those stamps and the module itself are used as a **disconnect-cause attribution**. The coordinator's telemetry sink derives a cause label for a disconnect from a short ordered chain: the app is quitting; else the client is offline (read straight off the module); else the host is mid-rebuild (restarting); else, failing a recent recorded failure, unknown; else the failure's endpoint classification separates a backend outage from a host outage (the reference tree's `source/electron-main/coordinator/coordinator-telemetry.ts`, line 7). The same file copies the two connectivity stamps into the reachability report, the transport-stream-down report, and the agents-unreachable report (line 8), so every one of those records can be read afterwards as "was this a sleeping laptop, a restarting host, or a down backend?".

The same power monitor also supplies the **user-is-away** signals for a separate consumer: an unattended relaunch that applies an already-staged update. The idle-signal factory exposes screen-lock state (read from the monitor's idle-state query), system idle seconds (the monitor's idle-time query), and a screensaver-active probe; it also carries a host-idle probe supplied by the caller (the reference tree's `source/electron-main/update/idle-relaunch-signals.ts`, line 5). On macOS the screensaver answer comes from a short-timeout process-table probe for either of two known screensaver process names, and returns false unconditionally on other platforms (same file, lines 2 and 4). The gate is a conjunction: opted in, gate enabled, update staged, the user away, and the host confirmed idle — where "user away" is defined as screen locked or screensaver running **and** idle seconds at or past a threshold whose default is ten minutes (the reference tree's `source/electron-main/update/safe-relaunch-gate.ts`, lines 3–5). The apply step re-reads the signals, re-checks that the update is still staged, and only then quits and installs, logging the reason when it does (the reference tree's `source/electron-main/update/idle-relaunch-apply.ts`, line 3). The wiring injects the real power monitor and derives the host-idle probe from host status, mapping busy to busy and a failed probe to unavailable rather than to idle (the reference tree's `source/electron-main/update/update-wiring.ts`, lines 4, 10, 22). One startup binding check requires the idle-time function to be present on the injected Electron port (the reference tree's `source/electron-main/production-binding-providers.ts`, line 310).

## What the current build does
Absent. No visibility handling, online/offline handling, or idle handling exists anywhere in `src/` (71 files) or `client/` (1 file): no visibility-change listener, no browser online-flag read, no presence or idle timer, no liveness input of any kind from the platform. Liveness in the build is instead a projection of host-observed session events — `src/core/liveness.ts`, ruled by ADR-0010 — and transport reconnect belongs to the host, not to this plugin.

The mechanism is also not reachable as it stands. The power monitor and the network-status API are main-process-only Electron ports; a Cordis plugin loaded into the dsh host has no connection to them, so a plugin cannot sense OS sleep/wake or idle even if it wanted to. The one consumer of the reference's idle signal — the unattended update relaunch — is updater territory and is not filed here (DD-221).

## The deviation
The reference treats the operating system as a source of two product-relevant facts: whether the user is present, and whether a disconnect was caused by the client rather than the host or the backend. The build treats the platform as opaque and derives presence from core state instead. Neither is an oversight on the build's side: the platform sensing is unreachable from a plugin, and the presence question has a recorded answer that deliberately excludes a platform-derived input.

The honest leftover is narrower than the whole feature. The disconnect-cause attribution — was that a client sleep, a host restart, or a backend outage? — is a genuine diagnostic distinction with product value, and it does not strictly require a native shell: a purely client-side variant could in principle exist. The build's nearest equivalent is its restart-notice plus durability replay (DD-173), which tells the user what happened after the fact but cannot distinguish a sleeping client from a restarting host, because it has no client-side presence input to compare against. That gap is real and is named here as an open point rather than closed.

The substantive analytical point is the second ruling, not the first. The build's liveness stance is a *positive* design position — presence is a projection of core state, with no presence store, no second source of truth, and no new core state (ADR-0010). Importing OS-level idle or sleep sensing would not be filling a hole in that design; it would be adding a *new input* to a system that deliberately derives presence from core state, and would re-open the question ADR-0010 answered. The reference's use of the same signals for an update relaunch also sits in a subsystem the build does not have.

## Verdict: DO-NOT-INCORPORATE
Two recorded rulings cover the mechanism, and they are independent. ADR-0020 (draft, non-human-approved) rejects a native/Electron desktop shell outright, listing it among the rejected shell options as a PRD non-goal — "do not chase Sand/Cursor/Grok Bot binary or UI parity" — with no evidenced connection point and exclusion "without further study" (`docs/adr/0020-wrapper-shell-vehicle-own-frame-over-shipped-runtime-draft-nonhuman-approved.md`, line 28); the power monitor and network-status API are main-process-only, so without that shell the inputs are simply unreachable. ADR-0010 (draft, non-human-approved) independently forecloses the presence half on design grounds: presence is a projection of existing core truth, there is no presence store and no new core state, and a field a surface seems to need but core does not expose is a stop-and-raise for a PRD amendment rather than an invented core state (`docs/adr/0010-dispatcher-presence-is-a-projection-of-core-state-draft-nonhuman-approved.md`, lines 11–16 and 26). Note that both are draft, non-human-approved: they are the highest recorded authority on the question, and no human ruling has been recorded that speaks to it. The one honest leftover — the client-versus-host disconnect attribution — is noted below and left open rather than claimed as covered.

## Incorporation notes
- **Where it would live:** Nothing to add under the current rulings. If ever reversed, the touch points would be the liveness module (`src/core/liveness.ts`), the restart-notice path (`src/adapter/restart-notice.ts`), and a new platform-port connection on the adapter side that does not exist today.
- **Constraints:** Any future design would have to clear ADR-0020's exclusion of the native shell, ADR-0010's projection rule and its no-new-core-state consequence (line 26), and the fact that the platform ports are main-process-only so a plugin cannot reach them without the shell that is excluded. The update-relaunch half is further blocked on DD-221's updater territory.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — not because the work is small but because there is nothing to build: the mechanism is unreachable and both halves are ruled. Any reversal is a ruling change, not an implementation task.
- **Key reference anchors:** the desktop-connectivity module — the two-question contract, the one-minute wake window, the Electron binding, and the two telemetry stamps (the reference tree's `source/electron-main/coordinator/desktop-connectivity.ts`, lines 1–11); its construction in the production coordinator (the reference tree's `source/electron-main/coordinator/production-provider.ts`, lines 45, 382); the disconnect-cause chain and stamp spreading (the reference tree's `source/electron-main/coordinator/coordinator-telemetry.ts`, lines 2, 7, 8); the idle-signal factory — lock state, idle seconds, macOS screensaver process probe with a short timeout, caller-supplied host-idle probe (the reference tree's `source/electron-main/update/idle-relaunch-signals.ts`, lines 2–5); the away-and-idle gate and its ten-minute default threshold (the reference tree's `source/electron-main/update/safe-relaunch-gate.ts`, lines 3–5); the apply step's re-checks and reason log (the reference tree's `source/electron-main/update/idle-relaunch-apply.ts`, line 3); the wiring's injection and its busy/unavailable mapping for a failed host-idle probe (the reference tree's `source/electron-main/update/update-wiring.ts`, lines 4, 10, 22); the startup binding requirement for the idle-time port (the reference tree's `source/electron-main/production-binding-providers.ts`, line 310).
