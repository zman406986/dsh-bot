# DD-184 — Proactive automation stance: proposing routines, cadence policy, self-expiring watches
- **Area:** A22 automation
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference carries prompt text that tells the agent how to treat scheduled work, rendered as one section of the automations system prompt (`the reference tree's source/host/automations/automation.ts:19`, entered through a prompt-node section titled for automation instructions in `the reference tree's source/packages/agent/prompts/user-info-auxiliary-sections.ts:29`). Described by category, never transcribed, that section does four things:

- **A push to propose routines** (`the reference tree's source/host/automations/automation.ts:31`). It instructs the agent to treat routines as the right tool far more often than the agent would reach for them, to prefer creating a routine over doing a repeatable thing once or promising to remember it, and to catch recurring needs the user only implied. It splits on certainty: when the need is unambiguous the agent creates the routine and says so; when it is unsure the routine is wanted, it offers one in a sentence rather than staying silent. This is a behavioural instruction, not a capability — it tells the model to *offer* the subsystem more aggressively.
- **A cadence policy** (`the reference tree's source/host/automations/automation.ts:37`, with the stated-exception rules at `:39`). It fixes a default firing window for scheduled routines rather than leaving the schedule unconstrained: weekdays and daytime hours in the user's zone, with roughly 10pm–7am recorded as quiet hours and the weekend off. It requires both the day-of-week and the hour to be pinned rather than left open, and treats departing from the window as something the agent must name out loud alongside the schedule — so an off-hours routine is a stated choice, not a leftover wildcard. Real user hours, when known from memory or the user's own words, override the assumption.
- **A self-expiry rule for watches** (`the reference tree's source/host/automations/automation.ts:58`). Short-lived, finite, or conditional watches are to be self-expiring by default: a scheduled watch carries a concrete deadline and deletes itself once the condition is reported or the deadline passes; an event-driven watch deletes itself immediately after handling its event. A watch that must vanish on a deadline even if no event arrives is to be built as a scheduled routine rather than a listener, and schedule and trigger are never combined in one routine. Permanence is reserved for work the user explicitly wants ongoing — a digest, a recurring reminder, a standing subscription.
- **An authentication-failure pause** (`the reference tree's source/host/automations/automation.ts:60`). When a routine cannot run because a dependency rejects it for auth, the agent is told to detect a *repeat* of the same failure across runs and, once it is clearly recurring, to pause the routine rather than firing and re-reporting the same error on every trigger, then tell the user what needs reconnecting and resume once it is fixed.

A live status reminder keeps the routine runtime state in view across turns (`the reference tree's source/host/automations/automation.ts:109-110`); that reminder half belongs to the routines subsystem and is filed under DD-183, not here.

## What the current build does
ABSENT. The build has no automation policy text, no cadence policy, no quiet hours, no watches, and no automation status reminder. Searching the build's prompt and policy code for automation, cadence, quiet-hours, self-expiry, recurring, and routine vocabulary returns nothing across `src/core/policy/prompts.ts`, `src/core/policy/assembler.ts`, and `src/core/wake-bus.ts`.

What the build's prompt policy actually contains follows the dispatcher's work, not automation: worker tool names and descriptions (`src/core/policy/prompts.ts:8-27`), dispatcher policy and standing-rules sections (`src/core/policy/prompts.ts:43-49`, builders at `:77`, `:111`), wake-instruction, access, and peer-wake blocks (`src/core/policy/prompts.ts:51-71`, builders at `:124`, `:145`, `:165`), and an assembler that renders a session policy, a per-turn ledger reminder, and wake turns (`src/core/policy/assembler.ts:38`, `:60`, `:91`, `:143`, `:200`). There is no section that speaks about scheduled or recurring work at all.

The build does nothing proactive beyond its own dispatcher reporting — workers settling, access requests, and peer traffic producing wakes. The wake bus does reserve vocabulary for future sources: its source union names `timer` and `external-event` alongside the four that actually fire, documented as accepted so later tickets can enqueue them without changing the contract (`src/core/wake-bus.ts:14-30`). Nothing in the build emits either.

## The deviation
The reference treats scheduled and recurring work as a first-class product feature to sell to the user: prompt text that pushes the agent to propose it, a cadence policy that keeps it inside normal waking hours by default, an expiry rule that keeps watches from accumulating into permanent obligations, and an auth-failure rule that stops a broken routine from becoming a repeated error loop. The build has none of it — no prompt text, no cadence, no expiry rule, no pause-on-auth-failure — because the build has no routines for any of those policies to govern.

The nuance worth recording: the push to propose routines is the behavioural half of the routines subsystem, not an independent feature. It is prompt text whose referent is a set of tool operations the agent can perform — create a routine, read one back, pause it, delete it. In the reference those operations exist (`the reference tree's source/host/runner/tools/sand-state-tool.ts`, cited in DD-183); in the build they do not exist and cannot, under C14. Prompt text telling the agent to propose routines aggressively is therefore only coherent where there is something to propose *into*. The cadence policy and the expiry rule are in the same position: they are constraints on a firing mechanism, and with no firing mechanism they have no subject.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 (accepted, position 2 in the authority stack) names this capability family in exception **C14**: no org chart, no routines/automations subsystem, no per-agent memory, no group rooms (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:29`). C14 names the *subsystem*; the proactive-proposal text, the cadence policy, and the self-expiry rule are prompt text belonging to that subsystem — they are instructions about how to use tooling the exception forbids, so they fail with it rather than surviving as separate policy. The capability-gaps research register independently reaches a compatible reading, framing the reference's automations subsystem as reference-side evidence while leaving routines explicitly to a later phase (`docs/research/prd-vs-reference-capability-gaps.md:42-48`), and the study's prompt inventory records the automation-instructions section as part of the reference's prompt without recommending it (`docs/research/reference-agent-prompt-inventory.md:179`, `:216`). Recorded honestly: C14 does not use the words "propose" or "cadence", so its reach over a pure conversational habit of mentioning that something could be done regularly is not literally stated — but no recorded ruling reopens the subsystem, and the prompt text as the reference writes it depends on creation tooling, so it is excluded together with the subsystem rather than being independently adoptable.

## Incorporation notes
- **Where it would live:** Nowhere, under C14. If the human ever reverses C14, the prompt text belongs as a new section builder in `src/core/policy/prompts.ts` (alongside the existing dispatcher and standing-rules builders) wired through `src/core/policy/assembler.ts`, and the firing side would arrive through the already-reserved `timer` / `external-event` wake sources in `src/core/wake-bus.ts:14-30` rather than by changing the wake contract — the same place to add it that DD-183 records.
- **Constraints:** Any prompt text would have to be re-authored from scratch (ADR-0018 B9), not adapted from the reference's wording. The build's assembler has no automations dependency to inject and no store behind it, so prompt text written today would have the agent offer recurring work the product cannot create, store, or fire — that is the concrete form of the argument above that the two cannot be separated. A cadence policy without a scheduler does nothing, and a self-expiry rule without a watch store has nothing to expire.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S for the prompt text and cadence clause alone (a section builder plus assembler wiring); L if it were built to mean anything, since watches and auth-pause need the store and firing runtime DD-183 rules out. Risk under C14: none, because nothing is built.
- **Key reference anchors:** `the reference tree's source/host/automations/automation.ts:19` (prompt renderer entry), `:31` (instructions to propose routines), `:37` and `:39` (cadence policy and its stated exceptions), `:58` (self-expiring watches), `:60` (auth-failure pause), `:109-110` (status reminder renderers, filed under DD-183); `the reference tree's source/packages/agent/prompts/user-info-auxiliary-sections.ts:29` (section title naming automation instructions).
