# DD-098 — Self-owned multi-section settings modal vs single card in host settings
- **Area:** settings (A12)
- **Type:** deliberate-divergence (the build reuses the host's own settings surface)
- **Date:** 2026-09-23

## What the reference does

The reference ships its own settings surface as a standalone modal overlay rather than living inside any host settings page. Its entrypoint declares a params object whose only field is the target section id (the settings overlay's optional section parameter), so the modal can be opened already navigated to a specific section (`overlay/entrypoint.ts`, which lazily loads the view). The view itself (`overlay/view.tsx`) defines a fixed list of four sections — a general section, a router/model section, a usage-and-billing section (gated behind an experiment/account flag and filtered out when the gate is closed), and an updates section — rendered as a left-hand navigation rail beside a per-section panel body, wrapped in a modal shell that keeps an active-section state and falls back to the first visible section on an unknown id. A toast-notice wrapper (`overlay/notice.tsx`) surrounds the surface. The directory also carries computer-side and desktop-side views under the same overlay (`computer.ts`, `computer-view.tsx`, `computer-view-internals.tsx`, `desktop.ts`, `desktop-preview.tsx`, `desktop-surface.tsx`) — out of scope here; per the intent docs they are noted by path only and excluded from this analysis, as are the supporting `panels.tsx`, `router.ts`, `updates.ts`, `updates-controller.ts`, `model.ts`, `auto-review.tsx`, and `view.css`.

## What the current build does

The build has no overlay at all. It exposes exactly one plugin settings card, registered into the stock dsh Settings page's 插件配置 tab through the keyed `settings.plugin.item` slot (`src/client/settings-card-store.ts:53-82` — the slot constant at line 53 and the registration builder at lines 76-82, keyed on the plugin's locale/settings namespace). The card is a collapsible component whose view models this store computes and whose rendering lives in `src/client/settings-card.tsx`. On the host side, the plugin claims a single settings namespace, `multitask-dispatcher` (`src/adapter/settings-section.ts:50`), inside the stock settings service via `register(ns, schema, { base })` after `ctx.inject(["settings"], …)` (`src/adapter/settings-section.ts:126-142`), so the host serves the namespace the browser card pairs with. The `settings-card-store.ts` header comment states the pairing contract explicitly: the tab renders the intersection of namespaces served by the host and cards registered into the keyed slot, and the slot key is the settings namespace itself — the host half and the browser half never learn more than that one shared string. Reads and writes go through the single `ctx.settingsScope` binding; no second channel is permitted.

## The deviation

The reference treats settings as a first-class, self-owned product surface: a modal with its own navigation, four sections, deep-linkable section routing, and a notification wrapper. The build treats settings as one claim inside the host's existing settings UI: a single collapsible card in the stock 插件配置 tab, paired to the host by one namespace string, with no independent navigation, no modal, no deep links, and no sections. The build's choice is deliberate — it is the one-slot, one-namespace, one-binding approach the `settings-card-store.ts` header documents — and it follows directly from the accepted decision on how the plugin is delivered, rather than being an omission.

## Verdict: DO-NOT-INCORPORATE

ADR-0021 (human-ruled, 2026-09-20) settled how the plugin is delivered: stock dsh stays the primary UI and the dispatcher is an addon whose functions live in the separate floating window (the capsule, per ADR-0022). A self-owned modal overlay would re-create exactly the whole-UI approach ADR-0021 replaced (ADR-0020's root-frame choice) and would cut the settings surface off from the host's plugin-settings contract the build deliberately follows. ADR-0018's exception-list rule likewise favors consuming the host surface through the shipped keyed slot. Nothing in the reference's section modal is needed for PRD behavior; if a future human ruling ever wants a richer surface, that is a new decision about delivery form for the human, not an incorporation.

## Incorporation notes
- **Where it would live:** nowhere under the current ruling; a hypothetical revisit would be a client-side overlay under `src/client/` paired with a new host registration strategy in `src/adapter/` — and would require a human ruling on the plugin's delivery form first.
- **Constraints:** must keep the one-claim-per-namespace rule (`src/adapter/settings-section.ts:41-42` — a second claim throws); must not introduce a second settings write channel (the store header forbids anything but the `ctx.settingsScope` binding); stock dsh remains the primary UI per ADR-0021, with dispatcher-only surfaces confined to the floating window.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M if ever built (modal shell, section routing, notice wrapper, plus a host-side surface decision); risk is architectural, not size — it contradicts an accepted human-ruled ADR, so the real cost is reversing that decision.
- **Key reference anchors:** build `src/client/settings-card-store.ts` header comment (host tab pairs served namespaces with browser cards via the keyed slot); `docs/adr/README.md` rows for ADR-0021 (addon coexistence) and ADR-0022 (capsule revival) and the 2026-09-20 addon-coexistence note; reference `overlay/view.tsx` section list and `overlay/entrypoint.ts` section param.
