# DD-041 — KaTeX math rendering vs literal delimiters
- **Area:** rich rendering (A5)
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference typesets assistant math in two places. Block level: the transcript parser (the reference tree's `frontend/src/recovered/features/conversation/workspace/transcript.tsx`) recognizes fenced display-math blocks (`$$…$$` per the A5 enumeration) as their own block kind (kind union at line 236, block collected at line 323) and renders them through an assistant-math component in display mode (line 398). Inline level: the inline renderer emits the same component per `\(...\)` span (line 255); the span splitting lives in a dedicated inline-math splitter (the reference tree's `math.tsx` lines 54–66), which matches single-line spans only and deliberately leaves single-dollar text math alone, noting the shipped remark-math config disables it. The component (the reference tree's `math.tsx` lines 88–103) first shows the raw expression in a `<code>` placeholder, then lazily imports a vendored prebuilt KaTeX asset — a hashed asset path (line 5, dynamic import with a vite-ignore marker at line 19); the reference's root `package.json` pins a KaTeX dependency version — and calls its `renderToString`. Rendering falls back in three steps (a markup-rendering helper, lines 33–45): strict `throwOnError: true` first; on failure, a retry with `strict: "ignore", throwOnError: false`; on a second failure, a red error-styled span carrying the escaped expression and error text. The result is injected as HTML after unwrapping the outer KaTeX span; if the runtime asset fails to load at all, the component keeps showing the raw-expression placeholder.

## What the current build does
No math handling exists. A grep for "katex" across `src/`, `client/`, and `package.json` returns zero matches — the build has no such dependency and no math scanner. The conversation pane (`src/client/conversation.tsx`, ticket 80, part 4 of ADR-0020's wrapper plan) renders turn text as plain pre-wrapped spans per DD-039/DD-040, so `$$…$$` fences and `\(...\)` spans surface as literal delimiter text inside the model's prose.

## The deviation
Assistant messages containing math display as raw TeX with visible `$`/`\(` delimiters in the build, versus typeset formulas in the reference. This is a missing feature in the A5 rich-rendering area, closely related to DD-039/DD-040 — and the reference's own prompt contract treats it as part of the ordinary reply format (inventory row 7 lists a "markdown/KaTeX/mermaid rendering contract"), so model output will routinely carry these delimiters. Unlike those related items, though, the gap cannot be closed by a hand-written scanner: TeX typesetting is exactly the kind of capability that only exists as a large third-party library, so incorporation is a dependency decision, not just new build code.

## Verdict: ASK-HUMAN
ADR-0018 (the top human ruling) directs imitation of the reference in its entirety against a closed exception list, nothing on that list names math rendering, and — following DD-040's reading — U-B's "rich ergonomics" exclusion as copied into ADR-0020's rich-chat-ergonomics row (area 9) does not expressly cover transcript math, so the default direction is to incorporate. But incorporation here cannot be a pure independent re-derivation: the only sane implementation is KaTeX or an equivalent TeX-typesetting library, which means a KaTeX-class runtime dependency pulled into the build's bundled esbuild client artifact — an architecture/policy question no recorded ADR currently settles. Under the authority-stack rule that an unruled conflict stops for the human rather than being silently picked, this file records the leaning toward incorporate and routes the dependency question to a human ruling.

## Incorporation notes
- **Where it would live:** a lazy-loaded math module beside the pane (e.g. `src/client/`, next to `conversation.tsx`); delimiter splitting goes into DD-039's block parser (`$$…$$` blocks) and DD-040's inline renderer (`\(...\)` spans) once those land; the KaTeX import stays behind a dynamic `import()` so the main bundle never pays for it, following the reference's lazy-load approach without copying its vendored prebuilt asset.
- **Constraints:** if the dependency is approved: import KaTeX from npm under our own pinned, audited version — never copy the reference tree's shipped prebuilt KaTeX asset; XSS-review the injected markup path (the reference injects `renderToString` output via `dangerouslySetInnerHTML`); error fallback must keep the raw expression visible; inline spans stay single-line with single-dollar text math off, matching the shipped remark-math behavior; KaTeX CSS/fonts need their own sizing decision inside the wrapper's `--dsw-alias-*` style contract.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree. (Also note: KaTeX itself is an independent OSS library, not reference code.)
- **Effort/risk:** M — the glue (delimiter splitting, lazy load, three-step fallback) is small; most of the work is the dependency decision, KaTeX CSS/fonts in the bundled artifact, and the XSS review of injected markup.
- **Key reference anchors:** the reference tree's `frontend/src/recovered/features/conversation/workspace/math.tsx` — asset path line 5, runtime loader lines 18–23, three-step fallback lines 33–45, inline-math splitting lines 54–66, placeholder-to-render component lines 88–103; the same tree's `transcript.tsx` — block-kind union line 236, inline math node line 255, display-block collection line 323, display render line 398; the reference's root `package.json` — a pinned KaTeX dependency version.
