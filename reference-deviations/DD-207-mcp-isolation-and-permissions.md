# DD-207 — Isolation and permission gates around MCP execution
- **Area:** A26 MCP machinery
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
MCP execution is surrounded by several independent gates, none of which the build has, because the build has no MCP servers at all. The gates, by role:

- **A precheck executor is its own resource.** Vetting a call before it runs is not a code path inside the invocation handler; it is registered as a separate controlled executor resource with its own serializers, so the allowlist decision travels the same resource/port machinery as any other cross-boundary operation (the reference tree's `source/packages/agent-exec/mcp-allowlist-precheck.ts:7-9`).
- **A read-before-invoke gate.** Before a tool may be invoked, a dedicated check requires that the tool's definition file has actually been read on the session's read path. The check returns a bounded, typed outcome set — read, unknown server, unknown tool, unread path — and the unknown-server and unknown-tool branches each carry a message instructing the model to go discover first (the reference tree's `source/packages/agent/tools/mcp/mcp-execution-guards.ts:9-13, 40-66`; discover-first messages at `:30` and `:35`). Unknown server, unknown tool, and unread definition are therefore three distinct, differently-worded failures rather than one generic rejection.
- **Per-server and per-tool enablement at dispatch.** Enablement is honored when tools are assembled for the model and again when a call is dispatched: a disabled tool does not execute, and per-server custom instructions are folded into the results written for that server (the reference tree's `source/packages/local-exec/mcp-file-system-writer.ts:319, 368, 371`).
- **Bounded annotations, carried through.** Only four annotation hints are accepted (read-only, destructive, idempotent, open-world) and they are normalized as a fixed set rather than passed through opaquely (the reference tree's `source/packages/local-exec/mcp-tool-annotations.ts:5-8, 18`). Read-only classification then feeds approval: the routed bridge derives the remaining hints from the read-only bit when it presents a tool (the reference tree's `source/node-agent-coordinator/routed-mcp-bridge.ts:69`).
- **An approval store with a fixed TTL.** A smart-mode approval store records per-call approvals with a 24-hour time-to-live, expressed as a named seconds constant multiplied to milliseconds (the reference tree's `source/packages/agent/tools/mcp/smart-mode-approval-store.ts:5-6`; the approval gate itself lives alongside it in the reference tree's `source/packages/agent/tools/mcp/smart-mode-approval.ts`).
- **Discovery is a workspace file tree.** Server and tool definitions are materialized under a fixed directory layout (a top-level directory of per-server folders, each holding a nested tools directory of definitions — the reference tree's `source/packages/agent-exec/mcp-disk-catalog.ts:1-2`), and the model is instructed to read them there; the file-system instructions are feature-flagged and suppressed when the meta-tool path or ask-mode filtering applies (the reference tree's `source/packages/agent/utils/mcp-file-system.ts:41-72`). Because discovery is a real file tree, reads of definitions pass through the normal file-access path — which is what gives the read-before-invoke gate above something to check.
- **A freshness checker with mismatch telemetry.** Access to a path under that discovery tree schedules a comparison of the canonical live tool set against the observed on-disk set; it classifies the outcome as match or mismatch on the symmetric difference, emits a histogram of that difference, and logs a warning on mismatch (the reference tree's `source/packages/local-exec/mcp-disk-freshness-on-access.ts:24-25, 70, 76-77`).
- **Confinement and policy.** Server-hosted execution is confined to a sandbox (a box exec port and a sandbox conversion, the reference tree's `source/host/box/box-mcp.ts`, the reference tree's `source/host/extensions/mcp/box-mcp-exec.ts`), and a team-admin policy can disable connectors outright, blocking both authentication and use.

## What the current build does
There is no MCP isolation or permission model, because there are no MCP servers: no allowlist precheck, no read-before-invoke gate, no per-tool enablement, no approval TTL store, and no sandbox for external servers.

What the build does have is permission machinery at a different granularity — **task-level, not server-level**:

- `src/adapter/access-prompt.ts` — worker access asks answered through a consent surface, with timeout-deny expiry that surfaces honest expired copy.
- `src/adapter/dispatch-approval.ts` — the approval path over the dispatch tool.
- `src/client/approval-feed.ts` — the client-side feed carrying pending and settled asks.
- `src/worker/tool-barrier.ts` — a deny-list intersected with live global tool names at spawn, restricting which tools a worker may use.

## The deviation
The missing feature is the whole family of checks, not any single one. Two of the reference's checks are, however, *not* tied to MCP and can be compared directly with machinery the build already ships — and that comparison is the substantive point of this file.

**(a) Read-before-invoke versus the tool barrier and access prompts.** The reference's gate conditions a call on *prior knowledge of the definition*: the model must have read that tool's definition file before it may call the tool, and the failure modes name which discovery step was skipped. The build's nearest analogues gate *authorization* instead: the tool barrier decides **who may call** by denying tool names at spawn, and the access prompt decides whether a worker's access ask is allowed at all. Neither asks what the caller has read. These are orthogonal questions — a worker could hold an authorized tool it has never inspected, and conversely reading a definition grants nothing in the build. Name the distinction precisely: **the reference gates on prior knowledge of the definition; the build gates on authorization.**

**(b) The bounded-TTL approval store versus the build's approval expiry.** The reference persists per-call approvals in a store with a fixed 24-hour wall-clock lifetime. The build's approvals expire too, but on entirely different terms: consent is session-scoped and never persisted, bounded by the session's lifetime rather than a timer (ADR-0011), with a separate timeout-deny path whose expiry is surfaced as honest copy rather than as a stored record (ADR-0008; the copy constant is `APPROVAL_EXPIRED_COPY` at `src/adapter/access-prompt.ts:170`, and the same expiry semantics apply to the relay at `:360-372`). So the build has *an* expiry notion and *no* TTL store — the two are not the same shape and should not be treated as interchangeable.

The remaining checks (allowlist precheck resource, per-tool enablement, annotation normalization, discovery-as-file-tree, freshness telemetry, sandbox confinement) have no build-side counterpart at all and belong to the MCP scope question rather than to this file.

## Verdict: ASK-HUMAN
The MCP scope question is the same one this whole family defers: whether the build takes on MCP servers at all is unsettled here and is delegated to DD-203, and no recorded ruling decides it. More specifically for the checks in this file: **no recorded ruling covers either the read-before-invoke idea or the approval-TTL idea.** The authority stack settles session-scoped, never-persisted consent (ADR-0011, "Consent can never silently widen: the remembered artifact is (session, class, exact target), bounded by the session's lifetime and the wildcard fence at three layers") and timeout-deny expiry (ADR-0008) — both of which limit how a build-side TTL store *could not* be built, but neither of which endorses introducing one, and neither of which speaks to read-before-invoke at all. The general patterns here are real, but a general pattern is not a recorded ruling: this file should not claim more than the family's existing ASK-HUMAN just because the gating idea is appealing.

## Incorporation notes
- **Where it would live:** If MCP were adopted, the family of checks would sit with the MCP surface — an allowlist precheck as a resource/port alongside the existing adapter points, a definition-read check next to the invocation path, and any approval store as a sibling of `src/adapter/dispatch-approval.ts` rather than inside it. The two ideas that do not depend on MCP, if taken up independently of MCP, would go in different places: a definition-read notion would extend `src/worker/tool-barrier.ts` (which today decides only membership, not familiarity), and any TTL store would have to be reconciled with `src/adapter/access-prompt.ts` consent, which is session-scoped by ruling.
- **Constraints:** ADR-0011 forbids a persisted, settings-managed consent rule store — session-scoped, never persisted, wildcard-fenced — so a 24-hour TTL store cannot be imported as-is without contradicting it; it would need a human ruling first. ADR-0008 governs timeout deny and its expired-copy honesty, so any new expiry path must surface the same honesty rather than a silent re-resolve. A read-before-invoke gate must also respect the build's task-level boundary: worker access prompts are the human's consent surface and are not a per-tool familiarity check, so the two must not be conflated in the same mechanism.
