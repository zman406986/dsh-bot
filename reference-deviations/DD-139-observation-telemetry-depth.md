# DD-139 — Turn observation instrumentation depth vs minimal counters
- **Area:** agent runner / turn execution (A16)
- **Type:** missing-feature (mostly unruled; build is deliberately telemetry-free)
- **Date:** 2026-09-23

## What the reference does
The reference runner carries a dedicated per-turn observation layer. `turn-observation.ts` sets up several instruments around each turn: dispatch and time-to-first-token clock-skew observation (it sorts skew deltas into buckets against plausibility guards for send-dispatch and time-to-first-token windows), an await-observation path that tracks pending awaits and flushes them when the stack unwinds, a bounded in-memory activity ring (a recent-activity list capped at 24 entries, removing consecutive duplicate lines), and a projection of in-flight async/subagent tasks (id/state/title/started-at maps). Alongside it, `turn-settle.ts` records per-step turn timings (protobuf step-timing entries with durations) and flags whether a turn ended on silent tool calls (via a turn-shape helper). Together these give the reference a rich, self-describing picture of what a turn did — useful for both live status surfaces and debugging after the fact.

## What the current build does
The build's per-turn instrumentation is intentionally minimal. Core exposes a single `noteToolCall(workerId)` counter (src/core/multitask.ts) which the adapter feeds from the host's worker-tool-call event (src/plugin.ts wires `host.onWorkerToolCall` → `multitask.noteToolCall`; src/adapter/cordis-dsh-host.ts documents the contract). Observable state reaches surfaces through the roster-snapshot projection (src/core/roster-snapshot.ts) — a deliberately dependency-light data contract whose v2+ schema includes per-worker `toolCallCount` and presence fields — plus the adapter-side activity channel fed by the host event stream, per tickets 29/75. There is no time-to-first-token measurement, no await observation, no activity ring, and no step-timing/silent-tool-call settle tracking anywhere in src/core, src/adapter, or src/worker (grep-verified absent).

## The deviation
The reference instruments turns at a depth the build does not attempt: skew-guarded dispatch and time-to-first-token timing, await lifecycle with flush on unwind, a 24-entry activity ring, async-task projection, and settle-time step timings plus an ended-on-silent-tool-calls flag. The build reduces all of that to one tool-call counter plus a roster snapshot projection. Per the hint, the time-to-first-token and dispatch-skew parts sit at the A15 boundary (optional telemetry surface); the remainder — activity ring, await observation, settle timings — is simply unrecorded in the build. This is a gap in depth, not in correctness: nothing in the build is wrong, it just cannot answer questions the reference can (what did this turn actually do, how long did steps take, did it end on silent tool calls).

## Verdict: ADAPT
No recorded ADR rules on turn-observation depth, so this is unruled territory below the PRD; the PRD (§surfaces) marks telemetry optional (dispatch count, steer count, time-to-first-reply while busy — no prompt text), and the build has deliberately shipped no telemetry sink — roster-snapshot itself documents the settings channel doing "telemetry duty" as an honest gap. That means the reference's clock-skew and time-to-first-token machinery feeds telemetry the build does not currently want, so it should not be imported wholesale; it only becomes relevant if the optional PRD telemetry surface is ever ruled in. But the in-memory, sink-free pieces — the bounded activity ring and settle-time step timings/ended-on-silent-tool-calls — are pure diagnostics that would materially aid debugging the dispatcher itself without changing the analytics policy, and those are worth re-deriving independently (ADR-0018 B9). Anything beyond that (await observation, skew guards) should wait for an explicit ruling; ask the human before building toward the optional telemetry surface.

## Incorporation notes
- **Where it would live:** a new core-side turn-observation module beside the runner/worker plumbing in src/core (ring + settle timing helpers), surfaced only through existing projections (roster snapshot and the host event stream's activity) — no new sink; the settle flags would attach wherever turn completion is currently recorded in core.
- **Constraints:** in-memory only, bounded (ring cap ~24 entries), no prompt text in any surfaced activity line, no new persistence or settings-channel load beyond the existing honest-gap channel; time-to-first-token and dispatch-skew instrumentation is out of scope until the A15 optional-telemetry question is ruled on; everything re-derived from behavior, not copied.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the ring and settle-timing helpers are small and self-contained, but wiring them through core/adapter projections without growing the surface contract needs care.
