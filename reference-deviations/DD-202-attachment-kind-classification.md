# DD-202 — Attachment kind classification and per-kind handling tables
- **Area:** A25 attachments & media
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference gives every attachment a **kind**, and then lets that kind drive what happens to it.

- A fixed union of kinds covers the taxonomy — image, video, audio, PDF, table/spreadsheet, JSON, Markdown, document, archive, text, and a generic file catch-all (`reference material-NOT LICENSE SAFE DONT COPY-grok bot/source/shared/media/attachments.ts:1`). The union is a compile-time type, so every consumer of a kind is checked against the same closed set.
- Kind assignment runs a three-tier precedence (`.../source/shared/media/attachment-summary.ts:84`): the MIME type is consulted first and mapped by prefix or set membership (image/video/audio prefixes, an exact PDF match, a Markdown exact match, then table, JSON including structured-suffix types, document, archive, and any remaining text type) (`.../source/shared/media/attachment-summary.ts:24`, with the table/document/archive sets declared at `:7`, `:13`, `:17`); failing that, the filename is classified by extension; failing that, the URL or path is classified the same way; and failing all three, the generic file kind is returned.
- A **parallel preview-kind classifier** is a second, independent mapping — extensions to a viewer strategy — that also declares which kinds need their bytes read before they can be shown (`.../source/shared/media/file-preview-kind.ts:16`, `:28`, `:43`). It shares the extension tables with the MIME tables rather than duplicating them (`.../source/shared/media/image-mime.ts:2`), so the two classifications stay in step.
- Per-kind handling then falls out of the tables rather than out of scattered conditionals:
  - **Byte ceilings are kind-sensitive.** A general ceiling and a larger video ceiling are declared together, and the applicable one is chosen from whether the filename's extension maps to a video type, with a companion notice formatter that renders the matching human-readable refusal and appends a video-specific qualifier only when the video ceiling applied (`.../source/shared/media/attachment-limits.ts:2`, `:3`, `:4`, `:6`). The ceilings themselves are already recorded as the sibling finding **DD-198** and are not re-derived here.
  - **Text previews are gated by an extension allowlist** — a set of text-previewable extensions, with a predicate that resolves the extension from a name or path and tests membership (`.../source/shared/media/attachment-preview.ts:3`, `:13`; the extension helper is at `.../source/shared/media/attachment-open-policy.ts:1`).
  - **A binary sniff catches mislabelled text.** A sample window of 8 KB is taken from the head of the bytes (the whole buffer if smaller), an empty sample is treated as non-binary, any NUL byte short-circuits to binary, and otherwise the count of control bytes outside the tab-through-carriage-return whitespace range is compared against a ratio threshold (`.../source/shared/media/attachment-preview.ts:18`, `:19`, `:21`). This is what stops a file whose name promises text from being rendered as text when its contents are not.
- Kinds are also **counted and phrased** for user-facing summaries: a per-kind count type, a label table carrying a singular and a plural for each kind, a phrase helper that picks between them by count, a merge routine that folds duplicate counts and demotes unknown kinds to the generic file kind, and a summary formatter that either names the single kind or lists a breakdown (`.../source/shared/media/attachments.ts:6`, `:8`, `:22`, `:27`, `:39`).

Read together: the tables are the reference's answer to "one attachment, many possible treatments". Rather than asking at each site what a file is, the reference asks once, at the boundary, and every downstream decision — which viewer, which ceiling, which refusal wording, whether to trust the bytes as text, how to describe the batch — reads the same answer.

## What the current build does
The build has **no classification of any sort**:

- Attachments appear in the product as a **capability advertisement**: the host adapter's structural command-definition type carries an optional input hint whose second field is a boolean attachments flag (`src/adapter/cordis-dsh-host.ts:135`, `:140`), with the surrounding comment noting the hint is menu-visible and never host-enforced. It says an attachment can be named; it says nothing about what one is.
- Attachments appear a second time as an **opaque array forwarded verbatim** through the command interface: the client's typed remote service takes the line plus a readonly array of unknowns and passes it through untouched (`src/client/context.ts:323`, `:331`). The element type is unknown, so nothing downstream could branch on a kind even if a kind existed.
- There are no extension tables, no MIME resolution, no preview-kind mapping, no per-kind byte ceilings, and no binary sniff anywhere under `src/`. Grep-level absence, not an exhaustive audit. The sibling finding **DD-198** records the same absence for the ceilings specifically, and for the same reason.

So an attachment in the build is a name in a list, and nothing more is ever asked of it.

## The deviation
The reference's classification exists to drive **display and validation** decisions: which viewer renders it, which ceiling applies, which refusal wording is shown, whether the bytes may be trusted as text, and how a batch of them is described to the user. Every one of those is a decision the reference's own surfaces make.

The build makes none of them, because it has no display layer of its own — the host renders, and the plugin's attachment handling is a pass-through with no consumer for a kind. Classifying an attachment in the build today would produce a value that nothing reads.

The deviation is therefore one of **architecture, not oversight**: the tables are the correct shape for a product that owns its viewers and its refusals, and the build owns neither. Two pieces of the reference's treatment, however, are not display concerns at all, and those survive the architecture difference:

1. **The per-kind byte ceiling with a human-readable refusal** — a validation policy. It bounds what may be accepted and says so in the user's language. This is already named as the transferable part of **DD-198**; DD-202 does not re-derive it and treats it as that finding's to own.
2. **The binary sniff that catches mislabelled text** — a correctness safeguard. It is the one piece of the reference's attachment machinery that answers "are these bytes what the name claims?", and that question does not depend on who renders the result or whether anyone renders it at all. DD-198 does not cover it.

The second piece is what DD-202 adds to the transferable set; the first is inherited from that finding.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 exception U-B excludes rich chat ergonomics and names rich attachment viewers explicitly (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:35`), which settles the **display half** of this deviation: the viewer strategy, the preview-kind mapping, and the summary phrasing have no place in the build and should not be imported just because they are called classification. The **validation half is not covered by any recorded ruling** — U-B governs display, not acceptance policy, and no ADR, PRD clause, or recorded ticket ruling names per-kind ceilings or binary sniffing, so that half is unruled rather than decided. The dominant verdict stays DO-NOT-INCORPORATE because the classification tables as a mechanism have no consumer in a pass-through architecture, but the split is real: the display half is excluded by U-B, and the binary sniff — a correctness safeguard rather than a display feature — is left open by the authority stack and named here as the piece a future consumer could justify. The ceiling half belongs to DD-198 and is not restated.

## Incorporation notes
- **Where it would live:** Nothing is proposed for incorporation as a mechanism. If the binary sniff were ever wanted, it would sit on the byte-reading path the build does not have — its natural neighbours are the deliver tool's path handling (`src/core/tools.ts`) and the client's command path (`src/client/actions.ts`), both of which DD-198 also identifies. A kind taxonomy would only acquire a consumer if the build ever owned a display surface, which U-B rules out.
- **Constraints:** Do not build a kind taxonomy ahead of a consumer — the union, the MIME sets, and the extension tables are all dead weight without a site that branches on them, and the build's opaque attachment array at `src/client/context.ts:331` is deliberately element-untyped. If the sniff is ever adopted, adopt it as a standalone predicate over bytes rather than as part of a classification system; it does not need the taxonomy to be useful, and the taxonomy does not need it. Any future decision to own a display surface re-opens U-B itself, not merely this deviation.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S for the transferable part — the binary sniff is a self-contained predicate over a byte sample with no dependency on the kind tables, so it is small and independently testable; the risk is low, and the main hazard is scope creep into the taxonomy it sits beside in the reference.
