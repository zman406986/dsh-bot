# DD-208 — Native application menu bar and main-process accelerator routing
- **Area:** A27 platform integration
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference builds a native application menu template at startup and installs it on the application. On macOS it leads with the application menu carrying the platform's standard roles (services, hide, hide-others, unhide, quit) plus an "about" entry whose click routes to a product intent; then File, Edit, View, Window and Help. Entries carry either platform roles or explicit accelerators, and the non-role entries route their clicks into product intents: about, feedback, an external help destination, full screen, reload, and a developer-tools toggle that is gated behind a developer-tools membership check (the template builder takes that check as an option and simply omits the entry when it fails). The menu is re-installed whenever that gate changes — the install is subscribed to the gate, and the gate itself is fed by a membership resolver wired at startup.

Independently of the menu, the main process owns window-level key combinations. A key-combination controller classifies an incoming key input into either a zoom direction (in, out, reset — with explicit min/max/step factors) or a window shortcut (reload, fullscreen, developer-tools toggle, quit) and applies it to the window and its web contents: fullscreen flips the window's fullscreen state, reload and the developer-tools toggle act on the web contents (the latter re-checked against the same developer-tools gate), quit goes to the app-quit callback, and zoom adjusts and then reports the resulting factor. Key-combination forwarding is attached to the window's web contents through a pre-input key-event hook, and the same controller exposes a host-input entry point so input arriving through the host's own path is classified and applied identically; a separate gate-enforcement routine closes an already-open developer-tools surface when the gate stops allowing it.

## What the current build does
Absent. No menu, accelerator, or native key-combination layer exists anywhere in `src/` or `client/` — a search for the platform menu and accelerator surfaces across both trees returns nothing. The only key handling in the build is renderer-side and DOM-scoped: Escape dismisses a context menu (`src/client/shell.tsx:595-600`, registered as a document-level keydown listener alongside the pointer and scroll dismissers) and the composer's Enter behavior (`src/client/conversation.tsx:210-222`, plain Enter submits, the modified key combination submits, Shift+Enter and IME composition keep the line break). Both are already recorded — DD-016 covers the renderer's document-level key registry, a different tier from a native menu/accelerator layer.

**Not reachable.** The host owns the application menu and the window; the host's client interface offers only slot registration (`src/client/index.ts:528-537`, an injection into the shell-overlay slot that registers the launcher entry), with no menu or accelerator interface. Only DOM-scoped key combinations inside the plugin's own floating window are possible.

## The deviation
The reference has a native platform-integration tier — an application menu bar plus main-process accelerator routing — and the build has no counterpart to it and no connection point from which to grow one. The build's key handling lives one tier down, in the DOM inside surfaces the plugin already owns; the reference's layer sits above the web contents, in the process that owns the window and the menu.

## Verdict: DO-NOT-INCORPORATE
ADR-0020 (`docs/adr/0020-wrapper-shell-vehicle-own-frame-over-shipped-runtime-draft-nonhuman-approved.md`, status draft / non-human-approved) rejects the native/Electron desktop shell as a PRD non-goal at line 28 — "excluded without further study" — and that ruling is decisive for this whole area: the build is deliberately not a shell, so a native menu bar and main-process accelerator routing have no place in this product. No recorded ruling grants the plugin a menu or accelerator interface on the host, and the host's client interface does not expose one (`src/client/index.ts:528-537`). The part that *is* reachable in-window — DOM-scoped shortcuts inside the plugin's floating window — is a different question from the native layer, and it belongs to the client-shell work the build already does (ADR-0022), not to this deviation. If a future human ruling reverses ADR-0020's exclusion, this is the item to revisit; until then it stands.

## Incorporation notes
- **Where it would live:** Nowhere in the current architecture. A native menu and main-process key routing require a native/Electron application shell, which ADR-0020 excludes; the only in-window analogue (DOM shortcuts in the floating window) would live in the client shell (`src/client/shell.tsx`) and is client-shell work under ADR-0022, not this deviation.
- **Constraints:** The host owns the application menu and the window, and the client interface offers slot registration only (`src/client/index.ts:528-537`), so the plugin could not install a menu or classify native key combinations even if it wanted to. Any key handling the plugin does is DOM-scoped inside its own floating window and must not collide with the host's own document-level handlers (DD-016).
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L + no place exists in the build for this work; the work depends on a shell choice ADR-0020 already rejected, and any partial DOM imitation would add key-handling collision risk (DD-016) for no product gain.
- **Key reference anchors:** the menu template builder and installer, the gate option and gate-subscribed re-install, and the key-combination controller's classifier, appliers, gate enforcement and two input paths (paths below).
