# DD-105 — Staged Save/Discard settings vs immediate persist-per-control
- **Area:** settings (A12)
- **Type:** deliberate-divergence (recorded in the module's own documentation)
- **Date:** 2026-09-23

## What the reference does
Every settings control in the reference commits the moment it settles. The shared settings store's private update helper loads the current document, applies the mutator, and writes it to disk synchronously on each setter call (`source/shared/node/settings/sand-settings-store.ts:106-107` — the write is the temp-file-plus-rename write, and every per-field setter like theme preference, box runtime, model selection goes through it). Upstairs, the settings overlay panels wire their callbacks to apply-and-write inline: a theme, timezone, or permission change writes as part of handling the control event (`frontend/src/recovered/features/settings/overlay/panels.tsx`), auto-review commits on each rule add/edit/delete, and the inference-router provider is written as the change happens (`frontend/src/recovered/features/settings/overlay/router.ts`, shared inference-router module :76-79). There is no draft state, no dirty flag, and no undo short of editing the value back.

## What the current build does
The build's settings card keeps edits in a staged draft map (`src/client/settings-card-store.ts:489-498` — `edit`/`reset` only fill the map and republish; nothing touches the stored document). One explicit Save applies the staged writes in field order (`save()`, :504-553), then re-reads the scope snapshot and flags a `failed` state if the stored document disagrees with what was staged — the store explicitly refuses to claim a success the document does not carry (:526-545). Discard drops the drafts (:499-503). The component shows an unsaved badge while drafts exist, a read-only notice when the scope is not writable, and disables Save unless the card is dirty and every draft validates (`src/client/settings-card.tsx:251-255`, :260-264, :275-297); invalid drafts block the save entirely rather than being silently dropped (`settings-card-store.ts:508-510`). The module header records the contract as deliberate: "nothing here writes as a control settles… the card's Save is the one point where a draft becomes a document mutation" (`settings-card.tsx:10-14`, ticket 47, following the shipped `card-form.d.ts` form contract).

## The deviation
Same surface, opposite write behavior. The reference treats each control as its own commit point — the save is an unobservable side effect of interaction, and the document can change under the user mid-editing-session with no visible difference. The build inserts an explicit transaction boundary: draft → review → single Save → read-back verification → commit or `failed`, with Discard as the escape hatch. Consequences of the build's choice the reference does not offer: a user can abandon an editing session without side effects; multiple fields are written together in one pass; and a write that the host accepted but changed is detected by reading back instead of being assumed. What the reference's model buys that the build gives up: no Save click, and no unsaved state to lose on navigation.

## Verdict: DO-NOT-INCORPORATE
The reference's persist-per-control stays out; the build's staged Save/Discard is the recorded deliberate divergence and should stand. Under the precedence order this is not a close call: the module header records the explicit-save contract as the shipped form contract for ticket 47 (recorded ruling, AGENTS.md level 6-7 territory, with ADR-0018 as the human-ruled master above it), and the divergence favors the build — it is strictly more conservative than the reference, adding a verification read-back and a Discard path the reference lacks. Nothing in the reference's immediate-persist behavior solves a problem the build has; adopting it would discard atomic multi-field writes and the mismatch detection for no gain. Revisit only if a human ruling or a product requirement demands fire-and-forget control persistence.
