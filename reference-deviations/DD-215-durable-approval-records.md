# DD-215 — Durable approval records, retirement, and refusal memory
- **Area:** A28 approval & policy
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

Granted approvals are durable, not session state. A grant is persisted as a record carrying an id, an action kind, a target, and an optional resource path, written into a JSON approvals file under the app's data root; a companion retirements file holds the ids of grants that have been withdrawn. Both files are written atomically (temp file, then rename), every write goes through a per-path serialized write queue, and a file whose set has become empty is deleted rather than left as an empty shell.

Retiring a grant adds its id to the retirements set, prunes ids whose grants no longer exist, and the consumer side resolves live grants as approvals-minus-retired, then asks whether a grant covers the described request — same action and target, or the same resource path the request is attached to. So a grant made on a resource path covers later requests attached to that same resource, and a withdrawal is itself durable. Unanswered asks expire on a ten-minute TTL, and the auto-review path carries its own ten-minute approval TTL.

Refusal memory is a separate, per-agent mechanism. A declined action is remembered keyed by agent, action kind, and target (the target hashed into the key), held under a per-agent cap with reclamation of entries older than a direction-epoch window (then oldest-first). A per-agent direction epoch advances with each new turn, and a "saturated direction" marker makes refusals from a superseded direction non-retryable — a later turn receives a stale-task refusal instead of a fresh ask. Widening the saved permission records the epoch it happened at, so requests that predate the grant are not retroactively authorized. Agents can also be forgotten wholesale (a bounded set), which purges their refusal memory.

## What the current build does

Approval memory is session-scoped and in-memory only. The review decision table's own header states there is no persistence beyond session scope and no settings-managed store; rows live in an in-memory map keyed by scope, owning session, class, and target pattern, and are dropped by a session-clear path wired through `Multitask.clearSessionAccessPolicy` — a decision-table row never outlives its session, by comment and by construction. Nothing in the access modules writes to disk: a search of the access and review-decision modules turns up no file write, no serialization, and no settings-backed store, only comments asserting their absence.

The build does have expiry-like behavior of its own: the relay's deadline for an unanswered ask is 120 seconds (`DEFAULT_ACCESS_TIMEOUT_MS`), ending at the shipped park/prompt/timeout path, and the shipped decision table is deliberately empty with a wildcard fence on writes, so no whole class or prefix of targets is ever remembered.

## The deviation

The reference design has three separable ideas, and the build sits differently against each:

- (a) **Durable grants** — survive restart, with a retirement ledger so a withdrawal is durable too. The build lacks this by design.
- (b) **Expiry of unanswered asks** — a TTL. The build has (b)-like behavior through its own deadline (120 s against the reference's ten minutes): not a gap in kind, only in the number.
- (c) **Refusal memory** — remembering a no per agent/action/target, plus the stale-task marker that makes a superseded direction's refusals non-retryable. Absent entirely: nothing in the build records that a user declined, so an agent can re-ask the same question indefinitely with nothing to stop it.

Two further pieces belong with (a) and have no counterpart: per-grant retirement (the build's session-clear is a coarse scope drop, not a per-grant withdrawal) and resource-path coverage (the build matches class plus target pattern only).

## Verdict: DO-NOT-INCORPORATE

ADR-0018 exception U-D is the decisive recorded ruling for the durable half: it reads that "Always allow" approval rules are session-scoped, not persisted, with no settings-managed rule store and no dedicated local tool-permission controller (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:37`, human-ruled), and the build's decision-table header cites U-D as the recorded point where imitation stops, reinforced by ticket 69's ruling that the shipped table stay empty (2026-09-19, agent-recorded, subject to human reversal). Durable grants, the retirement ledger, and the resource-path coverage they carry are therefore excluded, and (b) expiry is a conforming timeout rather than a deviation. The uncovered gap is (c) refusal memory: U-D reaches persistence and rule-store management, not remembering a refusal inside a session, and no other recorded ruling reaches it — DD-214 covers the permission model's setting, ceiling, and resolution shape, not refusal memory. That gap is named here for the human rather than read into U-D; incorporating it would need a new ruling.

## Incorporation notes
- **Where it would live:** A durable approvals/retirements store would sit beside the access modules under `src/core/` (the layer that holds `src/core/review-posture.ts` and `src/core/access-relay.ts`), with disk I/O behind an injected adapter the way the relay keeps host I/O in callbacks; refusal memory would live in the same decision-table and relay layer, keyed by owning session (ADR-0019) rather than by the reference's agent id.
- **Constraints:** U-D forbids the persisted store and the settings-managed controller outright — anything durable is a U-D amendment requiring a human signature first, and the rule that the shipped table stays empty (ticket 69 Q1) forbids a seeded default in the meantime. Refusal memory, if ever ruled in, must not silently widen or narrow consent (ADR-0011), must not be treated as a saved deny outliving its session, and must not collide with the wildcard fence on decision-table writes. Do not duplicate DD-214 (permission model) or DD-077/DD-078 (approval and permission card surfaces) — this file covers the record-keeping layer only.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the durable store is a small atomic-write module but is blocked by U-D, while refusal memory is small in code yet policy-visible and would need a human ruling before any design work.
