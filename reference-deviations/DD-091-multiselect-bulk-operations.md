# DD-091 — Multi-select with bulk actions vs single selection
- **Area:** sidebar / roster / agent management (A11)
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference sidebar supports modifier-based multi-selection of agent rows: a click with Cmd or Ctrl held toggles that row in or out of a selection set, and a Shift-click selects the whole range from the anchor (the last row clicked without Shift) to the clicked row (click handlers in the row component; a double-click still means rename, and a plain click still opens). When at least one agent is selected, the normal sidebar header is replaced by a selection-actions header offering, with count-aware labels (singular vs. a plural count phrasing): a move menu targeting any existing section or a freshly created one (a new-section entry), a delete button styled as dangerous, and a clear-selection button to drop the selection. Selection state lives with the sidebar caller (a selected-agents id set plus toggle/range/delete/clear callbacks), and move targets are the user-authored sidebar sections (see DD-086 — sections are themselves absent from our build).

## What the current build does
The shell sidebar's selection is a single session or nothing: `ShellSelection` in `src/client/shell-store.ts` is a `none`/`session` union, `select()` accepts exactly one known id, unknown ids are refused without state change, and removing the selected session resets the selection to none. `ShellRow` in `src/client/shell.tsx` binds a plain click to select; there is no modifier-key handling, no anchor/range concept, no selection set, and no header or any bulk affordance. The shell sidebar's rows are dsh dispatcher sessions, not agents inside sections; the only destructive affordance is the per-row delete that needs a second press to confirm (the arm-then-confirm pattern around `shellDeletePress`/`SHELL_DELETE_CONFIRM_MS`, ticket 101), whose confirm sends a host command per session.

## The deviation
The reference treats selection as a first-class multi-target mechanism with a bulk action header; our build treats selection as focus — exactly one session — and the rules that keep the UI from showing state we do not have (unknown ids refused, selection dies with its session) deliberately cover only that case. The interaction mechanics (modifier toggle, range select, count-aware header) are portable in principle, but every bulk action the reference offers assumes targets we do not have: sections to move into do not exist in the shell sidebar (DD-086 covers their absence), and bulk delete of dispatcher sessions has no defined host-side semantics and would collide with the existing per-row habit of confirming by pressing twice and sending one command per session; the confirm step, which arms one row at a time, has no defined behavior for a whole set of sessions at once.

## Verdict: ASK-HUMAN
The selection mechanics (modifier toggle, range anchor, a count-aware header that replaces the normal header) are worth adapting to the shell's store model, but they must be re-derived independently: `ShellSelection` would grow from one id into a set, keeping the same rules it has today (unknown ids refused, removal drops the id from the set), and bulk actions can only be ones the host actually supports. Bulk move-to-section is DO-NOT-INCORPORATE until user-defined sidebar sections exist (the feature filed as DD-086); bulk delete needs a ruling on how a destructive action over many sessions coexists with the current confirm-by-second-press behavior (and likely sends one host command per session), so that piece is ASK-HUMAN before any implementation. Net: adapt the mechanics behind a ticket, defer the targets.

## Incorporation notes
- **Where it would live:** `src/client/shell-store.ts` (selection state becomes a set of known session ids; removal drops the id from the set), `src/client/shell.tsx` (ShellRow modifier-click handlers; header swap to a selection-actions header), offline tests for the store transitions, in the style of success criterion S8 (core modules unit-tested with no network or LLM).
- **Constraints:** keep the existing rules — refuse unknown ids, never keep pointing at removed sessions; no modal or toast surface exists, so any bulk destructive confirmation must reuse or extend the confirm-by-second-press pattern (currently one armed row at a time); plain click must keep meaning "open/focus this session"; ADR-0018/ADR-0020 frame the sidebar as a list of dispatcher sessions only, so bulk actions operate on sessions, not on workers; bulk delete host-command semantics need a ruling (ticket + human sign-off) before build.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — store reshaping plus a new header component is moderate, but the collision between bulk delete and the confirm-by-second-press behavior, and the missing host command for mass removal, carry design risk; ship mechanics + clear-selection first, delete later behind a ruling.
- **Key reference anchors:** `the reference tree's frontend/src/recovered/features/conversation/workspace/sidebar.tsx` — the row component's click handler (Cmd/Ctrl toggle, Shift range), the selection-actions header component (count-aware move/delete labels, a new-section entry, a clear-selection entry), the selection callbacks in the sidebar props type, and the header swap when a selection exists (line ~455).
