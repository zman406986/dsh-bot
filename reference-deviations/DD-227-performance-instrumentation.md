# DD-227 — Performance instrumentation: startup phases, render and stream metrics, process sampling
- **Area:** A29 cross-cutting surfaces
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference treats performance as a first-class telemetry subject, in three separate subsystems.

**A startup phase tracker.** A module-level constant sets a 120-second stuck threshold. The tracker takes a monotonic clock and a three-valued architecture-translation flag (translated / not translated / unknown) as injected dependencies, stamps a start time, then walks named phases; each phase transition re-stamps a phase clock, and the tracker reports one of four outcomes per phase — start, stuck, ready, failed. The stuck report carries both total elapsed and phase-relative elapsed plus a tagged error code; the ready report carries total duration and a separate window-relative duration; the failed report carries elapsed plus a distinct error code and hands the error to a capture callback. Anchors: the reference tree's `source/electron-main/telemetry/desktop-startup-telemetry.ts:4` (threshold constant), `:13-14` (monotonic clock and translation flag as deps), `:19-52` (phase stamping and the four outcome reports).

**A render telemetry module with validated report shapes.** Two shapes are defined and each has a validator. The time-to-first-render shape carries a non-negative duration, an outcome from a three-value enumeration, an optional chunk-kind from a three-value enumeration, an entry epoch timestamp, optional trace / span / trace-parent / client-nonce / conversation identifiers, and a required fork flag. The stream-health shape carries an outcome from a four-value enumeration and five required non-negative numbers — chunk count, maximum gap between chunks, total stalled time, stall count, and stream duration — plus the same optional identifier set and fork flag. Both shapes project into log records, with the level raised to a warning when the outcome is the timeout case. Anchors: the reference tree's `source/electron-main/telemetry/render-telemetry.ts:1` (the three enumerations), `:3` (time-to-first-render validator), `:4` (stream-health validator — the five numbers are the whole measure), `:5-6` (projection into log records, warning level on timeout).

**A process-metrics subsystem.** A full area, not a single module: a collector with clamped subsample and sample rates (a 1s–300s subsample range and a 1–30min sample range, each with a default), a 10-second init delay, an environment-driven kill switch, and an injectable polling policy that schedules a named scan; a sampler exposing row and sample shapes; a native process-list scanner loaded through a require shim with a null-safe loader and a factory; heap-metric ingest with named metric keys (heap used, heap limit, loaded agents, loaded transcript entries, idle minutes) plus a flush coalescer; a redaction pass that hashes and sanitizes process names (its helper-name pattern is vendor-specific and is not reproduced here, per the copy policy); a transport with a 30-second report timeout, bigint wire conversion, and a reporter class; runtime wiring that resolves scan roots and assembles the runtime. Anchors: the reference tree's `source/electron-main/process-metrics/collector.ts:4-10, 34-43, 73, 159`; `sampler.ts:3-53`; `native-scan.ts:7-17`; `heap-metrics-ingest.ts:3-20`; `redaction.ts:3-14`; `transport.ts:3-14`; `wiring.ts:1`; `desktop-metrics-runtime.ts:24-53`; the reference tree's `source/shared/observability/heap-metrics.ts`.

## What the current build does
No performance instrumentation of any kind exists. A project-wide grep over `src/` and `client/` for a monotonic-clock call, a high-resolution timer, mark/measure, or any timing primitive returns exactly one hit — and it is a comment describing a monotonic *generation counter* (`src/adapter/parent-agent.ts:215`), not a clock. A grep for heap-used / memory-usage / RSS / process-memory / sampler / sample-interval returns nothing. A grep for trace, span, or trace-parent identifiers returns nothing. There is no startup timing, no phase tracker, no render or stream metric, no process or memory sampling anywhere in the build.

The nearest related things are projections and journals, not measurements, and the distinction matters:

- **An elapsed-time *display*, not a measurement.** `src/core/multitask.ts:729` derives `Math.max(0, now - worker.startedAtMs)` at read time for a worker row; `src/core/types.ts:49` types it; `src/core/tool-results.ts:126` formats it for human eyes. Nothing accumulates it, records it, or computes a statistic over it.
- **The roster channel as an acknowledged substitute.** `src/adapter/roster-channel.ts:15` states it plainly: this is a config channel doing telemetry duty, the documented honest gap. The same header requires that a telemetry write failure stay contained and never reach the host (`:25`, `:144`).
- **An unconditional event journal.** `src/core/todo-reconciler.ts:507` notes that telemetry outlives the item it describes; `:642` calls the event log the telemetry path and keeps it unconditional; `:679` insists that a failure and a give-up must not look the same in it. `src/core/multitask.ts:102` records the rule — telemetry can never break core flow, and the observer only reads core state.

So the build's only thing named "telemetry" is behavioural journaling of state changes. It is not performance instrumentation, and it has no timing content at all.

## The deviation
The three subsystems each have a different answer about whether the build could use them, and only one is a real gap.

**Startup phases — already owned elsewhere, small remainder.** The startup tracker is not new to this study: DD-213 already cites `desktop-startup-telemetry.ts:4, 12-52` under its taxonomy-and-lifecycle heading. DD-227 must not file it again. What DD-213 does not treat is the tracker *as a timing mechanism* — per-phase elapsed against a monotonic clock, total duration, window-relative duration, and the translation flag. That difference is real but small, and it only matters if the build ever owns a boot sequence; it does not, because it is loaded into a host process whose startup it does not control. Record the difference, cross-reference DD-213, do not duplicate.

**Process metrics — out of reach, and already excluded in the same way.** Sampling process trees, heap usage, and idle time presupposes a process the plugin owns. It runs inside the dsh host. ADR-0020 rejects the native/Electron shell as a PRD non-goal, and ADR-0021 keeps stock dsh primary with the dispatcher in a floating window, so no shell route arrives that way either. The transport part would also need somewhere to send data that the host boundary does not expose (`src/core/dsh-host.ts` has no log or telemetry interface). This is DD-213's finding applied to a different module family — cross-reference it, do not restate it.

**Render and stream metrics — the real difference, and the one worth arguing about.** This is the most transferable piece in the whole area, and specifically the *stream-health* shape: chunk count, maximum gap between chunks, total stalled time, stall count, stream duration. The build's entire product premise is that a dispatcher stays responsive while workers run, and its user-visible liveness signal comes from session events — so a stream-health measure is the natural way to detect a worker whose output has stalled, which is exactly the failure the build's own liveness check exists to notice.

Which forces an honest comparison, and the answer is not the flattering one. **The build's liveness check does not detect a stalled stream; it detects silence.** `deriveWorkerLiveness` (`src/core/liveness.ts:92-113`) is a pure verdict over four existing fields — status, start clock, counted tool calls, the last activity instant observed through the host session event stream — plus a caller-supplied clock, returning `active` / `quiet` / `stalled`. Its `stalled` verdict is a threshold on *one* interval: `nowMs - referenceMs > WORKER_STALL_THRESHOLD_MS` (`:38`, ten minutes), where the reference instant is the single most recent activity observation, or the worker's start clock only in the no-observation / zero-count case (`:99-101`). It has no memory of earlier gaps. A worker that emits one activity line every ninety seconds while spending eighty-nine of each of those seconds stalled reads `active` indefinitely, because each fresh timestamp resets the entire signal. It emits a verdict and never a measurement: no chunk count, no gap distribution, no accumulated stalled time, no stall-episode count, no stream duration, and no time-to-first-output at all (the zero-count case measures *silence since start*, which is not a first-output latency).

So the comparison is not "the build already answers this". It is: the build answers the coarse presence question ("has this worker gone dark?") and structurally cannot answer the structure question ("how healthy was this stream?"). The reference's five numbers are precisely the structure question. That is the real deviation, and it is a difference in detail rather than a difference in detection — the build notices the failure the reference measures, but only in its bluntest form, and the build's own documented rule (a stalled worker must be visible, D22) is better served by the more detailed measurement. The reference also names the *stuck-startup threshold* idea (a boot that never completes is reported as stuck rather than silently absent) — worth keeping on record for the same reason, though with no boot sequence to observe it has no home in the build today.

## Verdict: ADAPT
No recorded ruling names performance instrumentation, and the authority stack settles nothing here directly — so this territory is unruled, and the verdict is argued from nearby recorded points rather than from a decision that covers it. Two recorded points limit what is possible: ADR-0018's exception list excludes privacy/account gates (U-A, `docs/adr/0018-imitate-reference-in-entirety-exception-list.md:34`) but does not exclude instrumentation as such, and ADR-0020 excludes the shell (`:28`) while leaving a plugin free to measure its own work. The two parts that need somewhere to send data are therefore out — process sampling has no process to sample and no transport to send to, and the startup tracker belongs to DD-213 — but the stream-health measure has both a connection point and a consumer: the adapter already subscribes to the host's session event stream and already records the observation moment of each activity event (the same subscription `src/core/liveness.ts:56` describes), and the consumer is the liveness signal the build added by human ruling (ADR-0018 D22, `:33`), not a new dashboard. ADAPT is the right scope: re-derive a bounded, in-memory stream-health accumulator that sharpens an already-approved signal, and import none of the sending, transport, sampling, or reporting machinery. The one test that keeps this honest is the no-new-surface rule — if the measure cannot ride the existing roster/check projection and the existing event journal, it is a new surface and should stop for a human ruling instead.

## Incorporation notes
- **Where it would live:** a pure accumulator module beside `src/core/liveness.ts` — the same shape as the reconciler and the liveness verdict: take event arrivals with their timestamps as inputs, expose a fold, keep no timers of its own. It would be fed from the adapter's existing subscription to the host session event stream (the activity map that already carries an observation moment, ticket 29/75) and read by `deriveWorkerLiveness` as an extra input. Surfaced, if at all, through the existing `check_workers` row and roster-snapshot projection — the same contract that already carries `toolCallCount` and the activity instant.
- **Constraints:** in-memory only and bounded; no timers, no polling, no intervals — the gaps are computed from arrival timestamps the adapter already holds, which is what keeps this compatible with ADR-0010's rule to publish only on real state changes and never on a timer, and with D22's rule that liveness must not become a watchdog. Rule R1 applies (pass `nowMs` in; no `Date.now()` inside). Any new stall-episode threshold is a named constant, never a literal at a call site (R2). Terminal and blocked workers keep their R3 precedence — a stream measure must not change the label of a settled or parked worker. Any growth of the roster-snapshot wire contract is a fail-closed parse change and needs its own care. No prompt text in any surfaced number. No new persistence, and nothing added to send telemetry anywhere — a telemetry destination is a new surface and is excluded by DD-213's finding.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the accumulator itself is small and offline-testable in the same style as the liveness verdict, but connecting it to the roster projection means touching the wire contract, and the risk is that a stream-health field invites exactly the dashboard-and-telemetry-destination expansion this verdict excludes.
- **Key reference anchors:** the reference tree's `source/electron-main/telemetry/render-telemetry.ts:1, 3-6` (the two validated report shapes, the enumerations, and the log-record projections — the stream-health shape at `:4` is the transferable one); the reference tree's `source/electron-main/telemetry/desktop-startup-telemetry.ts:4, 13-14, 19-52` (stuck threshold, monotonic phase stamping, translation flag, four outcomes — cross-referenced to DD-213, not re-filed); the reference tree's `source/electron-main/process-metrics/collector.ts:4-10, 34-43, 73, 159`, `sampler.ts:3-53`, `native-scan.ts:7-17`, `heap-metrics-ingest.ts:3-20`, `redaction.ts:3-14`, `transport.ts:3-14`, `wiring.ts:1`, `desktop-metrics-runtime.ts:24-53` (the excluded subsystem, cited for the record).
- **Open cross-file numbers:** the client-side producer that constructs the render reports in the reference (the module calling the validators) is not enumerated here (DD number pending); the reference-side consumer of the projected log records sits in the reporting code already filed as DD-213 (no separate number needed).
