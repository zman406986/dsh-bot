# DD-096 — Persisted UI preferences (pins/selection/layout) vs in-memory only
- **Area:** sidebar / roster / agent management (A11)
- **Type:** missing-feature (needs a client-side way to store data)
- **Date:** 2026-09-23

## What the reference does

The reference treats small UI preferences as durable client-side data tied to the user's account, rather than as component state. Two recovered modules define the pattern. `the reference tree's frontend/src/recovered/features/conversation/workspace/sidebar-collapse-state.ts` declares a block of state about the agent list that is stored on the client (schema version 1, tied to the account). It holds pinned agent ids, collapsed section ids, recent mentions, and recent emoji; it reads through a wrapper that distinguishes absent, corrupt, and versioned payloads, so a malformed write degrades to empty state instead of crashing the sidebar, and it knows the previous storage key names (the legacy pinned-agents key and its siblings) so old data can be migrated forward. `sidebar-layout-state.ts` declares a layout block of stored state (schema version 3, not tied to the account) covering sidebar width, collapsed flag, and info-pane geometry, with explicit defaults and allowed minimum/maximum values (expanded width 240–400, collapsed rail 88). `the reference tree's frontend/src/recovered/features/roster/selection-state.ts` applies the same pattern to the roster's last selected agent. Net effect: reload or relaunch and your pins, section collapse state, last-selected agent, and sidebar width all come back as you left them, per account, with junk payloads and legacy keys handled.

## What the current build does

`src/client/shell-store.ts` keeps everything the shell sidebar knows in one immutable in-memory snapshot held in a closure: rows, feed-insertion order, the single selection, and per-session presence mirrors. Selection is a plain field on that snapshot — `select()` validates against known sessions and emits a new snapshot, nothing writes anywhere — and sidebar order is explicitly the feed's insertion order, not a user-arrangeable or remembered value. The store starts from an empty snapshot on every mount, so a reload forgets the selection entirely. The one thing that does cross the host boundary is presence: the host mirrors each dispatcher session's roster snapshot under a `roster.<sessionId>` settings key and the client applies it via `applySessionMirror` — but that is a presence signal fed by the host, not a user-preference store, and no similar channel exists for pins, selection, or layout. Nothing in the client writes UI preferences anywhere; there is no storage channel for them to use.

## The deviation

The reference persists the sidebar's small user preferences (pins, collapsed sections, last selected agent, width/collapsed layout) as schema-versioned blocks of stored state tied to the account, with migration for old key names and recovery from corrupt payloads; the build has no storage layer for any UI preference — selection and ordering are in-memory store fields that reset on remount. The missing capability is the storage path itself plus the continuity the user would get from it (the shell comes back with the same session selected, the same layout).

## Verdict: ASK-HUMAN

No recorded ruling located covers persisted UI preferences: ADR-0018's master rule (imitate the reference in entirety) pulls toward incorporating, but the exception rows checked in DD-002 address other state and do not settle sidebar preferences, and the build's in-memory-only design in `shell-store.ts` is documented as a deliberate choice not to claim persistence, rather than an oversight. This is the same underlying question DD-002 raised for window placement — the client has no storage channel today, and any persistence needs a host-side storage decision first (one that respects the no-second-database constraint); asking once about the storage path can settle both DDs together. Ask the human whether UI-preference persistence is wanted at all, and if so, which host-side channel carries it — do not pick silently.

## Incorporation notes
- **Where it would live:** a host-side storage path in the `src/adapter`/`src/core` style (the same path DD-002 would need — build it once, key it per preference group); the client-side shape goes in `src/client/shell-store.ts` as pure restore/apply functions over the existing snapshot (re-validate a saved selection against feed-delivered rows — an unknown id must be refused or dropped, matching the store's rule against showing state that is not there), with block metadata (name, schema version, account sensitivity) declared alongside.
- **Constraints:** the no-second-database rule (preference records live in existing dsh persistence, never a new store); the store's purity rule (restore is a pure function of the saved value plus feed state, no DOM reads); the requirement to degrade honestly — a corrupt or wrong-version payload must fall back to empty defaults, never render a lie, and a saved selection naming a session the feed has not delivered stays inert until the row exists; account scoping must follow whatever the host's keying offers, not something the client invents.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the store transitions are small and testable offline, but the host↔client storage channel does not exist yet and carries the real cost, shared with DD-002 if the human rules the storage path in once for both.
- **Key reference anchors:** `the reference tree's frontend/src/recovered/features/conversation/workspace/sidebar-collapse-state.ts` — block declaration with schema version and account sensitivity, legacy key table, and the rules for reading absent, corrupt, and versioned payloads; `the reference tree's frontend/src/recovered/features/conversation/workspace/sidebar-layout-state.ts` — layout block with defaults and width clamp bounds; `the reference tree's frontend/src/recovered/features/roster/selection-state.ts` — last-selected-agent block.
