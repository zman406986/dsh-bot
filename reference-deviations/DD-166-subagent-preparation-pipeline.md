# DD-166 — Subagent preparation pipeline vs prompt-string-alone spawning
- **Area:** A19 tool surface
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
Before a subagent starts, the reference runs a substantial dedicated preparation module (roughly 850 lines) that does real work on the subagent's behalf. It resolves model policy (which model the child should run on), assembles a context state object for the child, attaches files to the spawn, decides whether read-only inheritance applies, performs placement (which machine or environment the child lands on), and runs hooks at defined points in the spawn sequence. A separate subagent-configuration builder (in the reference's task module, around lines 157-193) constructs the subagent's system reminder from that prepared state. The net effect: a spawned subagent is not just handed a string — it is *assembled* from resolved policy, staged attachments, an explicit permission posture and a chosen placement, with hook points where the surrounding program can intervene.

## What the current build does
The build spawns a worker by handing it a prompt string. `src/core/policy/prompts.ts:91` records the self-containment stance explicitly: the spawn prompt must stand alone, because the worker cannot see the conversation, the user's earlier messages or sibling work — so goal, constraints, context, success criteria and report format all go into the prompt text. The worker-side contract is a static document (`src/worker/prompt.ts`) delivered in a system position as the spawn request's persona, with its sections in a fixed order and deliberately free of task content. There is no preparation pipeline, no model-policy resolution, no attachment staging at spawn, no read-only inheritance decision, no placement logic and no spawn hooks. The tool surface itself (`src/core/tools.ts`) is the spawn/steer/stop/check shape, not a pipeline.

## The deviation
This is fundamentally an ownership consequence. The reference owns the agent runtime, so it owns the decisions that precede a run — which model, which context, which files, which permission posture, which machine, which hook fires. The build delegates execution to the host, so those decisions are either the host's or absent by design. Framing it purely as a missing feature would misread the architecture: the reference has a pipeline because it has something to prepare *for*.

There is a residual point worth noting. The reference's insistence that a subagent's context be *assembled* rather than left implicit is a design rule, and the build partly mirrors it from the other direction: the self-containment rule at `prompts.ts:91` is exactly the claim that the child's context must be made explicit and complete at the point of spawning, because nothing downstream will fill it in. The reference assembles context programmatically; the build requires the dispatcher to write it out in the prompt text. Same rule, opposite mechanism, and the build's version is the consequence of not owning the runtime.

## Verdict: DO-NOT-INCORPORATE
No recorded ruling addresses this deviation directly, so the verdict rests on the PRD and by inference from the closest accepted rulings. PRD §2's non-goal excluding reconstruction of dsh's inference/tool runtime applies directly to model policy and placement: a build that does not own the runtime cannot own the choices the runtime makes, and rebuilding them to mirror the reference would be exactly the non-goal. The context-assembly stage is already covered in spirit by the self-containment rule — at the build's scale, "the prompt must stand alone" achieves what the reference's context-assembly module achieves in code, at a much smaller cost. Excluded as unnecessary machinery.

The one stage that may deserve separate treatment is attachment staging at spawn, which overlaps the attachment family rather than the runtime non-goal — see `(DD number pending)` for the attachment filings. Whether that stage has an independent case is a question for those filings, not this one; this deviation should be read as excluding the pipeline as a whole while leaving that boundary to them.

## Incorporation notes
- **Where it would live:** Not applicable for the pipeline as machinery. If any single stage were ever pursued independently, attachment staging at spawn would be adapter-side near the spawn request construction — not a new pipeline module under `src/core/policy/`.
- **Constraints:** PRD §2 non-goal excludes rebuilding dsh's inference/tool runtime; model policy, placement and spawn hooks fall on the wrong side of that line. The self-containment rule (`src/core/policy/prompts.ts:91`) and the static worker contract (`src/worker/prompt.ts`) already achieve what the reference achieves by assembling the context programmatically, at the build's scale, and the contract's fixed-section shape is pinned by tests — any change to how a worker is prepared must not disturb those markers.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S if the whole pipeline is excluded and only a note is carried forward; L and architecturally wrong if the pipeline were built, since it would amount to reconstructing the runtime the build deliberately delegates.
