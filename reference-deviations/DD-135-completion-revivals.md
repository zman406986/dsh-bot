# DD-135 — Hidden completion-revival turns vs visible dispatcher wake turns
- **Area:** agent runner / turn execution (A16)
- **Type:** deliberate-divergence (partially recorded)
- **Date:** 2026-09-23

## What the reference does
When a background subagent or shell command finishes, the transcript extension queues the completion keyed by its parent and removes duplicates (the reference tree's `source/host/extensions/transcript/completion-revivals.ts:103-118`). It then does not merely notify the parent — it *re-runs* the parent runner, batching all queued completions into one synthesized revival prompt (subagent variant at lines 28-47, shell variant at 64-90) and launching it as an exclusive background run (lines 160-232, 276-328). The revived turn is opened with hidden and silence-allowed flags and an auto-review epoch set to continue (lines 186-188 and 298-300), in a run slot whose source is tagged as a subagent revival or a shell revival (lines 215, 328) — the user never sees the turn itself, only any message the revived agent chooses to send. Work that originated from a quiet, self-initiated source gets a swapped-in, stricter instruction: speak once via a message only if the outcome is genuinely actionable, otherwise end the turn in total silence (lines 6-18 define the quiet-origin note; the quiet instruction variant is selected at lines 45 and 88). Every revival attempt resolves to a recorded outcome — delivered, superseded, or dropped with a reason (no runner, session unavailable, suspended, error, queue overflow) — and undeliverable completions fall back to a pending-wake store with a bounded retry (the three-attempt limit comes from the enumeration findings; the counter is not in this file and was not re-verified).

## What the current build does
A worker settle flows through `host.onWorkerSettled` → state transition → `wakeBus.enqueueWorkerSettled` (`src/core/multitask.ts:483-516`), and the wake bus batches and routes it to the dispatcher (`src/core/wake-bus.ts`, `requestDispatcherWakeup`). The wake is consumed by the dispatcher's ordinary, *visible* turn — it appears in the running-tasks surface like any other dispatcher activity — and the wake report body is clamped to a fixed length (ADR-0018 exception D21, register row A-7 at `docs/research/dsh-core-loop-deviations.md:68`). Delivery of the result to the user is not left to the revived agent's discretion: it is a duty recorded in the todo ledger and tracked across restarts, with a bounded number of redelivery attempts that ends in a "lost" state (ticket 58), mirroring the reference's bounded-retry discipline. Double settles never revive or re-wake (`src/core/multitask.ts:490-491`).

## The deviation
Same trigger, different turn shape. The reference answers a completion by resurrecting the parent agent on a turn that is hidden from the user and permitted to end in silence, with the send-a-message discipline pushed into the prompt text and only outcome records watching the result. The build answers the same trigger with one visible dispatcher wake whose report is clamped to a fixed length, and makes user-delivery a durable todo-ledger duty rather than a prompt-level hope. The build also has no per-parent revival queue: the wake bus batches settles, and the todo-ledger/redelivery path covers the "couldn't deliver yet" cases the reference handles by re-queueing.

## Verdict: ADAPT
The build's choice is the right adaptation and is well-grounded: ADR-0018's C15 (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:30`) permits only dispatched workers as a wake kind, which rules out the reference's extra hidden turn kind, and the rule that every turn is visible and honest — every agent turn the user's session takes is observable — directly contradicts hidden, silence-allowed revival turns, so importing the mechanism wholesale would violate that settled rule. The outcome semantics the reference pursues (deliver the meaningful result; don't spam) are preserved in build terms via the D21-clamped wake and the ledger's bounded redelivery that ends in "lost", which matches the reference's own bounded-retry spirit. However, the hidden-revival-turn *concept* has no explicit row in the deviation register — `docs/research/dsh-core-loop-deviations.md` contains no mention of revival (grep-verified), and C15/D21 cover the wake kind and its clamp, not the rejection of hidden parent-revival turns as such — so this deviation is only partially ruled; it should gain an explicit register/exception row, and any future desire to adopt hidden revival mechanics is a fresh ask-human decision, not a silent pick.
