# DD-013 — OS fullscreen state tracking vs DOM-maximize only
- **Area:** UI shell / window chrome (A1)
- **Type:** deliberate-divergence (follows the design that uses a DOM window)
- **Date:** 2026-09-23

## What the reference does
The reference renderer tracks real OS window state as first-class UI input. On boot it calls the bridge's window-state getter (ProductionRenderer.tsx:2749) and then subscribes to the bridge's window-state event feed (:2759-2761), keeping fullscreen / maximized React state (:892-893) continuously in sync with the Electron `BrowserWindow`. Those two booleans are then fed into the shell chrome — the workspace indicator, the status badge, and the window chrome each receive a fullscreen flag (the chrome also a maximized flag) (:3427-3443) — so when the OS window goes fullscreen the badge, workspace indicator, and window chrome hide/condense and the layout adapts. The data originates in the Electron main process: a window-state reader takes the Electron window's fullscreen / maximized flags off the BrowserWindow (the reference tree's `source/electron-main/window-chrome.ts:182-183`), and the renderer-facing surface is the desktop-bridge contract's window-state getter plus its window-state event listener (the reference tree's `frontend/src/recovered/contracts/desktop-bridge.ts:95-96, 408-409`).

## What the current build does
The build has no fullscreen concept at all (zero matches for "fullscreen" in `src/`). Maximize exists purely as the floating window store's own DOM-level state: a `maximized: boolean` on `FloatingWindowState` with a `toggleMaximize(viewport)` action that fills the viewport minus a margin, Windows-style, remembering the pre-maximize rect and restoring on drag (`src/client/floating-window-store.ts:28-45, 92, 139-144, 249, 473-489`, pinned offline by ticket 105). Nothing observes the OS: the build runs inside the stock dsh web page, using the DOM floating window that ADR-0021 chose, where there is no Electron main process of our own and no IPC bridge carrying window events. A maximized window even persists its maximized-ness across close/reopen by re-filling the *current viewport* — a geometry rule, not an OS notification.

## The deviation
The reference keys chrome presentation off OS-level window state delivered as a main-process event feed; the build substitutes its own in-page maximize bookkeeping with no external state source. The build's maximized flag is roughly the analogue of the reference's maximized flag, but nothing corresponds to the reference's fullscreen flag: a DOM window cannot see that signal at all, because it is not an OS window and has no main process to query or subscribe to. Layout/chrome behavior is therefore driven purely by the store's own geometry.

## Verdict: DO-NOT-INCORPORATE
OS window-state events are Electron-main territory (`BrowserWindow.isFullScreen()/isMaximized()` in the reference's `window-chrome.ts`), which the DOM floating window chosen by the human cannot see: ADR-0021 (accepted, decided by the human 2026-09-20) keeps stock dsh as the primary UI and hosts dispatcher functions in an additive DOM floating window over it, so there is no OS window of ours to observe and no recorded ruling asking for OS fullscreen behavior. Incorporating the event feed would require re-opening the design decision itself, which the authority stack does not allow on a divergence note. The only meaningful analogue available in this design — condensing window chrome while the store's DOM `maximized` is true, echoing the reference's fullscreen chrome collapse — is a new product choice nobody has requested, so it would need its own ticket and human sign-off rather than riding this deviation. No recorded ruling covers fullscreen state specifically; this verdict rests on ADR-0021's design decision plus the fact that a DOM page cannot see OS events.

## Incorporation notes
- **Where it would live:** (if the human ever wants the DOM analogue) the maximize branch already exists in `src/client/floating-window-store.ts` (`maximized` flag, `toggleMaximize`); a chrome-condensation consumer would use that flag in the floating window chrome component — no new state source, no bridge, no main process.
- **Constraints:** ADR-0021 decision 1 (stock dsh is never displaced) and decision 2's additive `shell.overlay` extension point stand — no Electron frame and no root-frame election; ADR-0018's master rule otherwise; the exact DOM technique is ticket-level evidence, not ADR-level (ADR-0021 open questions). Any chrome-hiding behavior changes what ticket 105 pinned offline (maximize/peek-clamp comments and tests), so it is a new ticket with its own evidence, per the recorded pattern for floating-window changes.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S for the optional DOM analogue (a conditional class/render on an existing store flag); the OS event feed itself is L and outside this design's scope (new host process surface).
