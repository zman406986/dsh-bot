# DD-006 — App-wide fatal error surface vs per-open window boundary
- **Area:** UI shell / window chrome (A1)
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference wraps the **entire renderer** in one root-level error boundary. Its app entry module mounts that root-shell error boundary around the whole production renderer at the DOM root, so any crash anywhere in the app — not just one pane — flips to a dedicated fatal surface. The boundary itself (the reference tree's `frontend/src/recovered/features/window-chrome/root-shell-state.tsx:143-169`) is a class component that captures error + component stack in `componentDidCatch` (logged under a renderer-root error tag) and renders the root-shell fatal-error surface (lines 129-141), which delegates to a shared error-boundary surface component (the reference tree's `frontend/src/recovered/features/error-boundary/view.tsx`). That surface offers real recovery affordances: a **reload** button (`window.location.reload()`) and a **copy-error** button (clipboard write with a copied-acknowledgment state swap), plus a detail disclosure — labeled copy for the title, reload, copy-error, and detail controls. On top of the app-wide net, the production renderer adds a second, narrower settings-overlay error boundary (`ProductionRenderer.tsx:158-176`, applied at line 3631) around the lazy/Suspense settings overlay with its own **retry/close** semantics (close clears the overlay) — so a settings crash degrades only the overlay, not the shell beneath it.

## What the current build does
The build cannot and does not own an app-wide boundary: stock dsh is the primary UI (ADR-0021 decision 1) and the renderer root is the host's, protected by the host's per-entry `SlotErrorBoundary` (one registrant crashing retires only its own entry — the crash-isolation rationale recorded in the `src/client/floating-window.tsx` header, lines 52-65). The build's own boundary is `DispatcherWindowBoundary` (`src/client/floating-window.tsx:209-236`), which wraps **only the hosted dispatcher shell inside the window body** — deliberately below the portal so a shell crash cannot retire the whole entry at the host layer (which would take the titlebar and launcher capsule with it). The titlebar renders outside the boundary; the boundary is keyed by the store's `openEpoch` (line 325), so every open mounts a fresh one and a crashed window recovers on close + reopen. The fallback is a single honest failed line (`data-window="failed"`, copy from the `launcher.window.failed` i18n key); `componentDidCatch` is intentionally empty — "Contained by design — the honest fallback line below IS the report." There is **no reload affordance, no copy-error affordance, and no error-detail disclosure** in the failed state.

## The deviation
Two deltas. (1) **Scope:** the reference's outermost boundary is app-wide with a full fatal surface; the build's outermost self-owned boundary is the per-open window body, because ADR-0021's additive-window approach leaves the renderer root to stock dsh — this part follows from the chosen setup, not from an oversight. (2) **Affordances:** relative to the reference's boundary surfaces, the build's failed line reproduces none of the recovery machinery — no reload button, no copy-error-to-clipboard, no detail/component-stack disclosure, and no logging of the caught error. The reference's inner pattern (a dedicated retry/close boundary around the lazy settings overlay) also has no counterpart around any heavy sub-surface inside the dispatcher window.

## Verdict: ADAPT
The scope delta is settled: ADR-0021 decision 2 (decided by the human) requires the floating window to "fail in isolation", and decision 1 forbids displacing stock dsh, so an app-wide root fatal surface of our own is structurally inapplicable — the per-open window body boundary keyed by `openEpoch` is the correct adaptation and is not up for re-litigation. What is **not** covered by any recorded ruling is the affordance gap: ADR-0018's master rule (imitate the reference in entirety, exception list) has no exception recorded for the error-surface affordances, so the reload/copy-error/detail machinery is an unruled imitation gap that should be folded into the existing `DispatcherWindowBoundary` fallback — adapted to the per-window context (recover by reopening that window rather than `location.reload()`, which would reload the host app and is exactly what the additive setup must not do). No ADR or ticket ruling speaks to boundary affordances precisely; this verdict rests on ADR-0018's default rule plus ADR-0021's constraints, and a human can reverse it.

## Incorporation notes
- **Where it would live:** the fallback branch of `DispatcherWindowBoundary` in `src/client/floating-window.tsx` (extend the `failed` chrome to carry affordance labels alongside the existing `launcher.window.failed` line, likely new i18n keys in the chrome/i18n module that defines it); the error capture would go in `componentDidCatch`, which is currently a deliberate no-op. If a lazy heavy sub-surface exists inside the shell (the settings analogue), a second nested boundary with retry/close semantics would mirror the reference's settings-overlay boundary layering.
- **Constraints:** keep the boundary below the portal and the titlebar/capsule outside it (ADR-0021 decision 2 isolation; the ticket-100 structural pin on child order); do NOT offer `window.location.reload()` — a renderer reload reloads stock dsh too, so window-level recovery means close-and-reopen (already served by the `openEpoch` key) plus a copy-error/detail affordance for diagnosability; keep `render()` hook-free and deterministic so offline tests can drive both branches (the S8 note at lines 204-207, where S8 is the PRD's offline-test success criterion); any copy must be independently re-derived wording, not the reference's strings.
