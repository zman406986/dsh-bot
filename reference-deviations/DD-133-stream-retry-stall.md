# DD-133 — Transient stream retry & first-token stall deadlines vs host-owned attempts
- **Area:** agent runner / turn execution (A16)
- **Type:** missing-feature (unruled policy)
- **Date:** 2026-09-23

## What the reference does
The reference host runner wraps every model stream in a bounded retry loop. The attempt factory runs the turn's stream through a generic bounded-retry helper under a retry policy (supplied by the host, otherwise a default policy for overload cases), with failure classification from a dedicated module: transient errno codes and message tokens, provider-declared retryability flags, and exceptions for terminal errors and context-overflow cases where retrying cannot help. Retrying happens only when it is safe — allowed only when no stream output was produced or a checkpoint has been accepted — and the retry resumes the stream from that last accepted checkpoint so already-produced output is not lost. Separately, a first-token stall deadline (a resolved base value; disabled when zero or negative) guards each attempt: if the provider produces nothing before the deadline, the attempt is cancelled with a dedicated stall error, and the deadline doubles per retry performed. The runner host injects the deadline timer implementation through the attempt contract. Telemetry is first-class: each retry reports one of three outcomes (a retry taken, the budget exhausted, or a give-up because the error was not retryable) with attempt number, budget, delay, and a server-paced flag, plus a user-visible retrying signal and trace attributes. Backoff is exponential with jitter, and server `retry-after` hints are honored under a cap.

## What the current build does
Nothing in the build owns stream attempts. The worker's model stream executes inside the dsh host loop (the installed dsh agent runtime); the dispatcher sees a turn's outcome only when it settles, via host events (cf. DD-125's streaming-ownership finding). There is no transient-error classification, no retry budget, no stall deadline, and no retry telemetry channel anywhere under `src/`. Core defines the opposite rule for dispatcher decisions: a remedy is a considered decision, not a blind retry (`src/core/types.ts:105`). The only "retry" language in the build is UI/worker copy forbidding blind retries and a todo delivery-retry path (`src/core/todo-reconciler.ts`), which redelivers messages and has nothing to do with provider-stream recovery.

## The deviation
The entire transient-stream retry and first-token stall machinery is absent: bounded attempts, checkpoint-resume-on-retry, the doubling stall deadline, the safety condition (retry only when no output was produced or an accepted checkpoint exists), and the three-outcome retry telemetry. This sits next to DD-127 (token-limit classification lives in the same area of error handling) but is a distinct, unruled policy: the deviation register carries no disposition for it (`docs/research/dsh-core-loop-deviations.md` — its only stream-adjacent row, B-1, is stream-key durability), and it does not appear in the ADR index. Under ADR-0018's master rule (imitate the reference except an enumerated exception list) it is therefore formally an open gap. Unlike DD-125, nothing in the build supplies an equivalent outcome by other means: whether the dsh host retries transient stream failures internally is unverified here (DD number pending), so a failed stream may currently surface to the dispatcher as a raw settle failure with no recovery and no telemetry.

## Verdict: ASK-HUMAN
The worker's model stream is started and owned by the dsh host loop, so nearly all of this machinery cannot be built here: the build cannot wrap attempts it does not start, cannot enforce a stall deadline on a provider request it cannot see, and cannot resume a stream from a checkpoint it does not hold — a build-side policy could only react after a turn settles, at which point the reference design's core benefit (resuming from the last accepted checkpoint before output is lost) no longer applies. The register has no disposition for this policy and no recorded ruling covers it, so under the authority stack it stops with the human rather than being silently picked: either rule it an accepted exception on host-reliability grounds (the host owns stream recovery; the dispatcher's settle-failure remedies already exist as decisions), or rule an adapted dispatcher-level remedy policy for failed worker turns, which would be a new design, not a port of the reference code.

## Incorporation notes
- **Where it would live:** If ruled build-side at all, the only feasible place is dispatcher-level reaction to worker-turn settle failures — around the dispatch/remedy handling in `src/core/multitask.ts` and the host-observation layer in `src/adapter/cordis-dsh-host.ts`. The attempt-level machinery (deadline timers, checkpoint resume, per-attempt telemetry) has no build-side home; any ruling should first record what the dsh host itself already does for transient stream failures (verification task, DD number pending).
- **Constraints:** Must not wrap, delay, or interfere with host-owned stream attempts. A build-side stall deadline cannot be enforced mid-flight — the strongest available action is stopping the worker task. Any settle-failure retry would be a re-dispatch decision, so it must respect one-worker-per-stream stream-key durability (register B-1 / ticket-59 rules) and the existing rule that a remedy is a decision, not a blind retry (`src/core/types.ts:105`); telemetry, if added, should ride the existing host-event observation path rather than a new channel (cf. DD-125 constraints).
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M if the human rules for a dispatcher-level settle-failure remedy policy (host-behavior verification plus a remedy point); the attempt-level port itself is L and cannot be built here — do not attempt without a ruling.
- **Key reference anchors:**
  - the reference tree's `source/host/runner/stream-attempt.ts` — the attempt-host contract (its deadline-timer factory, its retrying-signal emitter, and its turn-retry reporter carrying the three retry outcomes); the attempt factory doubling the stall deadline per retry performed, resuming from the accepted checkpoint only when output was produced, and driving the bounded-retry helper with the per-turn retry-eligibility predicate.
  - the reference tree's `source/host/runner/transient-stream-error.ts` — transient errno/message classification with exceptions for terminal errors and context-overflow cases; the first-token stall error type; the retry policy type; jittered exponential backoff with capped server `retry-after` pacing.
