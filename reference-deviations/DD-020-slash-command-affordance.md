# DD-020 — Zero-typing palette commands vs slash commands in the stock composer
- **Area:** command palette (A3)
- **Type:** behavior-delta (ruled direction)
- **Date:** 2026-09-23

## What the reference does
The reference ships a command palette: an on-demand action list whose rows are runnable commands carrying a label, icon, keyword set, and detail line, executed by click, Enter, or shortcut — the user never types a command line. A dedicated production module builds the rows that depend on the current chat from the state passed in: a Members row only when the active chat is a group (and not a shared room), a Channels row only when channels exist, an always-present Chat Settings row, and an app-update row that appears only when an update action is reported by status (`frontend/src/production/command-palette-root-commands.ts:34-76`; the row type comes from `frontend/src/production/command-palette-model.ts`). Rows open in-place info sections or a confirmation dialog; the palette is a surface where the user never types a command, layered over the reference's own whole-UI frame.

## What the current build does
The build exposes no palette. Its command surface is four host slash-commands — `/dispatcher-start`, `/dispatcher-stop`, `/dispatcher-steer`, `/dispatcher-resolve` — registered host-side in `src/adapter/activation-command.ts`, `src/adapter/stop-command.ts`, `src/adapter/steer-command.ts`, and `src/adapter/resolve-command.ts`, and reachable exactly as a typed line in the stock dsh composer. The client side never adds a second way to send: its only output path is the composer's own command transaction, and the visible affordances are thin wrappers over those same lines — the sidebar add/delete affordances execute `/dispatcher-start`/`/dispatcher-stop` verbatim in the target session, approval-card buttons execute `/dispatcher-resolve <workerId> <choice>`, and the per-row steer affordance prefills `/dispatcher-steer <workerId> ` into the user's draft (line constants and helpers in `src/client/actions.ts`; the transport binding is `bindCommandTransport` there). Some of these are one-click, but the underlying action is always the host command line, not a bespoke handler.

## The deviation
The reference's affordance model is "pick a labeled action from a searchable palette; the app runs it directly." The build's model is "affordances issue the host slash-command the user could have typed." The palette's execution of in-app handlers without typing anything is replaced by command lines — sometimes prefilled and submitted for the user, sometimes merely placed in the composer for review-and-send. State-conditioned rows (group-only Members, hasChannels-only Channels, status-driven updater) have no counterpart list; instead the state decides where an affordance is placed (roster rows, approval cards) at render time. The difference is a deliberate consequence of the ruled UI shape, not an omission: ADR-0021 records the human ruling that stock dsh stays the primary, undisplaced UI and dispatcher functions are called out additively, and the add/delete affordances were ruled to execute the host command in the target session (ADR-0021 decision 3; the verbatim-line constants cite ticket 101 in `src/client/actions.ts`).

## Verdict: DO-NOT-INCORPORATE
The ruled direction settles this. ADR-0021 (a recorded human ruling, the highest level in the repo's ruling order) makes stock dsh the primary UI that our client must never replace — a palette layer replicating the reference's command surface inside our own frame is the kind of replacement the ruling rejected, and its in-place handlers would be a second way to send, which ADR-0009's explicit-activation rule and the client output rule in `src/client/actions.ts` forbid. ADR-0021 decision 3 instead rules the affordance shape: sidebar add/delete executing the host command verbatim in the target session. The palette's useful property the build deliberately keeps is not handlers that need no typing but affordances that show only real outcomes, over the same send paths the user's typing reaches; changing the UI shape again is a human decision, not ours. If the human ever wants a dispatcher command list, that is a new ruling to request — this file records why the reference shape does not transfer.

## Incorporation notes
- **Where it would live:** nowhere under current rulings. A hypothetical palette would belong in the floating-window client surface (`src/client/`), feeding a command list over the same `CommandTransport` output path — never a second dispatch path.
- **Constraints:** any future list-based affordance must (a) execute host slash-command lines verbatim via the composer transaction, (b) stay additive to stock dsh per ADR-0021 decision 1, (c) report failure truthfully (`no-channel`/`unresolved`) rather than crash the floating window, and (d) never let the client stop a worker turn (`src/client/actions.ts` scope guard on `/dispatcher-stop`).
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — a palette would need its own overlay UI, command registry, and state conditioning, and it would fight the ruled requirement that stock dsh stays primary; do not build without a new human ruling.
- **Key reference anchors:**
  - `frontend/src/production/command-palette-root-commands.ts:34-76` — state-conditioned root rows (Members/Channels/Chat Settings) and the status-driven updater row, each with label/icon/keywords/detail and a direct run callback.
  - `frontend/src/production/command-palette-model.ts` — the palette row type and activation model (read-only reference; row shape only).
