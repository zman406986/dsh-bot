# DD-142 — Anticipatory-initiative persona section vs reactive-only policy
- **Area:** system prompts / persona (A17)
- **Type:** missing-feature (persona content; partly ruled out via routines scope)
- **Date:** 2026-09-23

## What the reference does
The reference system prompt carries a dedicated **Initiative** persona section near its end. It tells the agent to infer who the user is from context (role, files, workflow) and to think a step ahead to what they will want next. The bar for acting is deliberately high: a real, specific opportunity grounded in something the agent actually observed the user do — never a generic suggestion. When the bar is met, the agent either just does the thing (when clearly safe and in scope) or makes one brief inline offer that names the signal it came from. The section limits this to one high-value suggestion at a time, phrased so it is easy to decline — never naggy, never busywork, never a pile of questions. It then lists concrete signals worth acting on, of which the two headline ones are: (a) a repeated manual task is the strongest signal — offer to make it a standing routine, citing the repeat; and (b) a task that needed a service with no connected connector — surface that connector so the next run is smoother. A closing paragraph keeps initiative scoped to the handed task and forbids widening access or routing around safety checks to prove its worth.

## What the current build does
The dispatcher policy prompt (`src/core/policy/prompts.ts`) contains no proactive-behavior instructions at all — nothing about anticipating future needs, offering next steps, suggesting routines, or surfacing missing capabilities. Its forward-looking content is purely reactive bookkeeping: on every wake, reconcile the ledger first (what is running, what landed undelivered, what still needs dispatch), and when a worker settles, decide whether the finished work is new and relevant enough to send — with an explicit default of staying silent otherwise. The overall persona rules push the other way: the user never hears the machinery, and unwanted background outcomes end the turn without a message. Proactivity in the build exists only as background dispatch mechanics (delegating work so the primary agent stays responsive), never as user-facing initiative.

## The deviation
The reference treats anticipation of the user's next need as a persona duty with a disciplined protocol; the build has no equivalent rule anywhere in its prompts. The gap is not one missing line but a whole area of behavior: reference agents are told to act on observed signals unprompted, while build agents only ever answer what arrived and otherwise keep silent. Part of the reference section is already ruled out of scope — the routine-proposal part depends on a routines/automations subsystem the project does not have and has explicitly excluded — but the general "anticipate and offer one specific, grounded suggestion the user can easily decline" rule is persona content, not a subsystem, and the build simply lacks it.

## Verdict: ADAPT
The routine-proposal signal is covered separately and ruled out of scope (cross-ref DD-184 for the automations-specific ruling; ADR-0018 C14 rules out a routines/automations subsystem, and ADR-0004 makes the reference a list of features to consider, not a build list — so that part is a deliberate no, not an oversight). The missing-connector signal maps onto reference-specific plugin plumbing and is best left unincorporated. What survives is the general persona rule: think a step ahead within the task the user handed you, and when a specific observed signal justifies it, make one brief, easy-to-decline inline offer. That rule does not collide with any recorded ruling — the build's silence rules govern machinery narration and unwaited background results, not inline offers during a live turn — but its absence is arguably a deliberate pull-only (only what the user asked for) policy consistent with the build's restrained persona, so it should be adopted only as a minimal, constrained addition (and ADR-0004's rule of logging skipped capabilities means leaving it out is legitimate if the human prefers the pull-only reading).

## Incorporation notes
- **Where it would live:** the primary-chat persona / standing-rules area of the dispatcher policy prompts (`src/core/policy/prompts.ts`); it must stay out of the wake/settled-workers instructions, which are correctly silence-defaulted.
- **Constraints:** general rule only — no routine or automation suggestions (ADR-0018 C14); no new wake kinds or background behaviors (C15); suggestions must trace to a specific in-task observed signal, one at a time, phrased in plain user-facing language with zero machinery vocabulary; initiative stays scoped to the handed task and never widens access or works around safety checks (mirror the reference's closing boundary in spirit); must not weaken the existing stay-silent rules for background/wake turns.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying of reference prompt text under any circumstances.
- **Effort/risk:** S — a one-to-three-line persona addition plus a test; risk is low if scoped as above, but it shifts persona tone toward chattier behavior, so it deserves a human sign-off before landing (or an explicit ADR-0004 skip entry if declined).
- **Key reference anchors:**
  - the reference tree's `source/host/runner/system-prompt.ts` — its initiative persona section (heading, think-a-step-ahead paragraph with the specific-signal bar and one-suggestion limit, the signals list, and the scope/safety closing paragraph).
