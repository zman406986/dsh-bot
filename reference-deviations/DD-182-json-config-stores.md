# DD-182 — Atomic JSON config stores for coordinator and app settings
- **Area:** A21 storage
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference keeps several small configuration and state documents as plain JSON files on disk, written with a temp-file-then-rename sequence so a reader never observes a half-written document, and with a restrictive owner-only permission mode (recorded as 0600) applied at write time. The same pattern is applied everywhere rather than case by case: a shared client-persistence store opens its write on a temp sibling carrying a temp suffix and renames it into place (`the reference tree's source/shared/client-persistence-store.ts:8`, `:192`); the coordinator-side stores write their JSON with the private mode and then rename (`the reference tree's source/node-agent-coordinator/local-exec/daemon-files.ts:75-76`; `the reference tree's source/node-agent-coordinator/inference-router.ts:70`); and the window-state persistence path writes its temp file with the same private mode before renaming (`the reference tree's source/electron-main/window-state-persistence.ts:114-116`). App settings have their own host-side store and service modules (`the reference tree's source/host/extensions/settings/settings-service.ts`, also `the reference tree's source/host/agents/settings-file.ts`). Window geometry is one consumer of the same store pattern (`the reference tree's source/electron-main/window-state-store.ts`).

## What the current build does
The build writes no configuration JSON of its own. Configuration is delegated to the host: the adapter installs a settings section and registers a namespace plus schema with the host's settings service, getting back a settings scope bound to that namespace, and reads configuration through the scope rather than through files (`src/adapter/settings-section.ts`; the module's own header records why the owner scope comes from the scope-returning registration call rather than from the section install, and ties this to ADR-0005). Window geometry is held in memory by the client store (`src/client/floating-window-store.ts`); whether it should persist at all is the subject of DD-002, and is not re-filed here.

## The deviation
The reference owns its config documents end to end — path, JSON shape, permission mode, write atomicity — because it owns the whole application. The build is a plugin, and the host owns configuration storage, so the build registers a settings scope with a schema in the host's settings service instead of keeping files. The consequence is that the reference's atomic-write plus private-permission store pattern has no consumer here: there is no config file for the build to write, and no direct file-write or rename call anywhere under `src/`, client included. Applying 0600 is sound security practice on the reference side (private config and credential-adjacent documents are not left group- or world-readable), but it describes files the build never creates.

## Verdict: DO-NOT-INCORPORATE
Recorded rulings cover this. ADR-0018 A5 forbids a second store or database; ADR-0006 pins durable worker state to dsh's session/job store through the obligation-marker pattern rather than through a store of our own; and DD-177 already rules the A21 storage design DO-NOT-INCORPORATE. Delegating configuration to the host's settings scope is also the correct ownership boundary for a plugin, so adding a private JSON config store would invert that boundary rather than improve it. Window-geometry persistence is separately filed as DD-002 (which reaches ASK-HUMAN there) and is cross-referenced, not duplicated, here.

## Incorporation notes
- **Where it would live:** nowhere — the build has no config-file writer. Configuration belongs to `src/adapter/settings-section.ts`'s host-delegated scope; window geometry belongs to DD-002's area (`src/client/floating-window-store.ts` plus a storage path on the host side).
- **Constraints:** ADR-0018 A5 (no second store/database), ADR-0006 (durable state rides `ctx.sessions` / `ctx.storage`), ADR-0005 (settings-section install path), DD-002 (window geometry, ASK-HUMAN there), DD-177 (A21 storage design). A5 plus the plugin ownership boundary are what make the verdict a refusal rather than a deferral.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — nothing to build. The only lasting takeaway is a one-line habit: if the build ever gains a file-writing store of its own, write private and atomically. No such file exists today, so no narrow ADAPT is filed.
- **Key reference anchors:** `the reference tree's source/shared/client-persistence-store.ts:8,192` (temp-suffix write, then rename into place); `the reference tree's source/node-agent-coordinator/local-exec/daemon-files.ts:75-76` (private-mode JSON write, then rename); `the reference tree's source/node-agent-coordinator/inference-router.ts:70` (private-mode store write); `the reference tree's source/electron-main/window-state-persistence.ts:114-116` (temp path, private mode, rename); `the reference tree's source/electron-main/window-state-store.ts` (window geometry store — see DD-002); `the reference tree's source/host/extensions/settings/settings-service.ts` and `the reference tree's source/host/agents/settings-file.ts` (host settings store and service modules).
