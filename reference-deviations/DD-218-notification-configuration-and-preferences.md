# DD-218 — Notification configuration and per-agent notify preferences
- **Area:** A28 approval & policy
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
Notification behavior is not hard-coded in the reference: it is read out of persisted settings and out of per-agent state. The two parts are worth describing separately, because only one of them actually does anything.

**The stored-settings part is deliberately inert.** The settings store exposes a notification-config accessor pair (the reference tree's `source/shared/node/settings/sand-settings-store.ts:150-151`). The getter takes no argument, inspects what is persisted, and — if it is anything other than the single-key disabled value — rewrites the stored value to that value before returning a module-level disabled constant; it never returns what the caller previously stored. The setter accepts an argument and discards it, writing the same disabled value through the ordinary update path. The stored value therefore can never be anything but off, and neither accessor honors its input. The disabled constant itself (the reference tree's `source/shared/host-settings.ts:1`) is not merely an off flag: it also carries an empty list of apps permitted to notify and a rate-window triple (a minimum interval between notifications, a maximum count per window, and the window's length). So the permanently-off value still describes what an enabled configuration would have contained — an app allowlist plus a throttling policy — while nothing in the product can turn it on. These accessors sit on a live settings path, not a dead one: the settings service reads the config into its settings snapshot and routes an incoming settings update back through the setter (the reference tree's `source/host/extensions/settings/settings-service.ts:33,36`), so the read and write both happen on real user-visible settings traffic and both land on the disabled value regardless.

**The per-agent part is the live mechanism.** Every agent snapshot carries a boolean preference recording whether the user wants to be notified about that agent's updates (the reference tree's `source/shared/os-notification.ts:2-3`). It is mapped onto the snapshot's own notify flag (`:5`) and then read as one of the inputs to the single delivery gate — the gate requires the preference to be on, the agent not hidden from the sidebar, the window unfocused, and the per-(agent, transition-kind) throttle window elapsed (`:7`). The minimal agent summary used for lightweight listings defaults the preference on while a separate notifications flag defaults off (the reference tree's `source/host/extensions/session/session-summaries.ts:13`), so the two flags are not interchangeable. The writer that would change the preference is nonetheless a stub: the gateway API's per-agent notification-enablement command resolves immediately to nothing (the reference tree's `source/host/host-gateway-api.ts:342`), even though the RPC surface declares it (the reference tree's `source/shared/rpc/coordinator.ts:123`, dispatched in the reference tree's `source/host/gateway-protocol.ts:36`). The preference is read live and written never — the same asymmetry as the config accessors, at a lower level.

## What the current build does
No notification configuration exists in any form, and no per-agent notify preference exists.

A search across `src/` and `client/` for notification vocabulary returns only in-process signalling and comments. The core's roster-change fan-out (`src/core/multitask.ts:385`) is an observer callback that never lets a throwing observer break core flow; the access prompt exposes an expired-ticket callback and a secret-stored callback (`src/adapter/access-prompt.ts:426,432`). None of these is a preference, a persisted setting, or a config key — they are projection signalling inside the process, and DD-209 already records that none of them reaches an OS surface.

The plugin's settings schema defines exactly two fields — an enabled flag and an access-request timeout (`src/plugin.ts:56,61`) — and the settings card renders exactly those two, checked by an offline test against the schema so that a field added to the schema without a control fails the suite instead of rendering a card that hides part of the namespace (`src/client/settings-card-store.ts:194-214`). There is no third control, no notification namespace, and no per-agent preference on any worker record: workers carry a title, a status, and todo linkage.

The delivery path and the code that decides when to notify are already filed as **DD-209**, which also records that the installed host runtime has no notification or toast interface and that this absence is a decision rather than an oversight (`docs/surfaces.md:20-38`). In-app notification hosting is **DD-004**. The stored-key angle is **DD-107**, which files the reference's notification key inside its misc-key group and defers the key's shape and meaning here. This filing covers only what sits upstream of all three: the configuration surface and the per-agent preference.

## The deviation
The reference persists a notification configuration and reads a per-agent notify preference as a delivery-gate input. The build has neither: no notification config accessor, no config key, no settings control, and no per-agent preference field. The deviation is narrower than it first appears, and it should be stated that way. The configuration part of the reference is *vestigial* — its accessors force-write one disabled value and ignore caller input, so the stored value is permanently off by construction and the persisted key is a placeholder rather than a working setting. Only the per-agent preference part is a functioning mechanism, and it is an input to a notification system the build deliberately does not have.

## Verdict: DO-NOT-INCORPORATE
Both parts are reached by recorded rulings, though neither ruling names notification configuration as such. DD-209's verdict grounds the OS delivery path in ADR-0020's draft exclusion of the native/Electron shell — an exclusion that sits above ADR-0020 in the authority stack via the PRD non-goal and therefore survives the vehicle's supersession — and the designed-absence record rules out notify-me controls, fake toasts, and bell or badge affordances in writing (`docs/surfaces.md:32-35`); a notification configuration surface would be exactly such a control, and a per-agent preference would be a preference over a delivery path that does not exist. The configuration part is additionally vestigial in the reference itself: its accessors can only ever store the disabled value and both ignore caller input, so there is nothing to port but a permanently-off value. On the fairness side, that inert pair is honest engineering — it pins the feature off at the persistence layer instead of leaving a setting that is wired only partway and would silently do nothing — and this filing records the reference's restraint rather than counting it as a capability the build lacks. No recorded ruling was found that addresses notification *preferences* as a subject in their own right; the rulings reach them only through the notification delivery path they configure, and that is why this is DO-NOT-INCORPORATE rather than ASK-HUMAN.

## Incorporation notes
- **Where it would live:** Nowhere today. A notification config would have no consumer without DD-209's delivery path, and a per-agent preference would have no reader without DD-209's code that decides when to notify. If DD-209's deciding part were ever separated out and ruled in, the preference field would belong on the core's worker/roster projection beside the roster-change fan-out (`src/core/multitask.ts`), and a config field would belong in the plugin's `Config` schema beside the existing two (`src/plugin.ts:56,61`) with a matching control in the settings card (`src/client/settings-card-store.ts:203-214`) — the schema/control parity rule would make a config field without a control fail the offline suite.
- **Constraints:** Any notification setting or per-agent toggle rendered in a UI would break the explicit no-simulation rule the project committed to in writing (`docs/surfaces.md:32-35`), and the surfaces record's standing rule — presence is a projection of existing core state, and anything needing new core state, a new host extension point, or a second source of truth is out — would bar the preference field from being invented ahead of a real consumer. Adding a persisted key with no reader would also add a surface nothing reads, the same objection DD-107 raises for its misc-key group. ADR-0018's B9 rule against verbatim copying binds any re-derivation.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — the surface itself is tiny (one boolean and one config accessor pair), so the work is not the cost; the risk is that either addition would be unused configuration contradicting a written position, which is why the effort figure should not be read as an argument to do it.
