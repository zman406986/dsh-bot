# DD-214 — Local-tool permission model: three-state setting, admin ceiling, four-way resolution
- **Area:** A28 approval & policy
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does

The reference governs use of the user's own machine with one persisted three-state setting (always / ask / never), whose default is the middle value. The setting is stored as a plain scalar, alongside a **separately stored administrative ceiling** for the same three values; a small resolution helper compares the two through a rank table and returns whichever is more restrictive, so a user choice sitting above the ceiling is silently reduced to the ceiling rather than refused or surfaced as a conflict. The ceiling is not user-editable: it is fetched from the team/account administration surface and written into the same settings record by a different path, which is what makes the model two-level (a user preference under an administrator's bound).

The same controller that reads that setting also answers asks. It exposes a four-way resolution vocabulary (allow once / deny / always / never); the ask lifecycle records a settled status per outcome and resolves the waiting caller accordingly. Choosing the always or never setting writes the three-state setting back through an injected setter and then re-notifies the controller so pending and live approvals are reconciled with the new saved value. Crucially, the write-back is wrapped: if the setter throws or the value does not stick, the always choice **degrades to allow-once** instead of failing the action — the user's intent is honored for this one ask, and the failure to persist is swallowed rather than escalated. Related machinery hangs off the same controller: per-agent direction epochs that retire approvals when an agent's turn advances, remembered refusals, and a set of honest refusal messages for the disabled, unapproved, expired, cancelled, unavailable, and stale-task paths.

The resolution entry point validates the incoming answer against the four-value vocabulary, re-checks that the pending ask exists and belongs to the asking agent, and throws a dedicated stale-request error when it does not — with a fallback that asks the transcript surface to settle a card whose request has already been retired.

## What the current build does

There is no local-tool concept. The build never runs commands on the user's machine on the user's behalf, so there is no per-tool or per-action permission setting, no three-state setting, no rank table, no administrative ceiling, and no settings field for any of them. Nothing in `src/core` or `src/adapter` stores a permission scalar, and no path fetches an administrative bound.

The nearest analogue is the dispatch approval connection (`src/adapter/dispatch-approval.ts`). It asks the host's approval service one question and accepts only four outcomes — allowed-once / rejected / cancelled / unavailable (`:99-104`) — collapsing anything else to the fail-closed `unavailable`. Its structural view of the host service declares only the one verb this path needs and says in as many words that the service's policy-setting and override accessors are **deliberately unread** (`:54-59`): no policy mutation from this path, and the delegation pin and session policy are not this path's to touch. No answer to that ask therefore mutates any stored policy. The ask is bounded by the relay's deadline constant and an unanswered ask becomes the same fail-closed refusal (`:106-136`).

Recorded adjacent material: the review decision table (`src/core/review-posture.ts:46-56`) carries per-row `session` and `profile` scope with a deny/allow decision, and the access types' stored policy row (`src/core/access-types.ts:91-108`) has the same session/profile scope split with a wildcard fence on the target pattern. Both are consent memory in the build's own sense: session-scoped by default, cleared with the session, and never a settings-managed store.

## The deviation

The reference persists consent and bounds it from above; the build deliberately does neither. Three properties separate the two designs:

1. **A persisted three-state default.** The user's choice survives sessions and is read back at the start of every ask. The build has no persisted setting at all — its only durable consent artifact is a session-scoped policy row that dies with the session.
2. **An administrative ceiling (two-level authority).** A separately stored, administrator-supplied bound clamps the user's choice downward via a rank comparison. The build has no second authority level over approval: the approval connection has exactly one answerer and no bound above it.
3. **Degradation on refusal.** A failed write-back of a saved choice silently becomes allow-once rather than failing the action. The build's approval connection has the same *shape* of honest degradation but the opposite content: its failure modes all collapse to refusal (`unavailable`), never to a weaker grant.

The honest framing is directional. The build's approval connection is read-only with respect to policy on purpose, so consent cannot widen beyond the single ask it answers. The reference is willing to let a single answered ask widen consent for all future asks — and it is the *ceiling*, not the option set, that keeps that widening in bounds.

## Verdict: DO-NOT-INCORPORATE

A recorded human ruling covers this, and it covers it squarely. ADR-0018 (accepted, human-ruled master, authority level 2) exception **U-D** states that always-allow approval rules are session-scoped and not persisted, with "no settings-managed rule store, no dedicated local tool-permission controller" (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:37`). The reference artifact described above is exactly a dedicated local-tool permission controller with a settings-managed store for both the setting and the ceiling, so the persisted default and the ceiling's storage are inside the exception, not merely near it. ADR-0011 (draft, level 4) supplies the same rule from the other end — consent memory is session-scoped and never persisted, and "consent can never silently widen" (`:11, :28`) — but its reach is narrower: it constrains the *widening direction*, which is compatible with a downward-only ceiling and in tension only with the persisted default. U-D reaches further than ADR-0011 does, which is why the verdict rests on U-D and not on the widening rule. What is *not* covered by any recorded ruling is the degradation-on-refusal property (a general honest-degradation pattern the build already practices in its own fail-closed form) and the two-level authority idea as such; both are moot here because there is no local-tool concept in the build for them to attach to. Should the human ever want to re-open U-D, that is an ADR-0018 amendment, not a deviation ticket — so nothing here is left needing a fresh ruling.

## Incorporation notes

- **Where it would live:** If U-D were ever amended, the setting would belong beside the existing policy surfaces — a persisted scalar and ceiling read alongside the policy table (`src/core/access-types.ts:91-108`, `src/core/review-posture.ts:46-56`) — with a settings section following DD-099 and an editor following DD-102, and the answer path in `src/adapter/dispatch-approval.ts`. No such surface should be built under the current ruling.
- **Constraints:** ADR-0018 U-D is human-ruled and binds at authority level 2; amending it is the human's call, and a deviation ticket cannot do it. Any future re-open must also respect ADR-0011's wildcard fence (a remembered grant must never cover a whole class or prefix of targets) and its session-clearance rule, and must keep the fail-closed `unavailable` path intact for every absent or silent answerer.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — a persisted settings surface plus a two-level clamp plus a write-back path touches the policy table, the settings store, and the approval path at once, and the risk that consent quietly widens, which ADR-0011 already recorded, is the reason it is fenced off.
