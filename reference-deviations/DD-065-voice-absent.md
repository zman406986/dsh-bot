# DD-065 — Mic dictation vs none
- **Area:** voice dictation (A8)
- **Type:** missing-feature (undocumented absence)
- **Date:** 2026-09-23

## What the reference does
The reference conversation workspace ships complete in-composer microphone dictation. The voice module (`the reference tree's frontend/src/recovered/features/conversation/workspace/voice.tsx`) wraps `MediaRecorder` with a mic-permission request carrying echo-cancellation, noise-suppression, and auto-gain audio constraints; it prefers the Opus-in-WebM encoding, falling back to plain WebM and then MP4 (exported preference list at lines 8–11); it caps recordings at 300 s (a max-duration constant, line 3) with an automatic stop, and silently discards anything shorter than half a second (a matching minimum-length constant, line 4) so stray taps don't produce junk audio. A voice-session hook (line 361) exposes the session's lifecycle state, from idle through capturing to post-capture processing, plus an mm:ss elapsed timer, and typed error conditions for permission refusal, missing input device, network trouble, and interrupted recordings.

The composer (`the reference tree's frontend/src/recovered/features/conversation/workspace/composer.tsx`) wires it into both the empty state and the has-payload state: a mic toggle, an aria-live line announcing listening status, and while recording a stop-dictation chip animated by a live canvas waveform fed from a Web Audio analyser. A distinct transcribing spinner covers the speech-to-text wait, an error paragraph surfaces typed failures, Escape cancels an active session or returns focus out of the editor, and send/attach are gated while voice work is in flight. Finalized dictated text is inserted into the draft via a final-transcript callback.

## What the current build does
The build's composer is a plain textarea with a send button and an inline error span — no microphone control, no recorder, no transcription step (`src/client/conversation.tsx:180-239`). A repo-wide search of `src/` for voice/dictation/MediaRecorder/getUserMedia/waveform/microphone terminology returns only an unrelated comment ("dictates" in a module-comment note at `src/client/shell-store.ts:549`); there is no voice feature code anywhere in the build.

## The deviation
The reference treats dictation as a first-class composer affordance with permission handling, recording hygiene (ceiling, minimum length, MIME negotiation), visible state (waveform, timer, spinner), and error taxonomy. The current build has no voice input path at all — no recorder, no capture UI, no transcription hook. Per the spot-checks below, this absence is recorded nowhere: ADR-0018's exception list has no voice entry (its only near-miss grep hit is the word "ergonomics"), and `docs/research/prd-vs-reference-capability-gaps.md` contains no voice/dictation row. The sole dictation mention in docs is incidental — `docs/research/reference-floating-window-summon-kill.md:66` describes the reference's stop-dictation control while cataloguing stop-button behavior, without treating dictation itself as a scope question.

## Verdict: ASK-HUMAN
Under the ruling order defined in `docs/agents-rulebook.md` this absence has no recorded ruling: voice dictation appears on neither the ADR-0018 human-ruled exception list nor the capability-gaps research note, so nothing authorizes leaving it out of an otherwise imitate-the-reference build (ADR-0004 makes the reference the feature inventory, ADR-0018 is the master rule), and ADR-0017 makes standing deviations from the reference a human-approval matter. Beyond the paperwork gap there is a real feasibility fork the human must settle: dictation needs both a browser-media capture path in the client and a transcription backend the host may not offer, which is exactly the transport question recorded separately as DD-066 (voice transcription transport). Ask whether to build dictation to reference shape, adapt it to whatever transcription transport exists, or record it as a deliberate exception.

## Incorporation notes
- **Where it would live:** a `src/client/` voice-session module beside the composer (recorder wrapper + a voice-session-equivalent hook), with UI wiring in the composer in `src/client/conversation.tsx`; the transcription call site is where any host-provided backend connects.
- **Constraints:** browser media permissions and `MediaRecorder`/`getUserMedia` availability must degrade gracefully (typed errors, disabled control); MIME negotiation across webm-opus/webm/mp4; 300 s ceiling and sub-500 ms discard; send/attach gating while a session is active; Escape-to-cancel must not fight existing composer keybindings; all UI text independently written.

- **Effort/risk:** M — recorder lifecycle and state machine are moderate; the risk concentrates in the transcription backend, which may not exist in the host at all (see DD-066, the separately recorded voice-transport decision).
