# DD-100 — Router/provider choice + usage meters vs none
- **Area:** settings (A12)
- **Type:** missing-feature (host owns inference)
- **Date:** 2026-09-23

## What the reference does

The reference's settings overlay carries a Router section and a usage-and-billing section. The Router half is a small module (`overlay/router.ts`) that lists exactly four inference backends (a provider enumeration naming four backends), each with display metadata plus a tag saying whether its usage data comes from the product itself or from outside (lines 3-39). One backend is the default (line 13), the choice persists under a versioned router-provider storage key as a versioned provider-record blob (a schema version plus the chosen provider; write at line 78), and reads fall back to the default when the stored record fails the version or allowed-value check (line 63). The panels module (`overlay/panels.tsx`) renders a select built from that provider table and a usage panel: a list of usage meters (line 266), a loading state over a native usage summary (lines 273-275), and a usage-settings panel wired with retry, upgrade-button, and cancel-trial actions (lines 283-297), including copy about ending the trial and the card never being charged automatically (lines 294-295); backends tagged as external get a "managed externally" treatment instead of local meters. Beneath the UI, the reference's settings store accumulates an inference-provider field plus a usage record — request count, input/output/cache tokens, last-used timestamp — via a usage-recording call (`the reference tree's source/shared/node/settings/sand-settings-store.ts:29,158-168`), so usage accounting exists end-to-end, not just as markup.

## What the current build does

Nothing on any of these three axes. The build's entire settings surface is the single collapsible plugin card in the host's stock settings page (`src/client/settings-card.tsx`, backed by `src/client/settings-card-store.ts`) and the one claimed settings namespace on the host side (`src/adapter/settings-section.ts`). A content sweep of those files for provider/usage/router/billing/token vocabulary surfaces only unrelated matches: comments about Cordis `SettingsProvider` plumbing in the adapter and theming design-token comments in the card. There is no backend choice to make — the build never runs inference itself; the dsh host does — no usage meters, no usage summary state, and no usage accounting of any kind, on the client or adapter side.

## The deviation

The reference treats "which backend serves inference" and "how much of a paid allowance that backend has consumed" as first-class settings content, persisted and metered by the app itself. The build has no such concept to expose: inference is host-owned by design, so there is no provider hook for a client-side selector to control, and nothing in the dispatcher measures token or request consumption. The gap is therefore structural (no hook exists) rather than an unbuilt feature of an existing hook — with one residual question of whether the human wants dispatcher-side usage telemetry displayed somewhere, which would be new product behavior, not an incorporation of this reference slice.

## Verdict: DO-NOT-INCORPORATE

The PRD's non-goals (§2) place rebuilding dsh's inference router out of scope, and the build's architecture deliberately routes all inference through the host — so a four-backend router selector has nothing to select and no place to store its choice; the routing question itself belongs to the A15 filing (inference routing), and this deviation is only its UI side. The usage-and-billing panel is inseparable from the reference product's commercial model — trial cancellation, upgrade buttons, card-charge reassurance, a product-account usage feed — none of which has any counterpart in the dispatcher's contract. Incorporating either half would invent product behavior the PRD never asks for and contradict the one-settings-surface approach already ruled in DD-098. If the human ever wants a usage read-out for dispatcher work, that is a fresh ticket designing its own accounting, not a port of this panel.

## Incorporation notes
- **Where it would live:** nowhere under current rulings; a hypothetical usage display would live inside the single plugin card (`src/client/settings-card.tsx`) fed by new adapter-side accounting in `src/adapter/`, and only after a human ruling created the underlying product decision (routing per the A15 filing; telemetry per a new ticket).
- **Constraints:** host owns inference (PRD §2 non-goals); stock dsh stays the primary UI and the dispatcher confines itself to ruled surfaces (ADR-0021, as recorded in DD-098); the settings surface stays one namespace with the single `ctx.settingsScope` write channel; the meter panel's semantics presuppose a paid subscription (trials, upgrade buttons) the dispatcher does not have, so its information design cannot be carried over as-is.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S for a bare read-only usage line in the card once accounting exists, but M-L in practice because nothing measures usage end-to-end today; the real risk is scope, not size — building it means inventing PRD-absent product behavior.
- **Key reference anchors:** reference `overlay/router.ts` (the provider enumeration plus its router-provider storage key, lines 3-14, 63, 78); `overlay/panels.tsx` (the usage-meter component, line 266, and the usage-settings panel, line 297, with retry/upgrade/cancel-trial props, lines 283-297); the reference store's usage-recording call (`the reference tree's source/shared/node/settings/sand-settings-store.ts:29,158-168`); cross-ref the A15 filing (inference routing) and DD-098 (settings surface approach).
