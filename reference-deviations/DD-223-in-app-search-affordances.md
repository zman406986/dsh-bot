# DD-223 — In-app search affordances: find-in-chat and per-provider palette search
- **Area:** A29 cross-cutting surfaces
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

Two distinct **UI-level** search affordances exist, neither of which is a storage index. Both surfaces are already filed — the find bar as DD-046 and the palette's search pipeline as DD-021 — so this file records the cross-cutting view and the one idea inside them that is not filed elsewhere: how the find controller keeps the user's place while the underlying list is rebuilt.

**Find-in-chat (surface: DD-046).** A controller holds a scope (account slot + agent identity), a query, an ordered match list, and a current-match cursor, and exposes navigation and close alongside a transcript handle that jumps the viewport to a matched entry *without* painting highlights on it (`find-in-chat-controller.ts:7-10, 30-46`). Matches are projected out of transcript entries against a derived searchable-text projection that reads only the user-visible payload of supported entry kinds and returns empty for the rest (`:52-70, 72-88`). A match is keyed by **entry identity plus occurrence index within that entry**, not by array position (`:12-15`).

**What is different — keeping the current match when the list is rebuilt.** The interesting engineering is in what happens when the list is rebuilt. Rebuilding recomputes the full match list and then *finds the previous current match again inside it by identity*, keeping it when it is still present and dropping it to null only when it is gone (`find-in-chat-controller.ts:111-116`). That recompute runs whenever the entry list is replaced (`:125-131`) — i.e. on every live update — while an actual query change deliberately clears the cursor (`:132-139`) and a scope change bumps a generation counter and resets the whole computed list (`:161-171`). So typing a new query starts fresh, but the feed changing underneath does not move the user's place. A naive implementation recomputes and resets the cursor to the first hit, losing the user's position whenever the transcript grows — which in a live agent feed is constant; in a live-updating transcript that is the difference between a usable find and a frustrating one.

**Palette per-provider search (surface: DD-021).** The palette carries three independent search providers (routines, files/media, messages), each reporting its own pending or unavailable state, so one provider failing leaves the others usable and the palette says so rather than going blank. The state-isolation idea here is the same per-provider snapshot lifecycle already named and assessed in DD-222 (its "two separable ideas" analysis) — cross-referenced, not re-filed.

## What the current build does

**Absent at the UI level.** A case-insensitive search of `src/client/` for search, find-in-chat, and highlight terms returns only doc-comment false positives — every hit is the substring inside "research" or "Finding" in citations of `docs/research/*` (`src/client/actions.ts:4`, `src/client/context.ts:6`, `src/client/floating-window.tsx:31,42,55`, `src/client/toolviews.ts:60`, `src/client/conversation-store.ts:6`, `src/client/onboarding.ts:8`, `src/client/shell-feed.ts:5`, `src/client/index.ts:38`). There is no query box, no match counter, no next/previous affordance, and no highlighting in either surface that would host one: the shell renders session rows and the conversation pane renders the feed, and neither takes a search input.

**But the retention problem is real in the build's own shape.** The conversation pane re-renders from an external store via `useSyncExternalStore(store.subscribe, store.getBox)` (`src/client/conversation.tsx:398`), and the feed binds a source by snapshot-plus-subscribe with a paging path for older entries (`src/client/conversation-feed.ts:90-97, 124-130`). The rendered items are themselves a *derived projection* over raw transcript events (`reduceConversationWindow`, `src/client/conversation-store.ts:293`), with the transcript/state shapes at `:155-177` and the store at `:482`. So the build already has exactly the two ingredients the retention technique addresses: a derived, re-derived-on-update item list, and live updates that rebuild it. The build's module set is listed in DD-222; the relevant files here are `src/client/conversation.tsx`, `src/client/conversation-feed.ts`, `src/client/conversation-store.ts`, and `src/client/shell.tsx`.

**Not the storage-level thing.** This file must not be read as re-filing the index: the storage-level content-search index is DD-179, ruled out by ADR-0018 exception 19 (U-H). What is absent here is a client affordance over the *rendered* feed, which requires no index, no derived database, and no new corpus — the entries are already in memory in the pane.

## The deviation

The reference treats search as a first-class, always-available surface over whatever is in front of the user — a find bar over the live transcript and a multi-source query box in the palette — and, crucially, engineers the find so that a live feed does not destroy the user's position. The build has neither affordance. The deviation in this file is narrow: the surfaces are filed (DD-046, DD-021, DD-222, DD-179), and what is unfiled is (a) the cross-cutting framing — two independent UI-level search affordances that need no storage index — and (b) the technique for keeping the current match when the list is rebuilt, which is the main idea and is genuinely portable to the build's own derived, live-updating feed.

## Verdict: DO-NOT-INCORPORATE

A recorded ruling covers this, so the verdict is not an inference-only call. ADR-0018 exception 13 (U-B, "no rich chat ergonomics") names find-in-chat explicitly, which is the ground DD-046 already recorded as DO-NOT-INCORPORATE, and exception 19 (U-H) rules out the storage-level content-search index that DD-179 files — so neither the UI affordance nor an index behind it is open on the stack as it stands. The palette's search providers are contingent on a palette the build does not have: DD-021's ADAPT path is gated on DD-019's disposition, which DD-222 recorded as settled against under ADR-0009's activation rule. ADR-0022 does give the build its own window, so an in-window find over the pane is not categorically impossible — but no recorded ruling names one, and the retention technique filed here is meaningful only if the surface exists, so it cannot carry a surface the exception list excludes. Reviving any of it means asking the human to reverse exception 13, not quietly porting it.
