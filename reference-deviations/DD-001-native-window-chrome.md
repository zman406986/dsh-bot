# DD-001 — Native window chrome vs DOM floating panel
- **Area:** UI shell / window chrome (A1)
- **Type:** deliberate-divergence (build is an in-host DOM window by design)
- **Date:** 2026-09-23

## What the reference does
The reference is a desktop-packaged app: its renderer draws into a real OS-level window and a recovered feature owns that window's chrome. In the reference tree's `frontend/src/recovered/features/window-chrome/view.tsx` (whole file, 55 lines) the window-chrome component renders a drag region plus the standard three controls — collapse, size-toggle (with a separate restore glyph when already enlarged), and dismiss — each wired to a desktop-bridge window-controls API (`view.tsx:50-52`; the bridge contract is imported at `view.tsx:2`). The component adapts per host platform (`view.tsx:44-48`): on macOS it renders the drag strip only (the OS supplies the traffic lights); on Windows it emits a placeholder controls node styled `display:none` and instead drives a native title-bar overlay — an effect (`view.tsx:38-41`) calls the bridge's overlay-tone setter so the OS-drawn buttons match the theme, while a model module (the reference tree's `frontend/src/recovered/features/window-chrome/model.ts`, imported at `view.tsx:3,36`) pushes inset/block CSS variables so page content respects the overlay's reserved strip. On every other platform it falls back to fully custom in-page buttons. In fullscreen the custom controls are withheld entirely and only the drag strip remains (`view.tsx:46`). The sweep reports this component mounted near the top of the renderer's production tree (the reference tree's `frontend/src/recovered/app/dist` source's `ProductionRenderer.tsx:3443`) — not independently re-verified here.

## What the current build does
The build has no OS window to decorate: its surface is a DOM element inside the dsh web client, so its "window" is a positioned, border-radius'd div floated above the host UI. `src/client/floating-window.tsx` builds the titlebar as a pinned child of that div (`describeFloatingWindow`, `floating-window.tsx:297-323`): a drag handle spanning the strip (pointerdown wired at `:299-300`, drag math in `beginDrag`, `:394-416`), one size-toggle button that swaps maximize/restore labels and glyphs (`:303-313`), and a dismiss button (`:314-322`). There is no collapse/minimize control, no fullscreen handling, and no platform adaptation — a single Windows-style titlebar by choice (ticket 105's note, `:74-79`). The whole surface is a React portal into a module-owned container appended to `document.body` (`windowLayer`, `:351-361`; portal at `:528-543`), deliberately outside the host app frame, with the launcher capsule stacking above it (z-index note, `:117-139`). Window state (position, size, maximized) is in-memory only, in `src/client/floating-window-store.ts` — nothing here claims OS-level window semantics.

## The deviation
The reference decorates a genuine OS window with per-platform chrome, a native Windows title-bar overlay, and fullscreen awareness; the build renders an in-host DOM panel with one fixed Windows-style titlebar (drag, size-toggle, dismiss only). The reference's capability set (minimize, fullscreen suppression, platform branching, overlay-tone theming) is absent from the build, and much of it has no meaning without a native window manager behind it.

## Verdict: DO-NOT-INCORPORATE
This divergence is a recorded decision, not a gap. ADR-0021 (`docs/adr/0021-addon-coexistence-floating-dispatcher-window.md`, accepted, decided by the human on 2026-09-20) fixes the design: stock dsh stays the primary UI (decision 1), and dispatcher functions live in a separate floating window over it, added through the `shell.overlay` extension point, with crash isolation (decision 2). Its options table explicitly re-rejects a standalone/native shell (`:34`) — the only setup in which reference-style native chrome could exist. ADR-0022 (`docs/adr/0022-floating-capsule-revived-by-human-ruling.md`) refines the launcher capsule but leaves the window-as-whole-shell approach standing. The PRD's non-goals (§2, echoed in the repo stub: no chasing the reference's binary/UI parity) bind the same way. Nothing here warrants ASK-HUMAN: the human's own recorded words chose coexistence over replacement, and native window chrome only exists in the kind of app that ruling set aside. Any genuinely new affordance (e.g. minimize-into-capsule) would need fresh ticket-level evidence under the repo's ruling conventions — it is not this deviation.

## Incorporation notes
- **Where it would live:** Only the parts that live in the DOM could ever transfer: titlebar buttons and their store actions in `src/client/floating-window.tsx` plus state in `src/client/floating-window-store.ts`; a native-controls bridge would additionally need a new extension point under `src/adapter/` and a desktop-bridge-style contract that currently has no counterpart in this repo (dsh's client is a browser page, not a packaged shell).
- **Constraints:** ADR-0021 decisions 1-2 (the coexistence design, the floating DOM window, isolation) and its explicit non-revival of the standalone/native-shell option; ADR-0022 (capsule shape, one launch path); PRD §2 non-goals (no reference binary/UI parity); ADR-0013's rule of one registration entry per surface, as applied in `src/client/floating-window.tsx`'s header notes.
