# DD-203 — MCP server configuration, lifecycle, and management surface
- **Area:** A26 MCP machinery
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

The reference owns a complete MCP server subsystem, from declaration format through lifecycle to a user-facing management surface. It divides into four layers.

**1. Declaration and validation.** A runtime config object holds a map of server name to server config (the reference tree's `source/shared/node/mcp/mcp-definition-source.ts:2`). The config is a discriminated shape rather than a flat record: a remote form carrying a URL plus headers, or a local subprocess form carrying a command plus arguments plus environment. The two forms are distinguished structurally (membership of one key or the other) rather than by an explicit tag, and downstream code branches on which key is present. Server names are validated by a dedicated module (the reference tree's `source/shared/node/mcp/mcp-validation.ts:5`): the name is trimmed, must be non-empty, must not collide with the reserved set that names built-in servers, must not contain forward or backward slashes or a null byte, and must not contain a double-dash sequence. A second reserved-name guard fires at the manager layer for built-in collisions (the reference tree's `source/shared/node/mcp/mcp-manager.ts:318`).

**2. Account-scoped definition source and manager.** Definitions are account-scoped, not global. The definition source (the reference tree's `source/shared/node/mcp/mcp-definition-source.ts:6`) loads the account config behind a promise, keeps an epoch counter so a stale load cannot overwrite a newer one, retains a last-known-good config to fall back on when a refresh fails, exposes separate accessors for the remote-form and subprocess-form server names, filters built-in servers out of the user set, and offers explicit adopt/clear operations for the account config. The manager itself is a substantial module (the reference tree's `source/shared/node/mcp/mcp-manager.ts`, 562 lines) that owns per-account-slot lifecycle: logging an account out, renaming an account, and removing an account, each with tools-cache invalidation as a consequence rather than a separate caller responsibility (invalidation call sites at `:120`, `:146`, `:559`; the account operations at `:472-479`).

**3. The listing/summary model.** Every server is projected into a row that carries a transport label, the underlying command or URL, an enabled tool count, a disabled tool count (present only when nonzero), the per-connector custom instructions, whether the server is team-provided, and plugin attribution (which plugin supplied it, whether it is required, whether a team policy manages it) — the reference tree's `source/shared/node/mcp/mcp-listing-summaries.ts:3`, with the attribution helper at the reference tree's `source/shared/node/mcp/mcp-display-runtime.ts:8`. Rows are keyed to an account slot, and the slot carries whether a credential is present, which is what decides the auth state. Status comes from a fixed vocabulary normalized in one place (the reference tree's `source/shared/node/mcp/mcp-display-runtime.ts:10`): a connected state; an auth-needed state that always carries a detail saying authentication is required; a loading state that normalizes to an *initializing* label; an error state carrying either the backend's own detail or a generic load-failure detail; and a default branch that still reports error but distinguishes two causes in its detail — the host machine being unreachable, versus the host simply not having reported a status at all. A separate policy-disabled state exists for servers switched off by team administration, carrying its own explanatory detail. A companion path handles servers that execute on the product's own remote computer, including the case where that capability is not wired at all, which reports a disconnected state with a detail naming where the server runs.

**4. The management surface.** Lifecycle is exposed to the model as a family of management tools (the reference tree's `source/host/runner/tools/sand-mcp-management-tools.ts`, 442 lines). The dependency interface at `:61-77` enumerates the whole family: search a plugin catalog; fetch one plugin's detail; install a plugin with supplied values; add a remote server by URL; list installed servers; remove one server; uninstall a whole plugin together with its attributed servers; set per-connector custom instructions; restart all servers; authenticate one server (with a force-reauth flag and an account label); remove an account; rename an account. Around that family the file carries the supporting machinery the family needs to behave well: parameter schemas for each tool (`:86-107`, `:272-279`), plugin-query tokenizing with a minimum token length, scoring and lexical ranking (`:108-137`), remote-URL validation (`:139`) and server-config JSON construction (`:155`), one-line truncation for row rendering (`:164`), and description builders for installed servers, plugin summaries, and plugin details (`:169-238`). Confirmation etiquette is encoded as shared copy constants (`:239-240`) covering the two rules that matter: do not install, uninstall, restart, or authenticate in the same turn as a confirmation widget, and once a connect card has been placed in the chat the model should finish unrelated work and end its turn rather than sending a link or reaching the service another way while authorization is pending. Authentication returns a discriminated result rather than a boolean (`:54`, rendered at `:251-269`) with distinct branches for started, already-authenticated, not-configured, not-supported, and unreachable — the unreachable branch explicitly telling the model that this is a configuration failure rather than a missing credential, so sending the user to settings would hit the same error. Team-provided servers are recognized throughout (the team flag on every row, the team-policy attribution flag, and the policy-disabled status), which is what the refusals are based on. A separate meta-tool layer (the reference tree's `source/host/runner/tools/mcp-meta-tools.ts`, 151 lines) provides the discovery/inspection side of the same family.

**5. Desktop projection.** A facade module (the reference tree's `source/electron-main/mcp/desktop-mcp-manager.ts`, 161 lines) exposes the manager to the desktop application, including the account rename among its operations (`:31`, wired at `:141`), and a thin desktop bridge (the reference tree's `source/electron-main/mcp/mcp-desktop.ts:11`) names the remove-account and rename-account operations as the surface the UI calls. A host-side service module (the reference tree's `source/host/extensions/mcp/mcp-service.ts`, 232 lines) sits alongside. The net effect is that the installed-server list, the plugin catalog, plugin detail, per-account actions, and team-policy labels are all projected to the desktop UI from the same row model.

## What the current build does

ABSENT in every layer. There is no server model at all: no declaration format (no discriminated config union, no URL form, no subprocess form), no add/remove/restart operations, no status vocabulary, no account concept, and no management tools. The build has no MCP client, so it has nothing to manage.

The dispatcher's tool surface is a fixed set of six name constants declared together in `src/core/policy/prompts.ts:8-24` (spawn, check, steer, stop, deliver, send-peer), and the worker tool barrier in `src/worker/tool-barrier.ts` enumerates the same names as deny candidates, intersected at spawn time with the set of tools actually registered as globals (`src/worker/tool-barrier.ts:14`, `:52-59`). Nothing in either list is a capability-management tool; both exist to bound and defend a fixed surface, not to grow one.

The only user-facing configuration surface is the plugin's own settings card (`src/adapter/settings-section.ts`, `src/client/settings-card.tsx`). That card configures the plugin itself — its own namespace and flags — and has no notion of an external capability server, an account, or a connection state. A case-insensitive search for MCP vocabulary across `src/` and `client/` returns zero matches, confirming the absence at the vocabulary level as well as the structural level.

## The deviation

This is a whole-subsystem absence, and it is the largest single missing area in the reference comparison. The reference treats an external capability server as a first-class, named, validated, account-scoped, status-bearing entity with a lifecycle the model can drive; the build has no such entity and no vocabulary for one.

The nuance that decides the verdict is an ownership split. In the build's architecture, MCP is a *host-level capability*. The build is a Cordis plugin that lives inside dsh, and dsh owns tool sourcing: the plugin registers its own tools and asks the host what globals exist, but it does not discover, declare, connect to, or authenticate external capability servers. The reference is the entire application, so it necessarily owns MCP end to end — there is no layer above it to delegate to. The deviation therefore splits into two halves with genuinely different status:

- **The server-model half** (declaration format, name validation, account scoping, connection status, auth state) is a *capability question*: should the build grow an MCP client at all, and if dsh already provides one, should the plugin use it rather than rebuild it? PRD §2 excludes "rebuilding dsh's inference router, transcript storage, or tool runtime" (`PRD-dsh-multitask-dispatcher.md:34-36`), which on its face covers building a parallel MCP client inside a plugin.
- **The management-UI half** (the plugins catalog, the installed-server browser, per-account action rows, connect cards, the confirmation etiquette, the status vocabulary rendered as labels) is a *rich-ergonomics question*. It is a browser-and-panel surface of exactly the class ADR-0018 exception U-B is skeptical of — U-B excludes find-in-chat, threads, reactions, per-agent drafts, rich attachment viewers, and URL cards (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:35`), i.e. UI richness the build has deliberately declined where the reference is lavish. U-B does not name MCP server management, so it does not *reach* this half; it is a position of the same shape, not a ruling on this subject.

**Recorded ruling check, stated explicitly: no recorded ruling covers MCP server machinery.** ADR-0018's exception list does not mention MCP. The PRD §2 non-goal is a scope statement about dsh's runtime, not a specific MCP decision, and it does not distinguish the two halves above. The same scope question was already reached once: DD-156 recorded that the MCP half of its catalog finding was presumed out of scope by that non-goal, with the human to rule, and explicitly left the MCP machinery to a separate filing — this one. DD-157 reaches tool-registry governance and does not reach MCP. DD-103 covers per-server MCP settings and is strictly downstream of machinery that does not exist. So the recorded material settles nothing here, and the scope decision is the human's.

## Verdict: ASK-HUMAN

No recorded ruling covers MCP server machinery, and this file is the same scope question DD-156 reached on its MCP half — cross-referenced rather than re-argued: the PRD §2 non-goal excludes rebuilding dsh's tool runtime (`PRD-dsh-multitask-dispatcher.md:34-36`), which plausibly covers a plugin-side MCP client, but it is a scope statement rather than an MCP decision and the exclusion is inferential and reversible. The two halves stand differently: the server model is a capability question that the non-goal probably answers *no*, while the management-UI half is the rich-ergonomics class ADR-0018 U-B is skeptical of without actually naming it. Because the dominant question is whether the plugin should own an MCP client at all — and, if dsh already provides one, whether the plugin should surface a management interface for a capability it does not own — the call is the human's and not an engineering trade-off resolvable from the authority stack. Treat the server-model half as presumed out by the non-goal unless the human rules otherwise; do not let the non-goal quietly cover the management-UI half too, which it does not actually reach.

## Incorporation notes

- **Where it would live:** nothing is added now. If the human rules in, the correct shape is a *consumer*, not a client: the plugin would ask its host for whatever MCP surface dsh exposes and project it, rather than implementing declaration parsing, connection management, or authentication itself. A minimal read-only status projection would sit beside the existing settings card (`src/adapter/settings-section.ts`, `src/client/settings-card.tsx`) as a second section, consuming a host-provided server list. The management tools, if ever built, belong with the dispatcher tool surface declared in `src/core/policy/prompts.ts:8-24` and must be added to the worker barrier's candidate list (`src/worker/tool-barrier.ts:14`) so workers cannot reach them — the barrier is a candidate list intersected with live globals, so a new name is safe to add before the host registers it.
- **Constraints:** the build owns no tool sourcing, so nothing here can be built before the host exposes an MCP surface — a plugin-side MCP client would duplicate dsh's runtime and is the specific thing PRD §2 excludes. If any management tool is added, its name is a new dispatcher tool and must be reflected in the barrier; the confirmation etiquette in the reference is worth re-deriving as a rule (no mutating action in the same turn as a confirmation widget) but its copy strings must be rewritten from scratch. The status vocabulary should be re-derived as a small closed set with an explicit unknown/unreported branch, since the reference's value here is that an unreported host is distinguishable from a failing server. Any chat-side connect card would go in the card surface governed by DD-075, and the tool-side catalog question overlaps DD-156's prompt-side half — neither should be rebuilt here.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L for the server-model half (a full client: declaration format, validation, connection state machine, auth flow, account slots — and it is the half the non-goal probably forbids). M for the management-UI half *conditional on* a host-provided server list existing, since it reduces to a projection plus a status vocabulary; L in practice if the host exposes nothing. Risk is high on the first half — building it would put a plugin into dsh's tool-runtime territory — and low-to-medium on the second, where the main hazard is adding a management surface for a capability the plugin does not own.
