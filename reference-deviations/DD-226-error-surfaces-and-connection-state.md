# DD-226 — Error surfaces: a designed failure view and a connection-state controller
- **Area:** A29 cross-cutting surfaces
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
Two cross-cutting surfaces sit side by side in the reference.

**(1) A dedicated error-boundary feature.** A reusable failure view takes a caught error, an optional component stack, and a set of labels (title, detail, reload, copy-error, copied) and renders a centred alert region linked by label and description references, with a title, a formatted detail block, and two actions: a reload that reloads the renderer, and a copy action that writes the same formatted diagnostic text to the clipboard and then shows a copied acknowledgment (with a comment noting the view stays visible when clipboard access is unavailable). The formatted text is built in one helper: error identity first, then the stack trace when present, then the component stack with an explicit unavailable placeholder — so the diagnostics sit *inside* the formatted detail, separate from the friendly title. The root renderer wraps the whole app in a boundary class that captures the component stack in its catch hook, logs it, and renders the shared view through a thin wrapper for fatal errors. Anchors: the reference tree's `frontend/src/recovered/features/error-boundary/view.tsx:6-52`; the reference tree's `frontend/src/recovered/features/window-chrome/root-shell-state.tsx:129-169`.

**(2) A feature for surviving a lost backend, which owns connection state as a controller.** A controller holds a snapshot of account identity and kind, transport state, a phase (hidden / loading / connected / reconnecting / unreachable), a retrying flag, and three readiness values (whether the backend was reached, whether privacy blocked the view, and a failure code). The phase is computed purely from those inputs: not logged in or privacy-blocked hides the view; a connecting transport is loading; a connected transport with no failure code is connected; otherwise the "backend reached" flag decides reconnecting vs unreachable. A source adapter wraps the *existing* coordinator client and desktop bridge (the file's own comment: no new bridge API). The controller compares a generation counter so an account-identity change cancels in-flight retries and clears the pending waiter, and it queues a retry when the transport is not yet connected — the user's retry is held and re-run on the connected event rather than rejected. A host component subscribes through the external-store hook and renders the loading / unreachable / reconnect views, deliberately reusing the already-shipped roster status and reconnect views rather than introducing a new status style. It is created in the production renderer and mounted there by the root component. Anchors: the reference tree's `frontend/src/recovered/features/root-resilience/connection-state.ts:12-60, 96-101, 118-255`; `connection-state.tsx:15-32`; the reference tree's `frontend/src/production/ProductionRenderer.tsx:2178, 3448`.

## What the current build does
There is exactly one error boundary in `src/`, and it keeps a crash inside one component rather than giving the user a failure view: `DispatcherWindowBoundary` (`src/client/floating-window.tsx:209-236`) catches a crashing registrant, flips a failed flag, and renders a single line of copy at reduced opacity (`multitask-dispatcher-fwin__failed`, `data-window="failed"`, the `launcher.window.failed` chrome key at `:184-198`). Its `componentDidCatch` is an intentionally empty body with both parameters ignored (`:224`, comment: the honest fallback line below IS the report) — the error and the component stack are thrown away. The header documents the placement rationale (below the portal so a shell crash cannot retire the whole entry at the host layer, `:52-65`) and the boundary is keyed by the store's `openEpoch` (`:325`), so close + reopen recovers.

There is no connection-state controller of any kind: no phase model, no source, no host component, no offline/unreachable banner. The shell's header states failure states are honest copy only (empty / presence-unavailable) and deliberately retry-less — no retry control, no reconnect banner (`src/client/shell.tsx:36-38`, citing ADR-0018 U-A). The host contract carries no connection information a controller could use: `DshHost` exposes spawn, interrupt, send, settle/step subscriptions, wake, and access requests only (`src/core/dsh-host.ts:9-40`). A search of `src/client/` for connection-state vocabulary finds no indicator — every "offline" hit is the offline-testing vocabulary, not a transport state.

Per-call failures, by contrast, degrade honestly inline: the toolview parser falls back to a safe degraded row rather than throwing (`src/client/toolviews.ts:103-152`, degrade-only-when-nothing-parsed at `:200-205`), and the build-only send-failure status line (DD-060) follows the same approach. That part is correct — and it is not a failure *screen*.

## The deviation
The reference treats catastrophic failure as a designed screen and connection loss as state the app tracks; the build has neither.

**(a) Catastrophic failure of the plugin's own window.** The reference's boundary captures error + component stack and renders a titled alert with recovery and diagnostics; the build's boundary deliberately discards both parameters and renders one line of copy. The build's honesty rule covers *small* failures well — a degraded row, an honest status line (DD-060, `toolviews.ts`) — and *large* ones not at all: the one view that exists when the window itself dies offers no explanation, no diagnostics, and no action. That is not dishonesty; it is silence, which is the one outcome the honesty rule should not produce. The reference's separation matters here: the friendly title is separate from the formatted detail that carries the stack and component stack, so a user gets a calm sentence and a diagnosable artifact (copied to clipboard) from the same view.

**(b) Losing the backend.** The reference gives an unreachable host a first-class UI representation: one controller at the root turns transport + account + readiness into phases and renders the unreachable/reconnecting views (reusing the app's existing status views). The build has no controller and no representation — a lost connection shows up only as whatever per-call failures happen to occur — and the retry-less approach is a recorded position, not an oversight.

**Overlap check that this file had to make.** DD-006 has already filed the reference's root boundary + view affordances against `DispatcherWindowBoundary` and ruled ADAPT; this file does not re-rule it, and the failure-view part of the ADAPT below is the same conclusion limited to the catastrophic case. DD-089 already ruled the connection-lifecycle/retry part DO-NOT-INCORPORATE under ADR-0018 U-A (the reference's controller is largely that machinery, and its roster-facing part is exactly what DD-089 examined); DD-033 (transcript load-error retry) and DD-034 (offline-composed timestamp) are the same ruled-out family. DD-213 covers process-level crash reporting and log spill and is not duplicated here. DD-090 (privacy-blocked dialog) is adjacent because the reference's controller reads a privacy-blocked readiness flag to hide the connection view — cross-referenced, not duplicated. What this file adds is the split between catastrophic and small failures, plus the *ownership* observation: the reference's connection controller invents no new UI, it gathers the phases in one place at the root.

## Verdict: ADAPT
ADR-0018's exception list (accepted) explicitly rules out the connection-lifecycle model — "no transport state phases, reconnect banner … roster failure states" (item 12, U-A) — so the controller part is a recorded ruling and is not incorporated; DD-089 reached the same conclusion for its roster-facing part. No recorded ruling names a failure *view* for catastrophic failure of the plugin's own window: ADR-0010 (draft, non-human-approved) records the rule to report only what can be read, which the build's inline degradation follows, but it speaks to presence data, not failure rendering, so it supports honest failure display without covering the gap; ADR-0021 fixes the additive arrangement but says nothing about the window-body fallback's content. The ADAPT is therefore narrow and consistent with DD-006's already-filed ADAPT: keep the containment placement and the honest line, add a designed failure view (title + formatted diagnostics + a window-scoped recovery) inside the existing boundary. Any visible connection-state indication is barred by U-A absent an explicit human override, and no host interface exists to drive one. A human can reverse; nothing is being silently chosen.
