# DD-146 — Mid-flight supervision orders vs no-poll wake-driven stance
- **Area:** system prompts / persona (A17)
- **Type:** deliberate-divergence (opposite stance, recorded)
- **Date:** 2026-09-23

## What the reference does
The reference's background-work guidance orders active, watchful supervision of delegated work. The primary agent is told not to assume a running subagent is actually progressing: it should proactively inspect subagent status on a periodic basis, and always before reporting to the user that work is ongoing. It is taught to recognize a stalled worker from external signs — no recent tool activity, an unchanged screen, or the same action repeating — because a stuck worker is outwardly indistinguishable from a busy one. On spotting trouble it must act: inject a new instruction to redirect a looping worker (preserving its context) or abort one that is stuck and making no progress. And it must never cover a stall with a false claim of ongoing progress; the honest report of the real state is required instead. Notably, the reference itself draws a line at completion-polling — inspection is for spotting trouble, not for waiting out a finish — but periodic mid-flight checking is explicitly the standing order.

## What the current build does
The build takes the opposite stance: mid-flight supervision by the dispatcher is forbidden, not encouraged. The persona's never-do list forbids polling a worker in a loop during a turn and prescribes act-once — spawn, steer, stop, or check — then move on or end the turn. The check tool's description positions it as something to use when the user asks what is in flight, explicitly not as a wait loop. Findings arrive when the architecture delivers them: worker completion (and other events) wake the dispatcher, and steer-from-user carries user-initiated corrections into running workers. Progress information the dispatcher can offer mid-turn comes from the roster snapshot, not from actively questioning the worker. The honesty rule that survives from the reference is present in the build's copy: never pretend a spawn finished the work (a spawn only starts it) and never claim a stopped worker produced a result.

## The deviation
The reference makes periodic mid-flight checks a standing duty and treats them as the primary defense against silent stalls; the build bans that exact cadence and replaces it with a wake-driven model where the dispatcher learns of stalls only at the next wake (or when the user asks). This reverses the supervision stance, and the reversal is recorded: PRD §14 lists dispatcher thrash (too many short turns) as a risk whose mitigation is one reconcile pass per wake with coalesced wakes — a periodic-check duty would bring back exactly the churn that mitigation exists to prevent. The adjacent infrastructure agrees: ADR-0010 records that the roster channel publishes only when the state actually changes, with no tick or poll path. The genuinely portable part of the reference — never hide a stall behind a false claim that work is progressing — is already carried by the build's honesty copy, so the remaining difference is the polling cadence itself, which is the part intentionally rejected.

## Verdict: DO-NOT-INCORPORATE
The no-polling stance is a recorded measure against wasted turns (the reference calls it dispatcher thrash), sitting at PRD level in the authority stack, reinforced by ADR-0010's no-tick/no-poll channel decision, and the reference's supervision duty directly contradicts it; adopting the reference cadence would reopen a risk decision that is already settled. The reference's never-false-progress rule — the part of its supervision stance worth keeping — is already present in the build's honesty copy, so the only real difference is the polling cadence itself, which is precisely what the PRD rules out. Nothing here justifies asking the human: the divergence is deliberate, recorded, and the reference's protective intent (stalls must not go unnoticed or be lied about) is preserved through checking at wake time and honest reporting rather than mid-flight checks. If silent-stall detection ever becomes a real product gap, the fix belongs in core (classify stalls at wake time and surface them during the reconcile pass) — not in a prompt-level polling duty.

- **Constraints:** Any future change must preserve the PRD §14 mitigation (one reconcile pass per wake, coalesced wakes), stay consistent with ADR-0010's rule that the roster channel publishes only on real state changes, and keep the act-once-then-end-turn persona rule intact.
