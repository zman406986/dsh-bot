# DD-189 — Memory synthesis service (evidence-cited proposal and verification)
- **Area:** A23 memory
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference ships a background memory-synthesis service: a periodic LLM job that reviews recent conversation evidence and proposes changes to an agent's durable memory. DD-188 covers the memory feature itself; this filing covers only the synthesis engine inside it, described by role.

Its parts, described by role:

- **A debounced background job.** Synthesis is triggered off a debounce rather than per turn — a recorded delay of about fifteen seconds before a pass runs — plus a long-interval sweep for dated memories whose content needs a refresh (`the reference tree's source/host/extensions/memory/memory-synthesis-service.ts:11`, `:13-14`). Each attempt runs under a hard deadline of ninety seconds (`:12`), and the whole propose-then-verify attempt is wrapped in a retry policy of at most three attempts with backoff between two and thirty seconds (`:15-17`; the scheduling policies are constructed and named in `the reference tree's source/host/extensions/memory/production.ts:39-62`, and the job runs on a summarization-model session at `:68-72`). Evidence is queued per agent, with caps on pending agents and on the per-agent evidence backlog, and overflow is shed oldest-first and reported rather than silently lost (`:18-19`, `:193`, `:197-199`).
- **Bounded evidence excerpts.** Each side of a queued exchange is clamped to a recorded 8,000-character cap before it enters the proposal input, with an explicit elision when the cap bites (`:21`, `:59-62`, `:187`).
- **A two-stage propose-then-verify flow.** A first model call proposes a bounded set of changes; a second, separate model call verifies the proposal and must return an explicit approval flag before anything is applied. A rejection is a typed outcome, not a crash: the change set is discarded and reported (`:131-132`, `:262-273`).
- **A bounded, evidence-citing change set.** Each proposed change is a create, update, or remove over an existing fact, and every change must cite one or more evidence identifiers drawn from the supplied evidence — a change citing unknown evidence invalidates the whole proposal (`:25-27`, `:97-98`). The set is capped at 64 changes, and per-change validation bounds content length and identifier length as well (`:85`, `:106`, `:111-116`).
- **Optimistic concurrency on the memory store.** The job takes a snapshot carrying a content fingerprint before proposing; on apply, the store recomputes the fingerprint and refuses with a stale result if anything changed underneath, so the snapshot/propose/verify/apply sequence is a compare-and-swap (`the reference tree's source/host/extensions/memory/memory-service.ts:28`, `:111`, `:114`; the fingerprint is built by hashing the memory files' paths and raw contents with sha256 at `:130`). A stale result re-queues the agent for another pass (`memory-synthesis-service.ts:280-281`).
- **Outcome telemetry.** Every pass reports a typed outcome — commit, staleness, rejection, malformed output, failure, or nothing-to-do — with counts of evidence in, memories in, and changes proposed (`:123`, `:294-296`; translated for the telemetry port in `the reference tree's source/host/extensions/telemetry/memory-synthesis-telemetry.ts`).

## What the current build does
**Absent.** The build has no synthesis, no proposal/verification flow, and no evidence citation anywhere: a case-insensitive scan of `src/` and `client/` for "synthes" returns nothing. There is no background LLM job, no evidence queue, no change-set validation, and no snapshot/fingerprint check when writing.

The two closest analogs are practices, not the capability. The first is the report-clamp pattern: the build bounds every worker report, error, activity line, and result excerpt that reaches dispatcher context with named character caps and an explicit truncation marker, so oversized text is elided rather than silently destroying context (`src/core/report-clamp.ts:17`, `:20`, `:23`, `:32`, `:35`, `:48`, `:60`). The second is ledger disposition recording: when a dispatcher obligation closes, the todo reconciler records why it closed — a disposition plus a reason, with the first close winning, so a loss stays explicable (`src/core/todo-reconciler.ts:25`, `:73-74`, `:110-113`, `:488-491`, `:500`, `:645-647`). The dispatcher-private ledger that carries those records is owned by the core dispatcher module and is never passed into a worker (`src/core/multitask.ts:258-259`).

Both are ways of capping size and recording accounting over the build's own bookkeeping. Neither proposes anything to a model, verifies a proposal, or cites evidence, and neither is a periodic job — the build has no machinery for maintaining memory in the background at all.

## The deviation
The reference treats memory maintenance as a background inference pipeline with a proposal stage, a separate verification stage gated on an explicit approval flag, a bounded and evidence-citing change set, and optimistic concurrency against the store it writes. The build ships none of it and reserves no place for it.

This is a **ruled exclusion, not an oversight**. The synthesis service is the engine inside the per-agent memory feature that ADR-0018 exception **C14** rules out (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:29`); DD-188 records the feature-level exclusion and already names synthesis behavior among its sibling internals (`reference-deviations/DD-188-memory-feature-absent.md:12`, `:26`). This filing is that sibling and cross-references it rather than duplicating it.

One nuance worth stating plainly so a reader can see what C14 actually reaches: the individual design ideas here — propose then verify, cite the evidence behind each change, cap the change set, guard writes with optimistic concurrency — are general patterns, not memory-specific ones, and the propose/verify shape in particular resembles a review gate that could in principle sit on any change a model proposes. But in the reference they exist in service of a ruled-out feature, and the build has no place where a model proposes a change at all, so there is nothing here for them to gate. The separability is noted below as one small uncovered point; it does not soften the exclusion of the service itself.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 (accepted, position 2 in the authority stack, and the human-ruled master among the ADRs) names per-agent memory explicitly in exception C14 — no org chart, no routines/automations subsystem, no per-agent memory, no group rooms (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:29`) — and this synthesis service is that feature's engine, the periodic job that exists only to maintain the ruled-out memory store. The ruling is decisive and requires no new judgment: the capability is ruled, not unruled, and the sibling feature filing reaches the same DO-NOT-INCORPORATE verdict (DD-188). No recorded ruling reverses C14, and no PRD amendment (ticket-64 or later) is recorded as reinstating memory or any job that maintains it. The one point no ruling covers — whether the propose/verify pattern, taken away from memory, deserves consideration as a general review gate — is not addressed by any recorded ruling and is left for the human to decide rather than folded into this verdict.

## Incorporation notes
- **Where it would live:** Nowhere, under C14. If the human ever reverses C14, the natural shape is a core-side background job module under `src/core/` (sibling to `report-clamp.ts` and `todo-reconciler.ts`) driven through the adapter's host hook to a model session, with the durable store question deferred to the storage-architecture deviation, DD-177 — the build's only persistence today is dispatcher bookkeeping, so the store would have to be solved rather than inherited.
- **Constraints:** C14 forbids the feature outright, so any work here needs a dated human reversal of C14 first, not an agent ruling. If it were ever reopened: the build has no way to call a model from core, no periodic-job machinery, no durable per-agent store, and no prompt assembly this engine would feed — it would inherit every constraint recorded against the memory feature in DD-188. The propose/verify pattern in isolation has no home in the build: there is no flow where a model proposes a change for a verification stage to gate, and the build's approval flows are for humans, not verified by a model.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — the ruling is what blocks this, not the code: a C14 reversal would mean building the whole ruled-out memory feature (durable store, prompt injection, an agent-facing way to write facts) before this engine had anything to synthesize into, plus a background inference job with debounce/deadline/retry machinery the build does not have.
