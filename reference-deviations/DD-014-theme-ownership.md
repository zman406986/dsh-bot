# DD-014 — Theme ownership: reference self-themed engine vs host-token inheritance
- **Area:** UI shell / window chrome (A1)
- **Type:** deliberate-divergence
- **Date:** 2026-09-23

## What the reference does
The reference frontend owns theming outright. It keeps a user-facing theme preference (system-following, light, or dark) exposed through a theme bridge surface: on mount it builds a runtime theme installer bound to the document with the bridge's initially resolved theme (`ProductionRenderer.tsx:2757`), and subscribes to the theme bridge's change channel so every change updates the preference state, the resolved theme, the runtime installer, and applies the resolved theme to the root shell (`ProductionRenderer.tsx:2758`). It also registers a set of theme commands in the command palette — one entry per preference, marked active when selected, routed through the theme bridge's setter followed by the root-shell theme applier (`ProductionRenderer.tsx:3334-3341`). In short: the shell is self-themed, theme is a setting the product controls, and the document root's theme attribute / colour-scheme is driven by the app.

## What the current build does
The build has no theme control at all — no preference state, no installer, no palette commands. Instead every colour in the client surface resolves through the host's `--dsw-alias-*` tokens and inherits whatever theme the host dsh shell is in. This discipline is written into the style headers themselves: `shell.tsx` states colours come from the `--dsw-alias-*` token per "ticket 49's contract — no private palette" and that "the shell inherits the host's theme colour" (`src/client/shell.tsx:65-67`, token roster at :92-94); `floating-window.tsx` records that "Theme survives the portal: the `--dsw-alias-*` tokens are defined on" the host side and that every colour is a host token with no private text colour ("the host theme's inherits") (`src/client/floating-window.tsx:40, 71-72, 113`).

## The deviation
Ownership of theme: the reference treats the UI as a self-themed product with its own preference surface (a theme preference via bridge + palette commands + runtime installer applying the root theme attribute / colour-scheme); the build deliberately owns no theme and delegates theme resolution entirely to the host dsh shell through alias tokens. This is a structural difference, not a missing feature button: adopting the reference model would mean introducing a private palette or theme installer, which the build's recorded style contract (ticket-49 "no private palette", token-only faces) explicitly forbids.

## Verdict: DO-NOT-INCORPORATE
The authority stack settles this without stretching: ADR-0021 (decided by the human, accepted) makes stock dsh the primary, never-displaced UI, with our client module coexisting additively in a floating window — a coexisting module that inherits the host's theme is the arrangement that ruling implies, and the ticket-49 token contract ("no private palette") recorded in the shell/floating-window style headers is the concrete expression of it; accepted ADRs outrank any attraction from the reference tree. No recorded ruling specifically addresses *theme control* as a feature (whether users may set light/dark for our surfaces), so if that is ever wanted it is a new question for the human — but as an incorporation target, the reference's self-themed engine contradicts a recorded contract and must not be brought in. Re-open the preference idea only via a human ruling or a new ADR, not by gradual adoption from the reference tree.

## Incorporation notes
- **Where it would live:** If ever ruled in, a preference surface would live beside the existing client surface (`src/client/shell.tsx` / `src/client/floating-window.tsx`) and would need a host-side theme bridge the current architecture does not have; the runtime-installer/root-attribute pattern has no equivalent connection point in the additive floating window.
- **Constraints:** Ticket-49 contract forbids a private palette — any self-theming would have to be ruled in by the human or a new ADR amending it; ADR-0021's coexistence arrangement means the host shell keeps owning document-root theme state; the floating window must keep failing in isolation, so theme code must not add another hard coupling.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — mechanically small to add a preference, but it crosses a recorded contract (ticket-49) and the ADR-0021 coexistence boundary, so the risk is governance (needs human ruling) more than code.
- **Key reference anchors:** the reference tree's `frontend/src/production/ProductionRenderer.tsx:2757` (runtime theme installer on mount), `:2758` (theme-bridge change subscription → preference/resolved-theme/installer update/root-shell theme application), `:3334-3341` (the palette's theme entries calling the theme bridge's setter).
