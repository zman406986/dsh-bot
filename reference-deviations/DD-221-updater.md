# DD-221 — Updater: check, download, verify, stage, apply, tracks, managed gate
- **Area:** A28 approval & policy
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference ships a self-update subsystem in its main process, under the reference tree's `source/electron-main/update/`.

**Check.** A service performs a periodic check on a timer: an initial delay of thirty seconds, then a one-hour interval to which a random jitter ceiling of five minutes is added, so a fleet does not check in lockstep (the reference tree's `source/electron-main/update/sand-update-service.ts:14-16, 52`). The feed response is parsed and validated defensively — the version, the download location, and an optional integrity field that, when present, must be a non-empty string (the reference tree's `source/electron-main/update/update-feed.ts:30-31`). Backend and minimum-version gates can additionally force a check outside the timer (the reference tree's `source/electron-main/update/update-gate.ts`).

**Download and verify.** The download streams to a staging directory with progress reporting, computing a SHA-256 digest as bytes arrive; when the feed supplied an expected digest and it does not match, the download throws rather than proceeding (the reference tree's `source/electron-main/update/update-download.ts:1, 11, 24, 40-42`). Progress is reported on a stepped basis so the UI is not flooded (the reference tree's `source/electron-main/update/sand-update-service.ts:81`).

**Stage.** Staging is platform-split and both paths hand off to a platform installer mechanism rather than writing files itself. On macOS the service serves the verified archive to the platform's standard installer framework through a local feed server and starts a staging timeout; on Windows it stages through a signature-verified installer. The staging timeout is ten minutes; when it fires, staging artifacts are cleaned up, an honest timeout outcome is recorded, and the service returns to idle to retry on the next check (the reference tree's `source/electron-main/update/sand-update-service.ts:17, 81, 84`; the reference tree's `source/electron-main/update/squirrel-feed-server.ts`; the reference tree's `source/electron-main/update/win32-installer.ts`).

**Apply.** Applying is a quit-and-install path guarded by a durable apply marker. The marker records a phase — staged, requested, spawned, or spawn-failed — together with the mechanism, the target and source versions, and the relevant timestamps, and it is validated on read so a malformed marker is discarded rather than trusted (the reference tree's `source/electron-main/update/apply-marker.ts:8, 22`). On the next launch the marker is settled by comparing the running version against the target version and measuring the elapsed gap since the request: the outcomes distinguish a confirmed apply, a confirmed-but-late apply, and a stale-version case where the spawn happened but the expected version never came up — each carrying a distinct error code (the reference tree's `source/electron-main/update/apply-marker.ts:27-34`). An unattended relaunch can apply an already-staged update while the user is away; that tick is gated by a persisted opt-in plus an experiment flag, with the user-away and host-idle signals supplied by the platform (the signal factory, the conjunction gate, the apply step's re-checks, and the code that connects them are enumerated in DD-212, which owns the platform-sensing part).

**Tracks and the managed gate.** Three update tracks exist — stable, nightly, and dogfood. Nightly is disabled by default, dogfood is internal-only and gated behind an unlock input, and a disabled track is coerced back to the default whenever a value is read, so a stale or retired track falls back silently rather than being honored (the reference tree's `source/shared/update-track.ts:1, 4-5, 8`). A policy-managed track, when configured, overrides the user's own override, and the effective track is resolved through that precedence chain before any check runs (the reference tree's `source/shared/update-track.ts:10-11`).

**Pausing before an update.** Before an upgrade shuts the host down, pending approvals are expired with a separate expiry cause reserved for that situation, and the model is told explicitly that the interruption was not a denial and that it should re-run the action after resume (the reference tree's `source/host/runner/sand-auto-review.ts:10, 76, 163`; the pause is requested from the agent runner at the reference tree's `source/host/runner/sand-agent-runner.ts:1152` and driven from the host's prepare-for-upgrade path at the reference tree's `source/host/extensions/host-upgrade/host-upgrade-service.ts:39`, with the host surface at the reference tree's `source/host/sand-host.ts:740`).

## What the current build does
None of it. There is no update check, no download, no integrity verification, no staging, no apply path, no track concept, no managed-policy gate, and no apply marker anywhere in `src/` or `client/`.

The reason is structural rather than an oversight: the build is a Cordis plugin loaded into the dsh host. It does not own its own process, its own distribution, or its own launch, so it has no self-update channel to drive and no platform installer API within reach. The update-adjacent surfaces the build does have are all about *someone else's* restart:

- a one-time restart-honesty notice assembled from a rebuild report, which states unknown-state workers as unknown, states restored terminal rows plainly, emits nothing when the report is empty, and degrades to a single honest "nothing was restored and nothing was replayed" line if the marker store itself could not be read (`src/adapter/restart-notice.ts:1-23, 77-101`);
- the minimum-to-reconstruct durable marker and its rebuild report — the port, the marker shape, and the restored/unknown-state split (`src/core/durability.ts:1-28, 36-45, 55-77`);
- a pull-only worker liveness verdict that explicitly refuses to become a watchdog: no timers, no polling, nothing killed or redriven (`src/core/liveness.ts:1-20, 92-113`);
- a plugin unload/HMR teardown effect that unbinds the lifecycle, deactivates tool surfaces, clears session access policy, abandons outstanding prompts (leaving the relay's armed deadline to deny their asks), clears the roster mirror, and disposes the host and marker domain (`src/plugin.ts:781-801`).

## The deviation
The entire updater subsystem is present in the reference and absent from the build — check, download, integrity verification, staging through platform installers, the apply marker and the code that settles it on the next launch, the track set with its coercion and managed override, the forcing gates, and the pause-before-update shutdown. This is a missing feature at the level of a whole subsystem, and it is the same missing feature DD-101 filed from the settings side: DD-101 ruled the Updates settings panel out of scope and recorded that the updater it configures does not exist in this plugin, filing the mechanism here (`reference-deviations/DD-101-updates-section.md:13, 15-16`).

## Verdict: DO-NOT-INCORPORATE
Three recorded rulings independently settle this, and they do not need to be combined to reach the answer. ADR-0020 (draft, non-human-approved) lists a native/Electron desktop shell among its rejected vehicle options, on the ground that it is a PRD non-goal — the PRD's instruction not to chase the compared product's binary or UI parity — with no evidenced connection point and exclusion "without further study" (`docs/adr/0020-wrapper-shell-vehicle-own-frame-over-shipped-runtime-draft-nonhuman-approved.md`, status line 3, line 28). DD-101 already ruled the updates settings group host-app scope, holding that a plugin has no self-update channel and that the mechanism and its settings are one unit of scope (`reference-deviations/DD-101-updates-section.md:15-16`). DD-212 already reserved the unattended-relaunch consumer to this file while ruling the platform-sensing part out, and recorded the update-relaunch part as further blocked on updater territory (`reference-deviations/DD-212-power-sleep-and-idle-sensing.md:16, 25-26, 30`). Beyond the rulings, the staging part is unreachable by construction: both staging paths hand off to main-process installer facilities that a plugin loaded into the host cannot call. One caveat is recorded rather than glossed: ADR-0020's chosen vehicle was superseded by ADR-0021, but that supersession concerns which shell we build, not the rejected-options table's exclusion of a native shell, which remains the PRD non-goal citation. Both ADR-0020 and the ADR-0010 position DD-212 also cites are draft and non-human-approved; no human ruling speaking to the updater is recorded, and the verdict here follows the highest recorded authority rather than a human decision.

Two properties are worth naming as transferable even though the subsystem is not, and neither is opened as work here.

The first is the **graceful-stop protocol**. The reference's pause-before-update rule expires pending approvals before applying an update and tells the model the interruption was not a denial — a genuinely better ending than a bare timeout, because a model that reads a timeout as a soft refusal will abandon a plan the user never rejected. That taxonomy is already DD-217's ground: DD-217 recorded the shutdown cause as part of the reference's expiry-cause set and ruled that question ADAPT, deliberately declining to incorporate causes the approval code cannot observe, and naming the shutdown cause specifically as one the build cannot report because it has no host-shutdown path and no epoch notion (`reference-deviations/DD-217-approval-lifecycle-and-expiry.md:15, 17, 38, 41`). The build's teardown does have the *shape* of a shutdown — it abandons outstanding prompts on unload and lets the relay's deadline deny their asks (`src/plugin.ts:788-789`) — but it fires on plugin unload/HMR rather than on a host update, and it produces no not-a-denial signal, so the model gets the bare denial DD-217 described. That is DD-217's gap on the approval path, and this file does not re-file it.

The second is the **durable apply marker**. The reference writes a phase record before an irreversible step and settles it on the next launch by comparing what is running against what was intended, distinguishing a confirmed apply from a late one and from one that never took effect. Put plainly, this is a durable record of what was intended, checked on the next launch — and the build already implements exactly that pattern, for the part of the system it owns. The minimum-to-reconstruct marker plus the replay rules are a durable record written at spawn and settled at rebuild, and ADR-0012 pins the honesty rule on top of it: a marker whose state is unknown is reported once as unknown and never invented, restored rows are stated plainly, an empty report is silent, and a marker-store failure degrades to one honest line rather than a fabricated roster (`docs/adr/0012-restart-replays-durability-never-work-draft-nonhuman-approved.md:11-15`; `src/core/durability.ts:1-7, 47-64`; `src/adapter/restart-notice.ts:77-101`). So the honest answer to the question this file is really asking — does the build's restart notice plus durability replay already give the operator a truthful account of what happened across a restart? — is yes, for what the build is responsible for. It accounts truthfully and boundedly for worker obligations, and it claims nothing it cannot prove. What it cannot account for is *why* the restart happened, since it has no client-side presence input to distinguish an update from a crash or a sleeping machine; DD-212 already named that open question as the disconnect-cause attribution and left it open (`reference-deviations/DD-212-power-sleep-and-idle-sensing.md:21`). The reference's apply marker answers a question the build has no counterpart to — did the application's own upgrade take effect — so the pattern is not a new idea for this project and nothing here should be built on its account.

No recorded ruling reaches these two properties *as such*, and that is said explicitly rather than implied: they are existing gaps that already have owners, not open work. Nothing in this deviation should be read as authorizing a self-update channel, a track selector, a managed-policy gate, an apply marker, or an approval-cause vocabulary.

## Incorporation notes
- **Where it would live:** Nowhere under the current rulings. If a host-app updater ever existed, the updater itself would be host-app code, not plugin code, and the plugin's only defensible surface would be a read-only pointer in its settings section (`src/adapter/settings-section.ts`), which DD-101 already ruled against building. The two existing gaps do not add a location: the graceful-stop gap belongs to DD-217's approval code (`src/adapter/dispatch-approval.ts`, `src/core/access-relay.ts`), and the apply-marker pattern is already implemented by `src/core/durability.ts` plus `src/adapter/restart-notice.ts` for the part of the system the build owns.
- **Constraints:** A Cordis plugin cannot update, stage, or restart its host, and the reference's staging paths hand off to main-process installer facilities with no connection point from a plugin; the track set needs a host-side policy and experiment-flag source the plugin does not have; the managed track's override precedence is a host policy concern by construction. Any reversal would have to clear ADR-0020's native-shell exclusion (line 28) and DD-101's and DD-212's scope rulings first, and would be a ruling change rather than an implementation task.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — not because the work is small but because there is nothing to build: the subsystem is unreachable from a plugin and every part of it is ruled. Risk of incorporating anything here is inventing a self-update channel the plugin cannot honestly drive, and re-opening the shell question ADR-0020 and ADR-0021 already settled.
- **Key reference anchors:** the check timer and its jitter (the reference tree's `source/electron-main/update/sand-update-service.ts:14-16, 52`); the staging timeout and cleanup (`:17, 84`); the download-and-stage split with its platform hand-offs (`:81`, the reference tree's `source/electron-main/update/squirrel-feed-server.ts`, the reference tree's `source/electron-main/update/win32-installer.ts`); feed validation of the optional integrity field (the reference tree's `source/electron-main/update/update-feed.ts:30-31`); streaming SHA-256 verification and the mismatch throw (the reference tree's `source/electron-main/update/update-download.ts:1, 11, 24, 40-42`); the apply marker's phase set and validated read (the reference tree's `source/electron-main/update/apply-marker.ts:8, 22`) and its settlement outcomes (`:27-34`); the forcing gates (the reference tree's `source/electron-main/update/update-gate.ts`); the track set, internal-only track, disabled-nightly coercion, and managed-over-user precedence (the reference tree's `source/shared/update-track.ts:1, 4-5, 8, 10-11`); the shutdown cause, the not-a-denial reason, and the path that ends an ask with its cause (the reference tree's `source/host/runner/sand-auto-review.ts:10, 76, 163`), where the request is made (the reference tree's `source/host/runner/sand-agent-runner.ts:1152`), the host prepare path (the reference tree's `source/host/extensions/host-upgrade/host-upgrade-service.ts:39`), and the host surface (the reference tree's `source/host/sand-host.ts:740`). The idle-relaunch gate, apply step, and the code that connects them are DD-212's anchors and are not restated here.
