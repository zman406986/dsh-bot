# DD-152 — Project conversation type (a first-class project-agent role with a durable store)
- **Area:** A18 prompt sections
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference defines a distinct project-agent conversation type: a long-running chat that owns durable on-disk state and persists across many turns and delegated background work. Its prompt module is roughly 20 KB and carries four prompt variants behind one role definition:

1. **Root initial variant.** Sets the project-agent role, resolves and names the project, and establishes a session-scoped agent store — a persistent directory shared with child agents — that the agent is told to resolve to an absolute path before writing. It then specifies three durable artifacts by convention: a markdown notes file that serves as the task checklist (checkbox syntax only, with explicit rules for labels, nesting, pruning windows, and linking to subagents/PRs/artifacts); a documents directory for durable markdown (research, plans, specs, self-contained reports — including delegated reports); and a separate preferences/memory file kept deliberately apart from the task list. It adds report-writing rules (write a report instead of over-long chat replies; cite the report's absolute path) and a teammate-style reply manner, and instructs the agent to delegate blocking work.
2. **Condensed reminder variant.** A much shorter restatement of the same obligations, injected on later turns rather than replaying the full role text.
3. **Compaction variant.** Restates the project role after context compaction, so the durable-store obligations survive a lossy context event.
4. **Thread/subagent and side-chat variants.** These share the parent project's store directory and add report frontmatter (model-authored attribution metadata, explicitly framed as not authoritative provenance) plus ownership rules: a report may only be overwritten when its recorded owner id matches the writer, and non-owned material is cross-linked rather than edited.

A "scope-binding" line at the head of the root and reminder prompts limits the role to the root conversation, so a delegated child that inherits the text does not adopt the project role.

## What the current build does
ABSENT. The build's dispatcher persona is flat: a single heading-title persona string (`# Multitask dispatcher`) with two fixed bodies (`## How you work`, `## What you never do`) in `src/core/policy/prompts.ts`, plus reminder sections that are headings only. There is one dispatcher role, no project/child role distinction, and no scope-binding line, because there are no inheriting prompt variants to disambiguate.

The ledger is session-internal state, not a user-visible file on disk — `prompts.ts` renders it as a per-turn reminder section and an empty-ledger marker, not as a markdown checklist the agent owns and curates. There is no store directory, no notes file, no documents-directory convention, and no report frontmatter; the worker contract in `src/worker/prompt.ts` is a per-task contract for one leaf worker (role, autonomy, limits, access-asking, ledger, work style, final answer, safety) delivered as a system message, explicitly scoped as a task-bounded child rather than a durable project role. The only thematic overlap with the reference's Project role is a single delegation bullet ("hand non-trivial multi-step work to a worker").

## The deviation
The reference treats a durable, project-scoped agent identity as a first-class conversation type whose obligations are repeated at three lifecycle points (initial, per-turn reminder, post-compaction) and shared with children under an ownership rule. The build has no project conversation type at all: it has one dispatcher persona, a session-internal ledger that is not durable, per-task worker contracts, and no agent-owned on-disk artifacts. Adopting the reference's design would mean introducing a second prompt role, an on-disk agent store, three named durable artifacts (checklist, docs, preferences), and an ownership/frontmatter discipline for delegated reports — none of which exist in the build.

## Verdict: ASK-HUMAN
No recorded ruling names a project role with durable on-disk artifacts, so this is not covered by an existing decision and I will not pick for the human. The nearest recorded material is adjacent but does not govern this case: ADR-0018 exception C14 rules out an org-chart/routines/memory subsystem, and U-B rules out rich chat ergonomics — a project role with a user-visible notes file, docs tree, and preference memory is close to the class C14 is skeptical of, but neither exception literally names it, and "general skepticism about a class of features" is not a ruling about this particular one. The build's ADR-0021/0022 do apply, but only to *how* such a thing would land: they establish a single additive place to hook in, so any adoption would have to be an added prompt variant behind that hook rather than a rewrite of the flat persona. Because the deviation introduces a genuinely new subsystem family (durable agent-owned artifacts) rather than extending an existing one, the human should rule on scope before anyone builds it.

## Incorporation notes
- **Where it would live:** A new prompt-variant module alongside `src/core/policy/prompts.ts` (e.g. a project-role builder emitting the root/reminder/compaction variants), wired through the single additive hook established by ADR-0021/0022 in `src/core/policy/assembler.ts`. The store-path resolution and any ownership metadata would sit with the session/state layer near `src/core/session/parent-agent.ts`. Worker-side, the reference's thread/side-chat variants map onto the existing per-task contract in `src/worker/prompt.ts`.
- **Constraints:** The build's ledger is currently session-internal; making it a file on disk changes it from transient state to a user-visible artifact the agent curates, so the ledger's authority and lifecycle would need a recorded decision. Any prompt variants must survive compaction the way the existing worker contract does (delivered as a system message, recomputed per turn) rather than being appended to individual turns. A role/child scope-binding line is mandatory if variants are inherited, otherwise children will adopt the project role. Frontmatter-style attribution in the reference is explicitly non-authoritative metadata; if the build adopts anything like it, it must not be treated as provenance or a security boundary. Repo hygiene in the reference — keeping agent artifacts out of the repository by default — should be preserved or the build will write into users' repos.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — a new prompt-role variant plus a durable on-disk artifact family and a path that survives compaction touches policy assembly, session state, and the worker contract at once; risk is mainly scope creep into the memory subsystem that C14 rules out and writing agent files into user repositories.
