# DD-151 — AGENTS.md project-instruction injection into prompts
- **Area:** A18 prompt sections
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference assembles an explicit AGENTS.md rule block into the agent's prompt. In the reference tree's `source/packages/agent/prompts/testing/shared.ts` the exported AGENTS.md-instructions section (its internal title names agents-md-and-skills) states, in its own words, that the first user message may carry instructions drawn from AGENTS.md; that those instructions may hold environment-, code-, or testing-related guidance; and that the agent must follow them where they are relevant. Two precedence rules are stated in the same block: the system prompt overrides conflicting AGENTS.md instructions, and direct instructions arriving in system/developer/user messages override conflicting AGENTS.md content. The same section frames skills as standard operating procedures for a task, says the first user message lists the available skills with a filepath and a usage description, and requires the agent to read the relevant skill file when an applicable one exists.

Separately, the reference tree's `source/packages/agent/prompts/user-info-cloud-sections.ts` defines a cloud-instructions section, titled to name cloud instructions, whose description says the instructions are pulled from AGENTS.md, and which embeds the AGENTS.md file contents inline into the prompt (taking the file body as a rule-content argument).

## What the current build does
ABSENT. The build neither reads nor injects any repo-local instruction file into its prompts. A case-insensitive grep across `src/` and `client/` for AGENTS.md / agents_md / agentsmd returns zero matches. The worker prompt is a fixed contract assembled in `src/worker/prompt.ts` by `buildWorkerSystemPrompt()` from a fixed array of section strings (Role, Autonomy, Limits, Asking for access, Todo ledger, Work style, Final answer, Safety) with no reading of any file. The dispatcher-side prompt is likewise assembled from fixed text: `src/core/policy/assembler.ts` (`assembleTurnReminder`) and `src/core/policy/prompts.ts` (`buildStandingRulesBlock`). No step reads a repository file, either path.

## The deviation
The reference gives AGENTS.md a defined place in the prompt — a rule block that establishes that such instructions exist, that they must be followed where relevant, and how they rank against the system prompt and against direct messages, plus an inline embedding of the file contents in a cloud-instructions section. The build has no equivalent: it neither reads AGENTS.md nor states any precedence for repo-local instructions, and it does not tell a worker that such a file might exist or that skill files should be read before acting. The gap is structural rather than a wording difference — the build has no step that reads the file, so there is nothing to attach the rules to.

A nuance worth stating plainly: the build's workers run inside user repositories, and the host environment may already place repository context into the session on its own. So the build's silence is not automatically the build's omission — it may be delegated to the host layer. This deviation should be read as check-before-assuming: what is established is that the build neither reads nor injects AGENTS.md itself and states no precedence rule for it; whether some host-supplied mechanism covers the same ground is a separate question that a live check, not this comparison, would settle.

## Verdict: ASK-HUMAN
No recorded ruling in the project's authority stack covers reading repository instructions into prompts. The nearest recorded decisions do not settle this point: ADR-0018's exception list rules out org-chart/routines/memory (C14) and rich chat ergonomics (U-B), and neither exception settles whether AGENTS.md content may steer workers or dispatcher prompts, so neither can be stretched to cover it. Because this is a genuine capability with a real adoption question — it changes which instructions can steer a worker, and it introduces a precedence relationship the build does not currently define — and because no recorded ruling decides it, the authority stack does not settle the matter and the human must. The verdict is ASK-HUMAN on that basis, stated explicitly as an absence of ruling rather than a finding against the feature.

## Incorporation notes
- **Where it would live:** A new injection point feeding worker prompt assembly in `src/worker/prompt.ts`, most plausibly as an additional system-position section alongside the existing contract, and a parallel site in the dispatcher's prompt assembly (`src/core/policy/assembler.ts` `assembleTurnReminder`, `src/core/policy/prompts.ts` `buildStandingRulesBlock`). Any repository-file read would sit upstream of both, in whatever component resolves the working directory for a spawned worker.
- **Constraints:** The worker contract deliberately avoids repeating guarantees the host already states (see the header comment in `src/worker/prompt.ts` on the host's delegation-scope section) — an AGENTS.md section must not duplicate content the host already injects. The contract text also uses strict `{{…}}` interpolation and a test checks that no literal braces appear, so injected file content cannot be spliced into that string directly. Precedence wording must not contradict the build's existing rule that the host's guarantees outrank the worker contract. Worker prompts are built from a fixed template today; adding variable content changes caching and compaction behavior and needs a size limit.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the injection itself is small, but the precedence statement, the limit on stale and oversize file content, and the question of whether the host already covers this are what make it a design decision rather than a patch.
