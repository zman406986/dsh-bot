# DD-165 — Shell tool ownership: reference-owned vs host-owned
- **Area:** A19 tool surface
- **Type:** deliberate-divergence
- **Date:** 2026-09-23

## What the reference does
The reference application owns its shell tool outright. A single large module (~706 lines) constructs the tool and, inside it, selects how the tool is presented to the model: per-model description formatters exist side by side — one dedicated formatter for a particular model family, one for a terminal-multiplexer execution style, one for a sandboxed execution style — and a smart-mode parameter set is layered on top of the base parameter shape beginning at line 581 of that module. Because the reference ships the whole product, its agent runtime and its shell tool live in the same tree: the reference therefore controls the tool's description text, its parameter shape, and the mode selection that decides which of those variants the model sees on a given turn.

## What the current build does
The shell tool is host-owned, and the build does not define or describe one. Workers simply inherit whatever toolset dsh hands them: the worker contract's work-style section tells the worker to use the available work tools — naming shell alongside files, search, and web — as a category of inherited capability, not as anything this plugin registered or documented (`src/worker/prompt.ts:73`). The contract file's own header documents the same stance for the neighboring surface: permission scope is fixed at spawn by the host and stated by the host, so the build leans on it rather than restating it (`src/worker/prompt.ts:26`). What the build does own is removal only, not construction: `src/worker/tool-barrier.ts` narrows a worker's inherited toolset by intersecting a deny-candidate list with the tool names actually registered as globals at spawn time, because the host's restriction call rejects unknown names. Nothing in that path adds, shapes, or describes a shell tool.

## The deviation
This is a deliberate ownership boundary, not a gap. The reference is the whole application, so it necessarily owns its agent runtime and, with it, its shell tool; the build is a plugin *inside* dsh, and dsh owns the tool runtime. Under plugin ownership there is no place for the reference's mode-selection machinery to attach — the per-model description formatters and the smart-mode parameter layering are implementation details of the reference's ownership of the tool, and host ownership leaves them no consumer. The build's only legitimate contact with the shell tool is the deny side: it may remove names from what a worker inherits, never supply them.

## Verdict: DO-NOT-INCORPORATE
The recorded ruling is PRD §2, whose non-goals exclude "Rebuilding dsh's inference router, transcript storage, or tool runtime" (`PRD-dsh-multitask-dispatcher.md:36`). A shell tool authored by this plugin would be exactly that rebuilding, so the PRD forecloses it directly — the authoritative home for this rule is `PRD-dsh-multitask-dispatcher.md` §2, and it sits above draft ADRs and glossary entries in the authority stack. ADR-0018 supplies the adjacent hard constraint: even where the reference's presentation logic were attractive, that decision is about provenance (adaptation permitted, verbatim copying not), not about granting permission to cross the ownership line. No recorded ruling requires the build to own a shell tool, and none has been found that would license it.

## Incorporation notes
- **Where it would live:** Nowhere in the current build. The nearest host-owned surface the build touches is the deny path in `src/worker/tool-barrier.ts`; a shell-tool module would have to live beside it under `src/worker/` or in a new registration module, and would be a fresh tool runtime — precisely what PRD §2 excludes.
- **Constraints:** The build must not register, describe, or reshape a shell tool. Workers inherit it from dsh; the build may only subtract inherited names via the spawn-time intersection in `src/worker/tool-barrier.ts` (deny candidates intersected with live global names, never a hard-coded full list). Any future work on the shell surface belongs to dsh, not this plugin.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S to *close* (nothing to build — the boundary is already correct and only needs to stay documented); any incorporation attempt would be L with high risk, since it duplicates host-owned runtime and collides with PRD §2.
- **Key reference anchors:** `reference material-NOT LICENSE SAFE DONT COPY-grok bot\source\packages\agent\tools\core\shell\create-shell-tool.ts` — the owning module (~706 lines), with the per-model, terminal-multiplexer, and sandboxed formatter variants and the smart-mode parameter block beginning at line 581; sibling modules in the same directory and in the reference tree's `source\packages\agent-exec\` and `source\packages\shell-exec\` show the execution machinery the reference also owns.
