# DD-199 — Chunked attachment reads and a download path
- **Area:** A25 attachments & media
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The read side of the reference's attachment family is byte-oriented and windowed, and it ships alongside a save-to-disk path. Four parts, all on the desktop/main-process side of the boundary:

- **Windowed byte reads.** The desktop side asks the host for a byte range by offset and length and receives a chunk record that carries the total size of the file alongside the payload; it then walks the file window by window to exhaustion. The window size is a named constant of four megabytes, and the read path's signature is the offset/length pair (`.../source/electron-main/attachments/attachments.ts:6`, `:10`, `:14`).
- **Size probe first.** A zero-length read at offset zero is used purely to learn the total size before anything is decided — both in the bounded full-read helper and in the download path (`:67`, `:102`). The size is what the ceiling checks and the transfer loops are driven from.
- **Ceilings on reads.** Byte reads are gated on the preview kind actually needing bytes, and the ceiling is a preview byte cap of twenty-five megabytes, which a caller-supplied lower ceiling is clamped against (`:86`; the cap constant lives at `.../source/electron-main/attachments/attachment-manager.ts:8`).
- **A download path.** It validates the source, probes for size, computes a default save path from the operating system's downloads directory (the configurable-directory input is passed as null at this call site), shows a save dialog, opens the chosen target, writes it window by window at the running offset, and closes the handle. On a short transfer it deletes the partial file, reports a download-labelled failure carrying a typed error class, and shows a user-facing save-failure notice (`:100`-`:108`, `:75`).
- The protocol carries a chunk-read method and the host exposes a host-side chunk reader that resolves the file inside a directory it owns (`.../source/host/gateway-protocol.ts:116`, `.../source/host/host-gateway-api.ts:616`, `.../source/host/extensions/attachments/attachments-service.ts:206`). The RPC and bridge contracts expose the read-text, read-bytes and download trio to the renderer, and the renderer wires the download handler through at two sites (`the reference tree's frontend/src/recovered/contracts/main-rpc.ts:15`, `:54`, `the reference tree's frontend/src/recovered/contracts/desktop-bridge.ts:380`, `the reference tree's source/electron-preload/preload.ts:116`, `the reference tree's frontend/src/production/ProductionRenderer.tsx:803`, `:3514`); the full set of paths is enumerated at `.../source/electron-main/adapters/attachment-gateway.ts:49`.

Read together: both mechanisms exist because the reference's attachments cross a process boundary. The UI and the agent host are separate processes and may be remote from one another, so a path string on one side names nothing on the other — the bytes have to be moved, in windows, and the near side needs an explicit destination for them. The download path is that destination problem solved for the user's own disk.

## What the current build does
Both mechanisms are **absent**.

- **No chunked read path.** No offset/length read operation, no total-size probe, no byte-payload field, no window constant. A project-wide grep over `src/` and `client/` on 2026-09-23 for chunk vocabulary returns only streaming text deltas (`src/client/conversation-store.ts:319-327`) and the ticket-69 "chunk A/B" work labels — nothing byte-oriented.
- **No download path.** Nothing writes to a user-chosen destination or to an OS downloads directory; there is no save dialog, no partial-transfer cleanup, and no OS save surface of any kind in the build.
- **Attachment references are path strings.** The deliver tool takes an optional list of local paths the dispatcher chooses to attach, and the send path's signature is a list of paths (`src/core/tools.ts:567`-`:587`, `:104`-`:106`). The client's command transaction carries attachments as opaque values (`src/client/context.ts:323`-`:331`). Forwarding a path is the whole mechanism; nothing enforces a ceiling on the forwarded list. The staging/upload half of this story is DD-198 and is not re-described here.

## The deviation
The reference needs both mechanisms because it has a transport problem; the build does not have that problem. Its actors — dispatcher, workers, client — share one filesystem, so the bytes are already on the side where the user is, and a path is a complete and sufficient reference. There is no boundary to pay for, so a chunked read path would add an interface with nothing on the far side to cross, and a download path has no destination problem to solve: "downloading" a file that already sits on the local filesystem is a no-op, or at most a host-side copy the user can perform themselves.

One nuance must be stated carefully, because it has two sides. ADR-0018 exception U-B excludes rich chat ergonomics, naming rich attachment viewers among them — but U-B governs **display**: whether a viewer is built and what it is allowed to render. It says nothing about the byte-transport backend, and it must not be stretched to cover one. The build has no chunked read because its architecture makes the boundary disappear, not because U-B forbids viewers; conversely, U-B's viewer exclusion is not a licence to skip a transport layer if a boundary ever arrives. The two facts are independent.

The twenty-five megabyte preview cap is the one piece of this deviation that a recorded ruling does reach, and it reaches it as a **display** concern: the cap bounds what a viewer will accept, so while viewers are excluded the build is not held to that number. That half is covered.

## Verdict: DO-NOT-INCORPORATE
No recorded ruling names chunked transport or a download path — ADR-0018's exception list is silent on both, so the gap is formally open rather than settled, and this verdict rests on the build's architecture rather than on a signed exception. With a single shared filesystem across the build's actors, bytes never need to travel and a path is sufficient, so a chunked read path would add latency, a window constant, and a partial-transfer failure mode in exchange for solving a problem the build does not have. The one half a recorded ruling does reach is the preview cap, and it reaches it the other way: ADR-0018 U-B excludes rich attachment viewers, and a cap on viewer bytes is a viewer concern, so the build is not held to that number while viewers are excluded. This decision should be re-derived outright if remote or isolated workers ever arrive — that change reintroduces the process boundary and turns both mechanisms from answered questions back into live ones.

## Incorporation notes
- **Where it would live:** nowhere on this verdict — no read path and no save surface exist in the build and none is added. If a remote-worker transport ever arrives, a read path would attach beside the existing adapter layer (`src/adapter/cordis-dsh-host.ts`) and a save surface would be a client-side concern under `src/client/`, never a core one. The reference's equivalent lives in its main-process attachment service, a layer the build has no analogue of.
- **Constraints:** Any adoption is gated on a real process boundary existing first — adopting windows over a shared filesystem buys nothing. A future download path would need its own decisions about destination choice (save prompt versus a fixed directory) and partial-file cleanup; cleanup-on-short-transfer is the behaviour most likely to be forgotten, and the reference's typed failure classes are what make the failure visible rather than silent. Do not read U-B's viewer exclusion as a transport ruling in either direction. Cross-ref DD-198: this file is the read/save half of the same boundary story, and the two decisions are linked: either both hold or neither does.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S as ruled (record-only; zero code). A future transport is M-to-L and must be re-derived from scratch, with the boundary question answered before any window constant is chosen.
