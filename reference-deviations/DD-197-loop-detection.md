# DD-197 — Loop detection: periodic-repeat detector vs the build's visibility-only liveness
- **Area:** A24 context management
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference runs its own agent turn loop, and it defends that loop against self-repetition *inside a single assistant message*. A detector class consumes the streaming text delta by delta, splits it into lines, and looks for periodicity: a run of text repeating with a period of at most 256 units, seen at least three times (the threshold rises to four inside a code fence), gated further by a minimum product of period times repetitions (one hundred, two hundred inside a fence) and, for the multi-line path, a minimum total character count. Two independent scans run — one over substrings of the current line, one over a rolling window of completed lines held in a fixed-size ring buffer. The ring is sized as fifty times the multi-line minimum repetition count, which resolves to 100 entries, allocated once and addressed by modular index arithmetic so it never grows or reallocates. Detection is bounded in wall-clock time: a 500-millisecond deadline is computed per call and the scans bail out into a timeout flag once it passes, which makes the whole check **fail-open** — a slow detector never blocks, delays, or aborts the stream it is inspecting. On detection the streaming path throws a typed loop error built on the transport error base with the **failed-precondition** status kind, carrying a detail marked non-retryable and user-facing copy saying the turn was stopped because the model repeated itself and to try a different model or a new conversation. A companion constructor builds a reminder message naming the loop kind and directing the model to ask the user for guidance if it cannot make progress (with an instruction not to show the reminder). The caller catches that typed error and, behind a boolean feature flag, appends the reminder to the conversation and retries the turn once, logging a warning if the same loop trips again.

## What the current build does
The build has no loop detector at all — a project-wide grep over `src/` and `client/` for loop-detection vocabulary returns zero hits. What it has instead is a liveness verdict (`src/core/liveness.ts`) that is deliberately **visibility-only**. `deriveWorkerLiveness` is a pure function over fields the `check_workers` tool already returns (FSM status, start time, counted tool calls, last observed activity moment, blocked flag) plus a caller-supplied clock, returning `active` / `quiet` / `stalled`. Its header states the rule in as many words: it is "deliberately NOT a watchdog", nothing is killed, retried, polled, or timed, and it "must not be oversold" — it lets a user SEE a stalled worker, it does not recover one. That position is recorded twice over: in the module header, citing the fidelity audit's §2 stage-4 finding, and as ADR-0018 exception D22 (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:33`) — a bounded worker-liveness signal so a wedged worker can be noticed, with the reference matching by absence. The audit's §2 stage-4 row (`docs/research/dsh-core-loop-fidelity-audit.md:37`) is the underlying finding: the reference's watchdog is armed only when a user task waits, its remedy is abandon-and-advance, there is no worker-health probe at all, and that absence is "an admitted reference gap we need not inherit". Separately, the build's responsibility split for the turn loop is recorded in the loop-capability map (`docs/research/dsh-loop-capability-map.md`), which is cited in-code at `src/adapter/parent-agent.ts:67` for its stage 7 (settle→wake) finding that the host's waking primitive opens a turn boundary. Where the build does intervene in worker behavior — the worker contract (`src/worker/prompt.ts`) — it intervenes in prose only (role, autonomy, limits, access-ask, ledger, work style, final answer, safety), and no clause there speaks to repetition or looping.

## The deviation
Two-directional and asymmetrical. The reference's detector is a **self-protection mechanism for a layer that owns its own tool loop**: it watches the model's own streaming output, decides the model is spinning, aborts the turn with a typed error, and re-drives once with a reminder. The build delegates that loop to the host, which owns the iteration cap and the turn lifecycle; the plugin's job is dispatch, observation, and delivery. So the mechanism belongs to the layer that owns the loop, and the honest framing is that a faithful port would have to be a host-side feature rather than a plugin one — the plugin never sees the model's streaming output in the position the detector does, and it does not control how a turn ends. The second half is the recorded position: the build's liveness module is deliberately visibility-only, and that is a recorded position, not an oversight. But that rule was written for worker-health visibility, not for loop detection — **a detector that only reports is not the same as one that intervenes**, and nothing in D22, the audit stage-4 row, or the loop-capability map rules on a repeat detector specifically. The visibility-only rule therefore governs the *shape* any build-side signal must take (bounded, derived, pull-only, no recovery action) without covering what this deviation is about, which is intervening on repetition.

## Verdict: DO-NOT-INCORPORATE
ADR-0018's master rule makes an unmatched reference behavior presumptively to be imitated, and no recorded ruling covers loop detection specifically — so the gap is formally open rather than settled, and this verdict rests on the mechanism's ownership rather than on a signed exception. The mechanism is a self-protection device for a layer that owns the loop, and the build's loop is the host's: the plugin never observes the model's streaming output in the detector's position and does not control when a turn ends, so a port would be a host feature, not a dispatcher one. The recorded position nearest this deviation — D22 plus the audit's §2 stage-4 finding — establishes a visibility-only rule for build-side health signals and must not be stretched into a licence for a new intervening watchdog, which is precisely what a repeat detector is. A build-side detector that only reported would duplicate the liveness module's role without supplying the intervention that makes the reference's mechanism worth having. If the human wants dispatcher-side loop *visibility*, that is a new design ask to be raised as such, not a port of this mechanism.
