# DD-206 — MCP tool exposure and invocation pipeline
- **Area:** A26 MCP machinery
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

**1. Exposure through a materialized descriptor registry.** Tools become callable through a dynamic registry that turns discovered descriptors into on-disk definition files under a per-project layout: one folder per server beneath a fixed project-level subdirectory, a tools subdirectory inside it holding one JSON definition file per tool, sibling subdirectories for resources and prompts, an instructions file, a status file written only for servers in a non-ready state, and a per-server metadata file (the reference tree's `source/packages/local-exec/mcp-file-system-writer.ts:28,35-36,380-383`). Writes are atomic per server — a staging directory is renamed into place over a previous-version directory — and a fingerprint cache keeps unchanged servers from being rewritten (`:380,382`). A small reader module parses a tool name back out of a definition file (the reference tree's `source/packages/agent-exec/mcp-disk-catalog.ts:1-2`). The descriptor session pairs each server identifier with its folder and each server-and-tool pair with its definition path (the reference tree's `source/packages/agent/tools/mcp/mcp-call-options.ts:8-11,49-53`), and that path is what the invocation path later checks the model against.

**2. A reserved internal namespace.** First-party on-demand tools are exposed through the same registry under a reserved namespace name (the reference tree's `source/packages/agent-exec/mcp.ts:37`), described by a synthetic server descriptor built from the registered tool list (the reference tree's `source/packages/agent/tools/mcp/builtin-tools.ts:90-110`), with a dedicated predicate guarding the name against collision with real servers (`:108-110`) and the reserved descriptor merged into the discovery surface in place of any same-named real server (the reference tree's `source/packages/agent/tools/mcp/get-mcp-tools.ts:170-175`; the reference tree's `source/packages/agent/utils/mcp-meta-tool.ts:75-80`).

**3. The discovery/inspection meta-tool.** One meta-tool serves four lookup modes plus a no-argument catalog, and the mode is derived from which arguments are present: a whole namespace with full schemas, one named tool, a regex search across namespaces, a namespace-scoped regex search, and the full catalog (the reference tree's `source/packages/agent/tools/mcp/get-mcp-tools.ts:291`; argument shapes at `:272-286`). Patterns are compiled with a linear-time regex engine and capped at 256 characters (`:32,237-245`). Descriptions are sanitized and shortened to 200 characters with a truncation suffix in search and catalog modes, while targeted namespace and single-tool lookups return the complete text (`:28-29,130-139`); the generated description states that shortening rule and tells the model to fetch a tool directly when it needs the full text (`:409,420`). Responses carry a namespace status, and the description tells the model not to treat namespaces in auth-needed, error, or loading states as usable (`:150-162,410`). Oversized payloads above a 12,000-byte threshold are written to a project file and replaced by a short note naming the path and size (`:31,254-265`).

**4. Invocation and its per-call schemas.** A single invocation meta-tool resolves a server identifier plus a tool name into a call, and the argument record is typed as a lenient recursive JSON-value record rather than a per-server schema (the reference tree's `source/packages/agent/tools/mcp/mcp-call-options.ts:69-100`). When dynamic namespacing is on, the identity parameters change shape — a namespace plus tool name replaces server plus tool name — and the call gains a details channel that folds a plain-language description and the approval-related parameters into one optional object; when it is off, the same fields sit at the top level (`:101-135,194-208`). The description parameter asks for one plain-language sentence naming the outcome and where it applies, explicitly without tool names, argument keys, or JSON (`:107`). Malformed payloads are repaired leniently before validation (`:137-192`): a string-valued argument payload is re-parsed, folded details and description fields are lifted back into the envelope, and a missing identity pair is reported as a distinct error rather than a schema failure. Separately, a per-tool agent tool can be built directly from a server's declared input schema, normalized to an object-shaped schema and converted when the schema is tuple-shaped (the reference tree's `source/packages/agent/tools/mcp/mcp.ts:109-117,393-394,428`).

**5. Call ceiling.** One named constant caps total call duration at one hour, with a legacy alias of the same value (the reference tree's `source/packages/mcp-core/config/mcp-tool-call-timeout.ts:1-2`). DD-205 already recorded that neither constant has a consumer anywhere in the tree, so it is intent evidence and is not re-argued here.

**6. Error classification and typed errors.** Failures are classified from JSON-RPC codes — parse, invalid request, and invalid params mapped to invalid arguments, method-not-found mapped to an unexpected environment, and one server-specific code mapped to timeout — plus message-fragment tables for auth, environment, and timeout conditions, with the auth table also matching a bare status-code token (the reference tree's `source/packages/agent/tools/mcp/mcp-error-classification.ts:3-85`). A typed error family carries user-facing guidance: permission denied with a read-only variant, server does not exist, tool does not exist, exec-level tool not found, an error for invoking without having read the tool's definition, and an invalid-arguments reminder telling the model to inspect the schema before retrying (the reference tree's `source/packages/agent/tools/mcp/mcp-result-boundary.ts:17-106`); exec-level result cases are converted into those throws, including a fallback that distinguishes a missing server from a missing tool by the available-tool prefix (`:139-214`).

**7. Rendering, spill, and metrics.** Successful results are rendered from content items, with a text item that already carries an output location rendered as a pointer note rather than its text (the reference tree's `source/packages/agent/tools/mcp/mcp-result-boundary.ts:244-304`). Above a byte threshold the aggregate text is spilled to a project file and the result is rewritten to the pointer; when no project directory or the write itself fails, the fallback is a truncated inline text with an explicit notice recording the total and inline sizes and telling the model not to retry expecting the full output (the reference tree's `source/packages/agent/tools/mcp/mcp-output-spill.ts:30-73,102-109`). Each spill attempt emits an outcome metric (the reference tree's `source/packages/agent/utils/mcp-metrics.ts:153-155`), and each call emits success/failure metrics with duration and a search-then-call signal when the call followed a discovery search (the reference tree's `source/packages/agent/tools/mcp/mcp.ts:512-520`).

**8. Resource primitives, the read-definition gate, and a validator hook.** Resource listing and resource reading are their own executors alongside the tool-call executor (the reference tree's `source/packages/agent-exec/mcp.ts:149,168,187`), their names resolved per model family (the reference tree's `source/packages/agent/utils/mcp-file-system.ts:20-39`) and surfaced in the snapshot's tool-name set (the reference tree's `source/packages/agent/utils/mcp-meta-tool.ts:88-103`). Invocation is gated on the model having read the tool's on-disk definition file when a read-path state handler is present, returning a distinct unread verdict rather than executing (the reference tree's `source/packages/agent/tools/mcp/mcp-execution-guards.ts:40-66`). A post-execution validator hook audits responses through a shared base response validator (the reference tree's `source/packages/hooks/validators/afterMCPExecutionResponse.ts:1-2`).

## What the current build does

No MCP tool exposure or invocation pipeline. The build declares six dispatcher tools and one access tool with static descriptions (`src/core/policy/prompts.ts:27-40`, `src/adapter/dispatcher-tools.ts`, `src/adapter/worker-access-tool.ts:27,250`), validated by a barrier list (`src/worker/tool-barrier.ts:14-39`) that is intersected with the tools actually registered as globals at spawn time (`:52-59`). There is no dynamic registration, no namespacing or collision handling, no schema-to-validator conversion, no per-call timeout, no JSON-RPC error classification, and no output spill. Result text is delivered through the build's own result channel (`src/adapter/worker-access-tool.ts`, `src/core/access-relay.ts`). A case-insensitive search for MCP vocabulary across `src/` and `client/` returns no hits, matching DD-203 and DD-205. Registry governance is DD-157 and is out of scope here.

The one size boundary the build owns is the worker-report clamp: a hard character cut with a marker that records how many characters were kept out of the total and, when a transcript reference is known, appends a pointer to the full transcript (`src/core/report-clamp.ts:48-54,60-74`). That bound is itself a recorded, re-tuned decision — ticket 63 / register A-7, cited in the file's own header, which records that the reference has no equivalent settle-time bound (`:10-16`).

## The deviation

The build has none of this pipeline either, for the same reasons as DD-203's server model and DD-205's transports, and it has the same status as those two files. In the build's architecture tool sourcing belongs to the host: the build is a Cordis plugin that registers its own fixed surface and asks the host which globals exist, so it neither discovers external tools nor converts their schemas nor invokes them. The reference is the entire application and necessarily owns exposure and invocation end to end.

The MCP-bound parts are the registry materialization and its on-disk layout, the reserved-namespace collision rule, per-call schemas derived from a server's declared input schema, the JSON-RPC classification table, the typed error family, the resource executors, and the read-definition gate. None has a place in the build, and none can be built without the server model.

Two parts are not MCP-bound and are worth naming as transferable patterns:

- **Lenient argument repair before validation.** The reference does not fail a malformed argument payload outright. It first tries a direct parse; failing that it reconstructs a single faithful reading of a damaged payload, rejecting any reading that names a key twice and requiring exactly one surviving candidate; failing that it recovers a field envelope leaked into the argument text, accepting it only when the leaked fields are limited to the call-description field (the reference tree's `source/packages/agent/tools/mcp/dynamic-tool-argument-repair.ts:53-94,132-172`). The call-schema layer then normalizes the repair into the envelope, lifting folded details and description fields back to the top (the reference tree's `source/packages/agent/tools/mcp/mcp-call-options.ts:137-192`). No recorded ruling covers this pattern, and the build has no tool-argument boundary of its own to attach it to — its tools receive structured arguments through the host.
- **Output spill.** Above a byte threshold the oversized text goes to a project file and the result becomes a pointer; when the write cannot happen the fallback is a truncation with an explicit notice telling the model not to retry expecting the full output (the reference tree's `source/packages/agent/tools/mcp/mcp-output-spill.ts:30-73,102-109`). The build's clamp already applies the same discipline at the one boundary the build owns: cut, record kept-versus-total, and point at an addressable full copy — the transcript — which is the same "never silently truncate" rule, ruled and re-tuned under ticket 63 / A-7 (`src/core/report-clamp.ts:10-16`). Honest assessment: for worker report bodies the clamp is not a gap; it already delivers what the spill delivers for tool output. The difference is the point where each applies, not the discipline — the reference protects any tool result at the point of invocation, and the build has no such point because it does not own invocation. The spill pattern becomes relevant only if the human rules the pipeline in.

## Verdict: ASK-HUMAN

The scope decision is DD-203's — whether the plugin should own an MCP client at all — and it is cross-linked here rather than re-argued: if the human rules the server model out, this pipeline has nothing to invoke and follows it; if in, the pipeline comes with it, exactly as DD-205 held. No recorded ruling names MCP tool exposure or invocation; the PRD §2 non-goal excluding a rebuild of dsh's tool runtime (`PRD-dsh-multitask-dispatcher.md:34-36`) reads on its face as covering a plugin-side invocation pipeline but is a scope statement rather than an MCP decision, and ADR-0018's exception list does not mention MCP.

Stated explicitly: neither transferable pattern is covered by a recorded ruling. ADR-0018's exception list names neither argument repair nor output spill. The closest recorded material is ticket 63 / register A-7, cited in `src/core/report-clamp.ts:10-16`, and it covers the build's own clamp bound rather than either pattern as such. The verdict is not overstated because of those two patterns: argument repair has no surface in the build to attach to, and output spill's discipline is already practiced at the build's own boundary, so neither supplies an independent reason to incorporate. The reason the verdict is ASK-HUMAN is the MCP-bound pipeline as a whole, the same question DD-203 and DD-205 filed.

## Incorporation notes

- **Where it would live:** nothing is added now. If the human rules in, the shape is a consumer, not a client (DD-203): the plugin would call whatever MCP surface dsh exposes rather than implementing discovery or invocation itself. The discovery and invocation meta-tools would be new dispatcher-surface tools declared alongside the existing six in `src/core/policy/prompts.ts:8-24` and added to the barrier candidate list (`src/worker/tool-barrier.ts:14`) so workers cannot reach them — the barrier is a candidate list intersected with live globals, so a new name is safe to add before the host registers it. The descriptor-session map and the read-definition gate are the parts worth re-deriving regardless of transport, since they are policy rather than plumbing. If the build ever owns a tool-result boundary, the spill belongs next to the clamp in `src/core/report-clamp.ts` rather than in a new module, for the same reason DD-205 keeps timing policy in one place.
- **Constraints:** the build owns no tool sourcing, so a pipeline with no host-provided tool list would be dead code, and any invocation layer the plugin builds duplicates dsh's runtime — the specific thing the PRD §2 non-goal names. Protocol-level details (the JSON-RPC code values, the method and content-item shapes, the schema vocabulary) are protocol artifacts under ADR-0018 B9 and must be taken from the public specification, not from the reference tree; the reference's numeric values (the 200-character description bound, the 12,000-byte payload threshold, the byte threshold on spilled text, the one-hour ceiling) are the reference's numbers for the reference's architecture and must not be copied as values. The read-definition gate is a policy worth re-deriving on its own merits — it makes the model prove it read a definition before invoking — but it assumes the on-disk layout exists. The lenient-repair machinery is deliberately permissive and must never be allowed to widen what a repaired call is authorized to do; repair fixes the shape of an argument payload, not the authority behind it.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L for the MCP-bound pipeline — unreachable before the server model (DD-203) and the transports (DD-205), and it is the half the PRD §2 non-goal probably forbids. Near-zero for the transferable patterns: one has no surface in the build, and the other is already practiced and ruled at the build's own boundary. Risk is high on the pipeline half, which puts a plugin into dsh's tool-runtime territory, and low on the patterns.
