# DD-177 — Storage architecture: per-agent store DB plus blob store vs the build's marker durability
- **Area:** A21 storage
- **Type:** deliberate-divergence
- **Date:** 2026-09-23

## What the reference does
Storage is per-agent and split across two kinds of database. Each agent owns a relational store database on disk — a per-agent SQLite file whose path is derived from that agent's own directory, opened and closed as a unit of work (`the reference tree's source/host/extensions/session/agent-db.ts:3`, `:75`, `:86-91`), sitting on a shared store-database layer (`the reference tree's source/host/storage/store-db.ts`). Beside it is a second, separate database holding conversation payloads as rows keyed by a hex content id, one row per payload (`the reference tree's source/host/agent-isolation/conversation-blob-store.ts:11`); its path is constructed next to the agent's store-database path (`the reference tree's source/host/extensions/session/conversation-blobs-path.ts:8-9`).

The blob key is a content hash. Before a stored payload is treated as trustworthy, the store re-hashes it and requires the digest to equal its own row id (`conversation-blob-store.ts:17`). That is what makes the layer content-addressed rather than merely keyed: identical bytes collapse onto one row, and a stale-root sweep may delete a row only after re-deriving its hash. Payload storage is also *optionally* encrypted — the agent metadata record carries an optional blob-encryption key field, with a generator and a validator for it (`the reference tree's source/packages/agent-kv/agent-store.ts:52`, `:63`, `:69`, `:117`) — so encryption is a per-agent property of that record, not a fixed property of the store.

Payload lifecycle is a first-class concern with its own machinery: a reachability walk from a retained root id, a garbage collector, and a retirement path for a legacy payload database (`the reference tree's source/host/agent-isolation/conversation-blob-gc.ts`, `conversation-blob-db.ts`, `legacy-blob-retirement.ts`), plus a second payload store scoped to workers (`the reference tree's source/host/agent-isolation/worker-blob-store.ts`).

## What the current build does
The build has neither database. Its persistence is one narrow layer under ADR-0006: `src/core/durability.ts` declares a single durable record shape (`DurableWorkerMarker`, `:9-28`) and a single port (`DurabilityPort`, `:36-45`). The doc comment states the record is written at spawn through the host's session/storage facility and is "never a second transcript DB" (`:6`), and that core "must not invent its own transcript database" (`:34`).

The record lands in the dispatcher's own namespace marker inside the host's storage domain: `src/adapter/durable-marker.ts:27` names the marker domain and `:28` its one table, and the adapter opens that domain lazily through the host's storage-domain interface, keyed by worker id (`:98-112`). There is no per-agent database file, no content-addressed payload store, and no payload layer at all.

What survives a restart is the marker, not a session. `src/core/multitask.ts` imports the durability record and port (`:49-54`) and rebuilds the roster from those markers rather than reopening a store; a worker that was live at crash time is reported as `unknownState` and is never resumed or replayed (the rebuild path and that never-replay stance are what DD-167 records in full).

## The deviation
The reference's storage architecture is the foundation for several other reference features: a content-search index over agent content (`the reference tree's source/host/extensions/content-search/search-index-db.ts`, `search-index-service.ts`, `search-index-writer.ts`, `search-index-worker.ts`); a transcript mirror offloaded to worker-side storage (`the reference tree's source/host/agent-isolation/transcript-mirror-offload.ts`, `transcript-mirror-worker.ts`); and store-database capture and upload for box sync (`the reference tree's source/host/extensions/box-store-sync/store-db-capture.ts`, `store-db-bundle-capture.ts`, `store-db-snapshot-upload.ts`, `sqlite-snapshot.ts`).

The build substitutes a record of outstanding work only. Durability is scoped to exactly what a post-restart roster rebuild reads — worker id, transcript pointer, todo link, status, delivery-redrive budget — and nothing is stored that the rebuild does not consume. The reference stores state so it can be reopened, searched, mirrored, and shipped; the build stores state so that one specific question stays answerable: what was outstanding when the process died.

**This file holds the storage decision that the A21 records depend on.** The search index, the transcript mirror, and store-database sync are not three independent omissions: each depends on a storage layer the build does not have. They all receive the same verdict because they all follow from this decision, and none of them can accurately be assessed as a standalone feature gap. The per-agent *session* half of the same storage layer is treated separately in DD-167; this file covers the storage architecture as a whole and the features derived from the blob store.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 exception **A5** is decisive and explicit: "Persistence stays in dsh's session/job store; no second database" (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:25`). (That is the persistence A5 — distinct from the deviations register's colliding "A-5" row, per the 2026-09-19 identifier note in `docs/adr/README.md:73-78`.) A5 is accepted and human-ruled, so both halves of the reference storage are excluded from imitation by name — the per-agent store database, and the payload database beside it, since a separate payload database is a second database whatever it holds. ADR-0006 then names the architecture the build does use: a durable minimum-to-reconstruct record written through dsh's session/job store "rather than a new store", and it says in terms that this "is a deliberate divergence from the reference, not an imitation" (`docs/adr/0006-worker-record-durability-split.md:5`, `:27-29`). No part of this deviation is unruled, so nothing here is the human's to decide; adopting the reference's storage architecture would require reversing A5 first, which is a separate decision and not a fidelity fix.

## Incorporation notes
- **Where it would live:** Reversing A5 would centre on `src/core/durability.ts` (a real store behind `DurabilityPort` instead of a marker port) and `src/adapter/durable-marker.ts` (the marker domain at `:27-28` replaced by an opened per-agent store), with `src/core/multitask.ts` rebuilding from a reopened store rather than from markers. The content-addressed payload layer would be entirely new surface with no current home. None of this should be started under the current rulings.
- **Constraints:** ADR-0018 A5 forbids a second database outright, and that reaches the payload store as much as the store database. ADR-0006 requires durable worker state to ride dsh's session/job store (`ctx.sessions` / `ctx.storage`) and forbids inventing a second transcript DB. ADR-0012 governs restart: durability is replayed, work never is. Any proposal to adopt that storage layer must clear all three before touching code.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L + high — this is not a bounded feature but the replacement of the persistence mechanism that two accepted ADRs pin, and the risk lands on the accuracy of the post-restart roster rather than on any single call site.
- **Key reference anchors:** `the reference tree's source/host/extensions/session/agent-db.ts` (per-agent database open `:3`, `:75`, `:86-91`); `the reference tree's source/host/storage/store-db.ts`; `the reference tree's source/host/agent-isolation/conversation-blob-store.ts` (rows keyed by hex id `:11`; content-hash re-derivation `:17`) with its `conversation-blob-db.ts` / `conversation-blob-gc.ts` / `legacy-blob-retirement.ts` / `worker-blob-store.ts` companions; `the reference tree's source/host/extensions/session/conversation-blobs-path.ts:8-9`; `the reference tree's source/packages/agent-kv/agent-store.ts` (optional payload-encryption key `:52`, generator `:63`, validator `:69`, default minted `:117`).
