# DD-200 — Link metadata (unfurl) pipeline with cache and SSRF hardening
- **Area:** A25 attachments & media
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference ships a complete link-metadata (unfurl) pipeline behind a single entry point that takes a raw URL, normalizes it, serves a hit from an on-disk cache, and otherwise fetches and scrapes the page.

- **Cache.** Cache files live in a per-agent cache directory, keyed by a hash of the normalized URL. Each entry carries a schema version stamp and a fetch timestamp; a read is re-validated against both the current version and a 24-hour TTL, and a stale or version-mismatched entry is treated as a miss rather than trusted.
- **Safe outbound fetch.** The fetcher uses HTTPS only and is hardened against server-side request forgery (SSRF, where an attacker makes the server fetch internal addresses). It rejects URLs carrying credentials, URLs on a custom port, over-long URLs, non-public hostnames (bare labels, a blocked-label set, and a non-public suffix list covering loopback-, local-, internal-, cluster-, service-, onion- and address-space-style suffixes), and private/loopback/link-local/multicast/reserved destinations via a static CIDR blocklist spanning both address families. Hostnames are resolved under a 3-second DNS deadline and the chosen address is pinned into the connection (with the original host preserved in the request's host header and TLS server name); the request itself runs under an 8-second deadline, follows at most 5 redirects, and re-applies the full URL policy to every hop. Bodies are capped at 512 KB for HTML and 2 MB for images, with the byte limit enforced both from the declared length and incrementally as chunks arrive.
- **Scrape and resolve.** It scrapes OpenGraph, Twitter-card, title, canonical-link and favicon declarations, cleans and truncates the extracted text fields to per-field character limits, and converts the main preview image and favicon to data URLs, with a third-party favicon service as fallback when no declaration is present. Redirect chains that land on a login/identity destination (matched by host labels, path segments, and one known nested path shape that suggest authentication) abort the preview entirely.
- **Consumers.** Downstream, the Electron main-process attachment service re-encodes the main image to JPEG and the favicon to PNG at bounded maximum dimensions before returning them; the preload bridge exposes the call and a shared RPC method table declares it; and the renderer consumes it in a transcript URL card and a command-palette link provider.

## What the current build does
ABSENT. `src/adapter/content-blocks.ts` recognizes only text blocks (`src/adapter/content-blocks.ts:7,14,16`) and treats every other block kind as opaque, so a URL inside a message stays plain text all the way through the text-concatenation path (`src/adapter/content-blocks.ts:34`). There is no URL cache, no outbound fetch of message content, no SSRF policy, no metadata scraper, and no preview-image handling of any kind. A grep across `src/` and `client/` for unfurl / OpenGraph / link-metadata / link-preview vocabulary returns no implementation hits — only unrelated JSDoc cross-references.

## The deviation
The pipeline is best understood as two separable halves, and they sit on opposite sides of this project's authority stack.

- **(a) The display affordance** — a URL card or preview rendered in the chat surface. This is squarely rich-chat ergonomics: ADR-0018 exception **U-B** (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:35`) excludes exactly "rich attachment viewers, or URL cards". The card, its favicon/image presentation, and the renderer-side consumers are therefore deliberately out of scope for this build, by recorded ruling.
- **(b) The security rules** — the safe outbound fetch policy: HTTPS only, credential and custom-port rejection, non-public hostname and private/loopback/link-local/multicast CIDR rejection, DNS resolution with a deadline plus address pinning, a redirect cap with per-hop re-validation, request deadlines, and response byte caps. None of this is a display concern. It is a genuinely transferable hardening pattern for any code path that fetches a user-supplied URL, and **no recorded ruling in the authority stack covers it** — it is not named in ADR-0018's exception list, not in the PRD, and not in any ADR reviewed for this file.

So the deviation is not "the reference has a feature we lack". It is: the reference's *presentation* half is an explicitly excluded ergonomic, while its *fetch-safety* half is an unruled hardening pattern that nothing currently uses. The build has no consumer for (b) today because it never fetches a user-supplied URL at all — nothing in `src/` or `client/` performs outbound content fetching. The pattern only becomes actionable if such a fetch is ever introduced.

Adjacent attachment-transport work already filed elsewhere is not this deviation: upload lifecycle is DD-198 and chunked reads/downloads are DD-199; neither covers URL unfurling or outbound fetch policy.

## Verdict: DO-NOT-INCORPORATE
The pipeline as a whole is dominated by its display half, and ADR-0018 exception U-B (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:35`) explicitly excludes URL cards from the requirement to imitate the reference in its entirety, so the unfurl feature and its renderer consumers are out of scope by recorded ruling. The security half — the safe-fetch policy — is *not* covered by any recorded ruling; it is neither granted nor refused, and this file must not pretend otherwise. Because that half has no consumer in a build that never fetches user-supplied URLs, there is nothing to incorporate today and no basis to expand scope on a speculative future need. The correct disposition is to refuse the pipeline, record the split, and let the SSRF rules be revisited as a fresh decision only if and when the build acquires an outbound-fetch path.

## Incorporation notes
- **Where it would live:** Nothing now. If the build ever gains an outbound-fetch path for user-supplied URLs, the fetch-safety policy would belong beside that fetch site in `src/core/` (policy/pure logic: URL normalization, hostname and CIDR rejection, redirect accounting, byte-cap predicates) with any I/O wiring in `src/adapter/`, so the policy stays testable without network access. The display half would have no place to live — U-B excludes it.
- **Constraints:** Re-derive the policy independently from the *class* of controls, not from the reference's tables: an HTTPS-only scheme gate, credential/port rejection, a non-public hostname suffix policy, an address-family-aware non-public CIDR blocklist, resolution with a deadline and connection pinning to the resolved address, a redirect cap with full re-validation of each hop, and declared-plus-incremental byte caps. The build's own conventions apply (TypeScript core per ADR-0001, offline tests driven from `package.json`) and would govern shape and testability. Note that the reference's CIDR and suffix tables are *its* chosen coverage, not a standard — an independent derivation must justify its own ranges. Do not carry over the favicon-service fallback: it introduces a third-party request for a display concern the build does not have.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S if ever triggered, and zero today. The policy itself is a small, self-contained, unit-testable predicate set; the risk is the inverse of the effort — a partially-implemented SSRF policy (scheme check without address blocking, or a redirect cap without per-hop re-validation) is worse than no fetcher, because it looks safe while permitting exactly the classes it claims to stop.
