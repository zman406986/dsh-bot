# DD-057 — Composer focus management & paste-refocus vs none
- **Area:** composer editor (A6)
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference composer is an actively managed focus surface. The rich-text editor publishes a controls object to its parent with explicit methods for moving focus to the caret-at-end position, blurring, clearing, restoring prior content, and inserting text with smart spacing, plus a JSON getter; the parent receives it through a callback and owns the lifetime (null on unmount). Whenever content is set or replaced from outside — including an accepted-send clear and a scope switch — the editor programmatically refocuses with the caret at the end, guarded by a check that stops an external write from bringing back a draft that was already cleared. Separately, the window chrome registers a global focus-prompt shortcut bound to a pair of mod-key bindings, and the editor installs a document-level clipboard bridge: a mod+V pressed while focus sits outside any editable field first pulls focus into the composer, and a paste event that lands outside any editable field is intercepted and routed into the editor (text inserted at the caret, files staged as attachments) instead of being lost to the page.

## What the current build does
Nothing comparable exists. A grep of `src/client` for autofocus, programmatic focus calls, prompt-focus hotkeys, or a paste-refocus listener comes back empty. The build's composer draft is written through the host input API (`setDraft` on the conversation input resolver), and the steer-prefill implementation documents this boundary explicitly: focus is not part of that API because it is package-internal to the composer, so a roster-row prefill puts text in the draft but leaves the keyboard focus wherever it was, pairing the result with a locale hint instead of moving focus.

## The deviation
The reference treats composer focus as a first-class behavior (controls API, focus-on-external-change, global focus hotkeys, paste-refocus); the build has no focus behavior at all, and its one draft-writing path deliberately stops at the text boundary.

## Verdict: ADAPT
The underlying behaviors are worth having — focus-to-end on external content changes and the paste-refocus bridge fix real, common interactions (prefill, restore, paste from anywhere), and the web client would feel broken without some of them. But the recorded choice in `src/client/actions.ts` (tickets 36/40) that focus is not part of the `setDraft` API is a settled ruling in the repo's ruling order (the ordered list of ruling documents in `docs/agents-rulebook.md`; this one sits at the recorded-ticket-ruling level, human-reversible): incorporation must keep that API text-only and put any focus control inside the composer component itself, behind a composer-owned channel, not bolt focus onto the input resolver. The global mod+i/mod+l hotkey is a window-chrome decision the build has no registry for, so it needs its own ruling rather than silent adoption. Re-derive all of it independently per ADR-0018 B9 — the reference's guards and focus ordering inform the design but the code must be the build's own.

## Incorporation notes
- **Where it would live:** the build's composer component under `src/client` (the surface that owns the draft input element): a small controls object (focus/blur/clear/restore/insertText) exposed to its parent, an effect that refocuses caret-at-end when external content is set or cleared, and a document-level keydown/paste pair that routes out-of-focus clipboard traffic into the composer. A focus hotkey, if wanted, belongs in whatever window-chrome/shortcut layer the build grows, not in the composer.
- **Constraints:** ADR-0018 B9 — independent re-derivation, no verbatim copying; the recorded ticket 36/40 ruling keeps `setDraft` focus-free, so the `setDraft` signature must not grow a focus parameter; if a paste bridge is added it must yield to any editable target (input, textarea, contentEditable) so it never steals focus from another field; hotkey choice should not blindly mirror mod+i/mod+l (check build conventions and browser conflicts).
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the focus-on-external-change and paste-bridge behaviors are each small, but doing them without breaking the composer's ownership boundary (and deciding the hotkey question) is a design pass, not a copy-paste job.
- **Key reference anchors:** the reference tree's `frontend/src/recovered/features/conversation/workspace/rich-text-editor.tsx:75-82` (controls interface), `:832-850` (focus-to-end on external set/clear), `:852-871` (controls handed to parent), `:704-830` (document-level mod+V/paste refocus bridge); the reference tree's `frontend/src/recovered/features/window-chrome/global-keyboard-shortcuts.ts:51` (the two mod-key bindings carrying a focus-prompt label); the reference tree's `frontend/src/recovered/features/window-chrome/root-shell-state.tsx:50` (i/l mapped to focus-prompt).
