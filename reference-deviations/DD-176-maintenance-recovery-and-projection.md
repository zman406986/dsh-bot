# DD-176 — Session maintenance, database recovery, summaries, and roster projection
- **Area:** A20 session & durability
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference carries four related modules whose shared job is keeping a per-agent, SQLite-backed persistent session store healthy and readable.

**Session maintenance** (`the reference tree's source/host/extensions/session/session-maintenance.ts`). A versioned one-shot maintenance surface. Three repair passes are each guarded by a stored version stamp so they run at most once per store — legacy conversation-blob retirement, stale checkpoint-root cleanup, and hidden transcript-entry repair (`:10-12`, `:57-73`) — alongside a transcript backfill that appends only the tail the persisted entries are missing (`:52-56`) and a conversation-recovery entry for a store whose root pointer is absent (`:62-66`). A small sequential runner isolates a failing task and reports it by index rather than aborting the batch (`:76`). The host interfaces it declares (`:18-46`) show every one of these functions operating on a per-agent store handle plus a conversation store.

**Agent-database recovery** (`the reference tree's source/host/extensions/session/agent-db-recovery.ts`). The open path configures the database (busy timeout, write-ahead logging), retries once on an I/O error, and verifies integrity with a quick check before handing the handle out (`:24-100`). On corruption it quarantines the file — rename, falling back to copy-then-delete — through the SQLite-recovery helpers in `the reference tree's source/host/storage/sqlite-recovery.ts`, rebuilds a fresh database, and salvages what it can from the quarantined copy: key/value rows, blobs, and transcript entries (`:124-151`). The outcome is classified as recovered or reset, reported with counts, and followed by a re-index mutation so downstream consumers know the store was rebuilt (`:152-183`). A typed integrity error and a reject-if-corrupt option exist for callers that would rather fail than recover (`:22`, `:61-62`).

**Session summaries** (`the reference tree's source/host/extensions/session/session-summaries.ts`). Reads a per-agent store's extras — creation and update stamps, last entry, last message preview, newest entry id, unread state, an awaiting-user-response flag, origin, purpose, conversation partners, legacy avatar path (`:8`) — and joins them with the on-disk profile and settings files to build one agent summary row: name, description, title, avatar, unread counts, notification flags, and a hidden-from-sidebar flag (`:13`, `:16`). A minimal fallback row exists for a store that cannot be read at all, and two predicates decide whether a blank agent still deserves a row: a quarantined-store check and a durable-footprint check that counts memory, automations, and workflows (`:14-15`).

**Roster projection** (`the reference tree's source/host/extensions/session/session-roster.ts`, `the reference tree's source/host/extensions/transcript/roster-projection.ts`). The roster is derived, not stored: the listing scans the per-agent directories, summarizes each store, recovers an agent whose database file is missing, and degrades to a minimal row when summary building fails (`session-roster.ts:7-8`). The projection class layered over the transcript manager adds outline-stream coalescing, agent and media search, profile watching, agent-list snapshots, and per-agent update emission (`roster-projection.ts:25-56`, `:124-214`), while the emit side caches the summaries and writes a replica keyed for clients (`the reference tree's source/host/extensions/transcript/roster-emit.ts:1-20`).

All four exist to serve that store. The recovery module imports the database driver directly (`agent-db-recovery.ts:1`); maintenance's interfaces are store-handle shaped (`session-maintenance.ts:18-34`); summaries read the store's own accessors (`session-summaries.ts:9`); the roster host interface takes a database path per agent (`session-roster.ts:6`).

## What the current build does
The build has no database of any kind. There is no SQLite import or dependency anywhere under `src/`, under `client/`, or in `package.json` — a case-insensitive search for the driver name across those trees returns nothing.

Durability is instead a deliberately minimal marker layer. `src/core/durability.ts` defines a durable worker marker carrying only what a post-restart roster rebuild needs (worker id, parent session, stream key, title, status, transcript pointer, todo link, delivery-redrive budget) and a write/read/delete port for it (`:9-28`, `:36-45`); its header states the marker is never a second transcript DB and that core must not invent its own transcript database (`:6`, `:34`). The host-backed binding is `src/adapter/durable-marker.ts`, writing through dsh's own session/storage facility. Restart is handled by the restart-notice module at `src/adapter/restart-notice.ts`: one conversational notice stating unknown-state workers as unknown and restored terminal rows plainly, with an unreadable marker store degrading to a single "nothing was restored and nothing was replayed" line (`RESTART_DEGRADED_NOTICE`, `:33`) while activation still succeeds.

For the roster, the build has a live snapshot rather than a projection of stored sessions. `src/core/roster-snapshot.ts` shapes the snapshot, and `src/plugin.ts` builds it from the core's in-memory roster — the comment there is explicit that this is a pure projection of the core roster and never a second source of truth (`:342-343`), gated to the activated dispatcher session and built from `listWorkers`, pending access asks, todos, and the adapter's own recent-result observation (`:355-363`). Transport is the plugin's own settings namespace: `src/adapter/roster-channel.ts` publishes the snapshot through the owner scope that settings registration returns (`:7-14`), with a per-session mirror key family `roster.<sessionId>` (`:73-84`) and a `null` write on deactivation (`:32-35`); the namespace itself is claimed in `src/adapter/settings-section.ts` (`SETTINGS_NAMESPACE`, `:49-50`).

The build has no session summaries, no maintenance or migration passes over stored state, and no corruption handling — there is no file to corrupt.

## The deviation
These four modules are one group of maintenance machinery around a persistent per-agent store, and the build has no such store. That removes what each piece would act on.

Database recovery has nothing to act on: with no database file there is no integrity check, no quarantine, no salvage, no reset classification. The maintenance passes have nothing to act on either — legacy blob retirement, checkpoint-root cleanup, hidden-entry repair, and transcript backfill are all repairs to state that exists only inside that second database and its blob companion, so the stored data they act on is absent, not just their implementation. Session summaries have no stored per-agent data to summarize; the fields they compose (created/updated stamps, last-message preview, unread state, awaiting-response flag, hidden-from-sidebar flag) are exactly the fields a durable per-agent record would carry, and the build keeps no such record.

The roster projection is the piece most easily reused in principle, and the build already has a roster mirror — but for a different purpose, and the two must not be equated. The build's mirror carries a snapshot of live in-memory core state into the plugin's settings document so the browser side can render presence; it is a transport for state that exists only while the session lives, and the comment on the publish path says so (`src/plugin.ts:342-343`). The reference's projection derives roster rows out of durable per-agent stores, and adds derived-view machinery the build has no counterpart for — search over agents and media, profile watching, snapshot and per-agent update emission, subagent and async-task unions (`roster-projection.ts:124-214`). The underlying storage differs (live in-memory state versus stored session state) and the roles differ (client transport versus derived view), so the build's mirror is not a projection and should not be read as one.

## Verdict: DO-NOT-INCORPORATE
A recorded ruling covers this, and it covers it from two directions. ADR-0018 exception A5 is explicit and human-ruled: persistence stays in dsh's session/job store, no second database (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:25`). The database-recovery module and every maintenance pass in the group exist to service that forbidden database, so A5 removes what they would act on rather than merely discouraging them; ADR-0006 independently names the storage architecture the build does use and says in terms that this is a deliberate divergence, not an imitation (`docs/adr/0006-worker-record-durability-split.md:5`, `:28`). ADR-0012 then governs what survives a restart — durability is replayed, work never is — and the build's degraded notice is the ruled answer where the reference would recover and re-index.

The summaries-and-roster half is covered separately by exception C13, which forbids an agent-identity roster: no saved/hidden/pinned identities, avatars, per-agent persistent chats, or agent info panes as identity surfaces (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:28`). The reference's summary rows are precisely that payload — display name, description, title, avatar, unread badge, hidden-from-sidebar and notification flags — so a stored-session-derived roster view would land inside C13 by construction.

One sub-piece deserves to be named rather than buried: a session-summary-style derived view could in principle have an independent life, since "summarize what a session contains" is a capability and not a storage format. Here it does not survive on its own. Its role in this build is already filled by the live roster snapshot, and any version derived from stored sessions would require the second database A5 forbids and would produce the identity rows C13 forbids. Nothing in this deviation is unruled, so there is nothing for the human to decide; adopting any of it would mean reversing A5 and C13 first, which is a separate decision and not a fidelity fix. This sits alongside the already-recorded nearby deviations on the same storage question (DD-167 on the per-agent durable store, DD-173 on restart handling).

## Incorporation notes
- **Where it would live:** Nothing to add. If A5 were ever reversed, the touch points would be `src/core/durability.ts` (whose marker port would be replaced by a real per-agent store), `src/adapter/durable-marker.ts` (the binding), `src/core/roster-snapshot.ts` and the publish path at `src/plugin.ts:342-363` (which would become a projection over stored sessions), and `src/adapter/roster-channel.ts` (whose settings-scope mirror would become redundant). `src/adapter/restart-notice.ts` is where the build's answer to the recovery question currently lives.
- **Constraints:** ADR-0018 A5 forbids a second database outright, which removes the storage that recovery and maintenance would act on. ADR-0006 requires the durable marker to ride dsh's session/job store and forbids a second transcript DB. ADR-0012 fixes restart as durability replay and never work replay, so a recovery path that re-indexes or resumes would have to clear that too. ADR-0018 C13 forbids the identity-roster surface that summary rows and the roster projection together constitute.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L + the work is not the feature but the reversal: adopting these four modules means superseding A5 (and C13 for the roster half), which changes the build's whole durability posture rather than adding a module.
- **Key reference anchors:** the maintenance module (`the reference tree's source/host/extensions/session/session-maintenance.ts` — versioned passes `:10-12`, `:57-73`; backfill `:52-56`; root-missing recovery `:62-66`; task runner `:76`); the database-recovery module (`the reference tree's source/host/extensions/session/agent-db-recovery.ts` — open and integrity verify `:24-100`; quarantine `:101-120`; salvage `:124-151`; recover-or-reset `:152-183`) with its helpers in `the reference tree's source/host/storage/sqlite-recovery.ts`; the summaries module (`the reference tree's source/host/extensions/session/session-summaries.ts:8-16`); the roster listing (`the reference tree's source/host/extensions/session/session-roster.ts:6-8`) and the projection class (`the reference tree's source/host/extensions/transcript/roster-projection.ts:25-56`, `:124-214`) with its emit side (`the reference tree's source/host/extensions/transcript/roster-emit.ts:1-20`); the supporting conversation-recovery module (`the reference tree's source/host/extensions/session/conversation-recovery.ts:1-20`).
