# DD-153 — Multitask-mode user reminder vs the build's ledger reminder
- **Area:** A18 prompt sections
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference's multitask reminder module injects a user-position reminder block carrying the rules of a single mode, and it does so through three distinct lifecycle variants rather than as one unconditional text:

1. **Enter variant.** Announces that the mode is now on and stays on until the user explicitly leaves it; changes the identity from coding agent to coordinator that pushes meaningful work out through a named tool that can run work in the background; prioritizes finishing the user's request accurately with background help. It demands the response end immediately once delegation happens and forbids waiting or sleeping on a running worker. It warns against routinely splitting small or medium tasks into many sibling agents, and it exposes a scoping rule the user is deliberately not told about. It then lays out delegation criteria — an explicit when-to-delegate list, a when-to-use-multiple-siblings list, and a when-not-to-delegate list — followed by worked delegation examples keyed to request types (bug loop, minor improvement, large feature, plan/review/research), plus an exception for trivial requests needing no tool call or one tool call. Two optional branches ride along: an aggressive variant chosen by model that replaces the more-than-one-tool-call bar with an any-tool-call bar and drops the exception and the when-not list, and a persistence override that cancels turn-ending instructions inherited from other prompt material.
2. **Still-in-mode variant.** The recurring reminder on later turns: restates that the mode is still active, defaults to delegating to a single subagent, keeps foreground work near-zero-tool, forbids duplicating already-delegated work, and forbids restating a single worker's summary unless the user asks, a blocker needs parent action, or several workers need synthesis.
3. **Exit variant.** Declares the mode left and restores ordinary behavior, explicitly cancelling the aggressive strategy.

All three are wrapped in the same user-position reminder element by the module's exported renderers. The caller selects the variant, driven by the mode's enter/still/exit state.

## What the current build does
The build has one reminder, and it is unconditional. `assembleTurnReminder` in `src/core/policy/assembler.ts` composes exactly two sections: a dynamic ledger section built from the session's live todo items (id, status, title, and — for closed items other than delivered ones — a note saying why it closed) and a fixed standing-rules block from `buildStandingRulesBlock` in `src/core/policy/prompts.ts`. `REMINDER_SECTION_HEADINGS` pins the two headings. An empty ledger still injects the rules, with the ledger line collapsing to an empty marker.

There is no lifecycle. The reminder is emitted on user turns and on wake turns whenever the session is active, from three call sites: `src/plugin.ts:218` (wake composition, prepended to the wake body), `src/adapter/parent-agent.ts:264` (user turn), and `src/core/tools.ts:733`. Nothing distinguishes "just entered" from "still running" from "exited"; there is no exit state to announce and no mode on/off transition, because the dispatcher is always-on by construction rather than a mode the user toggles.

The build's reminder is the only place live session state reaches the prompt. The standing rules are static and cover the working discipline in six lines: keep the turn short and never wait on workers; spawn for non-trivial multi-step work and parallelize independent work; steer rather than clone on correction; record a todo before spawning and only mark completion once the user has the result; reconcile the ledger on every wake before speaking; and deliver worker results yourself without naming the machinery.

## The deviation
Both sides occupy the same functional slot — a recurring user-position reminder that governs delegation discipline — but different purposes shaped them. The reference's reminder is delegation *teaching* organized around a mode lifecycle: it teaches when and how much to delegate, supplies worked examples, carries model-specific and persistence variants, and exists in enter/still/exit editions because the mode itself starts and stops. The build's reminder is a *bookkeeping obligation*: it carries live session state (the ledger) and a fixed set of operating rules, and it is unconditional because the dispatcher never switches off. Neither the enter/exit distinction, the scoping rule withheld from the user, nor the aggressive model-specific variant exists on the build side in any form.

The two do share real ground, which is the part that matters for a verdict: do not block on workers, do not duplicate delegated work, do not expose the machinery, and treat silence as a valid outcome are already present in the build's standing rules and wake instructions. The build's wake-turn reminder is also richer than the reference's equivalents, since it carries settled-worker reports, transcript references, and access outcomes that the reference's short still-in-mode reminder does not.

## Verdict: ASK-HUMAN
The delegation-discipline core — don't block, don't duplicate, hide the machinery — is already PRD-required behavior in the build and is already expressed in the standing rules, so the teaching half needs no import; it is satisfied structurally. What is genuinely absent is the lifecycle apparatus: explicit enter/exit variants, mode scoping, and the aggressive model-specific branch. That apparatus only makes sense under a mode the user can toggle, and the build's dispatcher is always-on (ADR-0009's activation model, as amended by ADR-0018, treats the dispatcher as the shipped state rather than a mode to enter), so importing the transition machinery would add prompt contract surface with nothing to transition between. ADR-0021/0022 establish a single additive hook, which makes any added prompt section a bounded change if the human later wants one — but no recorded ruling decides this particular deviation, so the lifecycle half is not ruled in, and I have not picked it up. ADAPT: carry over the delegation-discipline wording where the build is thinner, and leave the mode-lifecycle apparatus out until the human rules it in.
