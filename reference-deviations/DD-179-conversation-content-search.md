# DD-179 — Conversation content search (full-text index over stored conversations)
- **Area:** A21 storage
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

The reference ships a host-level extension, gated behind a feature flag, that maintains a **local full-text index over stored conversations and attachment file names**, and exposes searching that index to the agent through the roster surface it already has for other agent-facing lookups.

- **The index is a separate derived database.** A dedicated index file sits under the product's root storage directory, opened in WAL mode with an incremental-vacuum policy, its schema version stamped in the database header, and a one-row metadata flag recording that a full reconcile has completed (`search-index-db.ts:4-30`).
- **Full-text tables are external-content tables over base tables**, kept in sync by insert/delete/update triggers rather than by the application writing both sides; messages and media names each get their own pair. Tokenization is unicode-aware with diacritic folding, and short prefixes are indexed so prefix queries stay cheap (`search-index-db.ts:11-24`).
- **Query construction is defensive**: input is unicode-normalized, term count is capped, each term is quoted and given a trailing prefix wildcard, and an empty or over-normalized query returns nothing rather than falling through to a match-everything path (`search-index-db.ts:6, 31`).
- **Results are ranked per agent, not globally.** A per-agent cap on matches is applied before the global limit, so one chatty agent cannot monopolize the result set; each hit carries a context-window snippet around the match, and the message timestamp falls back to the agent's newest entry when the entry itself has none (`search-index-db.ts:7, 35-67`). Attachment search mirrors this, and with an empty query it degrades to a recency listing (`search-index-db.ts:69`).
- **Index maintenance runs off the main thread.** A worker thread owns the index connection and processes a small job vocabulary: upsert a batch of entries for one agent, delete one entry, clear one agent, reindex a list of agents, and a global reconcile. Failures are returned to the caller as structured results, with SQLite corruption detected and flagged rather than thrown (`search-index-worker.ts:8-15`; `search-index-writer.ts:12`).
- **Freshness is tracked by a per-agent content fingerprint** — entry count plus the highest sequence number — stored next to the index. Reconcile walks the agents present on disk, compares fingerprints, reindexes the ones that drifted, and clears index rows for agents that no longer exist (`search-index-writer.ts:30, 33, 37-38`). The writer reads each agent's own conversation store **read-only** as its source of truth (`search-index-writer.ts:9, 27, 29`).
- **The service is lifecycle-managed**: it subscribes to transcript-mutation events and starts or stops indexing as the feature gate flips, reports index health through telemetry, and disposes under a bounded deadline (`extension.ts:12, 24-51`).
- **The agent-facing path has a fallback.** A roster-search class answers conversation and attachment queries from the index when it is ready, and otherwise falls back to a linear scan of transcript entries, so the capability degrades instead of disappearing. It filters out the live agent's own transcript from the indexed path (handled separately, since it is not yet on disk), skips outbound messages addressed to peers, and caps matches per agent at 5 with 50 results overall (`transcript/roster-search.ts:15-60, 93-106`; `agent-content-search.ts:1-8`).

## What the current build does

**Absent.** There is no search index and no search tool anywhere in the build. A grep for the term across `src/` returns exactly one hit, and it is unrelated: `src/worker/prompt.ts:73` names search as one of the worker's generic work-tool categories ("Use the available work tools (shell, files, search, web) as needed") — that is file/web search available to a worker, not search over conversations. The build's own durable corpus is not a searchable body either:

- The only durable artifact is the **minimum-to-reconstruct worker marker** (`src/core/durability.ts:4-45`): worker id, parent session, stream key, title, status snapshot, transcript pointer, todo link, and a redrive counter. Its doc comment states the constraint directly — it is written through the host's session/storage facility and is "never a second transcript DB," and "Core must not invent its own transcript database." The worker report itself stays in the host's transcript.
- `src/core/multitask.ts` holds the worker registry and the dispatcher-private todo ledger (`src/core/multitask.ts:258-259`). The ledger is deliberately dispatcher-only and is never sent into a worker (`src/core/multitask.ts:136-137, 508`); it is not a corpus anything would search.

## The deviation

The reference has a whole storage-adjacent capability the build lacks: a derived full-text index over conversation content and attachment names, maintained by a background service with fingerprint-based reconciliation and a fallback scan, and reachable by the agent as a lookup surface.

The deviation is not merely "one feature is missing." Search over conversations **presupposes a durable per-agent conversation store** — that is what the reference's writer reads as its source of truth (`search-index-writer.ts:27-30`), and it is the subject of DD-177 (storage architecture) and DD-167 (per-agent durable session store). The build rejects that storage layer by ruling: ADR-0018 exception **A5** keeps persistence in dsh's session/job store with no second database, and ADR-0006 repeats it at the record level ("No second transcript DB ... worker transcripts remain dsh's own"). The index is **built from stored conversations the build does not own**, and the transcript itself lives in the host. So both the capability and its input are absent, for the same reason.

## Verdict: DO-NOT-INCORPORATE

**A recorded ruling covers this, so the verdict does not rest on inference alone.** ADR-0018's exception list — which is by its own terms exhaustive and authoritative over anything not on it — names this capability explicitly at **U-H**: "no local content-search index." That exception sits directly on top of **A5** (persistence stays in dsh's session/job store; no second database), and ADR-0006 independently restates the same rule for records ("No second transcript DB"), while stating that the transcript is dsh's, not ours. Because the reference's index is a derived read-only projection over per-agent conversation stores that the build does not have and will not create, there is nothing to index and no host-provided equivalent to project from. Under the authority stack, imitating this would require reversing U-H and A5 first, which is a human decision and not one this deviation can carry.

One caveat, stated as a **separate possibility rather than folded into this verdict**: a search surface over the build's *own* ledger — worker titles, statuses, and delivered reports — is a different capability, and U-H's wording ("content-search index" over conversations) does not obviously reach it. It is not covered by this ruling, and it should be assessed on its own if anyone wants it. It looks weak on inspection: the marker is deleted once its obligation closes (`src/core/durability.ts:34-44`), report bodies are clamped by D21, and the ledger is dispatcher-private by design — so the corpus would be small, short-lived, and deliberately unshared. That assessment is a judgment, not a ruling; treat it as an open question for the human, not as settled here.

If the human ever reversed U-H and A5, the only coherent home would be adapter-side (`src/adapter/`) over a host-provided storage port, mirroring how the durability port is defined in core and implemented by the dsh adapter.
