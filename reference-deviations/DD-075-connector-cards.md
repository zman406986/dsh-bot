# DD-075 — Connector install/authorize cards vs none
- **Area:** message cards (A10)
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference renders dedicated transcript cards for connector suggestions, in two grouped variants. A singular card (the reference's connector view, for the singular connector message kind) shows the connector's display icon, display name (catalog name, else server name, else raw id), a team badge when the server is team-managed, a description (message reason, else catalog description), and a tool count rendered as a singular/plural phrase. Its action area is a small state machine: connected shows an added-status chip with a check icon; a team-policy-disabled server shows no button at all; an authorization handoff in flight shows a waiting-for-authorization line naming the connector, with a reopen button that re-launches the OAuth flow with the stored account key; a failed handoff shows an authorization-did-not-finish line with a retry button; otherwise a single button labeled add (not installed, catalog entry exists) or authorize (present but needing authentication, disconnected, or errored). The card also projects up to four suggestion chips — other related connectors mentioned in the message — each immediately installable. The list variant (the reference's connector-list view, for the plural message kind) renders the same card as a compact row (no suggestions) inside a list shell, one row per normalized connector name. Shared logic in the reference's connector-actions module resolves the MCP catalog and live server state through the MCP bridge's catalog and server-list calls, computes action keys per connector+account, and implements connect / authenticate / retry / reopen actions, treating team-policy-only servers as unavailable.

## What the current build does
Nothing. There is no connector card, no connector list view, and no connector-related module anywhere in the build: a case-insensitive search for "connector" across `src/` and `client/` returns zero files. The build has no MCP catalog/servers snapshot surfaced to cards, no install/authorize action surface, and no message protocol variant for connector suggestions.

## The deviation
The reference turns "you could connect X" suggestions into one-click install/authorize controls embedded in the conversation, with a full lifecycle (idle → installing/authenticating → waiting-for-OAuth → connected/failed → retry/reopen), team-policy gating, and related-connector suggestion chips. The build has no equivalent at any layer: the UI pattern is absent (A10 message cards), and beneath it the entire connector registry it reads from — catalog entries, server status, account keys, and the connect/authenticate/retry/reopen actions — does not exist either (cross-ref connectors area "(DD number pending)"). This is a missing feature, not a behavioral difference in something present.

## Verdict: ADAPT
The card pattern is worth having — it is exactly the kind of low-friction "agent suggests, human approves with one click" surface the PRD's chat-first story favors, and ADR-0018 (C14) permits consulting the reference for behavior while B9 forbids copying code. But it cannot be incorporated as-is: every prop and action the reference card renders comes from an MCP catalog/server-state snapshot plus an action provider the build lacks, so the card is downstream of the connector registry work (cross-ref connectors area "(DD number pending)"). Adapt means: re-derive the card independently against the build's own eventual registry/protocol, keeping the state machine's shape (add/authorize, waiting-and-reopen, failed-and-retry, added, team-policy suppression, suggestion chips) as a requirements checklist rather than a source.

## Incorporation notes
- **Where it would live:** message-card layer of the web client surface (`client/`), alongside the other transcript card renderers, keyed off the build's own card/protocol types; the action and snapshot plumbing belongs with the connector registry module (cross-ref connectors area "(DD number pending)"), not in the card component.
- **Constraints:** ADR-0018 B9 — independent re-derivation, no verbatim reference code or its recovered class names; card must degrade gracefully when the registry reports no catalog entry and no server (render nothing rather than a button that cannot work); team-policy-disabled connectors must not expose an action button; suggestion chips must not chain-install without explicit clicks; authorization handoff must survive page reloads (the Reopen path exists for that).
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the card itself is small, but only after the registry/action surface exists; until then it is blocked work, and the OAuth reopen/retry states carry moderate UX risk if the build's sign-in flow differs.
