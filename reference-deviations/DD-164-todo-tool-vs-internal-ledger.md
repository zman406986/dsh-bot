# DD-164 — Todo tool vs the build's core-internal ledger
- **Area:** A19 tool surface
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference ships a first-class todo tool that the model invokes as a normal tool call. The model hands over a whole batch of items, each carrying a stable id, a text body, and a status, plus a flag choosing between two write modes. In merge mode the incoming items are folded into the stored list keyed by id, so an update may name only the id and the changed status and leave the text out; in replace mode the incoming batch overwrites the stored list outright. Four statuses are supported — not started, running, done, and dropped. The tool result is written back to the model as prose: a confirmation line, a rendering of the current list, an advisory when nothing is marked as running while items are still waiting, and a nudge once finished items pile up past a threshold. The tool description itself is long-form coaching — when to reach for the list, when not to, one running item at a time, cancel dropped work immediately, batch the write alongside other calls — and it varies per model family. Several items per call, and several calls batched with other tools, are the expected shape. The list is the agent's own working artifact and is authored entirely by the agent.

## What the current build does
The build has no todo tool on any surface. Its ledger is core-internal and dispatcher-owned: the dispatcher creates an entry by passing a todo id to the spawn tool, and the entry is closed by the result-delivery path, not by the model flipping a status. The dispatcher policy copy tells the dispatcher to write an entry before it spawns, that several entries may be in progress at once, and to mark one completed only once the user actually holds the result rather than when the worker merely exits. So the ledger is a bookkeeping structure bound to worker lifecycle, not a general task list the agent keeps for itself. The build states the worker-side half of that split explicitly: the worker prompt carries a section saying the worker does not maintain a todo list and that progress travels only through the final answer and the side effects of its work tools. The tool surface itself has no todo entry.

## The deviation
Both systems have something called a todo list; they are different mechanisms that share a name. The reference's is agent-authored, general-purpose, self-directed — the model picks the items, revises them, and keeps itself on track using the tool's coaching text. The build's is dispatcher-owned and lifecycle-bound — entries are created by a spawn call and retired by delivery, and the model does not author or maintain them at all. The reference's tool is where the agent's own plan lives; the build deliberately has no such place, because the dispatcher does not do the multi-step work and the worker is told not to keep a list. So the gap is not that the build lacks the reference's feature and should add it — it is that the build chose the opposite arrangement for the same role, and the two arrangements cannot both be present without two overlapping lists.

## Verdict: DO-NOT-INCORPORATE
The build's ledger already covers the bookkeeping need that the reference's todo tool serves, in the build's own style: entries are spawned and retired by lifecycle rather than edited by hand, and the model-facing half of keeping the ledger up to date lives in the always-on reminder (DD-153) rather than in a tool's description. No recorded ruling names a todo tool for the build — nothing in the ADR set or the PRD requires one — so this verdict is not a citation of a settled decision; it rests on the duplication the two lists would create. The reference's coaching copy and its four-status vocabulary are also tuned to a self-directed single agent, which is precisely the role the build splits apart. ADR-0018 exception C14 excludes the memory/routines subsystems; the todo tool is neither, so C14 does not cover this item and no exclusion is being claimed here. The merge-semantics half is a separate question and is where an ADAPT could live without adding a second list.

## Incorporation notes
- **Where it would live:** Nothing to add for the tool itself. If the merge half were adopted, the change is to the ledger's update path in the core, not to the tool surface.
- **Constraints:** Two lists would diverge — the dispatcher's ledger tracks worker lifecycle, while an agent-authored list would track the agent's own steps, and reconciling them would be new work with no requirement behind it. The worker prompt's stance is deliberate in the other direction and any adoption would have to argue against it. The four statuses do not map cleanly onto ledger entries, which have no dropped state and are not edited mid-flight by the model.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — if the merge semantics were adopted at all, the change is small and confined to the ledger update path; the risk is low but the case for it is thin, since the ledger is updated call by call rather than by the model.
