# DD-108 — Interactive guided onboarding flow vs five static beats
- **Area:** onboarding (A13)
- **Type:** deliberate-divergence (recorded in the module header)
- **Date:** 2026-09-23

## What the reference does
The signed-in reference onboarding (the reference tree's `frontend/src/recovered/features/onboarding/signed-in/model.ts`, `view.tsx`) is a six-step guided sequence — the step list runs meet → computer-demo → jobs → tools → create → hand-off. It is animated and timed: the meet step types its tagline character by character every 35 ms (a character-typing helper and its per-step millisecond constant), the computer-demo and jobs steps advance on their own timers (900 ms / 800 ms), steps exit through a 200 ms transition (a named exit-duration constant), and the hand-off waits on a cancellable timer before releasing into the shell. An animated cast of characters — a hero plus three teammates, positioned frame by frame by `scene.ts` (the scene character list and the placement function) — carries the scenes, and the stylesheet honors the reduced-motion media query (`view.css:48`, matching check in `view.tsx:52`). Navigation is bidirectional (a previous-step action backs the Back button), and the whole flow sits behind route-level gating: the onboarding route resolver sends a signed-in user who already has an agent roster straight to the shell and treats onboarding as seen, and the account/roster probe fails open so a transient read cannot strand a first run. (The computer-demo step is out of this write-up's scope by instruction, as is the remote-computer-use capability behind it.)

## What the current build does
The build's first-run flow is a five-step static pane: `ONBOARDING_BEATS` in `src/client/onboarding.ts` holds intro → background-jobs → tools → first agent → hand-off, each step a heading plus one body paragraph keyed into the shell locales. Progress is a row of dots plus a step counter, and the only navigation control is the forward button (the store exposes `advance()` and `complete()` — there is no back action at all). There is no animation, no cast of characters, no step timer, and no route gate: the pane is mounted in the shell's main slot when no session is selected (`src/client/index.ts:878` wires `onboarding: onboardingPane`), and suppression is re-evaluated reactively from the settings watch and the dispatcher mirrors (`isOnboardingSuppressed`, plus the ticket-87 buffering state) rather than resolved once at route time. The build's own module header keeps a step-by-step disposition table (`src/client/onboarding.ts:15-25`) that records the sign-in step and the computer-readiness demo as gaps rather than steps.

## The deviation
Structure, interactivity, and motion. The reference is a timed, animated, six-step walk with a cast of characters, back navigation, and route-level first-run routing; the build is a static five-step pane with forward-only navigation, reactive suppression, and no animation at all. Two reference steps have no counterpart: sign-in (no account model in the build) and the computer-demo (the remote-computer area is ruled out elsewhere). The count and order still map one-to-one onto the reference's non-gap steps, so the sequence is preserved — everything that animates or navigates backwards is what diverges.

## Verdict: ADAPT
The build's static-counterpart choice is already the recorded adaptation: the module-header table (`src/client/onboarding.ts:15-25`) records a decision for every reference step, explicitly applying the shell CSS rule for the no-animation decision on the meet-intro row, and the two gap rows (sign-in under the privacy/account-gates exception; computer-readiness as the ticket-71-dependent remote-computer gap, capability-blocked per ADR-0018) are recorded rather than invented — exactly what the precedence order requires. ADR-0018 puts onboarding in scope but under adapted-copy terms (B9), and it does not mandate motion or interactive parity; the deviation is deliberate, documented in place, and consistent with the single-kind wake model recorded for the jobs step. Full incorporation of the animated cast, step timers, and Back navigation would contradict the recorded CSS/animation stance without a new ruling, so the static counterpart stands; if the human wants richer motion later, that is a fresh decision, not a fix.

## Incorporation notes
- **Where it would live:** Any fuller flow stays in `src/client/onboarding.ts` (step table and state machine) plus `src/client/onboarding-pane.tsx` and `src/client/index.ts` (mount wiring); nothing new is needed to keep the current adaptation.
- **Constraints:** No animation under the shell CSS rule unless the human rules otherwise; no Back unless a ruling adds it (the store is deliberately forward-only); suppression stays reactive with fail-open behavior and the ticket-87 buffering guard — do not replace it with a one-shot route resolver; sign-in and computer-demo stay recorded gaps (never staged as steps); copy is our own, adapted per B9.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M for a motion/Back upgrade (store changes ripple through offline tests); S/risk-free to keep as-is, which is the recommended default.
- **Key reference anchors:** the reference tree's `frontend/src/recovered/features/onboarding/signed-in/model.ts` (the step list, the step-timer constants, the previous-step and route-resolver actions, and the account-onboarded check); `scene.ts` (the scene character list and the placement function); `view.tsx:52` and `view.css:48` (reduced-motion handling).
