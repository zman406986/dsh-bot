# DD-205 — MCP transports and transport supervision
- **Area:** A26 MCP machinery
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

**Three transports, derived from the config shape.** The reference models exactly three ways a capability server can be reached, and the transport is a *derived* label rather than a stored fact: one classifier reads the server config and returns the child-process label when the config carries a command line (command plus optional arguments plus optional environment), the SSE label when a URL-form config carries the explicit SSE marker, and the HTTP label for every other URL form (the reference tree's `source/shared/node/mcp/mcp-validation.ts:3`). The config type is a two-branch union — a URL form (URL, optional SSE-or-HTTP marker, optional headers) and a subprocess form (command, optional arguments, optional environment) — so the two shapes are distinguishable structurally and the transport follows (the reference tree's `source/shared/node/mcp/mcp-display-runtime.ts:2`). Marketplace entries are normalized before they reach validation: a separately spelled transport field is folded into the config's transport marker when that marker is absent, and the marketplace's own alternate spelling of the streamable-HTTP transport name normalizes to the plain HTTP type (the reference tree's `source/shared/node/mcp/mcp-marketplace.ts:74-80`).

**Two hosting planes.** Remote HTTP/SSE servers execute on the backend; child-process servers execute on the product's own remote computer image. The desktop management tool that adds a server states the split as policy: it adds a *remote* server by URL and explicitly refuses local/child-process servers, telling the model they are not supported (the reference tree's `source/host/runner/tools/sand-mcp-management-tools.ts:343`). The execution layer repeats the split when it refuses an unreachable provider: HTTP/SSE servers run on the backend and child-process servers run on the product's computer, so an identifier that is neither is unsupported in that context (the reference tree's `source/shared/node/mcp/tools-discovery.ts:427`).

The child-process plane is driven by pushing configuration rather than by connecting directly: the host image receives the whole child-process server set as a JSON document and loads it with a remove-missing reconciliation, returning the names it loaded (the reference tree's `source/host/box/box-mcp.ts:5,7`), and the discovery layer serializes the child-process configs under a server-map wrapper, skips the push when the payload is unchanged since the last one, and performs it before listing tools (the reference tree's `source/shared/node/mcp/tools-discovery.ts:159-177`, invoked at `:459`). When the control RPC is not implemented at all — the unimplemented status, including its numeric code form — the failure is translated into a distinct error whose text says the product's computer is running an image too old for MCP support and points at the update path (the reference tree's `source/host/box/box-mcp.ts:3-6`). The image itself, its remote-desktop surface and its internals are outside this study's scope; the plane is named only because the transport split does not exist without it, and nothing here is filed as a box-internals deviation.

**Discovery splits by plane and fans out.** The discovery module keeps the HTTP/SSE names and the child-process names as separate lists, resolves them in parallel with per-plane failure semantics — an HTTP failure is fatal, while a child-process failure is tolerated as long as the HTTP side produced something (the reference tree's `source/shared/node/mcp/tools-discovery.ts:150-156`, `:244-262`) — and, when listing on the child-process plane, pushes the config first and then reports per-server status, optional status detail, and an enabled-tool count per server (`:449-469`). The model-facing discovery tool reports the catalog's total tool count and per-server tool rows (the reference tree's `source/packages/agent/tools/mcp/get-mcp-tools.ts:343-349`).

**Provider resolution.** Before execution, a provider identifier is classified into exactly three answers — HTTP, child-process, or unknown — by asking first whether it is an HTTP provider and then whether it is a child-process provider on the host image (the reference tree's `source/shared/node/mcp/tools-discovery.ts:471-477`); that resolution is exposed on the host's MCP port (the reference tree's `source/host/extensions/mcp/mcp-service.ts:151`).

**A loopback MCP bridge.** The coordinator can re-expose routed remote tools as a callable MCP surface: a loopback HTTP server bound to an ephemeral port behind a random secret path, speaking the standard handshake, tool-listing, and tool-invocation methods; the tool list is re-fetched on demand and re-keyed by the routed row names, and calls are forwarded into the routed tool set with a fresh call id while the product's own protobuf-shaped results are translated into MCP-shaped content, including image content and the error flag (the reference tree's `source/node-agent-coordinator/routed-mcp-bridge.ts:39-88`, translation at `:22-37`). Read-only classification is a name-and-description heuristic: read-flavored vocabulary with no write-flavored verb marks a tool read-only, and that verdict sets the read-only, destructive, idempotent, and open-world annotation hints on the listed tool (`:16-20`, `:67-70`).

**Supervision intent, and one live event stream.** Supervision policy is visible as named, bounded timing constants: a periodic keepalive probe delay of five minutes (the reference tree's `source/packages/mcp-core/config/mcp-fsm-timing-config.ts:1`), an inline reconnect cooldown of five minutes (the reference tree's `source/packages/mcp-core/config/mcp-inline-reconnect-cooldown.ts:1`), a focus-retry minimum cooldown of five minutes (the reference tree's `source/packages/mcp-core/config/mcp-focus-retry-cooldown.ts:1`), and a tool-call maximum total timeout ceiling of one hour with a legacy alias of the same value (the reference tree's `source/packages/mcp-core/config/mcp-tool-call-timeout.ts:1-2`). Those four constants have no consumer anywhere in the tree — a repository-wide search returns the declarations only — so they are cited here as intent evidence, not as proven live behavior. The lease-change stream, by contrast, is consumed: a reason vocabulary of five named causes, an event carrying optional server identifiers plus a reason, a predicate that treats an absent event or an absent identifier list as full invalidation, and a merge that collapses to full invalidation (the reference tree's `source/packages/agent-exec/mcp.ts:44-50`, `:68-71`, `:112-127`); the filesystem writer subscribes to it, debounces, refreshes only the named servers on a targeted event, and performs a complete refetch and rewrite when the event invalidates everything (the reference tree's `source/packages/local-exec/mcp-file-system-writer.ts:243`, `:355-357`, `:375-377`).

## What the current build does

ABSENT in every part. The build has no transports of any kind: no child-process spawning for capability servers, no HTTP or SSE client, no JSON-RPC bridge, no reconnect or keepalive policy, no call timeout, and no per-server status. A case-insensitive search for MCP vocabulary across `src/` and `client/` returns no hits, matching DD-203's finding at the vocabulary level as well as the structural one.

The build's only outbound surfaces are its own host callbacks and the dsh plugin channel it registers through (`src/adapter/cordis-dsh-host.ts`): it asks the host to spawn workers and observes a per-worker activity phrase and last-activity clock off the host firehose (`src/adapter/cordis-dsh-host.ts:251-263`, `:446-449`, `:563-575`). Worker processes are spawned and supervised for dispatch (`src/worker/agent-def.ts`, `src/worker/prompt.ts`, `src/worker/tool-barrier.ts`), and the supervision discipline the reference applies to capability servers is applied here instead, to workers: a named, bounded stall threshold with a three-state verdict in `src/core/liveness.ts` (`WORKER_STALL_THRESHOLD_MS` at `:38`, the verdict vocabulary at `:30`), surfaced on the check row (`src/adapter/dispatcher-tools.ts:187-188`). That is a task-isolation concern — bounding and observing delegated work — not a capability-server transport, and the two must not be conflated: nothing in the build opens a connection to an external capability server because the build has no notion of one.

## The deviation

This is the plumbing layer beneath DD-203's server model, and it has the same status as that file rather than adding a new one. A transport exists only to carry a capability server the build does not own: in the build's architecture tool sourcing belongs to the host, and the build is a Cordis plugin that registers its own tools and asks the host what globals exist — it does not connect to, spawn, or authenticate external capability servers. The reference is the entire application, so it necessarily owns the transports end to end; the build has no layer above it to delegate to and no server beneath it to carry. The scope decision is DD-203's, cross-linked here and not re-argued; DD-156 reached the same non-goal on the prompt side and left the machinery to DD-203.

What is specific to this file is that the transport layer is not one feature but four separable ones: the transport set and its derivation, the two-plane hosting split, the loopback bridge that re-exposes routed tools, and the supervision policy (keepalive, reconnect cooldown, call ceiling, lease invalidation). Three of those are unreachable without the server model itself — a plugin with no servers to reach needs no transports, no planes, and no bridge. The fourth is genuinely transferable as a *pattern* rather than as machinery: named, bounded timing policy for reconnection, liveness probing, and call ceilings. The build already practices exactly that discipline on its own workers (`src/core/liveness.ts:38`), so the reference's contribution here is corroboration of a pattern the build already holds, not a mechanism it is missing in a domain it occupies.

## Verdict: ASK-HUMAN

No recorded ruling names MCP transports. The only candidate is the PRD §2 non-goal excluding a rebuild of dsh's tool runtime (`PRD-dsh-multitask-dispatcher.md:34-36`), which reads on its face as covering a plugin-side transport stack — reaching external capability servers is what a tool runtime does — but it is a scope statement rather than a transport decision, and the exclusion is inferential and reversible. That is the identical question DD-203 filed ASK-HUMAN, and this layer is strictly downstream of DD-203's server model, so the same answer applies: if the human rules the server model in, the transports come with it and need no separate ruling; if the human rules it out, this file follows and nothing here is built. ADR-0018's exception list does not mention MCP, so it does not reach this either, and deciding the scope question twice with different verdicts would be worse than filing it once.

## Incorporation notes

- **Where it would live:** nothing is added now. If the human rules the server model in, transports belong *outside* the plugin: the plugin would use whatever MCP surface dsh exposes rather than implementing a transport, which is DD-203's "consumer, not client" shape and carries the same constraint. Should a transport ever be built inside the plugin, the child-process path would sit beside the existing worker spawn and observation points (`src/worker/`, `src/adapter/cordis-dsh-host.ts`), and the supervision constants would belong next to `WORKER_STALL_THRESHOLD_MS` in `src/core/liveness.ts` rather than in a new module — the point being that the build's timing policy should stay in one place. A loopback bridge would be a new outbound listener, of which the build has none today.
- **Constraints:** the build owns no tool sourcing, so a transport with no host-provided server list would be dead code, and any client the plugin builds duplicates dsh's runtime — the specific thing the PRD §2 non-goal names. The reference's timing values (five-minute probe, five-minute cooldowns, one-hour call ceiling) are the reference's numbers for the reference's architecture and must not be copied as values; re-derive the policy from the build's own measurements, as the worker stall threshold was derived. The bridge's read-only verdict is a name heuristic, not a capability fact — a read-flavored name does not make a tool safe — so if any read-only hint is ever emitted it must come from the tool's own declaration rather than from its name. Protocol-level details (the handshake shape, the method names, the version marker, the server-info block, the annotation keys) are protocol artifacts under ADR-0018 B9 and must be taken from the public specification, not from the reference tree.
