# DD-178 — On-disk transcript mirror with WAL-style checkpoints
- **Area:** A21 storage
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference mirrors each conversation to a plain file on disk as it happens, using the same write-then-commit steps a database journal uses. The target is one newline-delimited JSON file per conversation id, at a path derived from a sanitized id under a transcripts directory (`the reference tree's source/host/transcript-mirror/transcript-mirror.ts:23`). The write path is write-ahead-log shaped: the preparation phase derives the lines to append, then installs a pending checkpoint record — the append offset, the file's device and inode, the pending lines, and a cursor — through an atomic install that writes to a temporary sibling file, flushes it, renames it over the target, and syncs the parent directory (`:28`, `:39`); the commit phase appends the pending lines to the canonical JSONL file, flushes, then removes the pending record (`:40`, `:37`); the recovery phase replays the pending record when its checkpoint hash matches the durable one, discards it when only the predecessor hash matches, and refuses loudly otherwise (`:38`). The journal checks the file's identity before each write: before touching the canonical file it re-reads device/inode/size and treats a mismatch, a short tail, or a tail that disagrees with the pending lines as corruption rather than repairing silently (`:37`, `:39`). Writes to the same file are serialized per file path, so two checkpoint operations for one conversation cannot interleave (`:8`, `:31`).

Around that core sit four supporting roles. A router chooses per conversation between the journal path and a legacy incremental mirror, pins the choice for that conversation's life so a later switch-off cannot drag it back, and treats the legacy writer as observational — its failure never rolls back a durable checkpoint (`transcript-mirror-router.ts:1`, `:63-69`, `:46`, `:130-132`). An occurrence deriver decodes turns and steps and formats the user, assistant, and tool lines that become journal entries, and is the only source of them (`transcript-occurrence-deriver.ts:88`, `:188`, `:259-271`). The journal codec owns the pending-checkpoint record shape, its validation, the hash identity over the checkpoint's turns, and the corruption error type (`transcript-journal-codec.ts:10`, `:17`, `:13`, `:18`). And the whole write is offloaded to worker threads: a pool shards conversations across a small fixed set of workers and serializes per conversation, each worker running as its own thread with a read-only blob store whose non-write invariant is asserted (`the reference tree's source/host/agent-isolation/transcript-mirror-offload.ts:14`, `:57`, `:151-158`; `the reference tree's source/host/agent-isolation/transcript-mirror-worker.ts:60`, `:87-91`). The mirror's outcome is also instrumented: every operation reports a success-or-failure outcome with entry counts, byte counts, and duration, and failures carry a bounded error code (`transcript-mirror.ts:17`, `:15`).

## What the current build does
Absent. The build has no transcript mirror and no file-based transcript of any kind. Its entire persistence layer is one bounded record and one port: `src/core/durability.ts` declares `DurableWorkerMarker` (`:9-28`) and `DurabilityPort` (`:36-45`), and the doc comment states the record is written at spawn through the host's session/storage facility and is "never a second transcript DB" (`:6`), while core "must not invent its own transcript database" (`:34`). The marker holds a transcript *pointer* (`transcriptRef`, `:16-17`) and never transcript content. The adapter lands it in the dispatcher's own namespace inside the host's storage domain (`src/adapter/durable-marker.ts:27-28`, lazy domain open `:104-112`), and `src/core/multitask.ts` imports the durability port (`:49-54`) and rebuilds the roster from markers, carrying `transcriptRef` through as a pointer only (`:477`, `:494-495`, `:895`). The adapter comments say the same thing from the host side: the core stores no report text and no second transcript exists (`src/adapter/cordis-dsh-host.ts:455`).

The reason is ownership. In the build's architecture the conversation transcript is a **host-owned artifact** — `src/core/durability.ts:7` says in terms that the worker report itself stays in dsh's transcript — and the plugin is a dispatcher guest that holds references into host state rather than a copy of it. The reference owns its transcript (its own agent isolation layer, its own per-agent storage), so mirroring it to disk is its own business and its own responsibility; the build's plugin has no such responsibility and does not hold the data.

## The deviation
A missing feature, but not a standalone gap. The mirror **depends on a storage layer** the build does not have: it is named as such in DD-177, where the per-agent storage architecture is the root and the transcript mirror is one of the features built on it. The reference can mirror because it holds the transcript; the build holds a pointer. Adding a mirror here would mean copying host-owned conversation data into a second on-disk representation that the plugin then owns and must keep in step with the host's own — a second transcript copy, maintained by the party that does not own the original.

The two related records are DD-177 and DD-167. DD-177 owns the storage layer and already names this mirror as one of the features that depend on it, so the storage decision governs here. DD-167 owns the session half of the same storage layer — the per-agent durable session store the reference reopens rather than reconstructs. DD-178 is the narrower question those two leave open: given no second database and a host-owned transcript, is a file-based transcript mirror a fidelity gap worth closing on its own? It is not, because the file format was never the point; owning the data was.

## Verdict: DO-NOT-INCORPORATE
No recorded ruling names the transcript mirror by name — a search of `docs/` and the PRD finds nothing that rules on this specific mechanism — but the storage layer it depends on is ruled, and the ruling reaches it. ADR-0018 exception **A5** keeps persistence in dsh's session/job store with no second database (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:25`), and a JSONL mirror maintained by the plugin is a second persistent store whatever format it uses. ADR-0006 rules the build's durability split, stating "No second transcript DB" as a deliberate divergence from the reference rather than an imitation (`docs/adr/0006-worker-record-durability-split.md:5`), and adding that nothing beyond the minimum needs to be durable because "the transcript itself is dsh's, not ours" (`:25`), with worker transcripts remaining dsh's own (`:28`). The host-ownership argument decides the fidelity question on its own — the build cannot mirror an artifact it does not hold — and A5 plus ADR-0006 decide it as a matter of record. Adoption would require reversing A5 first, which is a separate human decision and not a fidelity fix; under the current rulings this is not the human's to weigh.

## Incorporation notes
- **Where it would live:** Nowhere under current rulings. If A5 and ADR-0006 were reversed, the mirror would be new surface with no current home — a file-backed writer plus codec, a deriver that would have to own transcript decoding the build deliberately does not do, and a per-conversation route selection — sitting beside `src/core/durability.ts` and reached through `src/adapter/durable-marker.ts`'s storage interface. The one existing hook a mirror would need, a per-worker transcript pointer, is already in place (`src/core/durability.ts:16-17`), which is exactly why the temptation to add the mirror looks cheap when it is not.
- **Constraints:** ADR-0018 A5 forbids a second database, and a file-based mirror is a second store; ADR-0006 forbids a second transcript DB and fixes the durability minimum; the transcript's ownership sits with dsh, so the plugin writing its own copy would create drift between two authorities for the same data. Any proposal must clear A5, ADR-0006, and the ownership question before touching code — and the ownership question is not clearable by the plugin alone.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — bounded as a subsystem (codec, writer, deriver, router, worker offload) but it cannot be built alone, and its real risk is not effort: it would create a second, drift-prone copy of host-owned conversation data that the plugin would then have to maintain.
