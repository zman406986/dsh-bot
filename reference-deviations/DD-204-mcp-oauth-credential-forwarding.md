# DD-204 — MCP OAuth: browser sign-in, loopback callback capture, and credential forwarding
- **Area:** A26 MCP machinery
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

Authentication is a first-class per-server, per-account flow, built in four layers.

**1. Status probe and auth watch.** A probe reports whether a valid token exists, whether authentication is required, and an authorization URL. A pending auth watch is then registered and polled against the backend's token-validation endpoint under a deadline and polling policy — a watch module carries a five-second poll interval, a fifteen-minute overall watch deadline, and a thirty-second per-poll timeout, and keys a watch per server and account (the reference tree's `source/shared/node/mcp/mcp-auth-watch.ts:1-4`). The lifecycle module (the reference tree's `source/shared/node/mcp/mcp-auth-watch-lifecycle.ts`, 418 lines) defines two closed reason sets. Refusals at `:26-33`, with call sites at `:121` (not configured), `:139` (disabled by team admin policy), `:149` (a local-process server, which cannot browser-sign-in), `:201` (invalid authorization URL), `:236` (host unreachable), and `:242` (no authorization link). Failures at `:34-37`, distinguishing a failed probe from an RPC timeout and chosen between at `:172-175`. Each outcome is a structured error carrying its reason rather than a boolean, and the invalid-URL refusal carries the scheme rule in its message — HTTPS only unless the server runs on localhost (`:204`). The watch entry is stamped with an absolute expiry from the watch deadline (`:264`) and settles with a timeout outcome (`:345`).

**2. Loopback callback capture.** A listener pool is keyed by redirect origin (the reference tree's `source/node-agent-coordinator/oauth/mcp-oauth-loopback-registry.ts:36-59`): one entry per origin, a bind per origin, a pending-promise entry that is removed if the bind fails, and a drain that closes the origin's servers when the entry is dropped. Pending authorizations are tracked as origin-plus-state pairs in a map keyed by state, with the backend's pending-state TTL at fifteen minutes and the client-side pending TTL a minute longer (the reference tree's `source/shared/node/mcp/mcp-oauth-loopback.ts:40-41`), armed through an expiry policy so a stale entry settles itself (`:97-100`, `:320-323`). A per-origin callback listener starts only while pending work exists and closes once the pending map empties (`:150`, `:256`, `:270`), retrying a failed bind while auth is still pending (`:289`), and a register-from-URL path parses the authorization URL to arm the pending entry (`:307`). The captured authorization code is forwarded to a completion port (the reference tree's `source/host/mcp-auth/host-mcp-auth-completion.ts`) with a coordinator-side forwarder (the reference tree's `source/node-agent-coordinator/oauth/mcp-oauth-forwarder.ts`); the browser sees a served callback page (the reference tree's `source/shared/mcp-oauth-callback-page.ts`), and a wait registry holds the pending watches (the reference tree's `source/host/mcp-auth/mcp-auth-wait-registry.ts`).

**3. Desktop wiring.** A desktop adapter (the reference tree's `source/electron-main/adapters/mcp-oauth.ts`, 283 lines) obtains the account-scoped auth service (`:57`, `:106`), keeps credential handling and manager construction as separate joins (`:96-97`), and drives the host through ports declared at `:20-21` — settings store, host MCP refresh, host-settings sync, broadcast, and a connector-auth reporting port — with the manager refresh at `:130-133`. An auth callback registration module (the reference tree's `source/electron-main/auth/auth-callback-registration.ts`) and a loopback provider (the reference tree's `source/electron-main/mcp/mcp-oauth-loopback-provider.ts`) sit on the same path, and the flow itself lives in a shared agent-core module (the reference tree's `source/packages/agent-core/mcp-auth-flow.ts`). The account-scoped auth service is a host-side extension (the reference tree's `source/host/extensions/auth/auth-service.ts`).

**4. Policy, telemetry, cleanup, and model etiquette.** Authorization URLs are constrained to HTTPS except on localhost (the reference tree's `source/shared/node/mcp/mcp-auth-watch-lifecycle.ts:204`). Auth start and refusal are telemetered (the reference tree's `source/shared/observability/connector-auth-telemetry.ts`). Credentials are cleaned up on logout and removal, including a sweep that deletes legacy credential files by filename pattern and reports not-found, error, or deleted with a removed count (the reference tree's `source/shared/node/mcp/mcp-auth-cleanup.ts:1-4`). Environment variables handed to a server are classified as secret by a name pattern over the usual secret-bearing vocabulary, with schema-level password-format and write-only markers as additional signals (the reference tree's `source/shared/node/mcp/mcp-plugin-variables.ts:2,5`). Failure surfaces as a needs-auth status plus a connect affordance, and the model is instructed to authenticate lazily: only when a server is marked as needing authentication or a call fails on an authorization error, then inspect that server again and retry, never authenticate merely because the tool is listed, never repeat an authentication that did not fix the failure, and never authenticate two servers at once (the reference tree's `source/packages/agent/utils/mcp-auth-instruction.ts:1`). DD-203 records the sibling copy rule: once a connect card is in the chat, the model should not also send a link or reach the service another way (the reference tree's `source/host/runner/tools/sand-mcp-management-tools.ts:239-240`).

## What the current build does

Nothing on this path. A grep for MCP and OAuth vocabulary across `src/` and `client/` returns zero matches: there is no auth status probe, no OAuth client, no loopback listener, no credential store, no forwarding path, and no token refresh. The build does not own external-service credentials at all. ADR-0008 records the rule — credential asks travel as a structured relay through the dispatcher, the access decision carries no value field, and credentials are named and resolved by the host runtime's scoped injection, only inside the adapter (`docs/adr/0008-worker-access-ask-structured-relay.md:5,26-27`).

The nearest existing concept is the human-approval flow, which gates rather than acquires. `src/adapter/dispatch-approval.ts` wires the dispatch approval path to the host's approval answerer, scopes the ask to the activated dispatcher's own agent, and degrades fail-closed to an unavailable outcome under a bounded wait with ADR-0008 deadline semantics. `src/adapter/access-prompt.ts` carries the prompt anatomy for an access ask, including a credential class whose copy names the credential and never a value, and whose payloads carry class and action metadata only (`:34`, `:68`, `:174-178`, `:258-267`). `src/client/approval-pane.tsx` renders the resulting access-ask and secret-ask cards in a needs-you area of the conversation surface — presentation only, no retry affordance, no success fanfare. So the build's credential surface is a human gate on a worker's request for access; it never acquires, stores, or forwards a service credential.

## The deviation

This is the acquisition half of the same subsystem whose lifecycle DD-203 covers, and it is entirely absent: no per-server auth status, no watch with refusal and failure reasons, no loopback callback capture with origin-keyed listeners and pending-state TTLs, no desktop credential wiring, no cleanup, no model etiquette for authenticating. The gap is a capability class rather than a missing helper: the reference is a credential-owning application that registers OAuth clients, captures authorization codes on a loopback port, and forwards credentials to a remote execution host, while the build deliberately is not one — the study's environment rule that the live-test credential stays in the human's session and is never exported, copied, or moved (`read-before-running-live-and-browser-tests.md:7`) is the operational expression of that position. The nearest build concept points the opposite way: the approval gate asks a human to authorize an action, and the resulting decision carries no value to forward.

## Verdict: ASK-HUMAN

No recorded ruling names MCP OAuth. Two recorded rulings reach parts of it and neither reaches the whole: ADR-0008 rules that the plugin never holds a credential value — asks are structured relays, the decision has no value field, and resolution is host-side scoped injection (`docs/adr/0008-worker-access-ask-structured-relay.md:5,26-27`) — which covers the holding-and-forwarding half and argues against it; ADR-0018 U-A excludes the connection-lifecycle and privacy/account-gate class (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:34`), which covers the needs-auth-status-and-connect-affordance half and argues against showing it. What neither reaches is whether the plugin should carry an MCP auth flow at all — the same scope question DD-203 filed ASK-HUMAN, and the two must be answered together, since auth is inseparable from an MCP client the plugin does not own. Because the dominant question is scope rather than an engineering trade-off resolvable from the authority stack, the human owns the decision; do not let ADR-0008's rule about credentials quietly settle the MCP scope question too, which it does not actually reach.

## Incorporation notes

- **Where it would live:** nothing is added now. If the human rules an MCP client in, the acquisition flow belongs to whoever owns the client — under DD-203's design that is the host, not the plugin — so the plugin's share would be a status projection plus a sign-in affordance, not an OAuth client. A per-server auth state would use the same status projection DD-203 describes beside the existing settings surface (`src/adapter/settings-section.ts`, `src/client/settings-card.tsx`), and any connect affordance in chat goes in the card surface governed by DD-075. A loopback listener, if ever owned, belongs with the host-facing wiring under `src/adapter/`, not in the client surface.
- **Constraints:** the recorded rule about credentials is binding — a plugin-side token store would contradict ADR-0008's no-value-field decision, and forwarding a credential to a remote host would contradict it twice. A loopback listener is an inbound network surface on the user's machine, so the reference's properties worth re-deriving are the origin-keyed pool, the per-pending TTL with grace, and the idle drain before the code is forwarded. The refusal vocabulary is worth re-deriving as a closed set of distinct reasons (not configured, admin-blocked, local-process server, invalid URL, no link, unreachable), because that is what lets a model answer honestly instead of sending the user to settings that would fail identically; the model-etiquette rule (authenticate lazily, re-inspect, never fabricate a link or card, one server at a time) is likewise worth re-deriving as prose. The URL-scheme constraint is a security property, not a preference.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — a full OAuth client, loopback listener pool, pending-state store, desktop credential wiring, and cleanup is a subsystem, and it is the half that presupposes a credential-owning application the build deliberately is not. Risk is high: building it would duplicate dsh's runtime territory (PRD §2) and put the plugin in possession of credentials ADR-0008 keeps out of its hands.
