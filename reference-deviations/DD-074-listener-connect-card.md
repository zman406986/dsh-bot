# DD-074 — Integration listener-connect card vs none
- **Area:** message cards (A10)
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

The reference transcript card surface includes a small card component rendered for integration listener-connect transcript messages (the platform protocol type comes from the transcript-card protocol module). Each card is single-platform — GitHub or Slack — and carries that platform's brand mark as an inline SVG. While not connected, the card shows a one-line pitch per platform (GitHub: watching repo PRs, comments, issues, and CI; Slack: waking on messages, mentions, and reactions), optionally extended with a reason carried on the message itself. The action row has three states driven by a live snapshot store subscribed via `useSyncExternalStore`: a checking-connection-status idle state while the store loads, a connect button (guarded against pending clicks and stale transcripts) that calls a connect action taking the platform on the injected provider, and a settled state that swaps the title to the platform name plus a connected suffix, hides the blurb, and shows a check glyph with a `role="status"` announcement. Snapshot state and the connect action both come from a provider wired through the providers shared by the transcript card components, backed by the reference tree's listener-integrations store module (199 lines) and, on the host side, an automations extension (under the reference tree's `source/host/extensions/automations/`: its listener-integrations store, connect watcher, extension entry, and backend relay source) composed in the host-runner composition module and surfaced through the production renderer and the shared module that supplies the providers to card components.

## What the current build does

The build has no integration or listener concept on any surface. A case-insensitive search across `src/` and `client/` finds "listener" only in event-listener senses (registration/removal of DOM and process event callbacks) — none of the matches touch integrations, Slack, GitHub, platforms, or connection state. Neither the listener-connect message kind nor its camel-case action analogue appears anywhere in build source, and there is no snapshot provider, connect action, or platform protocol type anywhere in the client card layer. The deviation brief hinted at a card-registry placeholder metadata line for the listener-connect kind; that line could not be located in the build, so the absence is even more complete than the hint suggested.

## The deviation

The reference pairs a polished branded connect card with a full host-side integration subsystem; the build has neither the card nor any of the machinery that makes it meaningful. This is a whole-feature gap, not a styling or interaction gap: the card is a small component on top of a snapshot store, a connect action, and an automations watcher backend, and all of those are absent (the backend stack is presumably tracked under its own entries — DD number pending).

## Verdict: DO-NOT-INCORPORATE

Under the authority stack the PRD governs scope, and nothing in it asks for GitHub/Slack integration surfaces; the non-goals also rule out the adjacent hub/Phase-2 area, and this card is inseparable from exactly that kind of backend. Incorporating the card alone would ship UI that cannot do anything — a Connect button whose provider, snapshot store, and platform protocol do not exist in the build, so there is no incremental value without a scope change. Any future incorporation therefore requires a human ruling or a new ADR that first lands the listener-integration backend (backend-side entries: DD number pending); the card itself is then a small component (size S) worth re-deriving independently.

## Incorporation notes
- **Where it would live:** if ever scoped: the card component in the client message-card layer (`src/client/`, alongside existing card rendering such as `approval-cards.ts`), a snapshot store in `src/client/` next to the other `*-store.ts` modules, provider wiring in `src/client/context.ts`, and the integration backend under `src/` (adapter or a new module) with dispatcher-side watcher support.
- **Constraints:** hard dependency chain the build lacks — snapshot provider + subscribe/get store, the connect action, host automations watcher and relay, the platform protocol type. Card must degrade to hidden when the provider is absent (the reference already returns null without a message, a pattern worth keeping). Scope change needs human sign-off per the authority stack before any build work.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** L — the 74-line component is trivial, but the feature is worthless without the integration backend, watcher, and protocol work; high risk of building UI that cannot do anything if the card is taken without the backend.
- **Key reference anchors:** `the reference tree's frontend/src/recovered/features/conversation/cards/transcript-card/views/listener-connect.tsx` (the card component, three-state action row, per-platform copy and inline brand SVGs); the sibling listener-integrations store module (`.../transcript-card/listener-integrations.ts`, snapshot store + connect action, 199 lines); the shared view module that supplies the providers to card components (`.../transcript-card/views/shared.tsx`); the host-side automations extension (`the reference tree's source/host/extensions/automations/`: connect watcher, extension entry, backend relay source, listener-integrations store); the host-runner composition module (`the reference tree's source/host/host-runner-composition.ts`, wiring); the production renderer (`the reference tree's frontend/src/production/ProductionRenderer.tsx`, production surface).
