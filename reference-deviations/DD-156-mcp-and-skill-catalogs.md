# DD-156 — MCP and skill catalogs in the prompt (discovery, budgets, degradation)
- **Area:** A18 prompt sections
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does

The reference prompt stack carries two distinct capability catalogs, each assembled from several cooperating modules rather than one single module.

**MCP discovery instructions.** The reference tree's `prompts/user-info-mcp-meta-instructions.ts` teaches a discovery-then-invocation rhythm rather than handing the model a flat tool list. The model is told to look up external services through a discovery tool and then act through a separate invocation tool, with an explicit instruction to minimize round-trips (the stated ideal is one lookup followed by one call). The discovery tool exposes several lookup modes — by server/namespace (returning every tool schema on it), by server plus a single tool name (returning one schema), and by a pattern search when the server is unknown, plus a full-catalog listing when nothing is known. Two behavioral instructions ride alongside: the model is told to *proactively* inspect a server when a request depends on an external product or service the user merely mentions, rather than waiting to be asked; and schema inspection before invocation is stated as mandatory, not advisory. The same file also covers degradation reporting (text search and catalog listings shorten long descriptions and mark them with a truncation suffix, while server-level and single-tool lookups always return the complete description — so the model knows when it is looking at a clipped view) and an authentication instruction telling the model to authenticate lazily, per-server, only when actually refused, and explicitly *not* to authenticate preemptively or repeatedly. The module carries two near-duplicate instruction bodies (an older namespace-flavored variant and a newer MCP-flavored variant), suggesting the flow was rewritten as the underlying naming moved from generic prefixes to MCP terminology.

**MCP catalog.** The reference tree's `prompts/user-info-mcp-catalog.ts` renders the server-and-tool catalog itself, and includes a "still loading" state: when discovery has not finished, the catalog is still emitted but prefixed with a notice that the list may be incomplete and that more servers may appear shortly. The notice is intentional — an incomplete catalog is presented as incomplete rather than withheld, so the model can still act on what is known.

**Skill catalog and its budget.** The skills half is the reference tree's `prompts/user-info-available-skills.ts` (the available-skills list, filtered and conditionally included) plus its `agent-skills-section.ts` (the section structure). The interesting machinery is its `skill-catalog-budget.ts`, which fits the skill catalog into a token allowance derived as a fraction of the effective context limit. It resolves to one of four named strategies, in a fixed order of increasing loss: a within-budget tier (everything fits as-is), a shortened-descriptions tier (descriptions abridged to a computed midpoint length until the rendering fits), a dropped-descriptions tier (path-only rendering — descriptions gone entirely), and an omitted-skills tier (whole skills removed, with an omitted-notice listing affected directories and a count, itself capped to a number of directories). Each tier reports the retained count, the omitted count, the omitted directories, the estimated rendered tokens, and the chosen strategy, so the caller knows exactly which tier it landed on. Selection and budgeting are separate: the available-skills module filters by agent environment, drops skills the model may not invoke, drops file-scoped skills, restricts to skills guided for computer-use on that subagent, and skips emitting the section at all when nothing survives.

## What the current build does

ABSENT, in both halves. A repository-wide search of `src/` and `client/` for MCP terminology returns no hits at all — the build has zero MCP integration and no MCP-related prompt emission. The only textual near-hit is an unrelated comment about model-facing context in `src/client/conversation-store.ts`; it concerns notices and goal rounds, not skills.

The build exposes exactly six dispatcher tools, declared as name constants in `src/core/policy/prompts.ts` (spawn, check, steer, stop, deliver, send-peer) plus `request_access`. The blocked-tool list in `src/worker/tool-barrier.ts` enumerates the same set. There is no catalog module, no token budgeting of any prompt section, and no staged reduction of any kind.

Two consequences worth stating plainly. First, the build's prompt assembly (via `src/core/policy/assembler.ts` and `src/core/policy/prompts.ts`, with the worker side in `src/worker/prompt.ts`) emits fixed prompt text of fixed size — nothing in it is measured against a token allowance or shrunk to fit. Second, there is no discovery step at all: no notion of a tool the model must find before it can invoke, and therefore no discovery-then-invocation instruction, no inspect-schema-before-invoke rule, no instruction to inspect proactively, and no rule to authenticate only when refused. Whatever tool vocabulary a build session has, it is handed to the model whole.

## The deviation

The reference treats a capability catalog as a *managed prompt artifact*: something discovered at runtime, rendered into the prompt under a token allowance, reduced step by step through named tiers when it does not fit, and accompanied by instructions that tell the model how to navigate it (look up, then invoke; inspect schema first; inspect proactively; authenticate lazily; treat a clipped description as clipped). The build treats capability knowledge as static: six fixed dispatcher tools that the prompt names outright, with no discovery step, no allowance, and no tiering. The gap is not one missing string — it is an entire missing subsystem: catalog rendering with a "still loading" state, a budget resolver with an ordered set of reduction tiers, and a family of navigation instructions. The two halves differ sharply in how they sit against the build's architecture, and the verdict below keeps them apart.

## Verdict: ASK-HUMAN

The two halves genuinely diverge. **MCP: out of scope by non-goal, and arguably DO-NOT-INCORPORATE.** MCP is a host-level capability — the build is a Cordis plugin sitting inside dsh and does not own tool sourcing, so a discovery-then-invocation flow, a server catalog, still-loading states, and lazy-auth instructions are prompt text for machinery the plugin neither provides nor advertises. PRD §2 excludes rebuilding dsh's inference/transcript/tool runtime, which on its face covers exactly this. But no recorded ruling names MCP directly — ADR-0018's exception list does not mention it, and the PRD non-goal is a scope statement rather than a specific MCP decision — so the honest reading is that the exclusion is inferential and reversible by the human. **Skills: this is a real missing capability and ADAPT is the defensible direction.** The plugin does own its own prompt surface and already injects task-and-dispatch guidance into it, so a budgeted catalog section is a natural extension of work it already does; the four-tier reduction is directly re-derivable as an idea without touching reference text. Whether the build should carry a skill concept at all is not settled by any ADR, PRD clause, or ticket ruling I found. Because the dominant question — should the plugin grow a catalog and budget subsystem, and if so on which half — turns on scope the human owns and not on an engineering trade-off I can resolve from the authority stack, the file's verdict is ASK-HUMAN. Treat the MCP half as presumed out by non-goal unless the human says otherwise, and get an explicit ruling on the skills half rather than letting the non-goal silently absorb it.

## Incorporation notes

- **Where it would live:** a new catalog/budget module beside the existing prompt policy — most naturally a sibling under `src/core/policy/` (e.g. a `catalog-budget` module the assembler consults before emitting), with the skills section assembled in `src/core/policy/assembler.ts` and mirrored into the worker prompt via `src/worker/prompt.ts`. The tool-name constants in `src/core/policy/prompts.ts` are the existing example of name tables the prompt emits; a catalog would sit alongside them.
- **Constraints:** the build has no tool sourcing of its own, so nothing here can invent tools to list — a catalog is only meaningful if the plugin is given a set of catalogable items from its host or from a new declared capability surface. Any budget tiering must be deterministic and observable, matching the build's existing habit of naming state explicitly (the tier names above are a good model but the strings must be re-derived, not transcribed). The dispatcher prompt is already a fixed-cost asset, so a budgeted section must not disturb the existing six-tool instructions; a loading-or-absent state must fall back to today's behavior, never to a truncated prompt.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M for the skills half (a catalog type, a budget resolver with four tiers, and section wiring — the tier arithmetic is simple but the tier boundary conditions need tests); M for the MCP half on the same mechanics, but it is blocked on a scope ruling and is L in practice because the plugin must first be given something to discover. Risk on the skills half is low-to-medium: the mechanics are self-contained, but an over-eager catalog can crowd out the dispatcher instructions that are the plugin's actual purpose.
- **Key reference anchors:** the reference tree's `prompts/user-info-mcp-meta-instructions.ts` (discovery modes, proactive-inspection stance, mandatory schema inspection, truncation reporting, lazy-auth discipline; two instruction variants); its `prompts/user-info-mcp-catalog.ts` (server/tool catalog; "still loading" notice around lines 103–104); its `prompts/user-info-available-skills.ts` (environment filter, non-invocable and file-scoped exclusion, conditional section emission around lines 151–183); its `agent-skills-section.ts` (section structure); its `skill-catalog-budget.ts` (budget as a fraction of context limit, the four-tier set named at lines 34–37, description truncation, droppable-skill elimination loop, omitted-directory cap and notice).
- **Cross-reference:** the MCP machinery itself is filed separately as `(DD number pending, MCP machinery)`; this file covers only the prompt-side catalog and budget concern. Refer to it by that placeholder, not a guessed number.
