# DD-002 — Window placement persistence vs in-memory-only placement
- **Area:** UI shell / window chrome (A1)
- **Type:** missing-feature (the client has no way to save state yet)
- **Date:** 2026-09-23

## What the reference does

The reference persists its OS window's placement across launches via a dedicated main-process store. The reference tree's `source/electron-main/window-state-store.ts` defines a zod-validated schema — a versioned record holding the window's normal bounds (x/y/width/height) plus a maximized flag — and a launch-placement resolver re-derives the launch bounds from the persisted record: it picks the monitor work area with the largest rectangle overlap with the saved bounds, discards the placement entirely when the overlap is too small (under 100×40 px) or the work area is smaller than the 512×520 minimum (a named minimum-size constant), otherwise clamps the saved size/position into the chosen work area, and honors the maximized flag even when the bounds themselves are dropped. Disk I/O runs through the window-state store class, which serializes writes (one in flight, a trailing write coalesced) and routes parse/write failures to a failure-reporting callback instead of throwing. Net effect: close the app, reopen — the window comes back where you left it, on the right monitor, maximized if it was maximized.

## What the current build does

`src/client/floating-window-store.ts` (ticket 100, ADR-0021; resize/maximize ticket 105) keeps placement purely in memory. The header is explicit: "In-memory ONLY — no persistence is claimed: a reload starts closed at the default placement again (honest; the store records no storage of any kind)." The published state is `FloatingWindowState { open, openEpoch, x, y, width, height, maximized }` plus a closure-held `preMaximize` rect — no read or write of any storage anywhere; the store never even reads `window` (the viewport arrives as a parameter, with a 1280×800 fallback). Within one session the store is well-behaved: reopen puts the window back where it was (re-clamped against the live viewport), and a maximized window survives close/reopen maximized (reopen re-fills the *current* viewport; the remembered rect survives until restore). But a page reload loses all of it — default top-right placement, default 760×520 size. The launcher capsule (ticket 107, ADR-0022) carries its own position under the same rule: "no persistence is claimed."

## The deviation

The reference restores window placement (normal bounds + maximized flag) across application launches from validated disk state that accounts for the monitor work area; the build's floating window resets to default placement on every reload, with persistence deliberately absent — not forgotten, but never claimed. The missing capability is cross-launch survival of x/y/size/maximized, together with the restore logic that checks the saved values against the current work area, drops or clamps them when they no longer fit.

## Verdict: ASK-HUMAN

No recorded ruling covers window-placement persistence: ADR-0021 (the human decision that chose the floating window) fixes the extension point, the coexistence arrangement, and crash isolation, but says nothing about the placement lifecycle, and the store's "no persistence is claimed" is a note about what the code does not claim, written during tickets 100/105/107 — not a decision. ADR-0018's master rule (imitate the reference in entirety) pulls toward incorporating, yet its exception list does not settle it — A5's "persistence stays in dsh's session/job store; no second database" constrains *how* it could be added without saying whether it should be, and C19/U-D address other state entirely. Since the build's in-memory-only approach is a deliberate, documented choice rather than an oversight, reversing it is a real product decision; ask the human rather than picking silently. Note for that conversation: any persistence needs a new host-side storage path — the client is in-memory/DOM-only and has no channel to any store today — and that path must respect A5's rule that there is no second database; factor that into the effort/risk call.

## Incorporation notes
- **Where it would live:** a host-side storage path (an adapter/core channel in the `src/adapter`/`src/core` style, e.g. alongside the roster-channel storage pattern) holding a small validated record {x, y, width, height, maximized}; the restore decision itself goes in `src/client/floating-window-store.ts` as a pure "first-open placement" variant — validate saved bounds against the live viewport, clamp when they fit, fall back to default placement when they don't, re-fill if `maximized` — following the reference's restore-at-launch shape without copying it.
- **Constraints:** A5 (no second database — the record is stored through existing dsh persistence, not a new store); the store's purity rule (no `window`/DOM reads, so restore must re-clamp against the viewport parameter, exactly like the reopen path already does); ADR-0021's crash-isolation guarantee (a storage read/write failure must degrade to default placement, never take the window or the shell down — the reference's discipline of reporting failures instead of throwing is the pattern to re-derive); the anti-revival clause of cancelled ticket 73 (a new ticket with its own evidence — this DD plus that ticket — is required for any floating-window change of record).
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — all the clamp/fill math already exists in the store, but the host↔client storage channel for UI state does not exist yet, and the failure-degradation path needs its own offline-pinned tests.
- **Key reference anchors:** the reference tree's `source/electron-main/window-state-store.ts` — the zod schema (lines 5–24), the launch-placement resolver's work-area overlap resolution with the 100×40 minimum overlap and 512×520 minimum size (lines 26–86), and the window-state store's coalesced-write/failure-reporting I/O (lines 88–136).
