# DD-210 — Deep links: protocol registration, argv extraction, single-instance forwarding
- **Area:** A27 platform integration
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference desktop app registers its private URL scheme as the OS-level default handler for that scheme, packaged builds only, with the scheme also serving as the authentication redirect target and an in-code note that client and backend share one scheme contract (the reference tree's `source/electron-main/auth/auth-callback-registration.ts:39-56`; note at `:26-33`). A dedicated main-process deep-link controller receives candidate link strings from three entry points: the initial command line, the platform's second-launch argument path, and the macOS URL-open event (the reference tree's `source/electron-main/main.ts:354-370`; single-instance lock at `:248`). Candidate extraction filters the argument list by two prefixes — the private scheme and an HTTPS mirror on the vendor's web origin (the reference tree's `source/electron-main/deep-link/deep-link-controller.ts:3`; the reference tree's `source/shared/deep-link.ts:3`). Parsing validates against a three-route set — an informational route carrying a fixed topic parameter, a plugin-installation route carrying a plugin id, and a generic open route — each in a private-scheme and an HTTPS-mirror form, behind length, printable-ASCII, percent-encoding, and query-allowlist checks (the reference tree's `source/shared/deep-link.ts:4-22`). Accepted links are deduped within a two-second window, queued (bounded at 16 entries) while the renderer is not ready, dropped with a log when that queue is full, and always paired with a window focus (`deep-link-controller.ts:2,8,13`). Readiness is cleared on page-load start and on window close (`main.ts:340-341`); when the renderer signals ready, the queue is flushed and the links are dispatched over the host bridge (`deep-link-controller.ts:11`; dispatch wiring the reference tree's `source/electron-main/main-production-services.ts:493,559`; preload-side ready call the reference tree's `source/electron-preload/preload.ts:151`). Renderer-side consumption of the delivered intents is already covered by DD-015 and is not re-run here.

## What the current build does
Absent — no protocol registration, no command-line argument inspection, no link router, and no single-instance/forwarding path. A grep of `src/` finds no deep-link, protocol, argv, or single-instance reference at all, and there is no main-process module of any kind. `docs/surfaces.md:139` and `:188` record the current "no deep-link / no navigation interface" verdicts for the build's surfaces, and `src/client/overlay.ts:19-34` documents the application shell as an additive overlay entry inside the shipped client runtime — the plugin runs inside the host app's renderer, not as a packaged OS application.

## The deviation
The reference owns the whole out-of-band delivery path: OS protocol association, command-line/second-launch/URL-event reception, validation, dedupe, bounded queueing while the receiver is not ready, focus-on-arrival, and flush-on-ready. The build owns none of it and structurally cannot: protocol registration and OS link events require a packaged-app identity and a main process, neither of which the accepted application shell has. The in-window half — an internal "open dispatcher X" intent point that a click could target — is already scoped by DD-015, which explicitly ruled the OS-side half structurally impossible; this file is the main-process delivery path, not a re-run of DD-015's renderer subscriptions.

## Verdict: DO-NOT-INCORPORATE
ADR-0020 (draft, non-human-approved) excludes a native/Electron desktop shell as a PRD non-goal — no chasing the competitor apps' binary or UI parity (`docs/adr/0020-wrapper-shell-vehicle-own-frame-over-shipped-runtime-draft-nonhuman-approved.md:28`). DD-015 already recorded that the OS-side delivery half is structurally impossible in the accepted application shell — no OS process, no packaged identity — leaving only the in-window parts open (`reference-deviations/DD-015-os-intent-seams.md:20,22-23`). Deep-link delivery is the main-process part of exactly that OS-side half, so the same ruling covers it twice over. The remaining piece worth naming, without recommending it: the pending-queue rules — dedupe window, bounded queue while the receiver is not ready, flush on ready, readiness reset on reload/close — form a general pattern for delivering an out-of-band signal into a consumer that is not ready yet, and the build has no such consumer today.

## Incorporation notes
- **Where it would live:** Nowhere in the current application shell — it presupposes a packaged main process. If a shell were ever admitted it would be a small main-process link module plus a preload-side readiness signal feeding the renderer's intent point; today there is no main-process module, and none is invented (DD-015's constraint: no OS-facing API may be invented — the host owns those).
- **Constraints:** ADR-0020's non-goal bar; the floating-window application shell (ADR-0021, as amended by ADR-0022) has no OS process; protocol registration additionally requires a packaged, signed app identity the plugin cannot have inside stock dsh. The in-window intent point remains DD-015's open ASK-HUMAN question — this verdict does not settle it.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the controller logic itself is small (extraction, validation, dedupe, bounded queue, flush), but the blocking cost is the shell and packaged identity the authority stack excludes; not buildable in this application shell at any effort.
- **Key reference anchors:** the reference tree's `source/electron-main/deep-link/deep-link-controller.ts:2` (dedupe window, queue cap), `:3` (argument candidate extraction), `:8` (validate/dedupe/queue/focus/dispatch), `:11-12` (flush on ready; readiness invalidation and recent-acceptance pruning); the reference tree's `source/electron-main/main.ts:248` (single-instance lock), `:340-341` (readiness cleared on load start and on close), `:354-370` (second-launch path, macOS URL-open event, initial argument list); the reference tree's `source/electron-main/auth/auth-callback-registration.ts:26-33,39-56` (packaged-only protocol registration, server-contract note); the reference tree's `source/shared/deep-link.ts:3-22` (scheme plus HTTPS mirror, three-route validation); the reference tree's `source/electron-main/main-production-services.ts:493,559,930` (controller wiring, ready entry point, main-side facade); the reference tree's `source/electron-preload/preload.ts:151` (ready call).
