# DD-005 — Modal alert host vs inline two-press confirmations
- **Area:** UI shell / window chrome (A1) + sidebar management (A11)
- **Type:** behavior-delta (paradigm difference; partially designed)
- **Date:** 2026-09-23

## What the reference does
The reference has a general-purpose modal alert system. A per-client alert-controller factory (the reference tree's `frontend/src/recovered/features/window-chrome/app-alert/controller.ts`) owns a queue of alert requests: each request carries title/description/warning body, confirm + optional cancel labels, a pending label, an optional **secondary action that can itself be flagged destructive**, and an async perform callback. While that callback runs the dialog shows a pending flag; a thrown error or returned string is normalized into a visible failure field on the still-open dialog; cancel and Escape are refused while performing, queued requests settle in order on close, and dispose/reset settle everything `false`. The host renders it via the alert-host component (`ProductionRenderer.tsx:3434`).

Destructive intents use this system as modal alert dialogs with copy that states the consequences. Section delete carries a consequence-stating body explaining that child agents are reassigned rather than deleted (the reference tree's `frontend/src/recovered/features/conversation/workspace/sidebar-section-delete-confirmation.tsx`, copy in `sidebar-sections-state.ts`). Agent delete (the reference tree's `frontend/src/production/AgentDeleteConfirmation.tsx`) carries a deletion warning distinguishing group deletion (history destroyed, member agents survive) from single-agent deletion, shows a pending label while the async confirm runs, and on failure shows a role="alert" failure notice telling the user the deletion did not go through and to retry, with the dialog still open — Escape, outside pointer-down, and focus trap handled, cancel/confirm disabled while pending.

## What the current build does
There is no modal anywhere; confirmation is an inline **two-press armed window**. The state machine lives in `src/client/shell-store.ts`: `SHELL_DELETE_CONFIRM_MS = 4_000`, `ShellDeleteArmState` (one armed row at a time), and the pure reducer `shellDeletePress(state, sessionId, nowMs, windowMs)` — first press arms, second press inside the window confirms, expiry or arming a different row disarms. `src/client/shell.tsx` binds it in two places: the row delete button (armed label swap with a revert timer so the "confirm" label never outlives its window) and the right-click context-menu "Close dispatcher" item, which feeds the same reducer through the same arm state. The rationale is recorded in the code itself — the ticket-101 comment states the destructive-ish action must not fire on a single click, but "the codebase has no modal/toast seam and the shell adds none", so the armed window *is* the whole confirmation; the confirm branch adds "The host command's own result copy is the surface — nothing here claims success" (ADR-0010's rule that the UI shows only what the host actually reported, carried into UI copy). Ticket-106 comments in `shell.tsx` record the same discipline for the context-menu close.

## The deviation
The reference centralizes confirmation in a queued modal host with pending, failure, and secondary-destructive affordances plus copy that states the consequences; the build has no modal capability at all and confirms destructive actions through a per-row 4s armed window whose only failure surface is the host command's own result copy. Concretely lost relative to the reference: (1) no pending state — a slow delete looks like nothing happened; (2) no dedicated failure surface — errors surface (or not) through whatever copy the host command emits, not a persistent in-place alert; (3) no copy stating the consequences, of the "no agents are deleted / can't be undone" kind, attached to the armed label; (4) no secondary-destructive path. The build's choice is deliberate and recorded (ticket-101/ticket-106 comments), so this is a visible paradigm deviation, not an oversight — but the reference's honesty *properties* (pending, failure, consequences in copy) are not fully reproduced by the inline pattern.

## Verdict: ADAPT
No ADR rules on this paradigm precisely — a grep of `docs/adr/` for modal/armed/alert-dialog rulings returns nothing — so per the authority stack this rests on recorded ticket rulings (level 7, reversible) plus the code's own recorded rationale. Do not port the modal host: the ticket-101 ruling that the shell adds no modal or toast capability is a recorded deliberate choice, and importing the reference's whole alert machinery is an architecture decision only a human or ADR can make (that part would be ASK-HUMAN if proposed). But adapt the reference's honesty content into the existing armed-window pattern — armed labels that state the consequences, and an explicit failure/pending surface consistent with ADR-0010's "nothing here claims success" rule — which strengthens the build's own recorded design rather than reversing it.

## Incorporation notes
- **Where it would live:** armed-label copy and revert logic in `src/client/shell.tsx` (row delete, context-menu close); confirm semantics and window constant stay in `src/client/shell-store.ts`; any pending/failure surface would attach to the existing host-command result copy path the confirm branch already cites.
- **Constraints:** keep the pure, clock-explicit reducer shape (offline tests drive exact transitions, S8 — the offline test success criterion in the PRD); keep the single arm slot; never claim success the host command didn't report (ADR-0010's rule that the UI adds no claims of its own); do not introduce a modal or toast capability without a human ruling reversing ticket-101; any copy must be independently re-derived wording, not the reference's sentences.

- **Effort/risk:** S/M — copy plus a small pending/failure projection through existing store channels; risk is low because the reducer and tests already pin the state machine.
