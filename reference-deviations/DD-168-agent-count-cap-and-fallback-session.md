# DD-168 — Agent-count cap and fallback session minting
- **Area:** A20 session & durability
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference keeps its agents as resident, resumable sessions on disk, so a user's agent population is a growing collection rather than a set of transient processes. Its session-materialization module therefore carries two defences that only make sense against an accumulating population.

First, a hard population ceiling. The same module declares a per-user ceiling constant and a dedicated error class raised when that ceiling is hit; a helper reports whether the ceiling has been reached, and that helper is checked before a new session is created, so the refusal happens up front rather than after work has started. The ceiling check is not a bare count: when the count reaches the threshold the module first attempts to reclaim pruned placeholder records, then re-counts, and only refuses if the population is still at or above the ceiling after that reclaim attempt — i.e. the reference treats the cap as a soft boundary with a reclamation pass in front of it. The reached-the-ceiling predicate is surfaced on the session facade so callers (lifecycle and runtime layers) can branch on it, and the typed error is mapped to a distinct transport status at the gateway boundary rather than collapsing into a generic failure.

Second, fallback session creation. A materialization request that cannot produce a normal, freshly created session instead adopts an existing agent as a fallback: the reference offers a fallback-session creation entry point that walks the available agent records and tries to open each in turn, reporting a distinct diagnostic when a candidate fails to open and moving to the next. A separate fallback path supplies the identity of the first listed agent to an opener callback, throwing an explicit error stating that no fallback session is available when the listing itself is empty. The intent is that a request never simply fails for want of a fresh session if any usable resident session exists.

Third, serialized session creation. Because the population count and the session creation are two steps that must not interleave, the module funnels session creation through a serialization helper: each new-session call is appended to a promise chain so that session creation runs strictly one at a time, and the chain is advanced in a way that survives a rejected link (the next link runs regardless of whether the previous one resolved or threw). Both the plain creation path and the fallback-capable creation path go through that same serialization, so the cap check and the count it reads cannot be raced by concurrent requests.

## What the current build does
Absent, and absently so. The build has no per-user agent-count ceiling, no fallback-session concept, and no typed agent-limit error. A search across `src/` and `client/` for agent-count, per-user, agent-limit, and max-agents surfaces nothing; the only caps that exist in the build's core are unrelated to agent population — a peer-message character cap (`SEND_PEER_TEXT_MAX_CHARS` in `src/core/tools.ts`) and a delivery-redrive bound (`MAX_DELIVERY_REDRIVES` in `src/core/multitask.ts`).

The build does, however, bound worker concurrency — but by a different mechanism and in a different dimension. `src/core/multitask.ts` holds a live-worker index keyed by `(parentSessionId, streamKey)` and refuses a spawn whose stream key already has a live (non-terminal) worker; the documented invariant is "one stream has one worker," and a terminal worker frees its stream key for reuse. The same module extends that invariant across a restart via a set of held stream keys owned by workers that were live at crash time and whose state is unknown, so a resumed dispatcher still cannot put a second live worker on a stream it never resolved. The bound is therefore per (dispatcher session, stream key), not per user, and it is enforced at the spawn site in `src/core/tools.ts` via the `spawnWorker` tool definition, which gates the dispatch and then delegates to the core's spawn worker entry.

Crucially, this is not a count cap: the number of distinct stream keys a dispatcher may occupy is unbounded in the build, so the total live worker population is bounded only by how many distinct streams the model chooses to author. The relevant architectural difference is that the build's workers are per-task and transient — they terminate, and termination is what frees the stream key — whereas the reference's cap exists precisely because its agents are resident sessions that accumulate and never free an identity by finishing. The two mechanisms are not the same feature at different strengths; they constrain different things.

## The deviation
The reference maintains a per-user population ceiling with a reclamation pass, a dedicated typed limit error, and a serialized session-creation path, plus a fallback path that adopts an existing resident session when a fresh one cannot be produced. The build maintains none of these. The build's nearest analogue — the one-live-worker-per-stream-key invariant — is per (dispatcher session, stream key), permits an unbounded number of distinct streams, and is released by worker termination, so it does not cap any accumulating population and would not drop straight into a count-based refusal.

The deviation is architectural rather than incidental. The reference's cap is a consequence of its resident-session model: an agent exists as a durable identity on disk, so identities accumulate, so something must eventually refuse the next one. The build's workers have no such accumulation — a finished worker frees its stream key and leaves nothing that needs a count — which is why a population cap has nothing natural to count in the build as currently shaped.

## Verdict: DO-NOT-INCORPORATE
The capability is coupled to the reference's resident-session architecture, and the build's own architecture rejects that shape: the core language and persistence rules are settled at ADR-0001 and ADR-0018 exception A5 (persistence stays in dsh's session/job store; no second database), and the build's workers are transient per-task units rather than resident sessions. No recorded ruling names an agent-count cap, a fallback session, or a count-based refusal — I checked the ADR index and the PRD and found nothing directly on point, so this deviation is decided on the architecture the build already has, not on a ruling that covers it. The build's transience also already supplies a bound of its own kind — the one-worker-per-stream-key invariant, held session-scoped and across restarts — so the build is not unbounded in the way the reference's cap guards against; what remains unbounded is the number of distinct stream keys, which is a product-shaping question about dispatcher behaviour rather than a durability gap. On that reading, importing a per-user ceiling here would be inserting a guard for a failure mode the build's worker lifecycle does not produce.

Note that no resident-agent registry exists to count, so a cap would need something to count first.
- **Constraints:** Any future bounded-population work must not introduce a second database or a new persistence store (ADR-0018 A5).
