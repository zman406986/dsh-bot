# DD-081 — Rich tool-result cards (output/diff/status) vs compact toolview rows
- **Area:** message cards (A10)
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
The reference ships a dedicated result-card layer for the core coding tools (shell execution, file editing, and file writing). A pure projection module turns one tool-call record into a card snapshot with a real status machine — running / success / error / denied / rejected / cancelled / background — inferred both from an explicit status string (with aliases folded onto one value, e.g. a streaming or pending status folded to running, and a timeout to error) and from which branch of a one-of result payload is present (a permission-denied branch, a rejection, a failure-with-abort, a timeout/spawn error, or success). The snapshot carries the heading data (command for shell, path for file tools), the shell working directory, accumulated output text, an extracted diff, and streaming flags. A merge function folds successive updates, concatenating streaming output deltas onto the previous snapshot so partial output accumulates across events. Companion modules adapt the wire types and splice card state into the transcript stream (a wire-type adapter and a transcript-boundary adapter); the view renders it all as a collapsible card with a status chip and an aria-live output region plus a diff pre. The module's evidence comments tie the shapes to the host's agent.v1 ShellToolCall / EditResult / WriteArgs / ShellResult wire types.

## What the current build does
The build has no equivalent card layer for shell/edit/write results — those are host tools, and their rows fall back to whatever the stock host tool-call UI shows. The only custom tool rendering is the six dispatcher tools' own views (spawn_worker, check_workers, steer_worker, stop_worker, deliver_result, send_peer), registered in the shipped keyed `tool.call.toolview` slot. Each is a compact read-only row of label/value pairs: text is whitespace-collapsed and clamped to 160 chars, and the outcome field is reduced to a bare "ok" or the verbatim failure reason string. There is no output text, no diff, no working directory, no streaming accumulation, and no status mapping beyond that ok/reason pair. What structure the rows do show (worker id, roster rows with core-FSM status labels, delivered flag, peer target) comes from the tool's own result record, delivered to the client through the host's durable `tool/result` event using the `presentationMeta` mapping added in ticket 81.

## The deviation
The reference invests in first-class result cards for shell/edit/write — a seven-state status machine, streamed output accumulation, diff extraction, and cwd display — while the build deliberately renders only compact rows for its six dispatcher tools and leaves host tool calls to the stock row. The gap is real but mostly out of scope: the card kinds the reference models are host-owned coding tools, not dispatcher tools, and the dispatcher's own results carry no output stream, diff, or working directory to display. The portable ideas are the status vocabulary (beyond ok/reason), delta-merging across updates, and the pattern of parsing new payloads and falling back to the safe row, which the build already practices.

## Verdict: ADAPT
The build renders inside the stock host tool-call UI by design — richer cards depend on what data the host event window exposes, and the `presentationMeta` mapping (ticket 81) already carries structured fields into the durable `tool/result` record, so richer presentation for dispatcher tools can reuse existing data without new authority. But the reference's shell/edit/write cards target host-owned tools: registering those keys in the shipped slot would override shipped UI (the toolviews header rules this out unilaterally), and rebuilding host tool-result UI touches the PRD non-goal of rebuilding the dsh tool runtime's presentation. Adapt the pattern where the dispatcher owns the surface — e.g. a fuller status vocabulary than ok/reason for its six rows, built from the structured metadata — and route any desire for true host-tool result cards (or any key registration beyond the six dispatcher names) to the human per the authority stack.

## Incorporation notes
- **Where it would live:** an extension of `src/client/toolviews.ts` parsing plus `src/client/toolview-panel.tsx` rendering — richer status mapping over the existing records fed by `presentationMeta`; no new slot registrations, no card component for host tools.
- **Constraints:** never register a toolview key the shipped UI already covers (`cordis_define` / `cordis_run`, let alone host shell/edit/write keys) without a human ruling; toolviews stay read-only presentation rendering only what the tool call already carries (design-16 §3.4); payload deviations must degrade to the safe row, never throw; the compact-row clamp limit applies to anything new; core FSM vocabulary stays verbatim where reused.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the status-mapping and merge patterns are small pure functions, but each new field must be justified against what dispatcher tool results actually carry, and anything touching host-tool keys is a separate human decision.
- **Key reference anchors:** the kind/status union definitions and the alias-folded status inference in the reference tree's tool-results model module (`.../tool-results/model.ts`); the per-kind mapping from one-of branch to status; the delta-concatenating merge function; the tool-results view's collapsible card with status chip and aria-live output region.
