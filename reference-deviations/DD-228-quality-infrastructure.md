# DD-228 — Quality infrastructure: graph-aware audits gating the build
- **Area:** A29 cross-cutting surfaces
- **Type:** behavior-delta
- **Date:** 2026-09-23

## What the reference does
Quality is not a test suite in the reference; it is a family of standing audit scripts, each a pass/fail check with a configurable failure-severity threshold. The reference's own description of itself is the reason: it is a source-oriented reconstruction of a shipped macOS application, so most of its quality tooling exists to prove that a reconstruction is faithful and a packaged bundle is complete.

**A renderer-closure audit** (the reference tree's `scripts/audit-renderer-closure.mjs`). It walks the module graph from a declared clean entry and sorts every path into one of three groups — reachable, intentional developer/catalog/type-support infrastructure, or possibly missing from production — where the infrastructure group is a list of *exact paths* rather than namespace-wide patterns, and the file says so in a comment stating the policy and why (`:224`). Findings carry a severity; the script's exit code is set nonzero only when findings at or above the configured threshold remain (`:709-715`), so the threshold is an option, not a hardcoded zero. Findings are also written to a checked-in report (`:26`), which makes it possible to compare runs.

**A UI-provenance audit and a runtime-composition audit** (the reference tree's `scripts/audit-ui-provenance.mjs`, the reference tree's `scripts/audit-runtime-composition.mjs`). The composition audit is the more specific of the two: its exemption policy is *derived from a recovery manifest* rather than hand-maintained, so an exemption is an exact manifest path plus its byte size plus its digest, and — when a packaged output is being audited — plus its exact placement in the packaged archive (`:49-55`, reading the manifest at `:55-69`). That records provenance rather than acting as an allowlist: the exemption expires the moment the artifact's bytes change. It also cross-checks a runner-parity audit report and asserts a set of structural invariants in one fail-closed predicate (`:453`).

**Three final checks.** A publication-tree verifier (the reference tree's `scripts/verify-publication-tree.mjs`) exports the repository to a scratch archive and checks what a publication would actually contain; a packaging-fidelity diagnostic (the reference tree's `scripts/package-fidelity-diagnostic.mjs`) checks the packaged payload; and a native end-to-end check (the reference tree's `scripts/native-e2e-check.mjs`) launches the packaged application and returns a **three-valued** exit status — pass, fail, or prerequisite — mapped to exit codes 0, 1 and 2 at `:681`, where "prerequisite" means the check could not run because the package was never built (`:530`, `:541`, `:653`). The three-valued status is the interesting design decision: "I could not test this" is a distinct, honestly-reported outcome rather than a pass or a spurious failure.

**How the npm scripts connect them.** One script combines the two typecheck passes and the test run (`package.json:13`); the two packaging scripts both run that script before doing any packaging (`:18-19`); the publication verifier has its own entry (`:20`); the native end-to-end check is reached through the smoke command (the reference tree's `scripts/smoke.mjs:2`); and the two audits are called from the build path itself rather than added beside it — the build entry calls a clean-build module (the reference tree's `scripts/build.mjs:1,3`), which imports the composition audit (the reference tree's `scripts/clean-build.mjs:29,138`) and the renderer production build (the reference tree's `scripts/lib/clean-build.mjs:12`), which imports the closure and provenance audits (the reference tree's `scripts/renderer-production-build.mjs:11-12`). A failed audit therefore fails `npm run build`.

**Eight Node test files** (the reference tree's `tests/`, `node --test`, `package.json:23`) covering MCP exec payloads, inference-router transcripts, publication bootstrap and packaging, a reconstructed updater guard, router settings, and research archives — all reconstruction-specific subjects. The frontend carries **ten manifests** (the reference tree's `frontend/manifests/`), including immutable fingerprints and a public package closure lock.

## What the current build does
The offline suite is broad and real: 59 files under `test/`, every one of them on `node:test` over pure modules, invoked by a single `tsx --test` script (`package.json`, the `test` entry). There is a documentation-lint check (`lint:docs`) that chains three tools — `tools/doc-lint.mjs`, `tools/issue-index.mjs --check`, `tools/adr-index.mjs --check` — and it is a genuine check rather than a formatter: three exit codes (clean, findings, usage error), a data-driven rule registry, and a rule whose fixture coverage is enforced by the tool's own self-test, so a rule cannot be added without a fixture that fires it (`tools/doc-lint.mjs:1-22`). It also carries a path allowlist whose entries each require a written reason (`:6-8`) — the same exact-path exemption rule the build already applies, for documentation rather than for code.

What is absent is everything else. There is no `.github/` directory — no CI configuration of any kind. There is no graph-reachability audit, no orphan detection, no provenance or ownership audit, no packaging-fidelity check, no publication verification, no native end-to-end check, no failure-threshold gating, and no evidence manifests. `tools/` holds exactly three entry points (the doc-lint, and the two index checkers) plus a shared lib and the doc-lint fixtures. A search for reachability or orphan-code auditing across `tools/`, `src/` and `scripts/` returns nothing: the only hits are prose usages of "reachable/unreachable" describing runtime states in `src/core/liveness.ts` and `src/plugin.ts`, not a static analysis.

So the build's quality checks are: one test command and one documentation command, both pass/fail, neither aware of the module import graph. Nothing fails a build on orphaned code, unowned views, or packaging drift.

## The deviation
The deviation is not "the build has no tests" — it has a large, honest suite. It is a difference of *kind*, on two counts.

**First difference: per-file versus whole-codebase.** Every one of the build's 59 test files is a unit test over a module, written by whoever wrote the module. None of them can see the whole. A module that nothing imports passes its own test forever. The reference's closure audit is the only tool in this comparison that asks about the whole import graph, and it is precisely the question a per-file suite structurally cannot ask.

**Second difference: enforced versus advisory.** The build's check commands are pass/fail, but they answer only "do the things I wrote tests for still work". There is no standing audit whose subject is the codebase's *shape*, no report file recording the shape at a point in time, and no threshold rule governing how much drift is tolerated.

The honest accounting of the reference's tooling, though, is that most of it comes from its unusual situation and does not transfer:

- **Packaging and publication machinery does not transfer.** The publication-tree verifier, the packaging-fidelity diagnostic, the native end-to-end check with its prerequisite state, and the part of the composition audit that checks placement inside a package all exist to prove that a *recovered* frontend, reassembled into a macOS application bundle, is complete and faithful. The build is a source-distributed TypeScript plugin: `files` ships `lib`, `client`, and the README; the client surface is one bundled script produced by a small esbuild step. There is no recovered tree, no archive assembly, no bundle, no codesigning, and no publication artifact. The prerequisite state — the single best idea in the native check — exists because a macOS launch test is unrunnable on a machine without a built package; the build has no such test to be blocked.
- **The provenance-chain exemptions do not transfer.** Path plus size plus digest plus packaged placement is the right rule for exempting files that must be byte-identical to a shipped original. The build exempts nothing by digest because it has no originals to be identical to.
- **The evidence manifests do not transfer.** They are provenance records for recovered UI, meaningful only inside a reconstruction workflow the build does not run.
- **The eight test files do not transfer as subjects.** MCP exec payloads, inference-router transcripts, publication bootstrap, a reconstructed updater guard, router settings, research archives — the build has none of these subsystems, and its own suite already covers the modules it does have.

**Two ideas do transfer, and they are worth naming.**

1. **The audit for code nothing reaches.** A plugin with worker/adapter/core layers plus a separate client surface, distributed as a package with a declared entry, has a real and specific failure mode: code that nothing reaches. The build is unusually exposed to it, because ADR-0018's exception list rules out a substantial number of candidate features — and the correct outcome of ruling a feature out is that the code for it should not be there. A module written under one reading and left unreachable by the next ruling will sit in the tree, passing its unit test, invisible to every check the build runs.
2. **Exact-path exemptions with a count threshold.** The reference's rule is that an exemption names one path, never a namespace, and that the check fails only above a count. Both parts matter and they serve different purposes: the exact path is what keeps an exemption from silently absorbing new findings, and the threshold is what makes an audit usable over time, since an audit that must be at zero before it can be turned on never gets turned on. The reference needs the threshold because it inherited a large legacy finding count; the build would need the *configurability*, not a nonzero default — its exemption list should start empty, one written reason per entry, in the same shape the doc-lint allowlist already uses.

## Verdict: ADAPT
No recorded ruling names quality tooling, and none of ADR-0018's enumerated exceptions reaches it — this territory is unruled, and the verdict is argued from nearby recorded points rather than from a decision that covers it. What *is* recorded is the practice: PRD §4 S8 makes offline unit testing a success criterion, milestone M1 gates on it ("S8 green", `PRD-dsh-multitask-dispatcher.md:381`), §12 lists the test layer matrix, and the rulebook records that npm drives typecheck, offline tests, and the build (`docs/agents-rulebook.md:61`). That recorded practice is why DO-NOT-INCORPORATE is defensible — but it is incomplete, because none of those records asks what *nothing* reaches, and the build is a plugin whose exception list has ruled out many candidate features, which is exactly the condition under which modules get written and then left unreachable. ADAPT therefore limits this to two transferable pieces: a reachability audit rooted at the plugin entry and the client entry, and the rule of exact-path exemptions with a configurable threshold — importing none of the packaging, publication, or provenance machinery, all of which exists because the reference is reconstructing a shipped application.

## Incorporation notes
- **Where it would live:** a new `tools/reachability.mjs` beside `tools/doc-lint.mjs`, in the same shape as the existing check — a data-driven config block (roots, exclusions, exemptions), a rule registry, and fixture coverage enforced by a self-test, with `tools/fixtures/` extended by a sibling folder. Run as its own npm script and appended to the existing `lint:docs` chain, or as a parallel `lint:graph` script if the two are to be runnable independently. Its report file, if any, belongs beside the doc-lint's output rather than in a new committed directory.
- **Constraints:** derive reachability from tooling the build already runs rather than writing a parser — the client bundle's esbuild step can emit a metafile naming every module it actually pulled in, which gives a reachable set for free, and the host `tsc` build already resolves the import graph for the plugin entry, so the audit should read those rather than reimplementing module resolution. Roots are the plugin entry and the client entry; the build outputs (`lib/`, the generated `client/index.js`) and the test tree are excluded by construction, or the audit fires on its own artifacts on every run. Exemptions are exact paths with a written reason each, matching the doc-lint allowlist precedent (`tools/doc-lint.mjs:6-8`); no globs, no namespace entries. Any severity threshold is a named constant with a written reason, never a literal at the call site. The audit must not become a CI platform: the build has no CI today, and adding one is a separate decision this file does not make — a local `npm run` script is the whole of the proposal. The question the audit asks is about *module* reachability, not about whether a module is *correct*; it must not be allowed to drift into a general static-analysis suite.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the client part is small if the bundler's metafile is used, but the host-side graph, the exemption mechanism, the fixture self-test, and the exclusion rules make up a complete check, and the ongoing cost is the work of maintaining exemptions as the tree changes. The risk is a stream of false positives: an audit that fires on legitimately-unreferenced modules (type-only modules, the client surface's own entry) will be switched off within a week, which is why the exclusion rules have to be designed before the audit is turned on rather than after.
- **Key reference anchors:** the reference tree's `scripts/audit-renderer-closure.mjs` — exact-path infrastructure policy `:224`, three-bucket classification and the checked-in report `:26`, configurable severity threshold and exit code `:709-715`; the reference tree's `scripts/audit-runtime-composition.mjs` — manifest-derived exemption policy `:49-55`, manifest read `:55-69`, fail-closed structural predicate `:453`; the reference tree's `scripts/native-e2e-check.mjs` — three-valued status and exit-code mapping `:681`, prerequisite returns `:530, 541, 653`; the reference tree's `scripts/verify-publication-tree.mjs`; the reference tree's `scripts/package-fidelity-diagnostic.mjs`; the reference tree's `scripts/smoke.mjs:2`; the reference tree's `scripts/build.mjs:1,3`; the reference tree's `scripts/clean-build.mjs:29,138`; the reference tree's `scripts/lib/clean-build.mjs:12`; the reference tree's `scripts/renderer-production-build.mjs:11-12`; reference `package.json` scripts block `:13, 18-20, 23`; the reference tree's `tests/` (eight files); the reference tree's `frontend/manifests/` (ten manifests).
