# DD-225 — Accessibility infrastructure: live-region announcements and focus management
- **Area:** A29 cross-cutting surfaces
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
Accessibility in the reference is infrastructure rather than per-screen polish, and announcement policy is chosen per surface. Transient status text is wrapped in polite live regions carrying an explicit status role — a progress banner that pairs a label with a polite status role (`reference material-NOT LICENSE SAFE DONT COPY-grok bot/frontend/src/recovered/features/computer/rebuild/banner.tsx:134`), with the same shape on field-level validation messages and loading indicators (`.../ui/sand-form-primitives.tsx:45`, `.../ui/sand-status-primitives.tsx:56`). Failures are raised on the assertive channel instead (`.../production/ProductionRenderer.tsx:194`), and a plain polite status region carries the running-status label (`:542`).

The most interesting piece is the streaming case. A live output region is declared as a log role with an additions-and-text relevance scope and a liveness value that is polite while the stream is running and switched off once it ends, so incremental output is announced as it arrives but the completed block is not re-announced in full (`.../features/conversation/tool-results/view.tsx:52`; the same switch plus keyboard reachability on the terminal output region, `.../features/terminal/output/view.tsx:41`). The transcript container follows a related policy with liveness off by design (already filed as DD-038).

Focus is actively managed by shared primitives rather than ad-hoc element grabs. An overlay primitive records which element held focus before the layer opened, moves focus to an initial target or the first focusable descendant with scrolling suppressed, wraps Tab at both ends of the focusable set (and focuses the panel itself when the set is empty), then on close restores focus to the recorded element if it is still connected (`.../ui/overlay-primitives.tsx:232-250`, wrapping at `:270-285`). The floating-layer primitive applies the same focus rules behind an explicit return-focus flag, suppressing scroll on both capture and restore (`.../ui/sand-floating-primitives.tsx:116-144`, focusable surface at `:190`). Composer-focus requests are routed through named handlers rather than DOM lookups: the window-chrome shortcut registry declares a focus-prompt callback in its handler interface and binds it to a hotkey (`.../features/window-chrome/global-keyboard-shortcuts.ts:34,51`; the composer-side controls channel is DD-057's subject). Reduced motion is handled the same way across the product too — the preference is honoured across a broad set of style modules, not one rule.

## What the current build does
No announcement infrastructure and no focus management exist. A grep of `src/client/` for `aria-live`, `aria-relevant`, and `tabIndex` returns zero matches; the same grep for programmatic focus calls, an autofocus attribute, or a focus-trap helper also returns zero.

What ARIA exists is static: accessible-name labels on a handful of controls (`src/client/conversation.tsx:206`, `src/client/floating-window.tsx:308,317,618`, `src/client/shell.tsx:457,469,660,760`), two pressed-state toggles for the floating window (`src/client/floating-window.tsx:307,617`), expanded-state attributes on the settings card and the shell disclosure (`src/client/settings-card.tsx:239`, `src/client/shell.tsx:507`), and hidden markers on decorative nodes (`src/client/onboarding-pane.tsx:111`, `src/client/panel.tsx:176`, `src/client/settings-card.tsx:116`, `src/client/shell.tsx:399,443`). The only role attributes anywhere in the client are two status paragraphs in the settings card — a read-only notice and a save-failure line (`src/client/settings-card.tsx:261,277`). Those are implicit polite live regions, but a static usage rather than a managed policy: nothing sets or clears a liveness value, nothing coordinates an announcement with stream state, and no other surface announces anything at all.

The only keyboard handling is the composer's Enter family (`src/client/conversation.tsx:210`) and the shell's menu dismissal, which closes on Escape, an outside pointer-down, or scroll (`src/client/shell.tsx:584-596`) — nothing moves or restores focus. Reduced motion is handled in exactly one place with one rule for one animation (`src/client/panel.tsx:93`; the comment at `:35` scopes it to that element). Earlier filings already recorded the specific a11y fixes in this neighborhood — a mislabeled accessible name (DD-059), transcript log semantics (DD-038), a busy marker (DD-031), composer focus management (DD-057); this file is the layer beneath all of them.

## The deviation
The reference treats accessibility as a layer — an announcement policy chosen per surface, shared focus primitives, and reduced-motion handling applied across the product — while the build has static attribute labels and nothing that manages announcements or focus. Two mechanisms make up the gap. First, the streaming log region whose liveness is switched off at stream end: announce incremental output while it is live, never re-announce the finished block. Second, focus restoration: record the previously focused element when a layer opens, restore it when the layer closes, and suppress scrolling at both points. Honest scoping: the build's surface is small — a floating window with a conversation pane, a roster panel, a settings card, and an onboarding pane — so the scope of the gap is smaller than in a full application with dozens of dialogs, and a general focus-trap framework would be too large for it. But the build's conversation pane is exactly a live-updating feed the user is meant to watch, so announcement behavior there is a real gap, and the dismissal paths that do exist (the shell menu, the floating window's overlay) currently drop focus with no restoration.

## Verdict: ADAPT
No recorded ruling covers this layer across the whole client: the authority stack's nearest touchpoints are ADR-0018's imitation standard with its B9 re-derivation clause and the ticket 36/40 ruling that the draft-entry connection point stays text-only (DD-057) — neither rules on announcements or focus infrastructure, and the peer filings' reasoning (DD-038's INCORPORATE for additive transcript attributes, DD-059's INCORPORATE for a label fix, DD-057's ADAPT for focus behavior) is consistent with taking these two mechanisms. ADAPT rather than INCORPORATE because the transferable content is two mechanisms at the build's scale, not a framework: the streaming liveness switch belongs on the conversation pane's own live-feed rendering, and focus record/restore belongs on the dismissal paths the build already has, re-derived inside the components that own them rather than added on as a shared focus-trap layer. This file must stay the cross-client layer and must not re-open the pieces already filed — DD-038's transcript log semantics, DD-059's field label, DD-031's busy marker, DD-057's composer focus channel — and any focus control must respect the ticket 36/40 ruling by staying inside the owning component. If the human reads the small surface as not justifying even these two mechanisms, that is a scope decision the human owns rather than a silent drop.
