# DD-042 — Mermaid diagram rendering + viewer vs literal fences
- **Area:** rich rendering (A5)
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference transcript treats a fenced code block tagged `mermaid` as a diagram, not code: the block routing (the reference tree's `frontend/src/recovered/features/conversation/workspace/transcript.tsx:455`) sends the mermaid language tag to a diagram component in the reference tree's `frontend/src/recovered/features/conversation/workspace/mermaid.tsx` and falls back to a plain code figure otherwise. That component lazily loads a vendored mermaid core asset (asset fingerprints pinned in the reference tree's `frontend/manifests/` — `mermaid-immutable-fingerprints.json`, `mermaid-public-candidate-lock.json`, `mermaid-public-package-closure.json`), initializes it with `startOnLoad: false`, `securityLevel: "strict"`, a light/dark theme mapping, and `fontFamily: "inherit"`, and keeps renders behind a bounded cache plus a serialized render queue. A diagram that fails to parse falls back to the plain code figure. On success the diagram shows inline with an expand button that opens a portal viewer supporting wheel/pinch zoom clamped between 0.1x and 8x (a min/max zoom constant pair), pointer pan, and Escape-to-close with stopPropagation. The reference prompt inventory records this display as part of the reply-format contract ("markdown/KaTeX/mermaid rendering contract", `docs/research/reference-agent-prompt-inventory.md:117`).

## What the current build does
Nothing. A repo-wide case-insensitive search for "mermaid" across `src/` and `client/` returns zero matches, and the build's web surface (`client/index.js`, a single ~207 KB file) contains no fence or markdown rendering machinery at all — fenced blocks, whether tagged mermaid or not, arrive as literal text lines. There is no diagram component, no vendored mermaid asset, no manifest, no viewer.

## The deviation
A whole rendering surface exists in the reference and is entirely absent in the build: agents that emit ```mermaid fences produce inert text here. This is a clean missing-feature gap, but the authority stack has already ruled on this area — ADR-0020 records the area-9 rich-chat-ergonomics row (find-in-chat, threads, reactions, drafts, attachment viewers, URL cards) as **excluded U-B**, and ADR-0018's rule 13 (U-B) states the no-rich-chat-ergonomics bar. Mermaid rendering is not named word for word in either list, but it belongs to the same rich-rendering area (A5) the exclusions cover, and the reference's own inventory ties it to the same reply-content contract as the other excluded ergonomics.

## Verdict: DO-NOT-INCORPORATE
ADR-0018 is the top accepted human ruling and its U-B rule, expanded by ADR-0020's area-9 exclusion rows (the rich chat ergonomics table), closes the rich-rendering area this feature lives in; the authority stack settles rather than re-opens, so mermaid rendering stays out unless a human amends the ruling. Two constraints frame any future reversal discussion. First, the reference's diagram path depends on a vendored third-party core with pinned asset fingerprints, which raises the vendored-dependency policy question — that policy decision does not yet exist in this repo and would have to be made before any incorporation, independently of this feature. Second, the viewer's pan/zoom interaction styling must respect the build's no-animation CSS discipline (transitions and motion are avoided in this codebase's rendering surfaces), so a port could not copy the reference's interaction feel wholesale even if the feature were admitted. Also worth noting: the PRD itself uses mermaid fences in its own documentation, which is unrelated to shipping a runtime renderer and does not imply one.
