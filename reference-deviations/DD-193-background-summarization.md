# DD-193 — Background summarization with multiple trigger modes
- **Area:** A24 context management
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
Alongside its summarization handler, the reference's summarization package carries a small, self-contained scheduling module (62 lines) whose whole job is to decide *whether* a summarization pass runs, *whether the caller waits for it*, and *whether the result is kept*. It exposes four modes governing the call shape: fire in the background and do not wait; fire in the background and persist the result if it completes; wait for completion; and wait for completion only when a run has already started. Firing is threshold arithmetic over caller-supplied token counts. A trigger level is derived from up to two independent signals — an absolute count of unused tokens, and a percentage of the unused window — each converted into a used-token level, with the earliest (minimum) candidate winning; a non-positive maximum-token value, or no configured signal at all, disables triggering entirely. Persistence has its own separate gate: a result is kept only when triggering fired *and* the room remaining is at or below a second configured limit, itself expressible either as an absolute token count or as a fraction of the window. A named disabled configuration — all four thresholds unset — serves as the off switch, and a further flag controls discarding the result on error. The module makes no model calls and reads no transcript; it is pure arithmetic over numbers the caller passes in, which is what lets summarization run without blocking the caller.

## What the current build does
**Absent**, and absent twice over. The build does not summarize conversation context at all — that is DD-192's finding, and this item is its scheduling half, not a second mechanism. With no summarization pass to schedule, there is no trigger, no wait mode, and no persistence gate.

What the build does have in the same area:
- **A task-oriented worker fleet.** `src/core/multitask.ts` spawns, steers, and stops delegated workers against a worker state machine, and `src/core/wake-bus.ts` delivers their outcomes as wakes. That background work is task-oriented: each worker exists to complete a delegated job and settle. It is not maintenance-oriented upkeep of the dispatcher's own context, which is the shape the reference's scheduler exists to drive. A direct search of both files for summarization or compaction vocabulary returns nothing.
- **A reserved trigger channel, unused.** `src/core/wake-bus.ts:8-30` accepts a timer source and an external-event source in its wake vocabulary so later tickets can enqueue them without changing the vocabulary — but only user turns, settled workers, access requests, and peer messages actually produce wakes at this stage. So the bus is where a periodic trigger *would* arrive if the build ever had maintenance work to trigger; nothing produces one, and nothing consumes one.
- **Inline, deterministic upkeep instead.** The build's real context hygiene is report clamping (`src/core/report-clamp.ts`, bounded as recorded by DD-192), which runs inline and synchronously and is never a background pass.

## The deviation
This is the scheduling half of a mechanism that the build's architecture assigns to the host. In the reference, the summarizer and its scheduler belong to the same product; in the build, the conversation, its window, and its token accounting are dsh's, and the plugin never sees the conversation nor the counts the threshold arithmetic consumes. The deviation is therefore not simply a missing module — the module's *inputs* are host data, so there is nothing on the build's side of the boundary to threshold against. What is genuinely separable is a design idea rather than a capability: maintenance work can be triggered from several independent signals, combined by taking the earliest, with a distinct second gate deciding whether the result is kept, and a caller-visible choice of whether to block. That idea does not depend on summarization — it is a scheduling pattern — but the build could not adopt it *for summarization* without owning the conversation, and it has no other maintenance workload of that shape to point it at.

## Verdict: DO-NOT-INCORPORATE
This follows DD-192, its parent finding: the mechanism is host-owned and the underlying data is absent, so the scheduling half inherits the same disposition. No recorded ruling covers this item, and that is verified rather than assumed — ADR-0018's exception list (`docs/adr/0018-imitate-reference-in-entirety-exception-list.md:19-42`) is exhaustive, a direct search of that file for summarization or compaction vocabulary returns nothing, and there is therefore nothing on the list to overrule; the nearest recorded rulings are exception 17 (U-F, `:39`), which fixes the build's context hygiene as clamping inline rather than spilling outputs to storage with prompt-side references, and exception 10 (D21, `:32`), which approves the clamp bounds themselves. Because the host owns the conversation, its window, and its token accounting, the threshold inputs this scheduler consumes do not exist on the build's side of the boundary, and a plugin reaching for them would be doing the host's job — the same `approved-by-necessity` shape DD-192 identified for the summarization mechanism itself. If the team ever wanted a register item here, it would require a new human ruling, since nothing on ADR-0018's list covers it.

## Incorporation notes
- **Where it would live:** Nowhere for summarization — no build-side code owns the conversation or its window, so there is no boundary to trigger across. If the *scheduling pattern* alone were ever wanted for a build-owned workload, the nearest existing home is the wake bus (`src/core/wake-bus.ts`), whose vocabulary already reserves a timer source and whose source list is the build's event vocabulary; but no build-owned workload currently has the maintenance-pass shape, so that is a note about where it would go, not a proposal.
- **Constraints:** The build is a plugin inside dsh; the host owns the conversation, the window, and token accounting, so the build can neither observe usage nor run a pass over the transcript. Any trigger the build did own would have to threshold over build-owned state, and any numbers would have to be derived from build-side measurement rather than borrowed from the reference's defaults — borrowing the arithmetic without the matching data would produce a threshold with nothing to measure.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — no implementation is proposed; the item closes as a documented absence. The one transferable idea (multi-signal trigger, earliest-wins combination, separate persist gate, caller-visible wait choice) is recorded here as a design pattern rather than opened as work.
