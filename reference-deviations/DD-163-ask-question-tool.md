# DD-163 — Ask-question tool: multi-question support and anti-nag behavior
- **Area:** A19 tool surface
- **Type:** missing-feature
- **Date:** 2026-09-23

## What the reference does
The reference ships a first-class ask-question tool in its core tool set: a general-purpose channel the agent uses mid-task to put substantive questions to its user. Two properties matter here.

First, one call carries more than one question. The tool's argument shape holds a collection of question entries, each entry carrying its own identifier, the question text, a set of candidate answers the user may pick from, and a per-entry flag for whether more than one candidate may be selected at once. The tool's serialized result mirrors that shape one-for-one: each question in the request comes back as its own answer record, so a single invocation yields a per-question result list rather than one answer to one question.

Second, the tool blocks a question asked as the very first move of a task. When the model calls the tool as its very first action, before it has consulted the codebase or the filesystem, the call is refused rather than surfaced to the user. The refusal is not a user-visible rejection — it is delivered back to the model as a tool error explaining that it must research first, that the tool is not for confirming details, soliciting feedback on proposals, or asking for confirmations, and that it may only be called again where the need is genuine (a destructive action, a major architectural decision, or a user-requested workflow) — together with an instruction not to mention the refusal to the user. The refusal is recognized by its text: the same error string is matched on the result-formatting side and swapped for the fuller guidance shown to the model. Auto-answered questions are distinguished from genuine refusals in a separate predicate, so only the reasons that mean "the user declined" suppress the receipt rather than every rejection. The tool also supports an asynchronous mode in which questions are dispatched to the user and the agent is told to keep working on current information until the answers arrive as a later tool result.

## What the current build does
The build registers six dispatcher tools and nothing else: spawn, check, steer, stop, deliver, and peer-send. There is no tool by which the agent asks its user a question.

The build does have the host's optional interface for asking the user structured questions, but that interface is used only by the permission flow, not by the agent. The access-prompt surface uses the host's existing structured-question service to present a pending access request — an allow / always-allow / deny choice — and routes the answer back into the unchanged core relay that a conversational answer would use. It is explicitly presentation-only: it re-implements none of the relay's timeout, decision, or delivery logic, invents no new prompt pathway, and preserves the deny-by-default timeout when the prompt goes unanswered, dismissed, or unknown. The host exposes that interface; the build does not offer it to the model as a tool.

Workers are denied the host's ask-question tool outright. The worker barrier's deny-candidate list names it under user messaging and delivery alongside the present/send-to-user tool, and the barrier intersects those candidates with the tool names actually registered globally before handing the deny list to the host.

The two surfaces are therefore different in kind. The build's access prompt is a permission flow: it fires when the dispatcher needs the user to authorize an action, it presents a fixed allow/deny choice set, and it is wired to a relay with a fail-closed timeout. The reference's tool is a general channel: the agent composes the questions, chooses the options, may ask several at once, and the answer is an ordinary tool result that the agent reasons onward from.

## The deviation
The build has no general ask-the-user channel for the model. What it has is a permission-relay presentation layer that borrows the same host service for a narrow, non-agent-authored purpose. The deviation is therefore not "the host lacks a user-questions capability" — it does not — but that the build never surfaces that capability as a model tool with agent-written questions, several questions per call, or the first-move refusal guard.

Consequences worth naming. A dispatcher that needs one decision it genuinely cannot derive has no clean way to get it: its only affordances are to deliver text and hope for a reply, to stall, or to assume. The build's own design leans on assumptions at exactly this point — the worker prompt is required to be self-contained and the worker does not see the chat, so any missing detail becomes an assumption baked into the work, and mistakes surface late as worker reports rather than early as a question.

The behavior that refuses a question asked as the first move does not transfer as a self-contained feature. In the reference it is implemented but its trigger lives in the model-facing prompt and tool-name surface, which is also why the reference could make it a fixed input-shape refusal rather than an evaluative check.

## Verdict: ASK-HUMAN
No recorded decision covers this. The PRD governs the dispatcher's posture and A19 governs the tool surface, but neither names an ask-question tool, and no ADR addresses model-authored questions to the user. The nearest recorded rulings are related but do not settle it: ADR-0008 settles that access asks are deny-by-default with a timeout and that the core relay owns that semantics, and the ticket-70 peer-message work rules that workers are leaves of the peer tier — both constrain an ask surface without deciding whether one should exist. This is a product-scope call about whether the design's stated posture (stay responsive, dispatch work, report back, never block) makes a blocking question channel unnecessary, or whether its absence just forces assumptions. The PRD partly answers it and does not settle it — that is a human ruling, and it should be made before any incorporation work.

## Incorporation notes
- **Where it would live:** A new model-facing tool definition alongside the six dispatcher tools, delegating to the host's existing structured-question service through the same optional host interface the access-prompt surface already reads. The access-prompt module is a precedent for using that interface, not the home for a second consumer — a general channel carries questions from the agent outward, whereas the permission flow carries a prompt from the build outward to the user — so they should be separate surfaces sharing the interface.
- **Constraints:**
  - The host interface is currently read structurally rather than by importing the shipped question service; any new consumer must keep that structural-only posture rather than taking a hard dependency.
  - The access prompt's own invariants are not to be disturbed: it is presentation-only, invents no prompt pathway, and preserves the deny-by-default timeout. A general ask channel must not claim the conversation-detail slot that the shipped code owns and that this surface is forbidden from touching.
  - Workers are denied the host ask-question tool by the tool barrier; a dispatcher-level channel does not change that, and because the barrier only denies names that are actually registered, a new tool name is denied only once a deny list already names it.
  - The guard that refuses a question asked as the first move needs a trigger. The reference's trigger is a fixed property of the model-facing surface; reproducing the behavior here means deciding what "the agent opened with an interrogation" means for this build's tool surface before writing any guard.
  - A blocking ask reintroduces a stall path into a design built around not stalling; whether the answer is a bounded wait, an async hand-off, or no channel at all is part of what the human ruling must settle.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** M — the plumbing is modest because the host interface already exists and is already used once, but the design question (does a question channel belong in a dispatch-first posture at all, and if so does it block) is unresolved and larger than the code.
