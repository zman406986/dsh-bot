# DD-224 — Runtime theming: dual-mode token installer vs the build's host-token-only doctrine
- **Area:** A29 cross-cutting surfaces
- **Type:** deliberate-divergence
- **Date:** 2026-09-23

## What the reference does
The reference owns its entire appearance layer in a dedicated runtime installer module (the reference tree's `frontend/src/recovered/features/runtime-theme-token-installer.ts`, recovered from a shipped renderer bundle and pinned to that bundle's digest at `:1-5`). The module declares the mode space (a two-member light/dark union, `:6`), a theme class per mode (`:11`), and a mode-value union in which any single token may be either a plain string or a per-mode pair (`:15`) — so one table can carry both mode-invariant values and values that differ between schemes. It then ships several token tables: a core palette of 130 entries (`:17`, with an exported count constant asserting that number at `:14`), an alias mapping that remaps the app's own variable namespace onto a shared token namespace (about 59 entries, `:19`), and a further per-mode token table (32 entries, `:20`) alongside a 54-token-per-mode data/gradient/blur scale (`:18`). CSS is generated from those tables rather than hand-written (`:21-28`), with the shipped light/dark output frozen as a literal as well.

The installer itself is deliberately defensive. It refuses to run against an absent or incomplete document — no document object, or one missing its root element, head, element factory or lookup, raises rather than half-applying (`:30`). Applying a mode writes exactly one style element into the document head (reusing an existing one if present), sets the root data attribute to that mode's theme class, and sets the root color-scheme property to the mode name (`:31`). The install handle it returns exposes an update operation and a dispose operation, tracks the element it created, and on dispose removes that element only if it is still the one in the document — so a second installer's element is never torn down by the first — guarded by a disposed flag that makes both operations idempotent (`:32`). Alongside the tables the module pins immutable per-mode snapshot hashes for the generated palettes (`:12`) and the renderer asset's own digest (`:13`), so a drifted palette is detectable by comparison rather than silently rendered.

On the main-process side theme is a first-class persisted setting: a controller reads the stored preference at construction and pushes it into the native theme port, exposes state and a setter, broadcasts on native theme updates, and removes its listener on dispose (the reference tree's `source/electron-main/prefs/theme-controller.ts:25-63`); a resolved-mode-to-window-background table lives beside it (`:16-23`).

## What the current build does
The build takes the opposite approach *by design*: it owns no appearance layer at all. Every surface is required to resolve colour through the host's shared token namespace (`--dsw-*`) and is forbidden from defining a private palette. The contract is written into the style headers of the surfaces themselves — the roster panel's colours are each "a host design token (`--dsw-alias-*`), inherited from the shell's theme stylesheet" (`src/client/panel.tsx:65-67`), the settings card borrows the shipped card's own vocabulary (`src/client/settings-card.tsx:21-31`), the shell records "ticket 49's contract — no private palette" and that the shell inherits the host's theme colour (`src/client/shell.tsx:65-67`), and the floating window records that theme survives the portal because the alias tokens are defined host-side and that every colour is a host token with no private palette (`src/client/floating-window.tsx:40-44, 71, 113`).

That contract is machine-enforced, not merely documented. `test/client-theme-tokens.test.ts` pins, per surface: that no raw colour literal may appear at all — hex, bare rgb()/rgba() or hsl() (`:50-54`); that every colour resolves through a token in the host's alias/elevation namespace and nothing else (`:56-66`); that no token is given a hex fallback, since a fallback would let the rejected private palette back in and make the contract optional (`:68-72`); that the high-contrast label token is never misused as an accent (`:74-83`); and that the token set each surface references is *exactly* the documented mapping, asserted by deep equality against an explicit roster (`:86-114`). Its header states the rule and the reason together: the surfaces "must style themselves from the host's shared design-token layer, not from a private palette", and because the tokens are ordinary custom properties defined host-side, "a surface becomes theme-correct simply by referencing them — no service, no subscription, no boot-graph edge" (`:1-19`).

So the build is theme-correct only for whatever theme the host is already in. There is no mode model, no runtime installer, no theme preference setting, no light/dark toggle, and no palette of its own.

## The deviation
Ownership of the appearance layer, and the mechanism that keeps it honest. The reference owns appearance because it owns the application: it defines both schemes, generates the CSS, installs it at runtime, drives the root attribute and color-scheme, and can therefore offer a theme preference as a product feature. The build deliberately delegates appearance to the host and enforces that delegation with an offline test, which buys consistency — the plugin can never look foreign inside the host, because it has no colours of its own to be foreign with — at the cost of autonomy: it cannot offer a theme toggle, and it renders only as correctly as the host theme does.

The constraint is the interesting part, and it is a structural difference rather than a missing button. This file is scoped to the installer's internals and the build's enforcement mechanism; the ownership question itself, together with the reference's preference surface and its palette commands, is already recorded in **DD-014** (theme ownership, area A1) and is not re-litigated here — DD-014's verdict stands, and this file covers only what DD-014 leaves out. Two pieces of that remaining difference are worth naming separately, and neither should be overstated:

(a) *Drift detection.* The reference pins immutable snapshot hashes for its generated palettes plus the renderer asset digest, so a palette that drifts from the expected output is detectable rather than silently rendered wrong. The build's token test covers a related hazard — a dead token reference, a hex fallback, an unexpected token — but only at build time, over the two surfaces it names. Nothing in the build checks at runtime that the host actually defines the tokens a surface references. That gap is real and is the one piece the build's host-token rule does not already provide.

(b) *Ownership-tracked teardown.* The installer removes only the element it created, and only while that element is still the one in the document, with idempotent update/dispose. This is a small hygiene pattern for any code that writes into a document head it does not exclusively own. It is genuinely small — the build's surfaces write no style elements at all, so there is currently nothing to apply it to — and should be recorded as a pattern worth remembering, not as a defect.

## Verdict: DO-NOT-INCORPORATE
For the palette, modes, installer and preference: do not incorporate. The host-token rule is *recorded*, not merely implemented — as resolved ticket rulings, with the rule's own home being ticket 49 (`Issue-tracker/resolved/49-capsule-panel-ignore-host-design-tokens.md`, whose symptom is exactly the private-palette failure this reference-side machinery would reintroduce) extended by ticket 47 for the settings card, with draft ADR-0020 naming "token discipline from 49" as re-host inventory (`docs/adr/0020-...:79`) and ADR-0022 keeping the floating capsule a host-themed surface. No *accepted* ADR records it, so the rule sits at the ticket-ruling level of the authority stack rather than at ADR level — worth stating plainly, since that is the level a future human ruling would amend. Importing the reference's own appearance layer would mean re-creating precisely the private palette ticket 49 removed and the test suite now forbids, so it contradicts a recorded ruling and must not be brought in. The one difference not already covered is the runtime drift check (a) above; that is a candidate for a small, separate ticket, not a reason to adopt the installer. This is a deliberate-divergence, not a gap.

## Incorporation notes
- **Where it would live:** Nothing to build for the palette/installer/preference path. A runtime drift check, if ever wanted, would live beside the existing token pins in `test/client-theme-tokens.test.ts` as an additional offline assertion over the host theme stylesheet — or, if it must be runtime, as a small check in the client shell that logs rather than repairs, since the build cannot define the tokens it would be repairing.
- **Constraints:** The ticket-49 contract forbids a private palette and is enforced by an exact-set deep equality per surface, so any new surface must add its own pin in the same shape rather than inventing a token. ADR-0021/ADR-0022's arrangement means the host shell keeps owning document-root theme state, so the build must not write a root data attribute or color-scheme property. Any runtime check must stay offline-capable as the test suite itself requires and must not add a boot-graph edge, a service dependency or a subscription — the test header's point is that referencing the tokens is sufficient.
- **License note:** ADR-0018 B9 — re-derive independently; no verbatim copying from the reference tree.
- **Effort/risk:** S — for the drift check alone, a build-time assertion over the host theme stylesheet is a few lines in the existing test file and carries no runtime risk; anything beyond that (modes, installer, preference) is M-to-L and crosses a recorded ticket contract, so its risk is governance, not code.
- **Key reference anchors:** the reference tree's `frontend/src/recovered/features/runtime-theme-token-installer.ts:6, 11, 15` (mode union, per-mode theme class, string-or-per-mode-pair value union); `:17, 19, 20` (core palette of 130 entries, alias mapping onto the shared namespace, further per-mode table); `:12-13` (immutable palette snapshot hashes and renderer asset digest); `:14` (exported palette-count constant); `:30-32` (incomplete-document rejection, single style element plus root attribute and color-scheme write, ownership-tracked install handle with idempotent update/dispose); the reference tree's `source/electron-main/prefs/theme-controller.ts:25-63` (preference read at construction, setter, broadcast, listener removal on dispose).
